## Q1 — 추이 화면이 "빠진 일지"를 밝힌다

수치를 적었는데 분석에서 빠진 일지를 화면이 말하지 않아, 사용자는 자기가 적은 값이
왜 그래프에 없는지 알 방법이 없었다.

**착수 전 전제를 실행으로 확인하다가 내 명세가 틀렸다는 것을 발견했다.** 제외 원인이
하나(가져온 DERIVED 값)라고 설명했지만 실제로는 **둘**이었다. `fieldProvenance`가
optional이고 `isEligibleForAnalysis`가 `undefined`에 false를 반환해서, 예전 버전
저장분과 출처 없는 백업 복원분도 함께 빠진다.

두 원인을 **뭉치지 않은** 이유: 사용자 행동이 정반대다. 가져온 값은 직접 다시 적으면
되지만, 출처 없는 일지는 사용자가 할 수 있는 게 없다(앱 문제). 뭉치면 "직접 적어
주세요"라며 불가능한 일을 요구하는 안내가 된다.

- `hasValueExcludedFromAnalysis()` — 값이 있는데도 부적격인 칸만 센다. "안 적어서 빠진
  것"은 세지 않는다(그것까지 알리면 소음)
- `analysisExclusionSummary()` — `excludedImported` / `excludedNoProvenance` 분리
- `Trends.tsx` — 빈 화면과 데이터 화면 **양쪽**에 안내. 가져오기만 한 사용자는 빈
  화면을 보므로 그쪽이 더 중요하다
- 계약 16개(도메인 9 + 화면 7). 화면 테스트를 따로 둔 이유는 "도메인은 맞는데 화면이
  침묵"하는 실패를 도메인 테스트가 못 잡기 때문이다

## Q3 — "전부 지우기"가 전부가 아니라는 사실 공개

삭제 기록(tombstone)은 일부러 남는다 — 지우면 재로그인 동기화 때 지운 일지가
서버에서 부활한다. 남기는 것은 옳지만, 화면이 "모두 지워요"라고만 말해 사용자는
아무것도 남지 않는다고 믿었다.

남는다는 사실 + 남는 것이 '내용'이 아니라 '지웠다는 표시'라는 구분 + 이유를 **확인
전에** 밝힌다. 지우는 선택지는 화면에 두지 않는다(사용자 결정) — 고르는 순간 지운
일지가 되살아나는 부작용이 생긴다.

## Q4 — 일지를 지키면서 계정 바꾸기 (도메인 + 화면)

계정 잠금을 푸는 유일한 안내가 '전부 지우기'였다. **직전 PR 상태에서는 도메인 함수만
있고 호출하는 곳이 없어 사용자 개선이 0이었다.** 이번에 화면을 붙여 실제 경로를 만들었다.

- `releaseSyncOwner()` — 잠금 키만 지운다. 일지·계획 보존, 삭제 기록 보존(지우면 지운
  일지가 새 계정에서 부활), 제거 후 재확인해 실패를 성공으로 보고하지 않는다
- `SwitchAccountPanel` — 로그아웃 **위에** 둔다. 계정을 바꾸려는 사람이 먼저 만나는
  것이 '전부 지우기'가 되어서는 안 된다
  - 묶여 있지 않으면 아예 나타나지 않는다(없는 문제로 불안하게 만들지 않음)
  - 확인 단계를 거친다, 백업을 권한다(강요하지 않는다 — 지우는 동작이 아니므로)
  - 순서: **동의 끄기 → 잠금 해제 → 로그아웃.** 동의를 먼저 끄는 것은 잠금이 풀린
    순간 자동 업로드가 끼어들 틈을 없애기 위해서다. 로그아웃까지 하는 것은 안 하면
    원래 계정에 다시 묶이기 때문이다
  - 실패하면 로그아웃하지 않고 실패를 말한다(상태 불명 방지)
- 잠금 실패 메시지 두 곳(`sync-run`, `sync-preview`)이 아직 '전부 지우기'를 가리켜서
  안전한 길로 바꿨다

## main의 대규모 변경에 다시 맞춤

직전 PR에서 충돌 때문에 rebase를 중단했다고 보고한 부분을 해결했다. main이 Trends를
`journal-observation` 파이프라인으로 재작성하고 `sync.ts`를 모듈 분리해서 단순
rebase가 불가능했다. **내 변경을 밀어넣지 않고 main 버전을 채택한 뒤 필요한 것만 다시
얹었다.** 그 전에 Q1 전제가 새 파이프라인에서도 참인지 실행으로 확인했다:

```
[가져옴]   주간거리: 0
[손입력]   주간거리: 8
[출처없음] 주간거리: 0
```

시한폭탄 테스트는 main도 독립적으로 고쳤고, main의 상대 시각(`Date.now()-2000`)
방식이 내 하드코딩 날짜보다 견고해 remote 쪽을 채택했다.
