## 0. 이 문서가 왜 따로 있는가

직전 턴에 나는 미해결 PR 17건을 훑는 문서를 냈다. 그건 소유자가 요청한 일이
아니었다. 요청은 **작업자들이 이미 해 놓은 작업을 평가·리뷰·공격해서 보완하고,
이후 작업이 같은 실수를 반복하지 않도록 기획/수정 제안을 하라**는 것이었다.

그래서 이번에는 병합된 코드에 실패를 주입해 공격했고, 찾은 것을 고쳤고,
**왜 그 결함이 리뷰를 통과했는지**를 규칙으로 바꿨다. 이 문서의 2절이 결함,
3절이 원인 분석, 4절이 제안이다.

## 1. 내가 틀린 것 먼저 (철회)

작업 중간에 나는 다음과 같이 판단했다.

> B1 결함: 휴지통 쓰기가 실패하면 일지가 영구 삭제되는데 `deleteEntry`가
> `ok:true`를 돌려준다. 확인 문구는 "30일 보관"을 약속했으므로 거짓 안내다.

**이 판단은 틀렸다. 철회한다.**

실행 결과(`ok:true, trashed:false`)는 맞았지만, 나는 그 값을 받는 화면을
읽지 않고 결함이라고 단정했다. 실제로 `LogDetail.tsx` 는 이 값을 정확히
처리한다.

```tsx
{justDeleted.trashed
  ? ` 휴지통에 ${TRASH_RETENTION_DAYS}일 동안 남아 있어요.`
  : " 이 기기에 자리가 없어 휴지통에 넣지 못했어요 — 되돌릴 수 없어요."}
```

되돌리기 버튼도 `justDeleted.trashed && (...)` 로 감싸여 있어 뜨지 않는다.
`journal-store.ts` 주석과 `journal-trash.ts` 설계 원칙에도 *"휴지통 보관에
실패해도 삭제는 진행한다 … 대신 `trashed: false` 를 실어 보내 UI가 사실대로
말하게 한다"* 로 **의도가 먼저 적혀 있었다.** 즉 이것은 결함이 아니라 설계다.
소유자 결정(삭제권을 저장 실패로 막지 않는다)과도 일치한다.

교훈은 4절 P-1 로 규칙화했다: **도메인 반환값만 보고 결함이라고 부르지 않는다.
그 값을 소비하는 화면을 읽은 뒤에 판단한다.**

## 2. 실제로 찾은 결함 (실행으로 증명)

### A-1 · 전체 삭제가 계정 userId를 남긴다 — 화면 문구가 거짓 (심각)

`erase-local-data.ts` 는 `trainoracle.sync.owner.v1` 을 **삭제 기록과 한 묶음**
으로 두어 기본 삭제에서 제외했다.

```ts
const DELETION_RECORD_KEY = "trainoracle.sync.tombstones.v1"
const SYNC_OWNER_KEY = "trainoracle.sync.owner.v1"   // ← 같이 제외됨
```

그런데 그 키에 들어가는 값은 `sync.ts` 에서 이렇다.

```ts
localStorage.setItem(OWNER_KEY, userId)   // 계정 userId 평문
```

화면(`Account.tsx`)이 사용자에게 하는 약속은 이것이다.

> 이 기기에 저장된 일지·계획·**로그인 정보를 모두 지워요.**
> …버튼: **네, 전부 지울게요**

`handleErase` 는 `eraseAllLocalData()` 를 옵션 없이 부르므로 userId가 남는다.
**"전부"라고 말하고 계정 식별자를 남기는 것은 거짓 안내이고 최소 수집 원칙
위반이다.**

묶음의 근거는 *"지웠다는 사실이 없으면 서버 사본이 되살아난다"* 였다. 그 근거는
tombstone에만 성립한다 — owner 키는 부활 방지에 아무 역할이 없다. 근거가 없는
채 같은 묶음에 들어가 있었다.

### A-2 · 기기를 넘겨받은 사람이 동기화에서 영구히 잠긴다 (심각)

A-1의 2차 효과다. `claimSyncOwner` 는 owner 키가 있으면 다른 userId를 거부한다.

```ts
const owner = localStorage.getItem(OWNER_KEY)
if (owner !== null) return owner === userId   // 다른 계정이면 영구 false
```

거부 자체는 옳다(남의 계정으로 이 기기 일지가 올라가면 안 된다). 문제는 **푸는
방법이 없다는 것**이다. 잠금을 푸는 유일한 수단이 전체 삭제인데, A-1 때문에
전체 삭제조차 owner 키를 남겼다. 화면에 나오는 말은 이것뿐이었다.

> 이 기기의 일지는 다른 계정과 연결되어 있어요. 다른 계정으로 업로드하지 않았어요.

막혔다는 사실만 있고 나갈 길이 없다. 중고 기기·가족 공용 기기에서 바로 발생한다.

### A-3 · 계약 테스트가 결함을 "정상"으로 고정하고 있었다 (과정 결함)

가장 무거운 발견은 코드가 아니라 테스트였다.

```ts
it("삭제 기록은 기본으로 **남긴다** — 서버 사본 부활 방지", () => {
  expect(window.localStorage.getItem(TOMBSTONES)).not.toBeNull()
  expect(window.localStorage.getItem(SYNC_OWNER)).toBe("athlete-a")   // ← 결함을 고정
})
```

제목과 주석은 **tombstone**만 정당화한다. 그런데 같은 `it` 안에서 userId가
남는 것까지 통과시켰다. 그래서 A-1은 "테스트가 초록색인 결함"이었다.
리뷰어가 테스트를 근거로 삼으면 절대 못 잡는다.

### A-4 · 쓰기 실패 경로에 테스트가 사실상 없었다 (커버리지 공백)

`localStorage` 에 쓰는 도메인 모듈은 5개이고 모두 실패를 `boolean` 으로 돌린다.
그런데 실패를 주입하는 테스트는 이번 작업 전까지 `tombstone.contract.test.ts`
하나뿐이었다(35개 테스트 파일 중 1개).

`deleteEntry` 는 저장소에 **세 번** 쓴다(tombstone → 휴지통 → 본문). 조합이
3가지인데 검증은 0건이었다. 그리고 이 순서는 PR #119에서 실제로 뒤집혔다
(`recordTombstone` 을 쓰기 앞으로 옮기고 롤백 추가). **성공 경로 테스트로는
순서 변경 회귀가 절대 잡히지 않는다** — 성공할 때는 어느 순서든 결과가 같다.

실패를 주입해 확인한 결과, #119의 롤백 작업 자체는 **옳았다**:

| 실패 지점 | 결과 | 판정 |
|---|---|---|
| tombstone 쓰기 | 아무것도 지우지 않음 | 정상 (fail-closed) |
| 본문 쓰기 | 일지·휴지통·기록 전부 원상복구 | 정상 |
| 휴지통 쓰기 | 삭제 진행 + `trashed:false` | 정상 (설계대로) |

즉 #119는 잘 만들었으나 **그 정확함을 지켜 줄 테스트가 없어서**, 다음 사람이
순서를 되돌려도 CI가 초록색이었다. 지금은 잠갔다(회귀 시뮬레이션으로 검증: `removeTombstone(id)` 한 줄을 주석 처리하면 F-2가 실패한다).

## 4. 이후 작업 개선 제안 (핵심 산출물)

이번 결함들과 지난 턴의 결함들은 **네 가지 패턴**으로 수렴한다. 사람의 실력
문제가 아니라 **규칙이 없어서 반복되는 것**이므로 규칙으로 제안한다.

### P-1 · 판단은 "값"이 아니라 "사용자가 보는 것"에서 끝낸다

내가 이번에 틀린 방식 그대로다. `ok:true` 를 보고 결함이라 단정했으나
화면은 정직했다.

**규칙**: 도메인 반환값이 이상해 보이면, 결함으로 부르기 전에 **그 값의
소비자(화면/문구)를 모두 grep 해서 읽는다.** 소비자가 정직하게 처리하면
결함이 아니라 설계다. 소비자가 없으면 그때가 결함이다.
비용: grep 한 번. 얻는 것: 오진 방지. 오진은 신뢰를 깎고 남의 시간을 태운다.

### P-2 · 저장소에 쓰는 코드에는 실패 주입 테스트를 의무화한다

근거: 쓰기 모듈 5개 중 실패 테스트 1개(A-4). `deleteEntry` 는 3중 쓰기인데 0건.

**규칙**: `setItem` 을 `try/catch` 로 감싸 `boolean` 을 돌려주는 함수는,
그 `false` 분기를 실행하는 테스트가 **최소 1개** 있어야 병합한다.
쓰기가 N번이면 N개의 실패 지점을 각각 검증한다.

구현 부담을 줄이기 위해 이번에 만든 헬퍼를 그대로 쓰면 된다
(`journal-delete-failure.contract.test.ts` 의 `failWritesTo`).

```ts
function failWritesTo(key: string): void {
  const real = Storage.prototype.setItem   // window.localStorage에 걸면 jsdom에서 안 잡힌다
  vi.spyOn(Storage.prototype, "setItem").mockImplementation(function (this, candidate, value) {
    if (candidate === key) throw new Error("QuotaExceededError")
    return real.call(this, candidate, value)
  })
}
```

**남은 대상(미적용)**: `journal-trash.ts`, `onboarding-state.ts`,
`account/sync.ts` 의 consent/owner 쓰기. 이번 PR 범위에 넣지 않았다 —
검증 없이 넓히면 이 문서가 지적하는 실수를 내가 반복한다. 별건으로 제안한다.

### P-3 · 픽스처가 스키마에 거부되면 테스트를 실패시킨다 (허위 통과 차단)

이번 작업 중 **내가 이 함정에 빠졌다.** 첫 탐침에서 `entries: 0` 이 나왔다.
`saveEntry` 가 `memoPurpose` 누락으로 픽스처를 조용히 거부했고, 빈 저장소에
`deleteEntry` 를 부르니 기대값이 우연히 맞았다. 그대로 커밋하면 **아무것도
검증하지 않는 초록색 테스트**가 남았다.

**규칙**: 저장 헬퍼는 반환값을 확인하고 실패 시 던진다.

```ts
function store(id: string): void {
  const result = saveEntry(makeEntry(id))
  if (!result.ok) throw new Error(`픽스처가 스키마에 거부됐다: ${id}`)
}
```

추가로: **새 테스트는 고치기 전 코드에서 반드시 한 번 실패시켜 보고**
그 출력을 PR 본문에 붙인다. 이번 PR의 `expected 'athlete-a' to be null` 이 그
예다. 이 절차가 없으면 P-3의 함정을 리뷰가 걸러낼 수 없다.

### P-4 · 테스트 제목이 정당화하지 못하는 단정을 같은 `it` 에 넣지 않는다

A-3의 정확한 형태다. 제목은 tombstone만 말하는데 `it` 안에서 userId 보존까지
통과시켰다. 그래서 **결함이 "계약"으로 승격**됐다.

**규칙**: 한 `it` 은 한 가지 계약만 고정한다. 어떤 `expect` 가 제목/주석으로
정당화되지 않으면 그 단정은 잘못된 자리에 있다. 특히 `not.toBeNull()` /
`toBe(<값>)` 로 **"남아 있음"을 고정할 때는 왜 남아야 하는지 주석을 붙인다.**
근거 없는 보존 단정은 삭제권·최소 수집 위반을 굳히는 가장 흔한 경로다.

### P-5 · 집계 표면은 "제외했다는 사실"까지 말해야 한다

**먼저 정정한다.** 이 문서 초판에서 나는 *"`Trends.tsx` 가 provenance 확인 없이
합산한다"* 고 썼다. **틀렸다.** `grep provenance` 가 0줄인 것만 보고 단정했는데,
`Trends.tsx` 는 원본이 아니라 `loadAnalysisEntries()` 를 쓴다. 그 경로가
`toAnalysisPostSessionEntry` 를 지나며 부적격 값을 빈 문자열로 지운다.

```ts
distanceKm: isEligibleForAnalysis("distanceKm", entry.fieldProvenance) ? entry.distanceKm : "",
```

실행으로 확인했다. 실제 가져오기 코드와 같은 모양(`derivationRuleId` 포함)의
일지를 저장해 보면:

```
[손입력] 저장: 1  분석대상: 1  distanceKm: ["10"]
[가져옴] 저장: 1  분석대상: 0  distanceKm: []
```

즉 **가져온 수치는 이미 그래프에서 빠진다.** 계산은 옳다. P-1을 만들어 놓고
같은 실수를 반복했다(값이 아니라 경로를 안 읽었다). 정정한다.

**다만 남는 문제가 있고, 이쪽이 진짜다.** 빠진다는 **사실을 화면이 말하지
않는다.** `Trends.tsx` 에 "가져온 기록", "제외" 같은 문구가 한 줄도 없다.
그래서 시계 파일 10건을 가져온 사용자가 트렌드를 열면 주간 거리가 0 km 이고,
화면은 이렇게만 말한다.

> 훈련 후 일지에 거리를 적으면 여기에 주간 그래프가 그려져요.

사용자는 방금 거리를 **넣었다.** 안 넣었다고 안내받는다. 이건 계산 결함이
아니라 **안내 결함**이고, "말없이 빠지는 것"을 금지하는 원칙(안전 백업 F-3에서
이미 같은 결론을 냈다 — `safeExportSummary` 로 빠지는 개수를 세어 알린다)에
어긋난다.

**규칙**: 일지 수치를 더하거나 평균 내는 화면은 두 가지를 함께 해야 한다.
① `isEligibleForAnalysis` 를 통과한 값만 쓴다(계산). ② **몇 건이 왜 빠졌는지
같은 자리에서 말한다**(안내). ②가 없으면 사용자는 자기가 입력하지 않았다고
오해한다. `safeExportSummary` 가 이미 이 패턴의 좋은 선례다.

**미해결로 올림**: `Trends.tsx` 의 안내 추가는 이번 PR에서 하지 않았다.
문구와 노출 위치는 소유자 결정이 필요하다(§5 Q1).

## 5. 소유자 결정이 필요한 것 (상세)

네 건 모두 **내가 임의로 정하면 안 되는 것들**이다. 이유는 셋 중 하나다:
사용자에게 보이는 것이 바뀐다 / 원칙 두 개가 서로 충돌한다 / 위험을 누가
감수할지가 결정 사항이다. 각 건마다 **무슨 일이 벌어지는지 → 선택지 →
각 선택의 대가 → 내 권고와 그 근거** 순으로 적는다.

### Q1 · 트렌드 화면이 "가져온 기록은 빠졌다"고 말해야 할까

**지금 무슨 일이 벌어지나**

시계·앱에서 활동 파일을 가져오면(`ImportActivities`), 그 수치는 사용자가 손으로
쓴 것이 아니므로 `DERIVED`(파생) 표시가 붙는다. 트렌드 그래프는 이 값을
**이미 제외한다.** 그건 옳다 — 기계가 계산한 거리와 사람이 적은 거리를 같은
줄에 섞으면 분석이 오염된다.

문제는 **그 사실을 말해 주지 않는다**는 것이다. 시계 기록 10건을 가져온
사용자가 트렌드를 열면 이렇게 된다.

- 주간 거리 그래프: **0 km** (또는 그래프 자체가 안 나옴)
- 화면 문구: *"훈련 후 일지에 거리를 적으면 여기에 주간 그래프가 그려져요."*

사용자는 방금 거리를 **넣었다.** 그런데 안 넣었다고 안내받는다. 사용자가
할 수 있는 합리적 추측은 "가져오기가 실패했나?" 또는 "이 앱이 고장났나?"다.
실제로는 정상 동작인데 그렇게 보이지 않는다.

**왜 내가 못 정하나**

이건 계산 로직이 아니라 **사용자에게 하는 말**이다. 무슨 문구로, 어디에,
얼마나 자세히 말할지는 제품 목소리에 대한 결정이다. 게다가 "가져온 기록은
분석에서 빼요"라고 밝히는 순간, 사용자는 자연스럽게 **"그럼 가져오기는
왜 있나요?"**를 묻게 된다. 그 답(가져온 기록은 보기·기록 보관용이고 분석은
직접 입력 기준)은 제품 방향이라 소유자 몫이다.

**선택지와 대가**

| 선택 | 사용자가 얻는 것 | 대가 |
|---|---|---|
| **가** 빠진 건수를 알린다 ("가져온 기록 10건은 분석에서 빠져요") | 오해가 사라진다. 왜 0인지 안다 | 화면에 설명이 하나 늘어난다. "그럼 왜 가져오나"에 대한 답도 함께 준비해야 한다 |
| **나** 가져온 값도 그래프에 넣는다 | 숫자가 바로 채워진다 | **분석 오염.** 기계 값과 손 입력이 섞인다. 프로젝트가 지켜 온 원칙을 정면으로 깬다 |
| **다** 그냥 둔다 | 없음 | 가져오기를 쓴 사용자는 계속 "고장난 것 같다"고 느낀다 |

**내 권고: 가.** 근거는 이 프로젝트가 **이미 같은 상황에서 같은 결론을 냈다는
것**이다. 안전 백업에서 "메모만 쓴 일지는 파일에서 빠진다"는 문제가 있었을 때,
택한 답은 "몰래 빼기"가 아니라 `safeExportSummary` 로 **빠지는 개수를 세어
알리기**였다. 같은 원칙을 여기 적용하면 일관된다. **나(가져온 값을 넣기)는
권하지 않는다** — 숫자를 채우려고 분석의 신뢰를 파는 거래다.

### Q2 · 실패 주입 테스트를 나머지 3개 모듈에도 넣을까

**지금 무슨 일이 벌어지나**

브라우저 저장 공간이 꽉 차면 저장이 실패한다(흔한 일이다 — 사진 많은 기기,
시크릿 모드, 용량 제한 설정). 이 앱의 저장 모듈은 그때 `false` 를 돌려주도록
잘 만들어져 있다. 문제는 **그 실패 상황을 실제로 시험해 본 테스트가 거의
없다는 것**이다.

저장하는 모듈은 5개인데, 이번 작업 전까지 실패를 시험한 것은 1개였다.
이번에 `deleteEntry`(삭제)를 시험해 2개가 됐다. 남은 3개는 이렇다.

- `journal-trash.ts` — 휴지통
- `onboarding-state.ts` — 첫 안내 닫음 표시 (실패해도 안내가 다시 뜨는 정도, 가벼움)
- `account/sync.ts` — 동기화 동의·소유자 (계정 관련이라 무겁다)

**왜 이게 중요한가 — 이번에 실제로 겪은 일**

`deleteEntry` 는 저장을 3번 한다. PR #119에서 그 **순서가 바뀌었다.** 순서가
바뀌면 저장이 중간에 실패했을 때 남는 상태가 완전히 달라진다(최악의 경우
일지가 어디에도 없게 된다). 그런데 **성공했을 때는 어느 순서든 결과가 똑같아서**
기존 테스트는 전부 초록색이었다. 검증 없이 통과한 것이다.

확인해 보니 #119는 **잘 만들었다**(3가지 실패 모두 올바르게 처리). 하지만
그건 운이 좋았던 게 아니라 그 사람이 잘한 것이고, **다음 사람이 되돌려도
CI가 못 잡는 상태**였다. 이번에 그 부분만 잠갔다.

**왜 내가 다 안 하고 물어보나**

지금 당장 3개를 더 할 수도 있었다. 하지만 그러지 않았다. **이 문서가 지적하는
실수를 내가 반복하게 되기 때문이다.** 검증 범위를 한 번에 넓히면 각각을 제대로
확인할 시간이 없고, "테스트를 추가했다"는 사실만 남는다(A-3이 정확히 그렇게
생긴 결함이다 — 테스트는 있는데 잘못된 것을 고정하고 있었다).

**선택지와 대가**

| 선택 | 얻는 것 | 대가 |
|---|---|---|
| **가** 별건 PR로 3개 추가 (권고) | 저장 실패 시 데이터 손실 위험을 실제로 검증 | 작업 1건 추가. `sync.ts` 는 비동기라 시간이 더 든다 |
| **나** `sync.ts` 만 먼저 | 위험이 큰 곳부터 막는다 | 휴지통이 남는다 |
| **다** 안 한다 | 없음 | 저장이 꽉 찬 기기에서 무슨 일이 나는지 아무도 모르는 상태 유지 |

**내 권고: 가 — 단 별건 PR로.** 헬퍼(`failWritesTo`)는 이번에 이미 만들어
뒀으니 복사해 쓰면 되고, jsdom 함정(`window.localStorage` 에 스파이를 걸면
안 잡히고 `Storage.prototype` 에 걸어야 한다)도 주석으로 남겨 뒀다. 즉
어려운 부분은 끝나 있다.

### Q3 · "삭제 기록까지 지우기" 선택지를 화면에 낼까 (원칙 충돌)

**먼저 배경 — 삭제 기록이 뭔가**

일지를 지우면 앱은 *"이 일지는 지워졌다"*는 쪽지를 남긴다(id와 시각만.
날짜·수치·메모는 없다). 이게 없으면 계정 동기화를 쓸 때 **지운 일지가
되살아난다** — 서버에 남은 사본을 앱이 "한쪽에만 있는 항목"으로 보고 다시
내려받기 때문이다. 그래서 "이 기기 데이터 전부 지우기"를 해도 이 쪽지는
일부러 남긴다.

**충돌하는 두 원칙**

1. **삭제권**: 지우고 싶다고 하면 흔적 없이 지워 줘야 한다. 쪽지가 남는다면
   "무엇을 지웠는지"의 흔적이 남는 셈이다(내용은 없지만 개수와 시각은 있다).
2. **삭제가 되살아나지 않을 것**: 쪽지를 지우면 다음 동기화에서 지운 일지가
   서버에서 돌아온다. 사용자가 가장 싫어할 결과다.

둘 다 맞는 원칙인데 여기서 정면으로 부딪친다. **이런 건 리뷰어가 정할 수
없다.** 어느 쪽 위험을 사용자에게 지울지는 제품 결정이다.

**현재 상태 (이게 문제다)**

코드는 이미 두 갈래를 **다 지원한다** — `eraseAllLocalData({ includeDeletionRecord: true })`
를 부르면 쪽지까지 지운다. 그런데 **화면에는 그 선택지가 없다.** 즉
*"만들어 뒀지만 사용자는 절대 쓸 수 없는 기능"* 이 있는 상태다. 이건
어느 쪽으로든 정리해야 한다.

**선택지와 대가**

| 선택 | 사용자가 얻는 것 | 대가 |
|---|---|---|
| **가** 선택지를 화면에 낸다 | 완전한 삭제가 가능해진다 | 켠 사용자는 다음 동기화에서 **지운 일지가 되살아날 수 있다.** 그 위험을 짧은 문구로 이해시키기가 매우 어렵다 |
| **나** 내지 않되, 남는다는 사실을 밝힌다 (권고) | 정직해진다. 되살아남 사고가 없다 | 흔적을 완전히 없애고 싶은 사용자는 브라우저 설정을 써야 한다 |
| **다** 지금처럼 아무 말 없이 남긴다 | 없음 | "전부 지웠다"는 안내가 여전히 부정확하다(A-1과 같은 종류의 문제) |

**내 권고: 나.** 근거는 **대가의 크기 차이**다. 가를 택하면 사용자가 잘못
이해했을 때 잃는 것은 *"지웠던 일지가 돌아오는 것"* — 통증·감정 메모까지
돌아올 수 있고, 되돌릴 방법이 없다. 나를 택하면 잃는 것은 *"완전 삭제를
원하는 소수가 브라우저 설정을 한 번 더 거치는 불편"* 이다. 회복 불가능한
위험보다 불편을 택하는 게 맞다고 본다.

**단 다는 안 된다.** 최소한 "지운 항목이 있었다는 표시(내용 없음)는 남아요"
정도는 삭제 화면에 적어야 한다. 그게 A-1을 고친 것과 같은 취지다.

### Q4 · 계정 잠금 안내를 문구로 끝낼까, 기능을 만들까

**지금 무슨 일이 벌어지나**

기기 하나는 계정 하나에만 묶인다. 다른 계정으로 동기화를 시도하면 막힌다.
**막는 것 자체는 반드시 필요하다** — 없으면 내 일지가 남의 계정으로 올라간다.

문제는 이 잠금이 **기기를 넘겨받은 사람에게도 걸린다**는 것이다. 중고로
휴대폰을 사거나 가족과 태블릿을 같이 쓰는 경우다. 그 사람 잘못이 아닌데
동기화를 못 쓰고, 예전에는 화면에 이렇게만 떴다.

> 이 기기의 일지는 다른 계정과 연결되어 있어요.

막혔다는 말만 있고 **어떻게 하라는 말이 없었다.** 게다가 잠금을 푸는 유일한
방법인 "전부 지우기"조차 A-1 때문에 실제로는 안 풀렸다. **완전히 막힌
상태**였다.

**이번에 한 것**: A-1을 고쳐 전부 지우기가 실제로 잠금을 풀게 했고, 안내에
길을 넣었다 — *"이 기기를 새로 쓰려면 계정 화면의 '이 기기 데이터 전부
지우기'를 먼저 해 주세요."*

**남은 결정**

이 문구로 충분한가? 아니면 계정 화면에 **"다른 계정으로 바꾸기"** 흐름을
따로 만들까(현재 데이터를 백업할지 물어보고, 정리하고, 새 계정으로 넘기는)?

| 선택 | 얻는 것 | 대가 |
|---|---|---|
| **가** 문구로 시작 (권고) | 지금 막힌 사람이 즉시 빠져나온다. 추가 작업 없음 | "전부 지우기"는 이름 그대로 다 지운다. 넘겨받은 사람에겐 맞지만, 계정만 바꾸려는 사람에겐 과하다 |
| **나** 전용 흐름을 만든다 | 데이터를 지키면서 계정 전환 | 새 화면 + 새 실패 경로. 실제 수요를 모르는 상태에서 만드는 기능 |

**내 권고: 가.** 근거는 **이 상황이 얼마나 자주 일어나는지 아직 모른다**는
것이다. 공개 베타 전이라 실사용 데이터가 없다. 지금은 **막힌 사람이 빠져나갈
길**이 있으면 충분하고, 실제 문의가 생기면 그때 흐름을 만드는 게 맞다.
없는 수요를 상상해서 화면을 늘리면 유지 비용만 남는다.
