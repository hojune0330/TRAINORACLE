# AthleteTime 페이스 계산기 차용 감사

- 날짜: 2026-10-05
- 상태: `AUDIT_COMPLETED_SOURCE_DEFECTS_FOUND`
- 범위: 공개 계산기 화면, 읽기 전용 로컬 소스, 합성 입력 계산 검증, TrainOracle 계약 대조.
- 앱 통합: `NOT_STARTED`. AthleteTime 수정, 실제 회원 기록 저장, 서버 변경, 배포는 하지 않았다.
- 연결 계획: [페이스 도구 차용·UX 구현 계획](../plans/TRAINORACLE_PACE_TOOLS_PORT_AND_UX_PLAN_2026-10-05.md).

## 1. 결론

**가져올 가치가 있다. 다만 페이지나 계산 모듈을 그대로 복사하면 안 된다.**

AthleteTime의 유용한 부분은 경기 기록을 구간 시간으로 빠르게 읽는 방식, 트랙 랩, 레인 거리, 구간표, 숫자 비교표다. TrainOracle에는 이미 기록 선택·동일 종목 환산·계획 변경·일지 스냅샷이 있으므로 이 부분을 재사용하고, 없는 트랙·구간표 도구만 추가하는 것이 적절하다.

`훈련 페이스 분석`이라는 원래 제목과 달리 핵심 기능 대부분은 **평균 속도 환산과 트랙 산술**이다. 이를 생리학적 능력 분석이나 개인에게 적합한 훈련 강도 판정으로 소개하지 않는다. TrainOracle의 행동 이름은 `페이스 계산`, 소속은 `오라클`을 권장한다.

## 2. 우선 수정해야 할 결함

### F-01 / P1: 유효한 입력을 바꿔도 이전 결과가 남는다

- 소스: `frontend/src/pages/PaceCalculatorPage/components/TargetPaceCalculator.tsx:28`, `:47`, `:108`.
- `result`는 계산 버튼을 누를 때 저장한다. 효과 함수는 입력이 무효가 됐을 때만 결과를 지운다.
- 라이브 재현: 800m 2:00을 계산한 뒤 10km를 선택하면 입력·거리 표시는 10km로 바뀌지만 결과는 이전의 2:30/km와 400m 1:00으로 남는다.
- 위험: 서로 다른 입력 시점의 숫자가 한 결과처럼 보인다. 장애물 구간표도 현재 입력을 따로 읽으므로 일반 결과와 다른 기준으로 계산될 수 있다.
- 구간표에도 같은 구조가 있다. `usePaceCalculator.ts:123`의 `splits`는 계산 시 저장하고, `SplitCalculator.tsx:106` 부근의 결과는 현재 거리·시간·전략과 함께 받는다. 입력·저장안 변경 시 기존 표를 지우거나 재계산하지 않는다. 이 확대 관찰은 정적 소스 확인이며 별도의 라이브 재현 수로 세지 않았다.
- 이식 기준: 입력의 단일 검증 스냅샷으로 모든 숫자를 파생한다. 입력이 불완전하면 이전 결과를 현재 결과로 보여주지 않는다.
- 증거: [입력·결과 불일치 화면](evidence/athletetime-pace-20261005/stale-target-result.jpg).

### F-02 / P1: 가속 구간표의 총합이 목표 기록과 다르다

- 소스: `frontend/src/pages/PaceCalculatorPage/utils/paceCalculations.ts:216`, `:234`, `:238`.
- 각 구간의 페이스 배율을 바꾸지만 길이를 고려한 총 시간 재정규화를 하지 않는다.
- 10km 40:00: 후반 가속 합계 39:57.6, 전반 가속 합계 40:02.4.
- 하프 1:30:00: 후반 가속 약 1:29:57.43, 전반 가속 약 1:30:02.57.
- 마라톤 4:00:00: 후반 가속 약 3:59:56.57, 전반 가속 약 4:00:03.43.
- 라이브에서도 10km 40:00 전반 가속의 마지막 누적 기록이 40:02로 표시됐다.
- 이식 기준: 거리·시간 합계 보존을 먼저 보장한다. 기본은 균등 분할이다. 가속 분할은 사용자가 조정하는 계산 예시이며, 임의의 ±1% 배율을 최적 경기 전략으로 추천하지 않는다.
- 증거: [목표 40:00과 마지막 40:02가 다른 화면](evidence/athletetime-pace-20261005/split-target-mismatch-375.jpg).

### F-03 / P1: 개별 시간 필드의 음수가 구간 계산에 들어간다

- 소스: `frontend/src/pages/PaceCalculatorPage/hooks/usePaceCalculator.ts:127`, `:130`.
- 총 초가 양수인지 검사하지만 시·분·초 각각의 범위를 검사하지 않는다.
- 라이브 재현: 시 1, 분 0, 초 -1을 입력하고 계산하면 59:59로 받아들여 구간표를 생성한다.
- 이식 기준: 각 필드와 합계를 함께 검증한다. HTML `min/max`만 믿거나 잘못된 값을 조용히 보정하지 않는다.

### F-04 / P2: 중거리 경기 기록의 소수 초를 입력할 수 없다

- 소스: `TargetPaceCalculator.tsx:16`, `:34`; `TrackEventSplits.tsx:39`.
- 초에도 정수 조건을 적용한다. 800m 2:01.5를 넣으면 계산이 거부된다.
- 안내는 0~59 범위만 설명해 소수 초가 거부된 이유를 알기 어렵다.
- 이식 기준: 초는 소수 허용, 0 이상 60 미만. 원본 정밀도와 화면 표시 정밀도를 구분한다.
- TrainOracle 검증: 800m 121.5초의 200m 환산은 30.375초이며, 기본 표시는 30.4초다.

### F-05 / P2: 시간 자리올림과 표시 정책이 일치하지 않는다

- 소스: `paceCalculations.ts:53`, `:70`, `:397`.
- 59.999초의 짧은 구간 표시는 `60.0`이 된다. 분 표시로 넘어가는 처리가 없다.
- km 페이스는 소수 초를 버리므로 239.9초/km가 3:59/km다. 이는 항상 결함인 것은 아니지만 TrainOracle의 반올림 정책과 다르다.
- 라이브 레인 계산의 기본값에서도 거리 400.00m, 시간 60초인데 km 표시는 2:29다. 내부 기하학 값과 버림이 결합한 표시 차이다.
- 이식 기준: 기존 `roundedPaceSeconds`와 `formatPaceSeconds`를 사용한다. 시계형 표기는 같은 반올림 값을 표현하는 얇은 어댑터로 만든다.
- `1:36 초`처럼 시계 표기 뒤에 초를 붙이지 않는다. `96초` 또는 `1:36`로 표기한다.
- 짧은 구간의 표시만 둥글게 만드는 것과 구간표 합계를 맞추는 것은 다르다. 내부 소수 값을 보존하고 누적 시간을 원본에서 계산해야 한다.

### F-06 / P2: 도구를 바꾸면 입력이 사라진다

- 소스: `frontend/src/pages/PaceCalculatorPage/index.tsx:165`, `:191`, `:197`, `:203`.
- 각 도구를 조건부로 마운트하고 내부에 입력 상태를 둔다.
- 라이브 재현: 10km 40분 입력 후 레인 탭을 열고 돌아오면 거리·시간이 비어 있다.
- 이식 기준: 계산 화면의 상위 상태가 도구별 초안을 보존한다. 도움말·도구 전환·뒤로가기와 계정 전환을 각각 구분한다.

### F-07 / P2: 레인 한 바퀴와 경기 400m의 의미가 섞인다

- 소스: `TrackLaneCalculator.tsx`, `paceCalculations.ts:102`.
- 외곽 레인의 같은 출발선 한 바퀴는 400m보다 길다. 이것을 경기 400m 목표 시간으로 읽으면 잘못 사용할 수 있다.
- 이식 기준: `같은 출발선에서 한 바퀴`와 `경기 400m · 레인별 출발선`을 명확히 분리한다.
- 표준 트랙 도형을 사용하는 기하학 계산 자체와, 실제 시설이 그 도형을 따른다는 확인은 별도다.
- 3레인 상수 414.70m가 공식과 다르다는 의심은 검사했으나 **소수 둘째 자리에서 동일해 결함으로 판정하지 않았다**.

## 4. 구조와 차용 판단

| 원래 기능 | 유용한 부분 | TrainOracle 적용 |
|---|---|---|
| 목표 페이스 | 경기 거리·시간에서 km·400m·100m 시간 읽기 | 기존 기록 환산 코어 재사용. 입력 변경 즉시 같은 기준으로 재계산 |
| 트랙 종목 | 800m·1500m 누적 랩, 장애물 구간 구성 | 기록에 맞는 200/400m 구간표. SC는 시설 규격 확인 전용 경로 |
| 페이스 표 | 거리별 같은 속도 비교 | `페이스 표` 추가 도구. 능력 등급 제거, 동일 속도 환산임을 명시 |
| 레인 거리 | 레인별 한 바퀴·직선·곡선의 기하학 분해 | `트랙 도구`로 이동. 출발선·거리 의미와 표준 규격 표시 |
| 스플릿 | km별 누적 목표, 마지막 부분 거리 | `구간표`. 합계 보존, 균등 기본, 가속 예시는 사용자 조정 |

키보드 탭 이동·Home/End와 같은 기존 접근성 의도는 유지한다. 외형의 색·그림자·타이포그래피와 전역 저장 훅은 가져오지 않는다.

## 5. 실제 검증과 증거 경계

### 5.1 실행 산출물

- 스크립트: [읽기 전용 계산 감사](../research/athletetime-pace-audit-20261005.mjs).
- 결과: [계산 감사 결과 JSON](../research/athletetime-pace-audit-20261005.results.json).
- **합성 산술 검사 388건 통과, 감사 스크립트 실패 0건.** 일부 조합은 생리학적으로 현실적인 선수 기록이 아니라 수학적 경계 입력이다.
- 별도 관찰에서 **불일치 14건**: 구간표 합계 8사례, 자리올림 2사례, 표시 정책 차이 1사례, 원시 함수 경계 위험 3사례. 14명의 사용자나 14개의 독립 제품 결함을 의미하지 않는다.
- 균등 분할·평지 트랙·SC·레인 검사는 주어진 숫자 안의 합계 일관성을 확인한다. 생리학적 적합성이나 실제 시설 치수를 증명하지 않는다.
- 합계 보존 수리안 18건은 감사 스크립트 안에서만 검사했다. 앱 코드나 경기 전략으로 채택하지 않았다.

### 5.2 브라우저에서 직접 확인한 것

800m 소수 초 거부, 입력 변경 후 낡은 결과, 탭 왕복 시 입력 소실, 구간표의 음수 초 수락, 목표 40:00과 누적 40:02 불일치를 확인했다. 375×812 화면도 확인했다. 임시 화면 크기는 조사 후 원상복구했다.

[정상 계산의 모바일 밀도 참고](evidence/athletetime-pace-20261005/target-mobile-375.jpg).

실제 계정 로그인·즐겨찾기 저장·회원 기록 변경은 하지 않았다. 전체 AthleteTime 테스트, TrainOracle 전체 회귀, 200% 확대, 모바일 실기기 검증은 이번 준비 작업에서 수행하지 않았다.

소스의 `TargetPaceCalculator.test.tsx:8`과 `SplitCalculator.test.tsx:8`은 정적 마크업 검사를 사용한다. 위 상태 변경·합계 오류를 막는 충분한 실행 증거는 아니다.
