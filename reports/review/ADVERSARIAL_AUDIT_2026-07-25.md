# 공격형 검증 보고서 (2026-07-25)

## 0. 검증 방식

**"괜찮아 보인다"는 결론을 금지**하고, 각 의심 지점마다 **깨뜨리는 테스트**를
먼저 작성했다. 통과하면 방어가 실재하는 것이고, 실패하면 결함이 실재하는 것이다.

중요한 절차 하나: **통과한 테스트도 다시 의심했다.** 실제로 1차에서
"provenance 위조가 차단된다"는 테스트가 통과했지만, **대조군을 넣어보니
정상 데이터도 똑같이 0을 반환**했다. 방어가 작동한 게 아니라 테스트가
공허했던 것이다. 이 재검증이 없었다면 아래 F-1을 놓쳤다.

총 4차에 걸쳐 16개 공격을 실행했다.

## 2. F-1 — 백업·동기화가 통계를 조용히 지운다 (높음, 수정 완료)

### 공격

```
[G-safe] 복원 전 분석=1 → 복원 후 분석=0
[G-safe] 복원된 provenance=undefined
[I]      기기A 분석=1 → 기기B 분석=0
```

### 실체

`toSafeJournalEntry`가 `fieldProvenance`를 버렸다. 그런데
`isEligibleForAnalysis`는 **출처가 없으면 무조건 false**를 반환한다. 결과:

- 안전 백업을 복원하면 일지는 돌아오는데 **통계·추이에서 사라진다**
- 메모 제외 동기화를 하면 기기A의 통계가 **기기B에서 비어 있다**

사용자에게 **아무 경고도 뜨지 않는다.** 일지 목록에는 보이니 손실을 알아채기도
어렵다. 무증상 데이터 손실이다.

이건 내 복원 기능만의 문제가 아니었다. **동기화에 원래 있던 결함**이며,
복원 기능이 같은 투영을 쓰면서 드러났다.

### 왜 이런 일이 생겼나

타입은 `Omit<PostSessionEntry, "memo" | "memoPurpose">` — **메모만** 제거하라고
되어 있었다. 구현이 타입 의도보다 더 많이 지우고 있었고, 아무도 그 차이를
검증하지 않았다.

### 수정

`toSafeJournalEntry`가 `fieldProvenance`를 보존하도록 했다 (3개 kind 전부).

출처를 보존하는 것이 프라이버시상 안전한가? 검토했다. 출처에는 메모 원문도
식별 정보도 없고 `{provenance, derivationRuleId, derivedFrom}` 뿐이다. 오히려
"직접 쓴 값인지 가져온 값인지"를 지켜 **파생값이 분석에 섞이는 것을 막는
안전장치**다. 빼는 쪽이 위험했다.

회귀 테스트 4건 추가 (복원 3 + 동기화 1). 각 테스트에 **대조군 단언**
(`expect(before).toBe(1)`)을 넣어 공허한 통과를 구조적으로 막았다.

## 3. F-2 — 기기 간 삭제 전파 없음 (높음, 수정 완료)

### 공격

```
ATTACK B: expected [ 'X' ] to deeply equal []
```

### 실체

tombstone이 기기 로컬에만 있었다. 그래서:

1. A기기에서 일지를 지운다 → A의 tombstone에 기록, 서버에서도 삭제
2. **B기기는 그 삭제를 모른다** → B는 자기 로컬 사본을 그대로 갖고 있다
3. B가 동기화 → 사본이 서버로 다시 올라감 → **A에서 부활**

사용자는 분명히 지웠는데 다른 기기를 열면 돌아와 있다. 삭제권 위반이다.

### 서버 용량 검토 (사용자 질문에 대한 실측 답)

| 항목 | 크기 |
| --- | --- |
| tombstone 1행 (uuid 16B + entry_id ~22B + timestamptz 8B + 행 헤더 ~24B + PK 인덱스 ~40B) | **~110 B** |
| 사용자당 최대 (상한 500건) | **~54 KB** |
| 비교: `journal_entries` 1행 (jsonb 본문) | ~0.5–1.5 KB |

**핵심: 순증이 아니라 순감이다.** tombstone 행은 삭제된 일지 행을 **대체**한다.
일지 1건(~1 KB)을 지우고 tombstone 1건(~0.11 KB)을 남기므로 서버 용량은
오히려 **약 89% 줄어든다.** 용량 우려는 실측으로 기각된다.

### 수정

- `supabase/migrations/0002_journal_tombstones.sql` — 테이블 + RLS 4종
  (**delete 정책 포함** — 이게 없으면 "지웠다는 사실"이 영구히 남아 삭제권이 반쪽이 된다)
- `mergeTombstones` — 합집합. 같은 id는 **더 이른** 삭제 시각을 남긴다
  (늦은 시각을 택하면 그 사이 동기화에서 부활할 틈이 생긴다)
- `syncNow` 1-b단계: 삭제 기록 pull → 5단계: push
- pull 실패는 동기화 전체를 막지 않는다 (로컬 삭제 보호는 그대로 유효)
- 최소 수집 유지: `{id, deletedAt}`만 올린다. 테스트로 잠갔다

## 4. F-3 — 수치 없는 일지는 백업에서 조용히 빠진다 (중간, 미수정)

### 공격

```
[A]  통증 메모만 적은 저녁 일지: payload=NULL(백업안됨)
[A2] painParts 있음:            payload=ok
```

### 실체

`toUploadPayload`는 `hasExportableStructuredSignal`이 false면 `null`을 반환하고,
`syncNow`의 push 루프는 `if (payload === null) continue`로 **조용히 건너뛴다.**

즉 **"무릎이 계속 아프다. 병원 가봐야 할 듯."처럼 메모만 적은 일지는
서버에 백업되지 않는다.** 사용자는 "동기화가 끝났어요"만 보고 전부 백업된 줄
안다. 기기를 잃으면 그 일지는 사라진다.

메모 제외 동기화에서 메모만 있는 일지가 빠지는 것 자체는 설계상 자연스럽다
(올릴 내용이 없으므로). 문제는 **그 사실을 사용자에게 알리지 않는 것**이다.

### 수정하지 않은 이유

세 가지 선택지가 있고 **어느 것도 단독으로 정할 수 없다**:
1. 개수만 알린다 ("메모만 있는 일지 3건은 백업되지 않았어요") — 정보 노출 없음
2. 메모 포함 동기화를 권한다 — 프라이버시 기본값을 흔든다
3. 껍데기라도 올린다 — 빈 일지를 서버에 만드는 셈

**1번이 유력해 보이지만 오너 판단 사항이다.** `SyncOutcome`에 `skipped`를
추가하는 스펙 변경이고, 문구는 프라이버시 안내와 충돌하지 않아야 한다.

## 5. F-4 — 백업 파일의 provenance 위조 (낮음, 의도적 미수정)

### 공격

```
[H] 위조 EXPLICIT 복원 후 분석 진입=1
```

백업 JSON을 텍스트 편집기로 열어 `{"provenance":"EXPLICIT"}`로 고치면,
원래 분석에서 제외되어야 할 가져온 값을 통계에 밀어 넣을 수 있다.

### 강등 방어를 만들었다가 **철회했다**

`demoteForgedProvenance`(EXPLICIT → 강등)를 구현했다가 스스로 공격해보고
지웠다. 이유:

1. **위협 모델이 성립하지 않는다.** 공격자는 사용자 본인이고, 대상은 자기
   기기의 자기 통계다. 게다가 같은 숫자를 화면에 직접 입력하면 어차피
   EXPLICIT이 된다. 강등은 **막을 수 없는 것을 막는 시늉**이다.
2. **강등이 실제 피해를 만든다.** 정상 사용자가 백업을 복원할 때마다 통계가
   비어버린다 — 방금 고친 F-1을 다시 만드는 셈이다.

**확실한 피해(F-1 재발) vs 성립하지 않는 위협.** 보존이 옳다. 판단 근거를
코드 주석에 남겼고, **"남이 보낸 파일을 받는 경로가 생기면 이 판단은 다시
해야 한다"**는 조건도 함께 적었다.

## 7. F-6 — 지운 일지를 되찾을 방법이 전혀 없다 (중간, 미수정)

### 공격

```
ATTACK E: 지운 일지를 백업에서 되돌릴 탈출구 → expected +0 to be 1
```

사용자가 **덮어쓰기를 명시적으로 골라도** 지운 일지는 복원되지 않는다.
"삭제는 절대 되살아나지 않는다"를 일관되게 적용한 결과인데, 뒤집어 보면:

**실수로 지운 일지를 되찾을 방법이 앱 어디에도 없다.** 백업 파일이 있어도
안 된다. 되돌리기(undo)도 없고 휴지통도 없다.

삭제권 보호와 실수 복구는 **상충한다.** 지금 설계는 삭제권을 100% 택했다.

### 미수정 판단

이건 결함이라기보다 **미검증 트레이드오프**다. 어느 쪽이 옳은지는 제품 결정이고,
가능한 절충안(삭제 직후 실행취소 토스트, 30일 휴지통 등)은 모두 스펙·프라이버시
영향이 있어 오너 판단이 필요하다. 현재 UI는 삭제 시 "되돌릴 수 없다"고
명시하지 않으므로, **최소한 그 안내는 추가할 가치가 있다.**

## 9-b. 5차 공격 — 내가 방금 쓴 코드를 공격하다

앞의 1~4차는 **기존 코드**를 공격했다. 그런데 이번 턴에 tombstone 서버 전파를
새로 썼고, 그건 내가 짠 코드다. 자기 코드를 변호할 위험이 가장 큰 지점이므로
별도 공격 파동을 돌렸다. 특히 `syncNow` **조립부에 테스트가 0건**이라는 점을
표적으로 삼았다 — 순수 함수(`mergeEntries`, `mergeTombstones`)만 검증되어 있었다.

### F-7 — 삭제 기록 push 실패를 "성공"으로 보고 (HIGH, 이번 턴에 내가 만든 결함)

가짜 Supabase로 tombstone upsert만 실패시킨 결과:

```
[M] ok=true message="동기화가 끝났어요." 서버tombstone=0
```

step 5를 `await client.from(...).upsert(...)`로 쓰고 **에러를 받지 않았다.**
step 4(일지 push)와 step 6(삭제 전파)은 둘 다 에러를 검사하는데 step 5만 빠졌다.

무엇이 문제인가: 서버에 "이 id는 지워졌다"가 없는 채로 사용자는 성공 화면을
본다. 다음에 다른 기기가 동기화하면 자기 사본을 밀어 올려 **지운 일지가
되살아난다** — F-2에서 고친 바로 그 구멍이 소리 없이 다시 열린다.

**수정**: 에러를 받아 `ok:false`로 반환하고, 로컬은 지워진 상태임을 함께 알린다.
`[M] ok=false message="삭제 기록을 서버에 올리지 못했어요. …"`

### F-8 — pull 실패의 침묵 (MEDIUM)

step 1-b는 마이그레이션 0002 미실행 환경을 위해 일부러 비차단으로 만들었다.
그 판단 자체는 유지한다. 그러나 공격 N이 드러낸 건 **비차단과 무언(無言)을
혼동했다**는 점이다:

```
[N] ok=true message="동기화가 끝났어요."   ← 삭제 기록을 못 받았는데도 동일 문구
```

사용자는 "다른 기기에서 지운 게 왜 아직 있지?"를 알 방법이 없다.
"실패해도 진행한다"는 맞지만 "실패를 감춘다"는 프로젝트의 fail-visible 원칙 위반이다.

**수정**: `SyncOutcome.tombstoneSyncDegraded` 추가 + 문구 분리.
`"동기화가 끝났어요. 다만 다른 기기의 삭제 기록은 가져오지 못했어요."`

### F-9 — `deleted`가 UI에 없었다 (MEDIUM, UX)

`SyncOutcome.deleted`는 계산만 되고 화면에 쓰이지 않았다. 다른 기기에서 지운
일지가 이 기기에서 사라질 때, 사용자에게는 이유 없이 **기록이 없어진 것**으로만
보인다. 삭제 전파는 옳은 동작이지만 설명 없는 소실은 신뢰를 깎는다.

**수정**: `Account.tsx` 동기화 결과에 `· N개 삭제 반영` 표시.

> 이 세 건은 "기존 코드가 나빴다"가 아니라 **이번 턴 내 작업물의 결함**이다.
> 자기 코드에 같은 강도의 공격을 돌리지 않았다면 F-7은 그대로 출하됐을 것이다.

### 11-1. 항목 1 — 실행할 수 없었다 (사실 보고)

크리덴셜을 다시 확인했고 전부 없었다: `app/.env` 없음, `SUPABASE_*` 환경변수 없음,
`gh secret list` → HTTP 403, `supabase`/`psql` CLI 미설치.

**"실행했습니다"라고 쓸 수 없다.** 대신 한 것:
- SQL을 **멱등**으로 고쳤다. `create policy`는 `if not exists`를 지원하지 않아
  두 번 붙여넣으면 42710 에러로 멈춘다. 사람이 손으로 붙여넣는 절차에서 두 번
  실행은 실제로 일어난다. `drop policy if exists` 4줄을 앞에 넣었다.
- `MIGRATION_0002_RUNBOOK.md` — 붙여넣을 SQL, **검증 쿼리 3개**(컬럼/RLS/정책),

- RLS 검증을 "가장 중요"로 표시했다. `relrowsecurity = false`면 타인의 삭제
  기록이 읽히는 상태이므로, 그 경우 중단하라고 명시했다.

### 11-2. 항목 4 — 내 추천이 기각된 건에 대해

나는 "삭제는 삭제여야 한다"는 이유로 즉시 삭제 유지를 권했다. 소유자는 휴지통
30일을 택했다. 이건 소유자 권한이고, 재론하지 않고 구현했다.

다만 **이 결정이 열어놓은 위험**을 그대로 적어 둔다. 재론이 아니라 구현 시
반드시 막아야 했던 것들이다:

1. **되돌린 일지가 다음 동기화에서 다시 지워진다** (실제 위험, 방어함)
   tombstone은 머지에서 항상 이긴다. 원래 id로 복구하면 서버 tombstone이
   내려와 복구본을 **또** 지운다. 사용자에게는 "되돌렸는데 또 사라졌다"로 보인다.
   → **새 id로 복구**하도록 만들었다. 옛 id는 계속 "지워진 id"로 남고 복구본은
   새 기록이 된다. 반대로 tombstone을 지우는 선택지는 기각했다 — 그러면 다른
   기기에서 이미 반영된 삭제가 풀려 지운 적 없는 일지가 늘어난다.
   → 계약 테스트 4건으로 고정 (`동기화 왕복 공격` describe 블록).

2. **휴지통에 메모 원문이 남는다** (실제 위험, 방어함)
   휴지통은 되돌리기 위해 일지 원본을 통째로 보관한다. `erase-local-data.ts`의
   삭제 대상에 `trainoracle.journal.trash.v1`을 넣지 않으면 "이 기기의 내 데이터
   전부 지우기"가 거짓말이 된다 — 기기를 넘길 때 가장 위험한 누락이다.
   → `CONTENT_KEYS`에 추가.

3. **"되돌릴 수 없어요" 문구가 거짓이 됐다** (수정함)
   `LogDetail`의 확인창이 "지운 일지는 되돌릴 수 없어요"였다. 휴지통이 생긴
   지금 이건 사실이 아니다. 겁을 주는 방향의 거짓이라도 거짓이다.
   → "휴지통에 30일 보관되고, 그 안에는 되돌릴 수 있어요. 30일이 지나면
   완전히 사라져요."

4. **휴지통 보관 실패를 성공으로 보고할 수 있었다** (방어함)
   localStorage가 꽉 찬 상황에서 휴지통 저장이 실패해도 삭제는 진행된다
   (사용자가 요청한 것이므로 막지 않는다). 그런데 "30일 안에 되돌릴 수 있어요"
   라고 안내하면 거짓이 된다.
   → `deleteEntry`가 `trashed: boolean`을 돌려주고, UI가 그 값에 따라 문구를
   바꾼다. `trashed: false`면 되돌리기 버튼을 아예 띄우지 않는다.

5. **순서 오류로 일지가 완전히 사라질 수 있었다** (방어함)
   본문 삭제를 먼저 하고 휴지통에 넣으면, 그 사이 저장 실패 시 일지가 어디에도
   없다. → 휴지통에 **먼저** 넣고 본문을 지운다. 본문 삭제가 실패하면 휴지통
   항목을 되돌려 놓는다(중복 방지).

### 11-3. 항목 3 — 500 유지의 근거 (기록)

코드 변경은 없다. 판단 근거를 남긴다:
- 상한 축출은 **이론적** 부활 경로다(§6). 500건이 밀려나려면 한 사용자가
  501건 이상을 지워야 한다.
- 500건 × 약 110 B ≈ **54 KB/사용자**. 2000으로 올리면 216 KB.
- 실사용에서 일지를 500건 넘게 지우는 패턴은 관측되지 않았고(오픈 전),
  올리는 쪽의 비용(4배)이 막는 위험보다 크다.
- 재검토 조건: 오픈 후 실제 삭제 건수 분포를 보고 상위 사용자가 300건을
  넘으면 다시 본다.

### 11-4. 이번 구현에서 잡은 테스트 함정 2건

작업 중 **테스트가 조용히 무의미해지는** 경우를 두 번 만났다. 기록해 둔다.

1. **픽스처가 스키마에서 거부되고 있었다.** 메모가 비어 있지 않으면 스키마가
   `memoPurpose`를 요구하는데(`journalEntryWriteSchema.superRefine`), 픽스처에
   빼놓았다. 31건 중 21건이 실패해서 드러났다 — 실패해서 다행이었다.
   상한 테스트는 `expect(length).toBeLessThanOrEqual(500)`이어서 **0 ≤ 500으로
   통과**했다. 공허한 통과였다. `toHaveLength(TRASH_LIMIT)` + 밀려난 id 확인으로
   바꿨고, 픽스처가 스키마를 통과하는지 검사하는 `assertStorable`을 넣었다.

2. **`vi.spyOn(window.localStorage, "setItem")`은 jsdom에서 걸리지 않는다.**
   직접 프로브를 돌려 확인했다(인스턴스 스파이 → 예외 안 던져짐, `Storage.prototype`
   → 던져짐). 인스턴스 스파이로 쓴 "되돌리기 실패" 테스트는 실패 경로를 전혀
   타지 않고 있었다. `Storage.prototype`으로 바꾸고, 실패 후 **일지가 없고 휴지통에
   되돌아와 있는지**까지 확인하도록 단정을 추가했다.
