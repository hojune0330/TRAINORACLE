## 1. 판정

PR #318의 기반 구현과 전체 제품 계획의 완료는 다르다. 기존 완료 보고의
"전체 계획 완료"는 정정해야 한다. 실제 사용자용 복수 방법 선택, 조정 저장,
전체 카탈로그 근거 제작, 변경 후 설명과 일지의 버전 연결이 남아 있다.
근거를 임의로 만들지 않은 판단은 맞지만, 근거 준비 자체는 이미 승인된 작업이다.
근거가 없다는 사실을 기록한 것만으로 그 작업을 완료 처리하면 안 된다.

## 2. 확인된 문제와 구현 격차

### R1 / P1: 완료 기준이 실제 사용자 흐름까지 도달하지 않았다

- `PrescriptionAdjustmentEditor.tsx:35,232`는 외부 `onApply`에 저장을 위임한다.
- 검색 결과 실제 앱 경로에서 이 편집기를 사용하는 호출자는 없고 테스트만 있다.
- `plan-candidate-prescription.ts:233`의 다중 배치 함수도 실제 화면 호출자가 없다.
- 구현 보고서 1절과 5절은 운영 저장 연결, 수치 규칙, 버전 연결을 잔여 작업으로 명시한다.
- 따라서 "정책만 넣으면 즉시 끝"도 아니다. 화면 상태, 저장 경쟁, 실패 복구,
  설명 갱신, 실제 일지 연결을 구현하고 검증해야 한다.

### R2 / P2: 추천 다양성 제약이 일정의 반복 허용까지 제한한다

- `impl/src/plan-generator/candidates.ts:255-257`은 다른 슬롯이어도 같은 방법 또는
  같은 구조를 거부한다. `plan-beta-schema.ts:552-557`와 `adaptation.ts:460`도 같다.
- 서로 다른 대표 후보 두 개를 선정하는 규칙과, 선택한 훈련을 다른 날 배치하는
  규칙은 별개여야 한다. 현재 코드는 두 책임을 함께 묶었다.
- 현재 다중 화면은 닫혀 있어 즉시 사용자 장애는 아니다. 그러나 향후 명시적 반복
  선택을 지원할 때 코어와 저장 스키마를 다시 바꿔야 한다.
- 제안: 슬롯 중복은 항상 금지하고, 방법 반복은 슬롯/주기 정책으로 판정한다.
  이 검토는 모든 반복 배치를 허용하자는 수치·노출 승인으로 사용하지 않는다.

### R3 / P2: 주기 맥락과 사용자 반복 선호는 앱에서 반영되지 않는다

- `plan-template-options.ts:41`은 기본 선호를 `PREFER_VARIETY`로 고정한다.
- 같은 파일의 assessments는 eligibility/purpose/context priority를 모두 0으로 전달한다.
- `method-recommendation.ts`는 입력된 전체 이력의 방법군별 완료 횟수로 동률을 푼다.
- 따라서 현재는 적격성 필터 후 완료 횟수 기반 정렬이며, 앞뒤 훈련·중주기 목적·
  회복 상태를 반영한 추천이라고 설명하면 과장이다. 조건별 방법이 하나라 순위
  다양성 자체도 아직 사용자에게 관찰되지 않는다.
- 제안: 기본 화면에는 추천 이유를 한 줄로, 상세에는 실제 반영한 맥락을 표시한다.
  반복/다양성 선호는 선택적으로 제공하고, 불필요한 필수 입력 단계를 늘리지 않는다.

### R4 / P2: 문서 내부와 문서 사이의 현재 상태가 충돌한다

- 선택·조정 계약 202-205행은 live history가 비어 있다고 기술하지만 505-509행은

  이후 배포를 추적하는 명확한 후속 링크가 없어 최신 인수자가 혼동할 수 있다.
- 제안: 과거 검증 기록은 보존하되 날짜/기준 SHA를 붙이고, 현재 상태 절을 하나로
  유지한다. 배포된 상태와 활성화되지 않은 기능은 별도 필드로 기록한다.

## 3. 확대 전에 확인할 위험과 제안

1. **완료 체크와 실제 처방 준수 구분.** `plan-method-history.ts`는 COMPLETED이면
   계획된 방법을 PERFORMED로 기록한다. 완료 체크는 실제 거리·반복·회복 일치를
   입증하지 않는다. 현재 순위 보조에는 제한적으로 쓸 수 있지만 적응/효과 평가로
   확장할 때 자기보고 완료, 실제 구조 확인, 수행량 결측을 구분해야 한다.
2. **방법군 ID 안정성.** 현재 familyId와 configurationId는 templateId와 같다.
   구성별 ID를 새로 만들면 같은 방법이 미경험처럼 집계될 수 있다. 카탈로그 확장
   전에 독립 방법군 레지스트리와 기존 이력 매핑을 준비한다.
3. **이력 기간의 정직한 표시.** 저장소는 마지막 18개 계획을 유지한다. 추천 코어는
   전달된 이력을 전부 사용한다. 이를 고정 24주 또는 최근 N일로 표현하면 안 된다.
   추천 근거에 실제 이력 범위와 누락을 표시하고, 장기 원장 보존과 분리한다.
4. **대표 후보와 나머지 선택지.** 방법 2개는 비교 시작점으로 유지하되 적격 전체
   목록을 열 수 있게 한다. 동일 구조의 구성은 한 방법 아래 묶어 가짜 다양성을 피한다.
5. **조정 UX.** 구간별 +/-는 단위와 변경 대상을 명시하고, 적용 전에 총 운동량,
   회복 합계, 예상 시간과 바뀐 이유를 함께 보여준다. 값이 없는 예상 시간은 계산하지 않는다.
6. **실제 성공 통합 시험.** 현재 앱 다중 배치 테스트는 같은 방법 거부를 확인한다.
   근거 채택 후에는 서로 다른 승인 방법 두 개의 선택→저장→재열기→실행→일지 연결
   성공 경로와 quota/다른 탭/계정 변경 실패 경로를 별도로 검증해야 한다.
