## 1. 결론

상세 MAIN은 실제로 생성된다. 이번 브라우저 표본 8개에서 구조화된 MAIN이 저장되고 재열렸다.
그러나 **저장된 계획의 카탈로그 훈련 교체가 화면에서 막힌다.** 생성 성공을 근거로
수정·수행 기록·다음 주기까지 완성됐다고 판정할 수 없다.

별도의 375px 전체 여정에서는 최초 기록 입력 → 계획 저장 → 새로고침 → MAIN 확인 →
일부 수행 일지 저장 → 연결된 일지 열람 → 다음 주기 요청 → 다음 계획 수락까지 통과했다.
이 여정은 교체하지 않은 계획이다. 편집 경로를 추가한 별도 실행은 교체 적용 앞에서 막혔다.

최우선은 훈련 가짓수 확대가 아니라 **이미 제시된 훈련을 실제로 수정할 수 있도록 연결을 고치는 것**이다.

## 2. 검수 방식과 정직한 범위

- 독립 작업자 3명: `gpt-6-luna`, `reasoning_effort=max`. 각각 8개 페르소나 관점으로 생성 / 편집 / 일지·다음 주기를 분리했다.
- Luna A: 코드·계약 검토. 브라우저 및 테스트 실행 없음.
- Luna B: 편집·저장 관련 코드와 집중 테스트. 16건 묶음에서 15 통과, 1 실패. 다른 테스트의 개별 통과 출력은 있으나 최종 종료 증거가 없어 합계에 더하지 않는다.
- Luna C: 일지·링크 관련 6개 파일 36건 통과. 다음 주기 적응 자체의 테스트는 실행하지 않았다.
- **24개 페르소나는 독립 검토 관점이지 24명이 브라우저를 완주했다는 뜻이 아니다.**
- 부모 검수자는 별도로 실제 브라우저에서 8개 생성·저장·재열기 표본, 1개 전체 수명주기, 1개 편집 차단 재현을 실행했다. 반복 재실행을 별도 사람 수로 세지 않는다.
- 320px/375px, 한 표본의 reduced-motion을 포함했다. 실제 iPhone Safari, 스크린리더, 로그인 계정, 서버 동시 저장, 라이브 배포, 실제 운동 효과는 검증하지 않았다.
- 격리한 Chromium 컨텍스트와 합성 기록만 사용했다. 사용자의 기존 브라우저·저장 데이터는 건드리지 않았다.
- 로컬 `http://127.0.0.1:4434/?app=1`의 현재 빌드를 검수했다. 다음 주기 여정에서는 테스트 브라우저 시각만 2026-10-02에서 2026-10-11로 옮겼다.
- 테스트 작성 중 잘못된 버튼 이름·선택자로 실패한 시도는 제품 결함으로 세지 않았다. 최종 재현과 코드가 일치하는 항목만 아래 확정 결함으로 분류했다.

## 3. P1 확정 결함: 저장된 훈련 구성 교체가 항상 거절되는 연결

### 실제 재현

1. 5km 18분 31.5초, 달성일 2026-09-25 입력.
2. `훈련 계획에 맞춰 달려 본 경험`, 9일 중 3일, 통증 없음으로 생성.
3. 계획 저장·새로고침 후 `계획 수정 → 훈련 내용 바꾸기`.
4. 1일차 오전의 45분 조깅 선택, `이 훈련은 아직 시작하지 않았어요` 확인.
5. 같은 BASE 목적의 `P-BASE-C`, 30분 RPE 3~4 선택.
6. 계산된 30분 처방은 화면에 나오지만 `이 구성으로 바꾸기`가 비활성이다.
7. `이 일정에는 적용할 수 없는 구성이에요. 같은 목적의 다른 훈련을 골라 주세요.`가 표시된다.

### 원인

- `app/src/screens/plan-beta/ActivePlanSessionEditor.tsx:306`의 `CatalogWorkoutEditor` 호출은 `onSelect`를 전달하지만 `canSelect`를 전달하지 않는다.
- `app/src/screens/plan-beta/CatalogWorkoutPicker.tsx:194`의 저장 계획 경로는 `(canSelect?.(...) ?? false)`를 적용 조건으로 요구한다.
- 같은 파일 `:200`의 즉시 대체 후보 필터도 같은 조건을 요구한다. 따라서 편집 화면의 `같은 목적의 다른 훈련`도 적격 목록을 잃는다.
- 계산 실패나 선수 적격성 부족이 아니라 부모-자식 컴포넌트 연결 결함이다. 임의로 운동 안전 조건을 해제할 사안이 아니다.
- 호출부는 `selectionMode="SAVED_PLAN"`도 명시하지 않는다. 적용 가능성 연결을 복원할 때 저장 계획용 시간·강도 동의 처리까지 함께 대조해야 한다.

### 영향 및 권고

저장 전 상세 처방을 확인할 수 있어도 저장 후 다른 구성으로 바꾸는 실제 사용이 중단된다.
카탈로그 바인딩을 가진 세션의 교체 경로에 광범위한 영향을 주는 P1이다.

권고: 저장 계획의 실제 도메인 적격성 판단을 `canSelect`로 연결하고 저장 계획 모드를 명시한다.
`?? true`로 바꾸는 식의 무조건 허용은 금지한다. 적격성, 과거·기록된 슬롯 보호, 강도·시간 증가 확인을 유지한다.
이후 교체 → 변경 전후 확인 → 적용 → 새로고침 → 변경된 세션 일지 → 원본 링크를 하나의 브라우저 회귀 시나리오로 잠근다.

증거: `.scratch/luna-prescription-audit-20261002/parent/edited/8-failure.txt`, 같은 이름의 PNG,
`parent/journey.mjs`의 `AUDIT_EDIT=1` 실행. 스크립트의 해당 오류는 적용 버튼 비활성 상태의 30초 대기다.

## 4. P2 UX: 기록 페이스 계획의 시작 확인이 멀리 떨어져 있음

800m 경험자 및 3000m 경험자 표본에서는 개인 기록 기반 처방이 실제로 생성됐다.
그러나 상단 `이 일정으로 시작`은 비활성이고, 화면 아래 기록 확인 영역에서
`이 기록으로 개인 페이스 적용`을 한 번 더 눌러야 활성화된다.

- 첫 시도 2건은 여기서 멈췄다. 해당 확인을 수행한 두 번째 실행은 저장·재열기까지 통과했다.
- 이는 데이터 오류나 영구적인 진행 불가가 아니다. **입력한 기록과 확인 행동이 떨어져 있어 발견하기 어려운 UX 문제**다.
- `PlanCandidates.tsx:245,359`, `PaceEvidenceFlow.tsx:120`에서 확인 요구와 문구를 확인했다.
- 동시에 `선택한 기록으로 ... 수치를 적용했어요`와 `새로 고른 기준 기록을 확인`이 보여 적용 완료와 추가 확인의 경계도 혼동하기 쉽다.

권고: 상단의 비활성 버튼 대신 `기준 기록 확인하고 시작` 행동을 제공해 필요한 확인 행으로 직접 이동한다.
기록·계산된 반복 초·회복을 한 묶음으로 보여주고 명시적 동의는 유지한다. 확인 자체를 몰래 생략하지 않는다.

## 5. P2 UX: 일지 저장과 계획 진행 완료가 분리되어 반복 입력을 요구함

부분 수행 일지 저장 후 정확한 세션에 일지가 연결됐지만 계획 상태는 `예정`이었다.
화면에는 `일지를 저장했어요. 계획의 진행 기록은 별도예요.`와 완료/휴식/건너뜀/통증 체크가 다시 나온다.

- 코드: `ActivePlan.tsx:434-476`.
- 다음 계획 버튼은 `ActivePlan.tsx:522`의 완료 조건을 사용한다.
- `plan-successor-activation.ts:555-569`는 비휴식 세션의 별도 진행 기록이 모두 종결됐거나 주기 종료일이 지났을 때 허용한다.
- 따라서 일지를 썼다고 반드시 즉시 다음 계획이 열리는 것은 아니다. 주기 종료일 이후에는 미기록이 있어도 다음 계획을 요청할 수 있으므로 영구 교착이라고 단정하지 않는다.

이는 현재 계약상 의도된 분리이나, 사용자에게는 같은 운동을 두 번 보고하는 느낌을 준다.
특히 부분 수행을 `완료`로 눌러야 하는지 불명확하다.

권고: 일지 저장 직후 `이 결과를 계획에도 반영` 확인을 같은 흐름에서 제공한다.
부분 수행을 완전 수행으로 바꾸지 말고 실제 결과와 진행 종결을 별도 필드로 보존한다.
다음 계획을 아직 만들 수 없다면 `미확인 훈련 2개 확인`처럼 이유와 바로가기만 보여준다.

## 6. P2 제품 경계: 상세 구성과 개인 숫자 페이스가 동일하지 않음

5km 18분 31.5초를 넣고 DEVELOPING/기본 MIX로 만든 표본은
`6 × (2min @ RPE 6–7 → 종료 뒤 60s Jog)`였다. 준비·정리와 회복은 구체적이지만
개인 5km 기록으로 계산한 초/거리가 아니다. 저장된 입력도 `fiveK: null`이다.

- 기본 카탈로그 바인딩: `impl/src/prescription/catalog-session-binding.ts:86,115`.
- 이번 8개 표본의 2개는 PACE_TARGET, 6개는 계산 카탈로그의 시간/RPE 상세 구성이었다.
- 서로 다른 경험·종목이 같은 시간형 훈련을 받는 것만으로 잘못된 운동이라고 단정하지 않는다.
- Luna A의 4종목 제한은 **기존 명시 PACE_TARGET 경로**를 말한다. 117개 계산 카탈로그 전체를 4개 템플릿으로 축소해 해석하면 안 된다.
- 반대로 117개 카탈로그가 있다고 모든 종목·경험에서 117개 개인 페이스 처방을 제공한다고 말해도 안 된다.

권고: 처방 옆에 `내 기록으로 계산` 또는 `시간·체감 강도 기준`을 짧게 구분한다.
개인 페이스를 사용할 수 있는 조건에서는 해당 기준 기록을 확인하는 경로를 제공한다.
정당한 페이스 근거가 없는 경우 숫자를 발명하지 않고, 왜 시간/RPE로 안내하는지 상세 설명에 둔다.

## 7. P2 개선 기회: 일부 수행의 이유와 실제 변경량이 다음 주기로 잘 전달되지 않음

`일부만 했거나 내용을 바꿨어요 → 오전 → RPE 8 → 아픈 곳 없음 → 저장`으로 기록할 수 있다.
실제 바뀐 거리·반복·시간은 선택 입력이며, 아무것도 넣지 않으면 무엇을 바꿨는지는 모른다.
연결된 설명은 이 기록을 원래 계획과 비교하지 않는다고 정직하게 표시한다.

- `QuickSessionForm.tsx:50`은 부분 수행과 다른 내용 수행을 하나의 PARTIAL 선택지로 묶는다.
- `:463-473`은 실제 운동 입력을 선택 사항으로 두고 그대로 저장할 수 있다.
- `catalog-cycle-successor.ts:234-239,278-299`는 같은 목적의 비교 가능한 반복 고RPE 증거가 충분할 때만 검토된 낮은 구성을 찾는다.
- 이번 한 건의 부분 수행 뒤에는 상세 구성이 유지됐고 다음 주기 수락은 성공했다. 이를 적응 알고리즘 실패라고 부르지 않는다.
- 실제 반복 고RPE 조건으로 구조가 줄어드는 브라우저 전체 경로는 이번에 실행하지 않았다.

권고: PARTIAL을 고를 때만 `횟수를 줄였어요 / 시간을 줄였어요 / 다른 운동을 했어요 / 지금은 간단히만`을 한 번 묻는다.
사용자는 간단히 저장할 수 있어야 하며, 부족한 숫자를 계획 수치로 채우지 않는다.
다음 계획에는 `변경량이 없어 이번엔 그대로 유지했어요`처럼 이번 기록에 맞는 한 줄을 우선 표시한다.
