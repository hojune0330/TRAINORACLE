## 우선 발견

### R1. MAIN 두 방법 선택은 아직 구현 격차다

`specs/active/PLAN_GENERATOR_SPEC.md:1426`은 같은 목적의 실질적으로 다른 방법 두 개를 목표로 둔다.
`app/src/domain/plan-candidate-prescription.ts:201` 전후는 같은 stored 처방을 두 후보에 전달한다.
`impl/src/plan-generator/candidates.ts:169`는 첫 QUALITY 한 개만 상세 처방으로 치환한다.
따라서 A/B 후보 수와 MAIN 방법 수는 다르다. 현재 A/B는 주요 훈련을 유지하는 보조 시간 범위 선택이며,
하나의 계획에 주요 훈련이 여러 개 있어도 모두 숫자 상세 처방이 되는 것은 아니다.

영향: 사용자가 기대한 방법 선택과 주기 안의 상세한 수행 안내가 충분하지 않다.
권장: 기존 후보의 반복 수만 변경하지 말고, 종목·목적·경험이 같은 두 번째 방법의 정확한 구성과 근거를 채택한 뒤 연결한다.
현재 계약도 이를 열린 전달 격차로 명시하므로, 무단 활성화 결함으로 분류하지 않는다.

### R2. 7종목 계획과 4종목 상세 페이스를 구분해야 한다

`specs/active/TEMPLATE_LIBRARY_SPEC.md:686`의 allowlist와 JSON approvals를 직접 대조했다.
800/1500/3000/5000m 각각 한 가지, 총 네 개이며 EXPERIENCED 범위다.
10km·하프·마라톤 및 별도 초보자 상세 처방을 모두 구현했다고 설명할 수 없다.
`app/src/domain/plan-candidate-prescription.ts:94` 전후에서 경험·동일 종목·기록 현재성을 검사한다.

이것은 현재 좁은 allowlist와는 일치하지만 전체 제품 목표에 미달한다. 청소년 전체를 차단하는 코드와도 다르다.
권장: 지원표에서 계획 생성/개인 페이스/구간별 상세/서로 다른 방법을 별도 열로 제시한다.

### R3. 일지 연동은 완전한 개인별 재설계가 아니다

`app/src/domain/plan-beta-flow.ts:438`의 생성 입력은 최근 일지의 수를 전달한다.
`app/src/domain/plan-cycle-response.ts:33`은 연결된 일지의 명시적 RPE 비교를 한다.
`impl/src/plan-generator/adaptation-transform-registry.ts:38`의 실제 변환은 기존 A/B 보조 시간 상한의 증감 두 경로다.
강도·빈도는 비활성이다. 이는 승인된 자동 증량 금지선과 정합하지만, 거리·구간·완수율·여러 주기 반응으로
다양한 다음 MAIN을 구성하는 시스템은 아니다. 상세 페이스 세션에는 비교할 계획 RPE를 발명하지 않는 것도 정상이다.

권장: 누적 분석 결과를 바로 처방으로 넣지 말고, 실제 수행을 어떤 이유로 비교에서 포함/제외하는지 먼저 연결한다.
PB/SB 또는 명시적 요청이라는 변경 조건과 기존 계획 불변성을 유지한다.

## 개선 순서

1. 현재 지원 범위와 문서의 역사적 상태를 정리한다. 기존 승인·청소년·자가 선택을 축소하지 않는다.
