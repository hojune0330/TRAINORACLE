### 1-1. 지난 턴 내 진단이 틀렸던 것 — 정정

지난 턴 나는 `journal-trash.spec.ts:8`을 `test.fixme`로 두면서
**"confirm 대화상자와 클릭이 서로를 기다리는 하네스 교착"** 이라고 적었다.
이 진단은 **틀렸다.**

진짜 원인은 `?uitest` 쿼리다. `app/src/components/Popover.tsx`의 `usePopover`는

```ts
const [open, setOpen] = useState<boolean>(UITEST)
```

즉 URL에 `uitest`가 있으면 **모든 팝오버가 자동으로 열린 상태로 시작한다**.
열린 `TermHelp` 팝오버(`role="note" class="popover-surface"`)가 버튼 위에 겹쳐
Playwright 클릭을 계속 가로챈다. 로그가 정확히 그렇게 말하고 있었다:

```
- element is visible, enabled and stable
- <div role="note" class="popover-surface">…</div> from <div class="plan-heading-row">…</div>
  subtree intercepts pointer events
- retrying click action
115 × waiting for element to be visible, enabled and stable
```

`dialog`와는 아무 상관이 없었다. 내가 로그의 `intercepts pointer events` 줄을
끝까지 읽지 않고 그럴듯한 가설(`confirm` 교착)에 맞춰 해석한 것이다.
**증상이 같으면 원인도 같다고 가정한 오류**이며, 다음에도 같은 실수를 할 수 있으니
여기 남긴다. 이 사실은 별개 화면(`NotationReader`)에서 동일 증상을 재현하고
`?uitest`만 뺐을 때 즉시 통과하는 것을 확인해서 증명했다.

해당 spec은 이후 #119에서 `window.confirm` → 앱 내 `alertdialog`로 교체되고
`Escape`로 팝오버를 닫는 처리가 들어가면서 fixme가 해제됐고, 지금 6/6 통과한다.
**내 원인 설명이 틀렸어도 결과적으로 고쳐진 것**이며, 이 둘을 구분해 기록한다.

| A9/A10 세트회복 | `R3′`, `R99999′` | 통과 |

### A8이 결함인 근거

`×`는 U+00D7이다. 한국어 키보드에서 바로 나오지 않는다. 사용자는 `x`, `X`, `*`로 쓴다.
그런데 파서는 `×`만 받고 `x`를 거부하면서 화면에

> "아직 이 표기 형식은 읽지 못해요. 예시처럼 세트·반복·회복 단위를 모두 적어 주세요."

를 띄운다. **표기를 정확히 옮겨 적은 사용자가 자기 입력이 틀렸다고 오해한다.**
안내문이 사실과 다르다 — 단위를 다 적었는데도 거부당한다.

이게 의도가 아니라 **누락**이라는 증거: 인용부호는 `″`와 ASCII `"`를 **둘 다** 받고
(`(?:″|")`), `′`와 `'`도 둘 다 받는다. 곱셈만 유니코드 전용이었다.
그리고 `x` 입력에 대한 테스트가 **아예 없었다** — 검증 공백이다.

### 수정 방침 — 숫자는 절대 관용하지 않는다

`normalizedInput`에서 **글자 별칭만** 정규화했다.

- `x`, `X`, `*` → `×`
- 자동 교정 둥근 따옴표 `”`/`’` → ASCII `"`/`'` (iOS·macOS가 실제로 이렇게 바꾼다)

숫자·구조는 손대지 않으므로 **잘못된 값이 사실로 표시될 위험이 없다.**
`toStrictEqual(원본 fixture)`로 5가지 별칭이 모두 원본과 **완전히 동일한 구조**를
내놓는 것을 고정했고, 별칭 치환이 빈 자리를 메워 통과시키지 않는지도
(`x(x400m)` → 거부) 테스트로 잠갔다. 회귀 테스트 +6건.

실제 브라우저 확인: `2x(10x400m) @5000m RP · r60" · R3'` →
`전체 반복 20회 · 빠르게 달리는 거리 8,000m · 계획된 회복 시간 합계 1,260초` 정상 표시.
화면 안내문에도 별칭을 쓸 수 있다는 사실을 적었다.

## 3. 고치지 않고 오너 판단으로 올리는 것

### 3-1. A3 — 거대수를 사실처럼 보여준다 (판단 필요)

`999999999×400m @5000m RP · r60″` 이 통과하고 화면에

- 빠르게 달리는 거리 **399,999,999,600m** (약 40만 km, 지구~달 거리)
- 계획된 회복 시간 합계 **59,999,999,880초** (약 1,902년)

이 뜬다. 계산 자체는 산수적으로 맞다. 값을 조작하지도 않았다.
하지만 **누구도 실행할 수 없는 훈련을 "표기에서 확인한 내용"이라는 제목 아래
사실로 제시**한다.

내가 마음대로 상한을 정하지 않는 이유: 합리적 상한(반복 100회? 200회?)은
종목·훈련 철학에 따라 다르고, 내가 숫자를 고르면 그건 근거 없는 훈련 판단이 된다.
이건 **훈련 도메인 결정**이므로 오너가 정해야 한다.

선택지:
1. 상한 없이 둔다 — 표기 그대로 풀어주는 게 리더의 일이라는 입장
2. 상한을 넘으면 **거부하지 않고** "이 표기는 실제 세션 범위를 벗어나 보여요"를 **함께** 표시
   (내 권고 — 사실 제시는 유지하면서 오해만 막는다)
3. 상한 초과를 거부 — 표기를 읽는 기능을 잃으므로 비권장

### 3-2. A6/A7 — 스프린트 표기가 리더는 통과, 런타임은 금지

`@60m RP`, `@100m RP`가 리더에서 통과한다. 그런데 `impl/src/prescription/anchor.ts`는

```ts
if (input.targetEventDistanceM < 60) return "SPRINT_RACE_PACE_FORBIDDEN"
// SPRINT_BENCHMARK kind → "SPRINT_RACE_PACE_FORBIDDEN"
```

즉 **처방 런타임은 스프린트 레이스페이스를 금지**한다. 두 경로의 기준이 다르다.

지금은 실사용 위험이 낮다 — 리더는 저장하지 않고 개인 페이스를 계산하지 않으며,
`preparePrescriptionRuntime`은 앱에서 호출되지 않는다(확인: `app/src`에서
`derivePrescriptionTotals`·`parsePrescriptionNotation`만 사용).
그러나 나중에 리더 결과를 처방으로 넘기는 순간 **리더에서 읽힌 표기가
런타임에서 거부되는 모순**이 사용자에게 드러난다.

이것도 임의로 맞추지 않았다. 어느 쪽 기준이 맞는지는 도메인 결정이다.

### ⛔ #126 `feat(journal): add local archive browsing` — **병합 보류**

**결함: 가져온(DERIVED) 값이 아카이브 합계에 조용히 들어간다.**

`app/src/domain/journal-archive.ts`의 `summaryForDate`는 `distanceKm`·`durationMin`을
문자열 파싱해 그대로 합산하고, **`fieldProvenance`를 한 번도 보지 않는다**

내가 직접 실행한 증거 — 워치 파일 가져오기와 동일한 provenance를 가진 일지 1건:

```
입력: distanceKm "10", durationMin "50"
      fieldProvenance: { distanceKm: DERIVED(import:activity-file), durationMin: DERIVED(...) }
출력: {"totalDurationMin":50,"totalDistanceKm":10, ...}
```

`isEligibleForAnalysis`는 이 값에 **false**를 돌려준다
(`REGISTERED_DERIVATION_RULE_IDS = []`이므로 DERIVED는 전부 부적격).
`safe-export.ts`는 이 규칙을 지키는데(10곳에서 호출) 아카이브는 지키지 않는다.

**프로젝트 불변식 위반**: "imported/DERIVED 값이 분석에 조용히 들어가면 안 된다."
아카이브 요약은 사용자가 자기 훈련량을 판단하는 화면이므로 분석 표면이다.

합산한다. **기존에 같은 문제가 있다는 게 새 코드의 면죄부는 아니다** — 다만
#126만의 신규 결함이 아니라 **기존 구멍이 새 화면으로 확산되는 것**이므로,
