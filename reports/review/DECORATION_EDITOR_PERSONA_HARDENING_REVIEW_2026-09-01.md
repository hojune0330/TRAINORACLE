## 1. 결론

P1-P6는 자유 배치, 제스처, 실행 취소, 스키마 v3, 글 스티커, 저사양 성능 게이트까지 갖춘 강한 기반이다. 그러나 `완결`이라는 표현은 구현 범위와 실행 증거를 함께 묶어 과장했다. 마스터 플랜에 있던 일반 환경 60fps, 입력 지연 100ms 이하, 실기기 핀치, 500ms 길게 누르기 메뉴, 날짜 간 세션 클립보드, 최종 시연 영상 중 일부는 구현되지 않았거나 실행 증거가 없었다.

이번 감사에서 재현된 제품 결함은 바로 수정했다. 다만 증거가 없는 항목은 완료로 바꾸지 않았다. 따라서 최종 판정은 `APPROVE_WITH_OPEN_EVIDENCE_GAPS`다.

## 2. 기존 구현의 장점

| 영역 | 장점 | 사용자 가치 |
|---|---|---|
| 직접 조작 | 드래그, 크기, 회전, 복제, 삭제, Undo/Redo가 한 편집기에 모여 있다 | 사진 편집 앱과 비슷한 조작 문법을 배울 수 있다 |
| 데이터 안전 | v2에서 v3로 마이그레이션하고 자유 배치를 구조화해 저장한다 | 기존 일지 장식이 사라질 위험을 낮춘다 |
| 내용 안전 | 글 스티커를 텍스트 노드로 렌더하고 XSS 스모크를 둔다 | 꾸미기 입력이 실행 코드로 변하지 않는다 |
| 접근 경로 | 캔버스 손잡이와 키보드 이동을 함께 제공한다 | 터치만 가능한 편집기로 고정되지 않는다 |
| 성능 기준 | CPU 4배 제한에서 30fps를 검사하는 게이트가 있다 | 저사양 환경을 고려한 최소 기준이 생겼다 |
| 표현력 | 이모지, 이미지 스티커, 테이프, 테마, 글 스티커가 함께 있다 | 단순 기록을 개인 다이어리로 바꿀 재료가 충분하다 |

## 3. 공격적 감사 발견

### A1. 완료 보고와 마스터 플랜의 증거 범위가 다름

**심각도: P1, 문서 진실성**

- 마스터 플랜은 일반 환경 60fps와 입력 지연 100ms 이하를 요구한다.
- 현재 성능 e2e는 CPU 4배 제한에서 평균 33.4ms 이하와 90% 프레임 50ms 이하만 검사한다.
- 완료 보고의 `rAF 60fps 파이프라인`은 구현 구조 설명이지 60fps 실행 증거가 아니다.
- 최종 시연 영상은 완료 보고 자체가 미제공이라고 적었다.

**판정:** P1-P6 구현 이력은 유효하지만, 로드맵 전체 증거 완결 주장은 철회가 필요하다. 기존 보고서는 변경하지 않고 이 감사 문서로 경계를 보정한다.

### A2. 핀치와 비틀기 경계 보정이 완전하지 않음

**심각도: P1, 사용 중 데이터/화면 정합성**

기존 코드는 드래그 종료에는 회전 인지 AABB 경계를 적용했지만 핀치, 손잡이 크기 변경, 회전, 키보드 크기 변경에는 같은 경계가 일관되게 적용되지 않았다. 큰 장식을 회전한 채 확대하면 일부가 페이지 밖으로 나갈 수 있었다.

**조치:** 모든 변형 경로가 동일한 `constrainToPage`를 거치도록 통합하고, 현재 회전각과 자산 크기로 가능한 최대 배율을 계산해 위치와 크기를 함께 제한했다.

### A3. 작은 화면에서 편집 도구가 캔버스를 과도하게 가림

**심각도: P1, 핵심 작업 방해**

375×667 환경에서 하단 도구 서랍의 최대 높이가 62dvh라 실제 꾸밀 일지가 충분히 보이지 않았다. 사용자는 도구를 고르는 동안 붙는 위치를 확인하기 어려웠다.

**조치:** 모바일 서랍을 `min(44dvh, 380px)`로 제한하고, 도구를 연 상태에도 캔버스 상단과 장식 위치가 남도록 했다.

### A4. 상단바가 상태에 따라 줄바꿈될 수 있음

**심각도: P1, 모바일 레이아웃**

상단바는 4열 고정 그리드인데 Undo와 Redo가 동시에 나타나면 자식 수가 5개가 되어 줄바꿈 위험이 있었다.

**조치:** 닫기, 제목, 우측 액션 그룹의 3열 구조로 바꾸고 Undo, Redo, 완료를 하나의 안정된 액션 그룹에 넣었다.

### A5. 모달 포커스와 숨은 도구의 접근성 결함

**심각도: P1, 접근성**

- 편집기에서 Tab을 계속 누르면 배경 일지로 포커스가 빠질 수 있었다.
- 도구 서랍이 닫힌 상태로 처음 열릴 때 내부 컨트롤이 즉시 `inert`가 되지 않는 경로가 있었다.
- 장식을 선택하지 않았는데도 접근성 이름에 `선택됨`이 붙었다.

**조치:** 모달 포커스 순환, 배경 `inert`, 서랍 초기 `inert`, 닫을 때 이전 포커스 복원, 실제 선택 상태에 따른 `aria-label`과 `aria-pressed`를 적용했다.

### A6. 같은 이모지를 다시 누르면 추가가 아니라 전체 제거

**심각도: P1, 다꾸 사용성**

다꾸 사용자는 별이나 불꽃을 여러 번 붙이는 동작을 자연스럽게 기대한다. 기존 팔레트는 같은 이모지를 두 번째로 누르면 같은 종류를 모두 지우는 토글이었다.

**조치:** 팔레트 탭은 항상 한 개 추가하도록 바꾸고, 현재 페이지의 같은 항목 개수를 배지와 텍스트로 표시했다. 삭제는 캔버스 선택 후 명시적으로 수행한다.

### A7. 여섯 번째 장식부터 정확히 겹칠 수 있음

**심각도: P1, 발견 가능성**

기본 배치 좌표가 5개 주기로 반복되어 여섯 번째 장식이 첫 번째와 완전히 겹쳤다. 사용자는 추가가 실패했다고 오해할 수 있었다.

**조치:** 페이지 최대 24개와 대응하는 24개 고유 배치 좌표를 만들었다. 폭이 긴 테이프와 글 스티커는 별도 안전 좌표를 쓴다.

### A8. 레이어 순서와 날짜 간 복사 기능이 화면에 없음

**심각도: P2, 마스터 플랜 누락**

레이어 순서를 바꾸는 순수 함수는 있었지만 사용자가 누를 UI가 없었고, 다른 날짜로 옮겨 붙일 세션 클립보드도 없었다.

**조치:** 선택 시 `뒤로`, `앞으로`, `복사`, `붙이기` 액션을 제공했다. 클립보드는 현재 브라우저 탭 메모리에만 두고 OS 클립보드와 localStorage에는 쓰지 않는다. 붙여넣을 때 대상 날짜의 안전 좌표를 사용한다.

### A9. 성공 안내가 화면에 계속 남음

**심각도: P2, 시각 피로**

장식 추가 같은 성공 안내가 다음 행동 뒤에도 계속 남아 편집 상태처럼 보였다.

**조치:** 일반 성공 안내는 2.2초 후 사라지게 하고, 저장 실패, 최대 개수, 오래된 상태 충돌처럼 사용자가 알아야 하는 안내만 유지한다.

### A10. 정확히 500ms 길게 누르기 메뉴는 미구현

**심각도: P2, 계획과 구현 차이**

마스터 플랜의 길게 누르기 미니바는 없었다. 이번 변경은 숨은 제스처 대신 선택 직후 보이는 액션 바를 제공했다. 초보자, 키보드 사용자, 스크린리더 사용자에게는 이 방식이 더 발견 가능하다.

**판정:** 장기적으로 길게 누르기를 추가할 수 있으나 동일 기능을 중복 제공할지 먼저 UX 결정을 내려야 한다. 현재는 선택 액션 바를 정식 경로로 본다.

### A11. 9월 1일부터 KST CI 픽스처가 만료됨

**심각도: P1, 저장소 공통 CI 차단**

꾸미기 회귀를 전체 검사하는 과정에서 `test:unit:kst`의 적응형 계획 테스트 6건이 2026-09-01부터 실패했다. 테스트가 실제 현재 시각과 고정된 2026-08-01 기록을 섞어 PB/SB 신선도와 계획 적격성이 달력 진행에 따라 바뀌는 것이 원인이었다. 제품 코드는 이번 변경과 무관하지만, 그대로 두면 모든 후속 PR의 app-quality를 막는다.

**조치:** 해당 두 계약 파일에서 `Date`만 2026-08-18로 고정하고 타이머는 실제 시간을 유지했다. 적응형 계획 의미나 런타임 코드는 바꾸지 않았다. UTC와 KST에서 같은 26개 계약을 재검증했다.

## 5. 구현 범위

1. 회전 인지 AABB를 모든 이동, 확대, 회전, 키보드 변형에 적용.
2. 24개 고유 기본 배치와 긴 자산 전용 안전 배치.
3. 같은 이모지 반복 추가와 항목별 개수 표시.
4. 레이어 앞뒤 이동, 세션 복사, 다른 날짜 붙여넣기 도메인 계약.
5. 모달 포커스 순환, 배경과 닫힌 서랍의 `inert`, 포커스 복원.
6. 상단바 안정화와 작은 화면 도구 서랍 축소.
7. 성공 안내 자동 소거와 중요 오류 안내 유지.
8. 새 동작을 잠그는 단위 계약과 모바일 e2e 추가.

### 테스트 환경 주의

기본 포트 4173에서 `reuseExistingServer`가 오래된 Vite 서버를 재사용해 새 코드가 아닌 화면을 검사하는 문제가 재현됐다. 이후 모든 브라우저 검사는 고유 포트의 새 프리뷰 서버에서 수행했다. 로컬 Windows에서는 Playwright가 테스트 완료 뒤 서버 프로세스를 회수하지 못하는 현상도 있어, 최종 성능 판정은 GitHub CI의 격리 환경 결과를 기준으로 한다.

전체 Vitest 최초 실행에서 적응형 계획 테스트가 UTC에서는 통과하고 KST에서는 6건 실패했다. 이는 제품 로직 회귀가 아니라 날짜가 진행되면 테스트 데이터가 만료되는 기존 픽스처 결함이었다. 후속 PR 전체의 CI를 막기 때문에 테스트 시계만 고정했으며 계획 엔진과 런타임 코드는 수정하지 않았다.
