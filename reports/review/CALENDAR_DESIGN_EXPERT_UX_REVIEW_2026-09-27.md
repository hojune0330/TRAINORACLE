## 1. 판정

**날짜 정확성·공통 컴포넌트 기반은 유지한다. 그러나 일정 확인에서 기록까지 이어지는 UX는 추가 개선이 필요하다.**

토스처럼 보이게 색·둥근 모서리를 바꾸는 것이 목표가 아니다. 사용자가 현재 상태와 다음 행동을 이해하고, 일정관리 앱처럼 날짜를 빠르게 탐색할 수 있어야 한다. 현재는 달력 구조를 개선했지만 기존 설명 화면과 날짜 카드가 겹쳐, 정보가 많이 쌓인 문제가 남아 있다.

이 문서는 이전 20개 가상 페르소나 검토를 취소하거나 반복 실행한 보고서가 아니다. 이전 검토가 다룬 날짜·저장 갱신·출처·초점 결함과 별도로, 시각 위계·조작 예측성·읽기 부담을 재검토했다. 코드상 관찰, 브라우저 재현, 디자인 제안을 구분한다. 새 치명적 데이터 손실이나 안전 게이트 우회는 이번 검토에서 확인하지 않았으나, 이를 전체 안전성 감사 통과로 해석하지 않는다.

## 4. 우선순위별 발견

P2는 주요 사용 흐름 개선, P3는 일관성·가독성 개선이다. 기능 오류와 디자인 개선 요청을 모두 동일한 출시 차단으로 취급하지 않는다.

### D1. P2: 오늘 요약과 긴 상세가 행동보다 앞선다

**브라우저 확인:** 375×667에서 계획 첫 화면의 월간 그리드 시작점은 약 y=721px였다. 상단은 오늘 제목, 날짜, 상태 설명, 세션 제목, 미기록 설명, 시간·강도·방법, 행동 버튼으로 채워졌다. 달력을 보기 위해 세로 이동이 필요했다. 9월 28일 MIX 상세에서는 `이 훈련 일지 쓰기` 버튼 시작점이 약 y=928px, `완료`가 약 y=980px였다. 페이지가 잘린 것은 아니지만 행동이 아래에 묻힌 상태다.

**근거:** `app/src/components/instant-plan/InstantPlanTodayView.tsx:44`, `:89`; `app/src/screens/plan-beta/ActivePlan.tsx:211`, `:269`; `app/src/screens/plan-beta/PlanSchedulePreview.tsx:349`, `:374`, `:401`.

**개선:** 계획 첫 화면의 오늘 요약은 날짜·세션명·핵심 수치·대표 행동으로 줄인다. 상세 화면은 정확한 방법을 먼저, 목적 한 줄과 이유·근거 진입점을 다음으로 배치한다. 기록 행동은 상단에도 접근 가능하게 하고, 긴 기전 설명을 읽어야만 기록할 수 있는 구조를 없앤다. 훈련 수치·회복·중단 조건은 숨기지 않는다. 저장 실패·현재 안전 경고도 접지 않는다.

**장점:** 반복 방문자의 읽기 비용과 스크롤 감소. **단점:** 너무 줄이면 처음 하는 훈련을 이해하지 못한다. 이를 막기 위해 핵심 수행 수치는 기본 노출하고 전체 방법·근거를 한 번의 선택으로 연다. 첫 화면에 달력 전체와 모든 훈련 내용을 동시에 넣겠다는 목표는 버린다.

### D2. P2: 주기 이동과 월 이동이 서로 다른 범위인데 화면이 충분히 설명하지 않는다

**브라우저 확인:** 주기는 `2026-09-27 ~ 2026-10-06`인 상태에서 `다음 달`을 두 번 눌러 11월로 이동했다. 위 주기 제목은 그대로이고, 현재 달력의 주기 강조 칸은 0개였다. 선택한 주기가 다른 달에 있다는 안내나 해당 주기로 돌아가는 전용 행동은 없었다. `오늘`은 선택 주기로 돌아가는 버튼이 아니다.

**근거:** `app/src/screens/CycleArchive.tsx:28`, `:39`, `:44`, `:63`. 월간 기록 합계가 주기 화면에도 그대로 전달되는 점은 `:31` 및 `app/src/screens/JournalMonthCalendar.tsx:40`에서 확인된다. 데이터가 있을 때 합계 범위를 혼동할 위험은 코드상 관찰이며 이번 브라우저에서 수치 오독을 실사용자로 시험한 것은 아니다.

**개선:** 월 이동 화살표는 연월 행에 유지한다. 주기 범위는 별도의 짧은 행으로 두고 `이전 주기 / 다음 주기`라는 의미를 보이게 한다. 표시 월과 주기가 겹치지 않으면 `선택한 주기는 9/27~10/6이에요 · 주기로 이동`을 제공한다. 합계에는 `이번 달` 또는 `선택한 주기`를 명시하고 실제 해당 범위를 집계한다. 주기 길이나 계획 날짜는 바꾸지 않는다.

**장점:** 범위 혼동 방지. **단점:** 조작 한 줄이 추가된다. 두 번째 툴바를 상시 크게 만들지 않고 범위 이탈 시에만 복귀 행동을 노출한다.

### D3. P2: 기록 없는 날짜를 열면 막다른 화면이다

**브라우저 확인:** 일지 달력에서 9월 26일을 열면 날짜와 `이날 작성한 일지가 없어요`만 나온다. 그날 기록 작성 진입이 없어 닫고 다른 메뉴로 가야 한다.

**근거:** `app/src/components/CalendarJournalDetails.tsx:39`, `:41`; `app/src/screens/JournalMonthCalendar.tsx:62`. 전달되는 `onOpenDay`는 기록이 있는 분기의 원문 열기에서만 사용된다.

**개선:** 과거·오늘의 빈 날짜에는 `9월 26일 기록 남기기`처럼 선택한 날짜를 포함하는 행동을 제공한다. 해당 날짜를 기존 작성 흐름에 전달하고 뒤로가면 같은 날짜로 복귀한다. 미래 날짜에는 실제 수행을 이미 했다고 기록하도록 유도하지 않는다. 미래 메모·시합 예정 입력은 별도 승인된 저장 계약이 있을 때만 열며, 없으면 일정 탐색만 유지한다.

**장점:** 기록을 찾다가 보충 작성하는 흐름이 연결된다. **단점:** 잘못된 날짜로 저장될 위험이 생긴다. 작성 화면의 날짜 표시, 초안 보존, 저장 후 원래 날짜 복귀가 수용 조건이다.

### D4. P2: 달력은 훈련 종류를 보여주지만 수행 상태는 보여주지 못한다

**코드 확인:** 날짜 칸은 세션 종류·오전/오후와 일지 개수를 읽는다. 세션별 완료·휴식·건너뜀 상태를 받는 입력은 없다. 같은 날짜에 일지가 있다고 예정 훈련을 마쳤다는 뜻은 아니므로 일지 개수로 상태를 대체할 수 없다.

**근거:** `app/src/screens/plan-beta/PlanSchedulePreview.tsx:440`, `:469`, `:475`; `app/src/components/CalendarJournalDetails.tsx:12`.

**개선:** 현재 저장된 세션 진행 상태를 읽기 전용으로 전달한다. 예정은 중립, 사용자가 명시한 완료는 체크, 일부만 기록된 날은 부분 상태를 표시한다. 일지는 별도 기록 개수로 남긴다. 상세에는 오전·오후 각각의 상태를 텍스트로 표시한다. 단순 미기록을 실패·미수행으로 색칠하지 않는다. 통증 표시와 훈련 중단 판정은 기존 안전 상태를 구분해 사용한다.

**장점:** 일정표가 매일 확인할 가치가 있는 진행 화면이 된다. **단점:** 작은 칸에 상태가 과밀해진다. 하나의 요약 표식과 정확한 접근성 이름을 사용하고 상세에서 풀어 쓴다. 자동 완료나 새 생리학적 판단은 추가하지 않는다.

### D5. P2: `오늘은 어려워요`가 실제로는 일정 위치로 스크롤할 뿐이다

**코드 확인:** `InstantPlanTodayView`의 해당 버튼은 `onChangeSchedule`을 부른다. 현재 `ActivePlan`은 여기에 `showSchedule`을 연결하며, 이 함수는 달력 위치 이동·초점만 수행한다. 휴식·건너뜀 선택이 바로 열리는 것이 아니다.

**근거:** `app/src/components/instant-plan/InstantPlanTodayView.tsx:137`; `app/src/screens/plan-beta/ActivePlan.tsx:102`, `:211`.

**개선 선택:** 현재 기능을 유지한다면 `다른 날짜 확인`처럼 실제 행동을 설명한다. 원래 의도를 유지하려면 해당 세션의 기존 `휴식 / 건너뜀 / 통증 확인` 선택으로 직접 연결한다. **권장은 후자**다. 단, 누르는 즉시 상태 저장·미래 계획 재배치는 하지 않는다. 명시적 선택 뒤 기존 처리만 실행한다.

**장점:** 버튼을 눌렀을 때 예상한 작업을 할 수 있다. **단점:** 선택 단계 하나가 필요하다. 이는 오조작 방지를 위한 유익한 단계이며 불필요한 확인창 반복과 구분한다.

### D6. P3: 작은 날짜 칸에 오전·오후와 축약어가 쌓인다

**화면·코드 확인:** 한 세션은 `오전` 다음 줄 `기초` 또는 `MIX`, 하루 두 번이면 같은 구조가 반복된다. 글자만으로 훈련 종류·시각·기록 개수가 같은 수준에서 경쟁한다. 375px 단일 세션 표본의 빈 주 행은 약 65px, 훈련 행은 약 77px였다. 가변 높이는 정보 보존에는 유리하지만 훑어보기 리듬은 일정하지 않다.

**근거:** `app/src/screens/plan-beta/PlanSchedulePreview.tsx:475`; `app/src/components/MonthCalendar.css:21`, `:27`. 하루 두 번 화면은 §3에 연결한 기존 320px 사진을 함께 확인했다.

**개선:** 날짜 칸에는 오전·오후를 두 개의 짧은 한 줄로 정렬하고, 한글 중심 훈련 라벨과 기존 의미색의 작은 표시만 사용한다. 약어만 남기거나 색 점만 두지 않는다. 기록이 더 있으면 짧은 `+N`과 상세 진입으로 처리한다. 줄 수 상한은 일반 글자 크기에서만 적용하며, 200%에서는 높이가 늘어나도 내용과 44px 터치 영역을 보존한다.

월 칸에 페이스·체중·통증 부위·메모까지 추가하는 방안은 반대한다. 한눈에 달력을 훑는 기능과 민감한 상세 확인을 모두 해친다.

### D7. P3: 오전·오후 바로가기가 어느 구간을 읽고 있는지 알려주지 않는다

**코드·기존 사진 확인:** 두 세션이 있으면 오전·오후 버튼이 항상 같은 스타일이며 클릭 시 본문으로 스크롤한다. 현재 읽는 세션을 나타내는 상태는 없다. 사용자가 탭처럼 해석할 가능성이 있으나 실제 사용자 오해를 측정하지는 않았다.

**근거:** `app/src/screens/plan-beta/PlanDayReader.tsx:25`, `:50`; `app/src/styles/plan-day-reader.css`의 `plan-day-reader__slots`.

**개선:** 두 세션을 함께 보존하는 바로가기는 유지하되, 본문 위치와 연동된 활성 밑줄·텍스트 상태를 제공한다. 실제로 다른 패널로 전환하는 탭이 아니라면 ARIA tab으로 가장하지 않는다. 오전·오후 요약은 상단에서 함께 볼 수 있게 한다. 오후 클릭이 훈련 선택 변경이나 저장으로 해석되지 않게 한다.

### D8. P3: 주기 화면 뒤로가기의 접근 가능한 이름이 실제 동작과 다를 수 있다

**코드·브라우저 확인:** `goBack`은 주기 모드에서 항상 월간 모드로 전환한다. 버튼의 이름은 `activeMode`를 보지 않고 선택 월에 따라 `이번 달로` 또는 `홈으로`가 된다. 이번 브라우저에서는 주기 화면의 이름이 `이번 달로`였고, 선택 월이 없는 경로라면 `홈으로`여도 월간 모드로 전환된다.

**근거:** `app/src/screens/JournalArchive.tsx:71`, `:100`.

**개선:** 주기 모드에서는 `월간 달력으로`로 이름을 고정하고, 월 이동·상세 복귀·화면 나가기의 목적지를 분리한다. 화면 내 화살표와 브라우저 뒤로가기가 같은 단계로 돌아가는지 확인한다. 이번에는 소스와 표시 이름만 확인했으며 모든 뒤로가기 경로를 재실행하지 않았다.

## 6. 권장 화면 구조와 대안

### 권장: 기존 전체 화면 상세를 유지하고 위계를 정리

1. 계획 상단: 짧은 오늘 요약과 대표 행동. 날짜·요일을 명확히 표시한다.
2. 월간 달력: 한 개의 연월 탐색 행, 오늘, 실제 날짜와 훈련 종류·진행 요약.
3. 날짜 선택: 현재처럼 크게 연다. 상단에 오전·오후 핵심 요약을 놓고 원하는 세션으로 이동한다.
4. 세션: 실제 수행 수치와 방법, 기록 행동이 우선이다. 이유·근거·용어는 명확한 진입점에서 읽는다.
5. 돌아가기: 선택 날짜·보던 월·스크롤을 보존한다. 반복 날짜 카드와 전체 화면 상세를 별개의 메인 흐름처럼 경쟁시키지 않는다.

기존 오너 요구인 `누르면 크게`를 보존하므로 위험과 작업량이 가장 작다. 날짜별 스와이프 카드는 달력과 별도 두 번째 기본 탐색기가 아니라 보조 보기로 정리한다. 단순히 삭제하지 않고 필요한 사용 경로를 보존한다.

### 후속 대안: 달력 아래 선택한 날 목록

날짜를 누르면 월은 남고 바로 아래에 오전·오후 목록이 바뀌며, 세션을 누르면 전체 화면 상세를 연다. 여러 날짜 비교에는 유리하지만 깊은 상세까지 한 번 더 눌러야 하며 현재 날짜 클릭 계약이 바뀐다. **이번의 첫 수정안으로 강제하지 않는다.** 비교 탐색 수요가 확인되면 별도 `월간 / 일정 목록` 보기로 추가한다.

### 데스크톱 후속

1440×900에서 현재 일지 본문 폭은 약 503px, 달력은 약 463px였다. 넓은 화면도 모바일 틀을 유지하는 기존 앱 구조다. 이는 이번 달력 코드의 신규 결함은 아니다. PC를 주요 도구로 확장한다면 `왼쪽 달력 / 오른쪽 선택 날짜` 구성이 유리하지만 앱 셸과 모든 화면에 영향이 있으므로 별도 반응형 범위로 다룬다.
