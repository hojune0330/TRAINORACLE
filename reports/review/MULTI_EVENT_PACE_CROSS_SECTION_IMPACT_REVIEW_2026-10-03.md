# 다종목 페이스 처방 및 주변 기능 영향 검토

검토일: 2026-10-03. 대상: 현재 미커밋 작업트리, 기준 HEAD `64774e30bae96e9cda41368a190eadc7386f5661`.
판정: REQUEST_CHANGES. 이전 세 가지 수정 완료와 전체 기능의 출시 준비 완료는 다르다.
이번 작업은 검토와 보고서 작성만 수행했다. 런타임 수정, 커밋, 푸시, 운영 DB 변경, 배포는 하지 않았다.

## 1. P1: 여러 훈련의 페이스 변경과 되돌리기에서 서버 일지 보호 누락

- 위치: `app/src/domain/account/active-plan-edit-journal-guard.ts:25`, `:34`; `supabase/functions/_shared/account-plan-collection-handler.mjs:289`.
- 서버는 source/target의 일지만 보호한다. PACE_REFERENCE의 target은 null이며, 실제 배치 대상인 replacements의 두 번째 이후 주소를 검사하지 않는다.
- 정상 UI가 보호 슬롯을 제외하는 것과 서버가 독립적으로 차단하는 것은 다르다. 제출된 protectedSlots에서 후속 슬롯을 빼고 현재 일지에 맞는 evidence fingerprint를 제출하면 해당 일지 의미 관문은 통과한다.
- forward와 undo 모두 첫 replacement를 source로 사용하므로 같은 영향을 받는다 (`app/src/domain/pace-plan-update.ts:115`, `:136`).
- 독립 검수자가 현재 생성 validator를 합성 자료로 실행했다. 후속 AM/PM, 슬롯 미지정, 다른 날로 이동했지만 원래 훈련에 연결된 일지에서 누락을 재현했다. source 보호, 무관 일지, 잘못된 fingerprint 대조군을 포함한 16개 경우를 확인했다.
- 증거 한계: 부분 receipt로 해당 서버 검증 함수를 실행한 결과다. 완전한 HTTP 요청이나 운영 DB 변경 성공을 재현한 것은 아니다. 검수 실행 Node는 24.11.1이며 이전 24.19.0 빌드 증거와 구분한다.
- 수정: 모든 replacement 주소에 서버 일지 보호를 적용하고 생성 validator를 갱신한다. forward/undo의 후속 슬롯만 보호된 경우를 handler 수준까지 확인한다.

## 2. P2: 하프 실제 기록의 친구 비교/공유 생성 실패

- 위치: `app/src/domain/friend-running-oracle.ts:19`, `:87`; `app/src/screens/account/PublicProfileSettings.tsx:97`.
- 새 계산과 기록은 21097.5m를 허용하지만 비교 snapshot은 정수 거리만 허용한다. 선택 기록의 거리를 변환 없이 parse하므로 새 하프 실제 기록을 공유 대상으로 선택하면 예외 경로에 들어간다.
- 증거: 독립 및 부모 정적 코드 대조. 브라우저/공유 API 실행 재현은 미실시.
- 수정: 지원 거리의 정본화 규칙을 공유 계약에도 적용하고 기존 21097m 자료의 읽기 호환을 유지한다. 공유 생성뿐 아니라 서버 validator와 받은 snapshot 렌더까지 같은 계약인지 확인한다.

## 3. P2: 지원 범위 안내가 새 처방 기능과 불일치

- 위치: `app/src/screens/plan-beta/plan-support-coverage.ts:11`; `app/src/screens/plan-beta/PlanSupportCoverage.tsx:24`, `:34`.
- 지원 표는 하프 21097과 21097.5를 단순 비교한다. RP-HALF-INTRO/TIMED/DISTANCE가 집계에서 빠진다.
- JSON 전수 집계 결과: 초보 13→14, 발전 단계 38→39, 경험자 107→109로 정본화 여부에 따라 차이가 난다. 이 수치는 종목/경험에 해당하는 구성 수이며 지금 사용자에게 모두 적용 가능한 수가 아니다.
- 표의 개인 페이스 설명은 예전 템플릿 목록만 읽어 새 catalog 경로를 표현하지 않는다. '같은 종목 기록의 페이스 계산은 준비 중', '현재 기록', '한 번의 주요 훈련' 문구는 새 목표기록/장거리 RP/배치 갱신 범위를 온전히 설명하지 못한다.
- 수정: 런타임의 종목 정본화 및 실제 계산 능력 정보를 사용한다. 구성 수, 기록 환산 가능 여부, 개별 적격 여부를 별도로 표시한다.

## 4. P2 후보: 공개 프로필 직접 진입의 내 기록 출처 불일치

- 위치: `app/src/App.tsx:20`, `app/src/AppShell.tsx:296`, `app/src/screens/PublicProfilePage.tsx:45`, `:120`.
- 공개 URL은 계정 런타임/AppShell을 건너뛰지만 내 비교 기록은 loadAthleteRecords를 읽는다. 새 페이지 로드에서 활성 계정 초기화가 없다면 계정 미러 대신 게스트 기록을 읽는다.
- 증거: 독립 정적 경로 추적. 실제 로그인 상태의 새 페이지 진입 재현 필요.
- 수정 방향: 공개 상대 자료 조회와 나의 계정 기록 조회를 분리한다. 계정 준비 전에는 '내 기록 없음'으로 확정하지 말고 로그인/불러오기 상태를 구분한다. 게스트 기록을 계정 기록처럼 표시하지 않는다.

## 5. P2 후보: 온라인 경기 기록 도착 후 화면 갱신 누락

- 위치: `app/src/screens/account/PublicProfileSettings.tsx:33`, `app/src/screens/Home.tsx:48`, `app/src/components/OracleResume.tsx:17`, `app/src/AppShell.tsx:488`.
- 공개 설정은 최초 records 배열을 setter 없는 useState에 보관한다. 홈/오라클에는 경기 기록 도착 이벤트를 직접 구독하지 않는 경로가 있다. 온라인 응답이 늦게 오면 다른 렌더/재진입 전까지 빈 목록이나 이전 요약이 남을 수 있다.
- 중요한 제외: 일반 앱의 온라인 기록은 계정별 로컬 캐시에 미러링된다. loadAthleteRecords 사용 자체를 동기화 누락으로 판정하지 않았다 (`useAccountAthleteRecordsRuntime.ts:12`, `athlete-records.ts:241`).
- 증거: 독립 정적 경로 추적. 지연 응답을 주입한 화면 테스트 필요. 다른 상태 변경이 우연히 재렌더하는 상황은 누락을 가릴 수 있다.
- 수정 방향: 계정별 공통 기록 snapshot 구독으로 갱신하고 로딩/빈 상태/실패를 구분한다. 새 기기·느린 응답·계정 전환을 확인한다.

## 6. 처방 범위: 숫자로 구분해야 할 것

현재 catalog 126개: ATP-PC 18, BASE 16, GLY 13, LT 20, MIX 28, OFF 1, REC 9, VO2 21. hold 항목 0개.
이것은 126개 모두 모든 선수에게 자동 페이스 처방된다는 뜻이 아니다. 종목·경험·환경·시간·입력 적격성 검사는 별개다.

- catalog 자동 기록 모델은 5km 기반 LT/VO2와 명시된 10km/하프/마라톤 RP 경로가 중심이다 (`impl/src/prescription/record-pace.ts:6`).
- 800/1500/3000/5000의 기존 PACE_TARGET 경로는 별도로 유지된다. catalog 경로 하나만 보고 미지원으로 판단해서는 안 된다.
- 스프린트·언덕·근력·플라이오를 평지 경기 평균 페이스로 무조건 환산하지 않는 것은 누락이 아니라 승인된 경계다. 직접 목표/운동시간/체감 강도 중 실제 적용 기준을 화면에서 명확히 해야 한다.
- 종목 간 예측은 비교 제공과 처방 적용을 구분한다. 채택되지 않은 예측 조합은 완료 범위에 합산하지 않는다.
- 목표기록을 제한하는 과거 distance-adoption 템플릿 경로가 남아 있다. 개별 채택 조건이 실제 기록만 요구하는지 대조하기 전에는 일괄 개방하거나 결함으로 단정하지 않는다 (`plan-template-options.ts:93`).
