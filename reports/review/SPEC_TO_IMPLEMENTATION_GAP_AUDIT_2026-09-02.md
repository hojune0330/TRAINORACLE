## 1. 결론

TrainOracle은 문서만 있는 상태가 아니다. 일지 저장, 꾸미기, 기록 기반 상세
페이스, 계획 선택과 진행, 계획-일지 연결, 누적 거리, 에너지 원장, 개인 오라클,
훈련법 비교의 실제 코드가 있다. 반대로 이 사실을 근거로 **스펙 전체가 구현된
개인 맞춤 코칭 엔진**이라고 말할 수도 없다.

가장 큰 빈틈은 다음 연결에 있다.

> 실제 수행 기록을 충분히 분류하고 검증한 뒤, 그 선수에게 맞는 다양한 세션을
> 구성하고, 여러 주기의 반응을 다음 후보에 제한적으로 반영하는 과정.

현재는 **기록으로 페이스를 개인화하는 부분**이 **훈련 구성과 훈련량을 개인화하는
부분**보다 앞서 있다. 일지와 꾸미기 경험도 코어 처방 엔진보다 많이 완성되어 있다.

우선순위는 장식을 줄이거나 청소년 사용을 다시 막는 것이 아니다. 이미 구현된
경험을 유지하면서 `세션 분류 -> 규칙 평가 -> 상세 후보 -> 수행 근거 -> 다음 주기`
연결을 완성하는 것이다.

### G02. 상세 처방은 4종목에 각 1개이며, 후보의 MAIN 구성은 같다

**판정: 구현은 있으나 제품 약속에 비해 범위가 좁다.**

현재 `app/src/domain/detailed-prescription-manifest.json`의 활성 항목을 직접
재계수하면 다음 4개다. 모두 `EXPERIENCED` 범위다.

| 종목 | 실제 활성 템플릿 | 표기 |
| --- | --- | --- |
| 800m | `MD-800-01` | `10x200m @800m RP, r60s STAND` |
| 1500m | `MD-1500-01` | `3x500m @1500m RP, r180s STAND` |
| 3000m | `MD-3000-01` | `4x800m @3000m RP, r180s WALK` |
| 5000m | `V2-SEED-05` | `5x1000m @5000m RP, r150s JOG` |

`detailed-prescription-runtime-authority.ts`의 위임 활성 목록은 비어 있다.
문서에 30개 예시가 있는 것과 앱에 30개가 활성화된 것은 다르다. 10km·하프·마라톤은
계획 진입 범위에 있지만, 이 상세 페이스 템플릿 범위에는 없다.

역시 후보 안의 한 QUALITY 세션만 상세 표기로 연결한다.

**사용자 영향:** 후보를 바꿔도 본운동이 비슷하고, 같은 주기를 반복할 때 다른
훈련을 경험하거나 종목·수준에 따라 방법을 고르는 재미와 효용이 제한된다.

**권장:** 기존 연구와 카탈로그에서 종목·경험·목적별로 수용할 템플릿을 명시적으로
늘린다. 첫 단계는 MAIN 하나에 2~3개 실질적 대안과 그 차이를 주는 것이다.
준비/본운동/회복/정리, 정확한 반복·거리·페이스·근거를 함께 검증한다. 단순히
카탈로그 전체를 ACTIVE로 바꾸는 방식은 사용하지 않는다.

분리하고, 간편 기록의 결측을 0이나 기본값으로 채우지 않는다.

### G04. 24주 계보는 있지만, 실제 경기와 에너지 배분을 반영하는 주기 설계는 아니다

**권장:** `날짜/오전·오후의 불변 세션 ID -> 계획 버전 이력 -> 실제 일지 연결 ->

### G06. 웨어러블은 파일 가져오기와 준비 경로가 있으며, 자동 연동 완료는 별도다

자동 연동이 이미 되는 것처럼 표시하지 않는다.

### G07. 생리 데이터 신뢰 판정과 근거 설명 계층이 빠져 있다

`PHYSIO_SOURCE_TRUST_SPEC`의 출처·최신성·충돌·동의·종목 적합성 판정 경로를

대상별 설명/비공개 이유 분리도 현재의 짧은 `rationaleCodes`와 같은 것은 아니다.

**사용자 영향:** 숫자가 어디서 왔고 무엇을 반영하지 못했는지, 왜 이 세션이
선택됐는지를 사용자가 깊게 확인하는 기능이 충분하지 않다.

## 4. 개인정보 경계에서 발견한 잠재 충돌

`app/src/domain/account/sync-run.ts:50`과 계정 UI는 현재 원문 업로드를
`shareTrainingNotes: false`로 강제한다. 따라서 이번 감사에서 활성 경로의 원문
유출을 확인한 것은 아니다.

그러나 `sync-local.ts:163`의 공개 함수 `toUploadPayload`는 인자로
`shareTrainingNotes: true`가 들어오면 분석용 메모가 포함된 entry 전체를 반환한다.
`supabase/migrations/0013_shared_journal_projection.sql:54`도
`TRAINING_NOTE` 권한에서 원문 `memo/note`를 반환하는 경로를 갖는다.
`sync.contract.test.ts:110`은 이 원문 포함 동작 자체를 성공으로 고정하고 있다.

이는 현재 `LOCAL_FIRST_SYNC_AND_PROMOTION_CONTRACT.md:137`의 첫 베타
구조화 데이터 전용·원문 서버 저장 금지와 함께 남아 있는 **비활성 잔여 경로**다.
상위 호출 한 곳의 `false`를 나중에 제거하면 정책이 다시 열릴 수 있다.
따라서 기존 테스트가 통과한다는 사실만으로 최신 개인정보 계약과 정합하다고
판정하면 안 된다. 직렬화 함수와 호출부가 서로 다른 정책을 테스트하고 있다.

**권장:** 별도 작은 변경으로 업로드 직렬화 경계 자체를 구조화 전용으로 만들고,
구형 raw-note 공유 SQL/권한의 실제 사용 여부를 확인한다. 기존 저장 데이터가
있을 가능성을 조사하지 않고 삭제나 마이그레이션을 실행하지 않는다. 공개 다이어리
정책을 나중에 수용하더라도 분석용 구조화 경로와 공개 글 전송 경로를 분리한다.

## 7. 간편 일지 V2 후속 검토

이번 HEAD에서 다음 경계는 코드와 계약에 함께 반영되어 있다.

- 직접 고른 정확한 RPE 또는 미기록. 중간값/기본값 자동 저장 없음.
- 운동 후 몸 상태 확인을 구조화하며, 휴식/건너뜀은 수행 거리·시간에 합산하지 않음.
- 간편 기록 후 자세히 쓸 때 같은 ID를 사용하고 계획 연결을 보존함.
- 날짜가 같다는 이유만으로 계획 세션을 자동 연결하지 않음.
- 기기 파일 후보는 자동 덮어쓰지 않고 사용자 확인을 거침. 휴식/건너뜀은 합치기 후보가 아님.
- 포인트는 오늘의 안전한 기록 행동 기준이며, 지난 날짜 입력이나 반복 수정으로 중복 지급하지 않음.
- 비교에서 결측을 0으로 만들지 않고 비밀 메모를 비교하지 않음.

남은 문제는 간편 입력을 다시 길게 만드는 것이 아니다. 짧은 입력이 끝난 뒤
현재 확보한 근거 수준을 설명하고, 필요할 때만 상세 기록/기기값으로 이어지는
흐름이다. 간편 기록만 있는 사용자를 배제하지 않되, 그 자료로 정밀한 부하 처방을
했다고 과장하지 않는다.

V2는 관측 main보다 2커밋 앞선 로컬 작업이다. 배포 여부와 현재 코드의 테스트
결과는 §10에 별도로 기록한다.

## 8. 권장 처리 순서와 장단점

**모든 계약이 완성될 때까지 기능 개발을 멈추자는 뜻은 아니다.** 두 작업 흐름을
분리하는 편이 낫다.

1. 현재 승인된 베타 입력/안전 경계 안에서 상세 템플릿과 선택 경험을 확대한다.
2. 전체 규칙·분류기·장기 원장·운영 거버넌스를 단계적으로 연결한다.

첫 흐름은 두 번째의 모든 미정 계약을 기다릴 필요가 없다. 다만 해당 새 템플릿이
실제로 의존하는 종목·경험·기록·회복·안전 기준은 확정해야 한다. 연구 파일의
존재와 실행 허가를 섞지 않고, 이미 승인된 동일 범위를 반복 승인받지도 않는다.

### 단계 A. 현재 상태와 개인정보 잔여 경로 정리

- 현재 구현표/최신 결정 연결을 고정하고, raw-note 업로드 경계의 잠재 재개 경로를
  작은 변경으로 정리한다.
- 장점: 중복 구현과 정책 역행을 줄인다. 범위가 작아 검증하기 쉽다.
- 단점: 사용자에게 바로 보이는 새 기능은 적다. 오래된 모든 문서를 전면 수정하면
  코어 개발이 다시 밀릴 수 있으므로 필요한 포인터와 충돌 절만 고친다.

### 단계 B. 코어 데이터와 규칙 연결

- 실제 세션 분류, 승인된 규칙 입력, Formation-규칙 어댑터, 선수/출처 스냅샷을
  먼저 연결한다. 정해지지 않은 기준은 UNKNOWN/검토 상태로 명확히 둔다.
- 장점: 이후 상세 템플릿과 적응이 같은 사실을 공유한다.
- 단점: 과거 스펙의 미정 기준을 제품 결정으로 해소해야 한다. 임의 한도나 공식으로
  빨리 채우면 오히려 잘못된 정밀함이 생긴다.

### 단계 C. 상세 처방 다양화와 실질적 후보 선택

- 종목별 1개 템플릿에서 벗어나, 승인된 MAIN 대안 2~3개와 준비/회복/정리까지
  완전한 세션을 제공한다. 기본 시간 처방과 상세 처방의 사용자 설명을 구분한다.
- 장점: 사용자가 즉시 체감하는 핵심 가치가 커진다.
- 단점: 템플릿 숫자만 늘리면 유사 세션 남용과 조합 폭증이 생긴다. 종목·수준·목적·
  주기 위치 적격성과 미선택 대안의 이유를 함께 다뤄야 한다.

### 단계 D. 날짜·주기·실제 수행을 연결한 제한적 적응

- 불변 occurrence와 계획 역사, 9.5일 경계, 경기일·중주기 배치를 연결한다.
  그 뒤 수행 근거를 다음 후보의 유지/제외/변경 설명에 사용한다.
- 장점: 반복 주기가 단순 재생성이 아니라 선수의 이력이 된다.
- 단점: 서버/다기기 충돌과 과거 기록 수정이 어려운 영역이다. 자동 증량을 기본으로
  하지 않고, PB/SB·명시적 요청과 한 차원 변경 원칙을 유지한다.

### 단계 E. 데이터 유입과 반복 방문 경험

- 자동 기기 연동 운영, Daily Brief, 누적 목표, 선수용 확장 보기를 연결한다.
- 장점: 기록 부담을 줄이면서 코어 분석의 근거가 쌓인다.
- 단점: 제공자 승인은 외부 의존성이 있다. 파일 import 경로를 별도로 유지한다.

### 단계 F. 공개 다이어리와 미디어

- 팔로워 공유·공개 미리보기·SEO·복수 비밀 포스트잇·사진/전사를 별도 개인정보
  계약과 함께 구현한다.
- 장점: 기록/꾸미기/공유의 일상성이 커진다.
- 단점: 공개 범위·삭제·철회·미성년자·신고 운영이 생긴다. 지금 존재하는 공개
  프로필 권한을 일지 전체 접근 권한으로 재사용하면 안 된다.

## 9. 그대로 유지해야 할 결정과 보류

- 청소년이라는 이유만으로 일률적으로 훈련계획을 막지 않는다.
- 혼자 쓰는 선수의 자기 선택을 유지하고, 코치 연결이 항상 필수라고 바꾸지 않는다.
- 매일 훈련·일 2회 선택은 최신 결정대로 유지한다. 옛 PM 건수 제한을 복구하지 않는다.
- 기본 보기를 빈약하게 만들고 선수용에만 핵심 정보를 숨기지 않는다.
- D9 ACTIVE/UNKNOWN의 안전 경계, 개인정보와 출처 원칙은 유지한다.
- 컨디션이 좋거나 일지를 많이 썼다는 이유로 강도·양·빈도를 자동 증가시키지 않는다.
- CTL/ATL/TSB·TRIMP·균형 비율·범용 피로 점수의 미수용 공식을 구현 완료로 취급하지 않는다.
- 해시/서명 형식, 테스트 PASS, 소스 수용, 제품 승인, 실제 운영 검증은 서로 다른 증거다.
- 이번 보고서는 이슈를 닫거나 소스의 정본 지위를 바꾸지 않는다.
