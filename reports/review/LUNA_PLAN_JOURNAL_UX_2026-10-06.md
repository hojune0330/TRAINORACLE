## 범위와 방법

`Plan intake → 계획 달력 → 계획에 연결된 일지 → 실제 일지 보기 → 다음 계획`과 통증 확인 후 읽기 전용 계획안 경로를 현재 코드와 계약 테스트에서 따라갔다. 16개 합성 첫-사용 관점에 4~6개의 구체 동작을 배정했다(총 88개 논리 동작). 기존 계획이나 일지가 필요한 장면은 합성 선행조건으로만 표시했다. 이 수는 사람 수, 완료율, 소요 시간 또는 사용성 측정치가 아니다.

시나리오 seed `20261006`은 고정된 분기 순서를 다시 검토할 때 쓰는 식별자다. 브라우저 랜덤화나 확률 시험은 실행하지 않았다. 키보드, 작은 화면, 다시 진입, 이전 단계 이동, 기록 건너뛰기, 위험 재확인을 섞었다. 별도 Luna 모델 호출, 실제 사용자 인터뷰, 브라우저 조작, 테스트 실행은 하지 않았다. 따라서 아래 판정은 코드 근거가 있는 정적 가설이며 런타임 결함 재현이라고 주장하지 않는다.

지침은 `PRODUCT_NORTH_STAR.md` §3.2, `TRAINING_PLAN_CURRENT_SCOPE.md` §1, `docs/UX_UI_VISUAL_STANDARD.md`를 따랐다. 디자인 핸드오프 README와 Risk Review는 참고했으나, 그 자료의 Session Prep·Weekly Wrap 시안을 현재 계획 화면의 구현 증거로 취급하지 않았다.

## 우선 발견

### P1 · 통증 신호가 남아 있을 때 재확인 경로가 같은 안내로 되돌아갈 수 있음

`PlanBeta.tsx:1138-1160`에서 안전 재확인 결과가 계속 차단이면 `blocked` 상태로 돌아간다. 같은 컴포넌트의 계약 테스트 `PlanBeta.contract.test.tsx:546`는 최근 구조화 고통 신호가 있으면 긍정 응답만으로 차단을 풀 수 없음을 확인하도록 작성돼 있다. 그러나 `PlanBlockedGuide.tsx:11-83`은 차단 원인을 받지 않고, 결과 문구와 `몸 상태 다시 확인하기` 행동이 반복해서 보인다. 신호가 계속 유효한 사용자는 왜 같은 화면으로 돌아왔는지 알기 어려워 같은 확인을 반복할 수 있다.

**최소 수정:** 재확인 결과가 계속 검토 필요일 때 현재 계획과 미리보기가 그대로라는 점, 이 응답만으로 게이트가 해제되지 않았다는 점을 짧은 상태 문구로 구분한다. 민감한 메모 원문이나 진단을 보여주지 않고, 실행·적용·저장은 계속 막는다. 최근 기록을 다시 보거나 멈추는 선택은 분명한 라벨로 제시한다.

### P1 · 첫 화면에서 종목·기준·시간·날짜를 한꺼번에 요구하고 행동 라벨이 결과를 과장함

`components/instant-plan/InstantPlanEntryForm.tsx:62-180`은 기본 `내 기록`이 선택된 상태로 기준 라디오, 종목, 분·초, 기록 날짜를 같은 화면에 렌더한다. 기록 날짜는 선택 사항인데 설명·입력까지 첫 화면에 상시 보인다. `내 계획 받기` 제출은 `screens/PlanBeta.tsx:1023-1043`에서 기록 입력 준비 후 다음 인테이크 단계로 이동하며, 완성된 계획을 즉시 받는 행동은 아니다. 기록이 없는 첫 사용자에게는 시작에 필요한 값이 모두 필수처럼 보일 수 있고, 행동 이름은 다음 화면 전환과 맞지 않는다.

**최소 수정:** 종목 → 기준 → 현재/목표 기록 상세로 나눈다. 선택한 종목·기준을 보존하고 명시적인 `기록 없이`는 별도 확인 제출 없이 기존 `onSubmit`으로 넘긴다. 날짜는 닫힌 선택 공개 안에 두되 잘못된 날짜 제출 때 자동으로 열고 오류 필드에 초점을 둔다. 기록 저장은 기존 제출 경로에서만 한다. (이 보고서 저장 후 별도 구현 단계에서 이 수정이 적용될 예정이며, 본 검토의 관측 상태는 수정 전이다.)

### P2 · 완료 뒤 다음 주기 행동이 서로 다른 결과를 한 화면에서 경쟁함

`screens/plan-beta/ActivePlan.tsx:337-345,506-544`는 프레임 완료 후 일정 아래에 `PlanAdaptationFlow`를 노출하면서 별도로 `현재 기준으로 다음 계획안 만들기`도 보여준다. 적격 조정이 있으면 첫 진입은 `다음 계획 조정하기`; 없으면 `이번 주기 기록 확인`으로 바뀐다. 이미 보류된 안은 다시 `선택한 다음 계획 시작하기`와 몸 상태 확인을 요구한다. 실제 저장·검토·활성화 단계는 서로 달라야 하지만, 일반 사용자가 “기록 검토”, “새 안 만들기”, “보류안 시작”의 차이를 빠르게 파악하기 어렵다.

**최소 수정:** `다음 주기` 아래에서 새 계획안 보기, 이번 주기 기록 확인·조정, 저장된 안 시작을 서로 다른 결과가 보이는 동사로 묶고 한 줄 설명을 붙인다. 새 안의 검토·저장, 보류안의 몸 상태 재확인과 시작은 합치거나 자동 실행하지 않는다.

### P2 · 계획 달력 통합 회귀 파일이 현재 흐름을 실행하지 않음

`screens/PlanBeta.calendar.contract.test.tsx:1-`에는 기존 11단계 인테이크 순서를 전제한 세 테스트가 `it.skip`으로 남아 있고 파일 주석도 새 4질문 흐름으로 재작성 예정이라고 밝힌다. 개별 계약은 보강돼 있다. 예를 들어 `PlanSchedulePreview.contract.test.tsx`는 날짜 선택·큰 보기·연결된 세션 복귀를, `JournalDayReader.contract.test.tsx`와 `CalendarJournalDetails.contract.test.tsx`는 일지 원문 열기·날짜 복귀를 다룬다. 다만 현재 PlanBeta 인테이크부터 다음 계획까지의 전체 브라우저 왕복 증거는 이 정적 검토에서 확인하지 못했다.

**최소 수정:** 담당 통합 테스트 오너가 새 인테이크 라벨을 반영해 한 개의 좁은 브라우저 경로를 다시 연결한다. 기존 skip을 통과로 세거나 전체 회귀로 대체하지 않는다.

## 보존할 강점과 경계

- 통증 계획안 미리보기는 명시 체크 뒤에도 읽기 전용이다. `PlanBlockedGuide.contract.test.tsx`는 활성화 버튼 부재, 저장 상태 부재, 기존 계획·일지 불변, 개인 페이스 처방 제외를 검사하도록 작성돼 있다. 이를 실제 처방 시작으로 바꾸지 않는다.
- 통증 기록 작성은 `AppShell.tsx:698-736,1039-1085`의 기록 원점 보존 경로를 사용한다. 기록 중 원래 화면을 숨겨 유지하고 저장 후 복귀시키도록 돼 있다. 정적 검토상 통증 기록 때문에 인테이크 초안이 버려진다고 단정할 근거는 없었다.
- 계획 달력 날짜 선택은 `PlanSchedulePreview.tsx:199-245,355-368`에서 날짜 독자 화면을 열고, 실제 기록은 `CalendarJournalDetails.tsx:60-91`의 별도 원문 행동으로 연다. 계획·실제 기록·원문은 분리돼 있다. 날짜 위치 복원과 기록 보존을 단순화한다며 이 단계를 제거하지 않는다.
- `ActivePlan.tsx:449-499`는 계획 진행 상태를 일지와 별도로 저장한다. 완료·휴식·건너뜀·통증 확인을 일지 내용만 보고 자동 추정하거나 계획을 자동 완료로 바꾸면 안 된다. 대신 저장 직후 연결 상태와 명시적 진행 행동이 가까이 보여야 한다.
- 상위 지침의 read-only 예외는 계획안 미리보기뿐이다. 개인 페이스 적용, 시작, 활성화, 동기화, 수행 연결, 내보내기에는 기존 확인과 차단을 유지한다.

## 검토 한계

코드와 테스트 소스만 읽었다. 브라우저를 열거나 화면을 클릭하지 않았고 어떤 테스트도 실행하지 않았다. 따라서 UI 크기, 실제 초점 이동·애니메이션, 브라우저 뒤로가기의 런타임 결과는 미검증이다. 생산 계획·일지·사용자 계정에는 접근하거나 쓰지 않았다. 다음 구현자는 이 보고서를 사람 대상 사용성 연구나 실행 증거로 인용하지 말고, 위 계약과 좁은 테스트로 별도 확인해야 한다.
