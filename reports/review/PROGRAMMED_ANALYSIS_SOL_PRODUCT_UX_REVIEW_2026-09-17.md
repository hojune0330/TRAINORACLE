## 2. 고가치 발견

### F1. [설계 P1 · 운영 결함 미재현] “첫 결과물”과 구현 순서가 뒤집혀 첫 가치가 계약 작업 뒤로 밀릴 위험

- **근거:** 검토안은 훈련 해설표를 첫 핵심 결과물로 정하고 기존 구조화 처방만으로도 가치가 충분하다고 말한다. 그러나 권장 순서는 외부 자료 허용표·계약 충돌 패치를 1단계로 두고 해설표를 2단계, 실제 비교를 3단계로 둔다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:95-124,245-266,317`. North Star는 제품의 본체를 “무엇을 했고 어떤 의미인지 분석·조언”하는 코칭으로 정의하며, 안전을 이유로 핵심 가치를 빼는 축소를 경고한다. `TRAINORACLE-private-memo-save-hotfix-20260913/PRODUCT_NORTH_STAR.md:15-31,153-160`.
- **사용자 피해·반례:** 기록이 없는 첫 사용자는 외부 필드 계약의 혜택을 받을 데이터가 없다. 받은 훈련 한 줄은 있지만 워치 연결이 없는 사용자는 가장 빨리 가치를 받을 수 있는데, 현재 순서에서는 백엔드·계약 선행 작업이 끝날 때까지 기다린다.
- **수정 방향:** `기존 계획/지원 표기 → 구성 확인 → 계산 → 검토된 설명 → 다음 가능한 행동`을 첫 세로 완결 단위로 앞당긴다. 동시에 첫 외부 출처의 허용 필드부터 가져오기·분석 결과까지 잇는 별도 경로를 병행하되, 두 경로가 공통 이벤트 정체성·출처·상태·결과 컴포넌트를 사용하게 한다. 해설표 V1은 새 처방이나 새 공식 없이 현재 `SessionExplanation`과 처방 합계 기능을 재사용한다.
- **장점/비용:** 장점은 실제 선수 데이터나 공급자 승인이 없어도 첫 가치를 검증할 수 있고, 기존 계획 사용자의 가치가 즉시 커진다는 점이다. 비용은 외부 데이터 전략과 별도로 UI·설명 구성의 범위를 먼저 고정해야 하며, 범용 자연어 입력 약속을 의도적으로 미뤄야 한다.
- **검증법:** 합성 계획과 검토된 예시만으로 여섯 페르소나가 첫 결과까지 가는 화면 전환·필수 입력·막힘을 기록한다. 결과를 본 뒤 “무엇을 할 훈련인지, 무엇이 미정인지, 다음에 무엇을 할 수 있는지”를 사용자가 찾을 수 있는지 관찰한다. 실제 사용자 검증 전에는 성공률을 주장하지 않는다.

### F2. [설계 P1 · 운영 결함 미재현] 새 세 입구가 현재 정보구조와 겹칠 위험

- **근거:** 검토안은 `내 기록 가져오기 / 받은 훈련 풀어보기 / 지난 훈련과 비교`를 핵심 입구로 제시한다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:207-215`. 현재 홈은 이미 분석·계획·예시·학습의 목적별 입구를 제공하고, 주 탭은 홈·일지·기록하기·계획·분석으로 고정돼 있다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/home/TrainingHome.tsx:179-184`; `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/components/AppChrome.tsx:27-33`. 실제 라우팅도 가져오기는 기록 하위, 비교는 분석, 설명은 계획 상세에 연결돼 있다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/AppShell.tsx:311-409`.
- **사용자 피해·반례:** 세밀한 일지를 쓰는 러너가 계획 상세의 `훈련 방법과 이유`와 새 `받은 훈련 풀어보기` 중 어느 쪽이 정본인지 알기 어렵다. 뒤로가기·선택 유지·스크롤 복귀 규칙도 두 경로에서 달라질 수 있다.
- **수정 방향:** 새 최상위 허브나 탭을 만들지 않는다. `받은 훈련 풀어보기`는 계획/세션 상세의 확장, `지난 훈련과 비교`는 세션 상세와 분석의 교차 진입, `내 기록 가져오기`는 기록하기의 대체 입력으로 유지한다. 홈에는 사용자 목적을 말하는 짧은 진입 버튼만 두고 동일 결과 화면으로 수렴시킨다.
- **장점/비용:** 장점은 기존 탭 의미와 저장된 하위 화면 복귀 규칙을 보존하고 중복 설명 엔진을 막는 것이다. 비용은 각 기존 화면의 상태와 라우팅을 확장해야 하므로 독립 페이지 하나를 붙이는 것보다 초기 조정이 필요하다.
- **검증법:** 현재 5개 탭을 유지한 프로토타입에서 각 페르소나가 동일 결과를 두 경로 이상으로 열어도 제목·근거·뒤로가기 목적지가 일치하는지 점검한다. 브라우저 실측이 아니라 상태 전이표와 정적 화면 흐름으로 먼저 검토한다.

### F3. [설계 P1 · 운영 결함 미재현] 워치 가져오기를 핵심 분석 입구로 승격하면 “저장 뒤 분석 불가” 절벽이 생긴다

- **근거:** 검토안은 워치 사용자가 일지를 다시 쓰지 않고 필요한 정보만 추가하면 된다고 제안한다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:211,217`. 하지만 현재 가져오기 화면은 자동 연동이 아니라 사용자가 워치 앱에서 파일을 내보내야 하고, 저장 후에도 가져온 값은 분석에 포함되지 않는다고 명시한다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/import-activities/ImportStages.tsx:21-25,86-90,182-188,237-243`. 외부 기록 스펙도 별도 출처 규칙이 채택되기 전 통계·추이·오라클·계획 사용을 금지한다. `TRAINORACLE-private-memo-save-hotfix-20260913/specs/reconstruct/EXTERNAL_RECORD_INTEGRATION_SPEC.md:120-149`.
- **사용자 피해·반례:** 현재 화면은 분석 제외를 알리고 있으므로 이 자체를 재현된 운영 결함으로 판정하지 않는다. 다만 향후 이 경로를 “내 기록 분석”의 핵심 입구로 홍보한 채 제약을 유지하면, 바쁜 러너가 파일 내보내기·선택·중복 검토·저장 뒤 “분석할 기록이 없음”을 만나 실패로 오해할 수 있다. 같은 수치를 직접 다시 쓰게 유도하면 출처를 거짓으로 바꾸는 더 큰 결함이 된다.
- **수정 방향:** 외부 필드 분석 채택 전에는 `내 기록 가져오기`를 분석의 핵심 입구로 홍보하지 않고 “일지에 보관·확인” 도구로 명확히 둔다. 허용 범위가 채택된 뒤에는 저장 결과 화면을 끝점으로 두지 말고 `반영 가능 / 보관만 / 충돌 확인`을 나눈 영수증과 해당 보고서로 연결한다. RPE처럼 정말 필요한 주관값만 선택적으로 묻되, 건너뛰어도 원자료 확인 가치는 남긴다.
- **장점/비용:** 장점은 재입력과 출처 세탁을 막고 기대를 정직하게 맞추는 것이다. 비용은 분석 활성화 전에는 마케팅 가능한 가치가 줄어 보이며, 공급자별 허용 범위가 생길 때 결과 영수증을 갱신해야 한다.
- **검증법:** 합성 파일로 `전부 보관만`, `일부 분석 가능`, `중복 후보`, `계정 전송 대기`, `충돌` 흐름을 각각 walkthrough한다. 어느 경우에도 사용자가 같은 값을 직접 다시 입력해야 분석된다는 인상을 받지 않는지 검토한다.

### F4. [설계 P1] “세 번 안팎” 약속과 개인화 입력 요구가 충돌한다

- **근거:** 검토안은 종목·주기 목적·가능 시간·시설·선호·승인된 선수 정보를 읽은 뒤 후보를 좁히는 6단계 개인화와, 세 번 안팎의 선택이라는 UX 약속을 함께 둔다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:159-176,207-217`. 현재 계획 흐름도 종목부터 경기일자까지 최대 11개의 명시적 단계를 갖고 있다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/plan-beta/plan-intake-navigation.ts:6-18,65-89`; `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/plan-beta/PlanIntake.tsx:158-175`.
- **사용자 피해·반례:** 받은 훈련의 뜻만 알고 싶은 사용자가 시설·주기·선호까지 묻게 되면 해설 전에 이탈한다. 반대로 개인 페이스를 원한 사용자가 필요한 기준 기록을 묻지 않으면 겉보기만 개인화된 결과가 나온다.
- **수정 방향:** 입력을 `결과를 계산하는 데 지금 막는 질문`, `결과 품질을 높이는 선택 질문`, `다음 계획에서만 필요한 질문`으로 분리한다. 해설은 가능한 범위부터 먼저 보여주고, 페이스·비교·추천을 열 때만 해당 질문을 한 개씩 요청한다. 모르는 값을 추론하지 말고 `미정인 채로 계속`을 제공한다.
- **장점/비용:** 장점은 바쁜 사용자와 기록 없는 사용자의 첫 가치가 빨라지고, 상세 사용자는 나중에 깊이를 추가할 수 있다는 점이다. 비용은 부분 결과 상태와 재진입 상태를 설계해야 하며, 하나의 긴 intake보다 상태 수가 늘어난다.

### F5. [설계 P1] 보수성이 ‘정직한 계산기’에 머물면 AI 코치의 가치가 사라진다

- **장점/비용:** 장점은 사실 요약을 의사결정 보조로 바꾸면서도 자동 증량·새 템플릿·의학 판정을 만들지 않는 것이다. 비용은 화면별 행동 규칙과 문구를 별도로 검토해야 하며, 모든 카드에 동일 CTA를 복제할 수 없다.
- **검증법:** 결과를 본 사용자가 “지금 할 수 있는 다음 행동”과 “앱이 판단하지 않은 것”을 각각 한 문장으로 구분할 수 있는지 확인한다. 행동이 새 처방·안전 해제·출처 변경을 유발하지 않는지 권한표로 대조한다.

### F6. [설계 P1] 결과 위계에 온라인·오프라인·저장·분석 적격 상태가 빠져 있다

- **근거:** 검토안은 결과를 `한눈에 / 자세히 / 계산·근거`로 나누지만, 저장 위치·전송 대기·충돌·분석 제외가 어느 층에 항상 보여야 하는지 정하지 않는다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:215-219`. 구속 UX 기준은 저장 실패·전송 대기·충돌·처방 적용 불가를 접힌 설명에만 숨기지 말라고 요구한다. `TRAINORACLE-private-memo-save-hotfix-20260913/docs/UX_UI_VISUAL_STANDARD.md:29-39`. 승인된 계정 저장 계획도 `초안 저장 중 / 계정에 저장됨 / 연결 대기 / 로그인 필요 / 충돌 확인`을 구분한다. `TRAINORACLE-private-memo-save-hotfix-20260913/ACCOUNT_CANONICAL_STORAGE_IMPLEMENTATION_PLAN.md:33-50`.
- **사용자 피해·반례:** 오프라인에서 만든 보고서를 코치에게 보여 주는 사용자가 서버에 저장된 최신본이라고 오해할 수 있다. 반대로 전송 대기 중인 기록을 “분석 불가”와 혼동해 데이터를 다시 입력할 수 있다.
- **수정 방향:** 결과 제목 가까이에 작은 상태 레일을 둔다: `자료 종류`, `기준 날짜`, `출처`, `저장 상태`, `분석 반영 범위`, `마지막 갱신`. 행동이 필요한 상태만 본문에 노출하고 긴 원인은 펼친다. 전역 “온라인/오프라인” 배지보다 현재 보고서와 각 원자료의 상태를 표시한다.
- **장점/비용:** 장점은 신뢰와 복구 가능성이 커지고 공유 실수를 줄이는 것이다. 비용은 화면이 조밀해질 수 있어 상태 우선순위와 축약 문구가 필요하다.
- **검증법:** 동일 보고서를 `기기만 보관`, `계정 저장 확인`, `전송 대기`, `충돌`, `일부 분석 제외` 상태로 렌더하는 정적 변형을 나란히 검토한다. 사용자가 현재 행동이 필요한 상태를 펼침 없이 찾을 수 있는지 확인한다.

### F7. [설계 P1] 차트 원칙은 있으나 질문별 시각 문법과 모바일 축소 방식이 제안에 없다

- **근거:** 검토안은 거리·시간·반복 변화·목적 구성·AM/PM을 보여 주자고 하지만 어떤 질문을 어떤 차트로 답할지, 미기록·제외·충돌을 어떻게 표현할지 정하지 않는다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:126-157,215`. 구속 기준은 비례 길이, 미기록과 0의 구분, 접근 가능한 표, 제외 건수, MIX 미배분 표시, 375px 무가로스크롤을 요구한다. `TRAINORACLE-private-memo-save-hotfix-20260913/docs/UX_UI_VISUAL_STANDARD.md:112-135,185-214`. 현재 거리 차트는 이 패턴을 이미 구현한다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/trends/CumulativeDistancePanel.tsx:188-230`.
- **사용자 피해·반례:** 좁은 화면에서 여러 반복 기록을 선 그래프로 압축하면 회복 차이와 누락 랩이 사라진다. 목적별 횟수를 100% 누적 막대로 만들면 생리 기여율처럼 오해될 수 있다. 색만 쓰면 접근성도 깨진다.
- **수정 방향:** 질문별 시각 문법을 고정한다. 계획 대 실제는 같은 행의 표/레일, 반복 수행은 점·숫자와 회복 주석, 주간 거리는 비례 막대, 목적 구성은 횟수표와 막대, AM/PM은 두 레인으로 표시한다. 스무딩·3D·이중축·가짜 100% 채움은 쓰지 않는다. 모든 차트에 동일 데이터의 표와 단위·반영/제외 건수를 둔다. 종이 질감은 보고서 프레임에만, 차트는 차갑고 정확한 분석 세계를 유지한다. `TRAINORACLE-private-memo-save-hotfix-20260913/docs/UX_UI_VISUAL_STANDARD.md:57-66`.
- **장점/비용:** 장점은 해석 오류를 줄이고 기존 디자인 언어와 접근성 자산을 재사용하는 것이다. 비용은 차트 하나를 재사용하는 대신 질문별 컴포넌트가 늘고, 320/375px 및 200% 글자 상태를 각각 설계해야 한다.
- **검증법:** `값 없음`, `0`, `일부 제외`, `충돌`, `한 번만 기록`, `AM/PM 두 건` 합성 상태를 320px·375px·글자 200% 정적 레이아웃으로 검토한다. 표와 차트가 같은 수치·단위·기간을 말하는지 대조한다.

### F8. [설계 P1] 하루 두 번 훈련은 집계 원칙만 있고 불변 이벤트 정체성과 관측 이력 모델이 부족하다

- **근거:** 검토안은 오전·오후를 합치지 않고 시간 순서를 보존한다고 말하지만, 사용자 흐름은 비교할 두 기록을 고른다고만 한다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:128-145,207-215`. 현재 계약은 모든 세션에 `DAY n · 오전/오후`를 표시하고 두 슬롯의 진행을 독립 보존하도록 요구한다. 같은 날 QUALITY 두 번은 명시적 고지와 검토·수정 경로가 없으면 허용되지 않는다. `TRAINORACLE-private-memo-save-hotfix-20260913/specs/reconstruct/DOUBLE_SESSION_BETA_SAFETY_CONTRACT.md:180-198,206-224`. 현재 설명 화면도 날짜·슬롯을 함께 표시한다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/plan-beta/SessionExplanation.tsx:83-85,166-174`.
- **사용자 피해·반례:** 엘리트 선수가 같은 날 오전 조깅과 오후 인터벌을 기록했을 때 날짜만으로 비교하면 오전 기록이 오후 계획에 붙거나, 하루 합계가 한 세션 성과처럼 보일 수 있다. 반대로 `날짜 + 슬롯 + planSessionId + 원자료Id`를 복합 기본키로 고정해도 날짜·슬롯 정정, 계획 없이 한 운동, 여러 공급자가 같은 운동을 보낸 경우에 동일 운동이 새 이벤트로 갈라지거나 수정 이력이 끊긴다.
- **수정 방향:** 1차 보고서의 복합 기본키 제안을 철회한다. 채택안이 아니라 설계 대안으로, 운동 사건에는 날짜·슬롯·계획과 독립적인 불변 `eventId`를 두고, 계획 연결은 선택적 관계로 둔다. 공급자·수동 입력·파일별 원본은 각자의 `observationId`와 출처 식별자를 유지하며, 정정은 새 `revisionId`가 이전 리비전을 가리키게 한다. 날짜·시각·슬롯·계획 연결은 수정 가능한 선택/표시 속성이고, 자동 병합 키가 아니다. 여러 관측을 같은 이벤트로 묶는 reconciliation은 출처를 지우지 않는 가역 관계여야 하며, 이중 공급자는 승인된 동일성 규칙이나 사용자 확인 전에는 조용히 합치지 않는다. 하루 화면은 AM/PM을 묶어 보여도 계산과 완료 상태는 합치지 않는다.
- **장점/비용:** 장점은 날짜·슬롯 정정과 계획 없는 운동을 수용하고, 이중 공급자의 원본·충돌·수정 계보를 보존하는 것이다. 비용은 이벤트·관측·리비전·계획 연결의 네 층이 생겨 단순 복합키보다 구현과 설명이 복잡하며, reconciliation의 생성·해제·감사 규칙이 필요하다. 이 대안은 새 런타임 스키마 승인이나 채택 권한이 아니다.
- **검증법:** 합성 AM/PM 세션, 날짜·슬롯 정정, 계획 없는 운동, 동일 공급자 수정, 서로 다른 두 공급자의 동일 후보, 잘못 묶은 관계 해제를 대상으로 `eventId`는 유지되고 observation/revision 계보와 출처가 사라지지 않는지 정적 추적한다. 같은 날 두 QUALITY 상태는 현재 계약의 고지·수정 경로가 없으면 새로 열지 않는다.

### F9. [설계 P1] 혼자 훈련하는 청소년에게 “제한을 새로 만들지 않는다”만으로는 안전한 가치 경로가 되지 않는다

- **근거:** 검토안은 청소년에게 일괄 제한을 새로 만들지 말라고 하지만 별도의 이해·검토 경로는 설계하지 않는다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:174-176,287-289`. 소스의 FAQ 문구와 외부 연결 초안은 만 14세 미만의 온라인 계정·연결 제한을 표현한다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/faq/EasyFaq.tsx:71-76`; `TRAINORACLE-private-memo-save-hotfix-20260913/specs/reconstruct/EXTERNAL_RECORD_INTEGRATION_SPEC.md:169-190`. 이는 **검토 체크아웃의 제품 문구·초안 정책 근거일 뿐**, 현재 배포 설정이나 적용 법률의 독립 증거가 아니다. 이번 검토는 환경값·운영 동작·법률 판단을 확인하지 않았다.
- **사용자 피해·반례:** 실제 배포에서 해당 제한이 적용되는지는 미확인이지만, 제한이 적용되는 구성에서는 청소년이 기기 전용 상태의 상세 해설과 참고 페이스를 “오늘 그대로 수행해도 된다는 승인”으로 읽을 수 있다. 반대로 제한이 적용되지 않는 배포를 가정하고 공유 CTA를 설계하면 현재 권한·동의 경계를 넘을 수 있다.
- **수정 방향:** 새 연령별 처방 규칙이나 법률 결론은 만들지 않는다. 배포별 실제 기능 상태를 읽어 존재하는 경로만 보여 주되, 해설에서는 `구성 설명`, `개인 계산 조건`, `수행 적합성 미판정`을 화면상 분리한다. 기존 안전 상태가 검토를 요구할 때만 보호자·지도자·의료 경로를 명확히 보여 준다. 쉬운 문구와 용어 도움말을 기본으로 하고 전문 보기는 선택으로 남긴다.
- **장점/비용:** 장점은 청소년을 기능 전체에서 배제하지 않으면서 설명과 승인 오인을 줄이는 것이다. 비용은 같은 데이터에 쉬운 기본 문구와 전문 상세 두 층이 필요하고, 기기 분실·백업 한계를 반복 없이 알려야 한다.
- **검증법:** 합성 청소년 계정 불가 상태에서 `일반 설명`, `참고 페이스`, `안전 검토 필요`, `공유 기능 닫힘` 화면을 검토한다. 사용자가 무엇이 설명이고 무엇이 실행 허가가 아닌지 구분할 수 있는지 가상 인지 walkthrough 후 실제 청소년·보호자 검토는 별도 미확인으로 남긴다.

### F10. [설계 P2] 한 장 공유는 유용하지만 다수 선수를 보는 코치의 제품 경로로 과대평가돼 있다

- **근거:** 검토안은 코치와 공유할 한 장 HTML 자료를 제안한다. `reports/research/PROGRAMMED_TRAINING_ANALYSIS_AND_EVIDENCE_PRODUCT_REVIEW_2026-09-17.md:219`. 소스의 안전 기본값은 공유를 끄고 FAQ 문구도 코치 연결을 준비 중으로 설명한다. `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/domain/product-features.ts:13-23`; `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/faq/EasyFaq.tsx:27-29,53-62`. 그러나 feature flag 기본값과 FAQ는 **배포된 환경값이나 실제 공개 상태의 증거가 아니다**. 이번 검토는 배포 설정을 읽지 않았다. 분석 계약의 Coach Review 표면도 현재 체크아웃에서는 설계 참조이며 UI·공유 경계 이슈가 열려 있다. `TRAINORACLE-private-memo-save-hotfix-20260913/specs/reconstruct/ANALYSIS_AND_VISUALIZATION_DATA_CONTRACT.md:605-615`.
- **사용자 피해·반례:** 여러 선수를 보는 코치가 개별 HTML을 하나씩 열면 최신 여부, 확인 필요 선수, 누락·충돌, 동의 철회를 한눈에 관리할 수 없다. 반대로 이 제안을 “코치 대시보드 준비 완료”로 부르면 현재 공개 범위를 과장한다.
- **수정 방향:** 1차는 **선수가 명시적으로 만드는 단일 선수 요약물**로 이름 붙인다. 다수 선수 코치 경로는 공유 런타임과 권한이 실제로 검증된 뒤 별도 제품으로 다룬다. 그때 필요한 최소 구조는 선수 목록, 마지막 갱신, 확인 필요 이유, 데이터 범위, 철회/만료, 세션 상세 진입이며 자격 미확인 표시를 유지한다.
- **장점/비용:** 장점은 한 장 자료의 낮은 비용 가치를 보존하면서 코치 제품 완성을 허위로 주장하지 않는 것이다. 비용은 다수 선수 코치 가치가 뒤 단계로 미뤄지고, 단일 HTML과 장래 대시보드의 버전·출처 모델을 맞춰야 한다.
- **검증법:** 실제 선수 자료 없이 합성 선수 목록으로 갱신·누락·충돌·동의 만료·공유 철회 상태를 검토한다. 공유 기능이 닫힌 상태에서는 내보내기와 코치 연결이 혼동되지 않는지 확인한다.

## 4. 반드시 유지할 장점

1. **외부 AI API가 코칭 가치의 선행 조건이 아니라는 판단.** 구조화 계산, 검토된 설명, 출처·버전 연결을 우선한다.
2. **원자료 확인·기술 분석·설명·다음 계획 권한을 분리한 구조.** 앞 단계 통과가 뒤 권한을 자동 획득하지 않는다. 검토안 `:59-70`.
3. **계획·실제·주관 느낌·연구 자료를 섞지 않는 원칙.** 검토안 `:72-78`.
4. **미기록을 0으로 바꾸지 않고 부분 성공과 제외 이유를 보여 주는 태도.** 검토안 `:91-93,128-157`.
5. **처방과 설명의 버전·출처를 함께 묶고 과거 이유를 새 문장으로 창작하지 않는 원칙.** `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/domain/session-explanation.ts:8-19`; `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/domain/training-explanation-receipt.ts:26-72`.
6. **종이 같은 현재 정체성.** 보고서·일지 프레임은 따뜻한 종이 질감을 유지하되, 분석 차트와 상태는 직각·hairline·절제된 색의 정확한 세계로 둔다. `TRAINORACLE-private-memo-save-hotfix-20260913/docs/UX_UI_VISUAL_STANDARD.md:57-66`.
7. **차트의 접근 가능한 쌍둥이와 제외 건수 공개.** 새 시각화가 현재 `AccessibleTrendTable` 패턴보다 후퇴하지 않게 한다. `TRAINORACLE-private-memo-save-hotfix-20260913/docs/UX_UI_VISUAL_STANDARD.md:112-135`; `TRAINORACLE-private-memo-save-hotfix-20260913/app/src/screens/trends/CumulativeDistancePanel.tsx:204-230`.
8. **공유 기본 제외와 명시적 범위 확인.** 메모·건강 원자료·개인 근거를 자동 포함하지 않는다.

## 5. 하지 않을 것

- 외부 AI API로 선수 자료·메모·건강 원자료를 보내지 않는다.
- 새 자연어 만능 파서, OCR 만능 추출, 손글씨 자동 이해를 핵심 선행 조건으로 두지 않는다.
- 초안 공식·미채택 템플릿·새 증감 규칙·새 종목 환산을 이 UX 제안으로 승인하지 않는다.
- 가져온 값을 사용자가 확인했다는 이유만으로 직접 입력 `EXPLICIT`으로 바꾸지 않는다.
- 목적별 횟수를 생리 기여율·강점·약점·부족 점수로 바꾸지 않는다.
- “오라클 점수”, “궁합 93점”, 훈련 준수 점수처럼 의미가 검증되지 않은 정밀 점수를 만들지 않는다.
- 새 최상위 AI 채팅 탭이나 독립 분석 스튜디오를 만들지 않는다.
- 저장 실패·전송 대기·충돌·분석 제외·오래된 기준을 접힌 근거 안에만 숨기지 않는다.
- 코치 연결·다중 선수 검토·공급자 자동 연동을 현재 공개된 기능으로 주장하지 않는다.
- 이 가상 페르소나 검토를 실제 사용자 연구, 청소년 검증, 코치 검증, 스포츠과학 독립 승인으로 표시하지 않는다.

| 선택지 | 첫 가치 | 현재 구조 재사용 | 주요 장점 | 주요 비용·위험 | 판정 |
|---|---|---|---|---|---|
| A. 기존 자료 해설 세로 완결 경로 | 빠름. 기존 계획·지원 표기·예시로 시작 가능 | 높음 | 새 권한 없이 가치 검증, 라우팅·디자인·접근성 패턴 재사용 | 이것만 계속하면 워치 사용자의 핵심 가치와 출처 통합을 영구 연기할 수 있음 | **즉시 착수 경로** |
| B. 첫 외부 출처 end-to-end 경로 | 공급자·허용 필드 준비에 따라 변동 | 중간 | 워치 사용자에게 가져오기부터 실제 분석 결과까지 한 번에 증명 | 공급자·권한·출처 채택에 막힐 수 있고 한 공급자 특수 구조가 공통 모델을 오염시킬 수 있음 | **좁은 범위 병행** |
| A+B. 공통 근거 모델 위 병행 | A의 빠른 가치와 B의 외부 경로 학습을 함께 확보 | 높음 | 어느 한쪽의 지연이 전체 제품 가치를 멈추지 않음 | 설계·검토 인력이 분산되고, 두 UI가 갈라지거나 서로 다른 정체성·상태 모델을 만들 위험 | **권장, 공통 계약 필수** |
| C. 새 독립 “분석 스튜디오”와 세 입구 구축 | 겉보기에는 명확하나 실제 입력·라우팅 중복으로 느려질 수 있음 | 낮음 | 미래 기능을 한곳에 모으기 쉬움 | 기존 홈·분석·계획과 경쟁, 모바일 정보 과밀, 중복 설명·상태 관리 | **반대** |
| D. 공유용 한 장 자료부터 구축 | 기존 데이터가 있는 사용자에게는 중간 | 중간 | 결과물 형태가 명확하고 코치 대화에 활용 가능 | 원자료·최신성·공유 권한이 준비되지 않으면 정적 스냅샷 오해; 첫 사용자 가치 없음 | **A의 결과 모델 이후 제한적 채택** |

**A/B 병행안의 반론:** 병행은 외부 연결을 영구 후순위로 밀지 않는 가장 나은 균형이지만 공짜가 아니다. 두 팀이나 두 작업 흐름이 각자 이벤트 ID, 출처 상태, 제외 사유, 결과 카드, 저장 영수증을 만들면 나중에 합치는 비용이 더 커진다. B는 공급자 승인이나 권한이 지연될 수 있고, 한 공급자의 필드 의미를 전체 제품 표준으로 성급히 일반화할 위험도 있다. 따라서 병행의 전제는 공통 `event/observation/revision/provenance` 개념과 동일 결과 컴포넌트를 먼저 합의하고, A는 합성·기존 자료로, B는 **한 공급자·최소 필드·한 보고서**로 범위를 고정하는 것이다. 어느 쪽도 다른 쪽의 출시를 자동 차단하지 않되, B의 임시 우회가 `EXPLICIT` 출처나 새 처방 권한을 만들 수는 없다.

### 권장 순서

1. **공통 근거 뼈대:** 채택안이 아닌 설계 초안으로 불변 event identity, 원본별 observation/revision, provenance, 저장·분석 상태, 결과 컴포넌트의 공통 어휘를 정한다.
2. **A 발견성·해설 완결:** 홈의 기존 목적 입구에서 현재 `SessionExplanation`으로 이어지는 경로를 명확히 하고, 방법·합계·회복·목적·미정·근거·다음 가능한 행동을 한 세션 안에서 연결한다.
3. **B 첫 외부 출처 세로 경로:** 한 공급자·날짜/거리/시간의 실제 승인된 최소 필드·한 보고서로 가져오기부터 결과까지 연결한다. 저장 성공과 분석 반영을 분리한다.
4. **A 비교 확장:** 불변 event identity를 중심으로 계획/실제/과거를 비교하고 날짜·슬롯·계획 연결은 표시·선택 속성으로 다룬다.
5. **A/B 통합 검수:** 두 경로가 같은 출처·제외·충돌·리비전·상태 문구와 결과 컴포넌트를 사용하는지 대조한다.
6. **사용자 주도 공유 자료:** HTML 결과를 같은 근거 모델에서 생성하고 저장·분석·버전 상태를 표시한다. 실제 배포의 공유 기능은 별도 확인한다.
7. **다수 선수 Coach Review:** 공유·권한·철회·만료가 런타임에서 검증된 뒤 별도 범위로 검토한다.

## 8. 최종 권고

이 제안의 가장 강한 부분은 외부 생성형 AI를 빼도 **훈련을 구조화하고, 계산하고, 검토된 원리와 연결하고, 비교 가능한 자료로 만드는 것 자체가 제품 가치**라는 판단이다. 그 판단은 유지한다.

다만 성공 조건은 “더 많은 분석 항목”이 아니라 다음 세 가지다.

1. 기록이나 공급자 연결이 없어도 기존 계획·받은 훈련·검토된 예시에서 첫 가치를 준다.
2. 보수적 경계를 유지하면서도 사용자가 취할 수 있는 다음 행동을 남긴다.
3. 새 허브를 만들지 않고 현재 홈·계획·일지·분석의 정본 흐름에 결과를 박는다.

따라서 제품 전략·UX 관점의 결론은 **조건부 진행**이다. F1~F3은 재현된 운영 P0가 아니라 구현 전에 풀어야 할 설계 P1이다. A의 기존 자료 가치와 B의 첫 외부 출처 end-to-end를 공통 근거 모델 위에서 병행하지 않으면, 한쪽은 워치 가치를 영구 미루고 다른 쪽은 첫 가치를 공급자 작업 뒤로 밀 수 있다. F4~F10은 두 세로 흐름의 수용 기준으로 함께 설계하되, 새 기능·스펙·처방 채택 권한을 만들지 않는다.

## 9. 2차 반론 검토 부록

### 9.1 우선순위 재판정

| 발견 | 1차 표기 | 2차 판정 | 이유 |
|---|---|---|---|
| F1 | P0 | **설계 P1 · 운영 결함 미재현** | 구현 순서가 첫 가치를 늦출 위험은 크지만 현 서비스 장애를 재현하지 않음 |
| F2 | P0 | **설계 P1 · 운영 결함 미재현** | 신규 IA 제안의 중복 위험이며 현재 라우팅 장애 증거가 아님 |
| F3 | P0 | **설계 P1 · 운영 결함 미재현** | 현재 화면은 분석 제외를 고지함. 핵심 분석 입구로 승격할 때 생길 미래 기대 불일치 |
| F4~F9 | P1 | **설계 P1** | 구현 전 해결 가치가 높지만 운영 심각도는 부여하지 않음 |
| F10 | P2 | **설계 P2** | 단일 사용자 가치 이후의 코치 규모 문제이며 배포 공유 상태도 미확인 |

**반론 수용:** 1차의 P0 표기는 운영 차단과 제품 설계 우선순위를 혼합했다. 2차에서는 운영 P0를 모두 철회했다. 향후 운영 등급은 실제 배포 버전, 기능 설정, 사용자 경로, 재현 절차, 영향 범위를 확인한 별도 증거가 있을 때만 부여한다.

### 9.2 F8 정체성 모델 교정

1차의 `날짜 + 슬롯 + planSessionId + 원자료Id` 복합 기본키는 충분하지 않다. 날짜·슬롯 정정은 같은 운동을 다른 사건으로 만들 수 있고, 계획 없는 운동에는 `planSessionId`가 없으며, 이중 공급자는 서로 다른 원자료 ID로 같은 운동을 보고할 수 있다. 반론의 불변 event identity와 observation/revision 분리가 더 견고하다.

아래는 **채택 스키마가 아닌 제품·UX 검토용 개념 모델**이다.

| 층 | 역할 | 바뀔 수 있는 것 | 보존해야 하는 것 |
|---|---|---|---|
| Event | 사용자가 한 번 수행한 운동 사건 | 표시 날짜·시각·슬롯·계획 연결 | 불변 `eventId` |
| Observation | 파일·공급자·직접 입력 등 원본별 관측 | event와의 reconciliation 관계 | `observationId`, source, provider record identity, 원자료 의미 |
| Revision | 같은 observation의 수정·삭제·공급자 update | 최신 표시값 | `revisionId`, 이전 revision 연결, 수신 시점과 원본 시점 |
| Plan link | 계획 세션과 실제 event의 선택적 연결 | 연결·해제·정정 | plan identity와 실제 event identity를 서로 대체하지 않음 |

날짜·슬롯은 검색·표시·후보 추천에 쓸 수 있지만 정체성의 최종 판정자가 아니다. 동일 이벤트 후보 점수나 규칙도 자동 병합 권한이 아니며, 충돌하거나 여러 후보가 있으면 별도 관측으로 남기거나 사용자가 확인한다. UI는 “오전/오후”를 이해 가능한 표시로 유지하면서, 정정해도 공유 링크·비교 이력·원본 출처가 끊기지 않게 해야 한다.

### 9.3 feature flag·FAQ·법률 증거 경계

- `product-features.ts`의 안전 기본값은 환경값이 없을 때의 코드 동작 근거일 뿐, 배포 환경에서 공유가 꺼져 있다는 증거가 아니다.
- FAQ의 만 14세 문구는 현재 체크아웃의 제품 안내 근거일 뿐, 실제 배포가 그 문구와 일치하는지 또는 어떤 법률상 제한이 필요한지 증명하지 않는다.
- 외부 연결 초안의 under-14 차단도 문서 정책 상태의 근거이며 법률 의견이 아니다.
- 따라서 F9/F10의 경로는 배포 설정과 권한을 런타임에서 확인한 뒤 달라져야 하며, 이 정적 검토는 법률 결론을 만들지 않는다.

### 9.4 A/B 병행안 재판정

기존 자료 경로 A와 첫 외부 출처 end-to-end 경로 B는 병행하는 편이 낫다. A만 하면 워치 사용자의 핵심 가치와 실제 출처 통합이 계속 밀리고, B만 하면 공급자·권한·계약 지연이 전체 제품의 첫 가치를 막는다. 다만 병행은 인력 분산, 중복 UI, 서로 다른 이벤트 정체성, 공급자 특수 필드의 성급한 일반화라는 비용이 있다. 공통 근거 모델과 결과 컴포넌트를 먼저 공유하고, B를 한 공급자·최소 필드·한 보고서로 제한해야 병행이 두 개의 제품으로 갈라지는 것을 막을 수 있다.

### 9.5 완료 범위

2차 반론의 수용·기각·교정을 문서에 반영한 **정적 검토만 완료**했다. 코드, 원안, 활성 스펙, 배포 설정, 실제 선수 자료는 변경하거나 검증하지 않았고 테스트도 실행하지 않았다. 이 부록은 event/observation/revision 스키마나 외부 출처 분석을 채택하는 권한이 아니다.
