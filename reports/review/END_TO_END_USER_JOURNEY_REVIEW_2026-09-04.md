## 1. 결론

**기능별로는 작동하지만, 전체 사용자 흐름을 완성됐다고 판정할 수는 없다.**

이번 PR의 운동·회복 순서 저장, 재열기, 기존 계획 호환 경로에서 새로 확인된
차단 결함은 없었다. 그러나 경기 기록 추가, 일지 작성 후 복귀, 완료 표시,
설명 진입에서 사용자가 다른 화면으로 넘어갈 때 맥락을 잃는 문제가 확인됐다.
이 문제들은 대부분 PR #316의 신규 변경이 아니라 현재 제품에 남아 있던
연결부 문제다. PR의 저장 기능 승인과 전체 제품 UX 승인을 동일시하지 않는다.

아래 판정은 소프트웨어·사용성 검토다. 개인 훈련 효과, 과학적 적합성,
실사용자 만족도 또는 운영 서버 보안의 최종 승인을 뜻하지 않는다.

## 4. 직접 재현한 개선 필요 사항

### UX-01 · P1 · 개인 페이스를 받으려다 기록 추가 단계에서 흐름이 끊긴다

재현 경로: 새 브라우저 → 5000m → 고등부 → 숙련 → 이상 없음 → VO₂ → 상세 훈련
→ 훈련일·9일·오전·1회 선택 → 후보 비교.

이 화면은 사용할 경기 기록이 없다고 알리지만 `기록 추가` 행동이 없다.
상세 방식 상태에서는 계획 선택 버튼도 비활성이다. `질문 다시 보기`는 마지막
경기 날짜 질문으로 돌아간다. 요약의 종목을 눌러 첫 단계로 이동해야 기록 관리를
찾을 수 있고, 기록을 추가한 뒤 `계획으로` 돌아오면 처음 종목부터 다시 입력한다.

근거:
- `app/src/screens/plan-beta/PaceEvidenceFlow.tsx:53-60`: 빈 기록 안내에 추가 행동 없음.
- `app/src/screens/plan-beta/PlanIntake.tsx:393-413`: 기록 관리가 첫 종목 단계에만 있음.
- `app/src/screens/plan-beta/PlanCandidates.tsx:71-73,187-189`: 상세 기준 미확인 시 선택 불가.
- `app/src/AppShell.tsx:308`: 기록 화면과 계획 화면을 교체해 미저장 컴포넌트 상태를 잃음.
- 합성 브라우저 `manual.mjs`, `results.json`, `09-return-from-record.txt`.

권장 수정: 기록 선택 영역에 `경기 기록 추가`를 직접 제공하고, 현재 답변·선택한
방법·후보 단계·시작 날짜를 임시 보관해 돌아온다. 새 기록은 자동 적용하지 않고
사용자가 다시 확인한다. 상세를 원하지 않는 사람에게는 같은 자리에서
`기록 없이 시간·RPE로 받기`를 제공한다.

장점: 재입력과 이탈 감소, 개인 페이스라는 핵심 기능에 도달하기 쉬워진다.
주의: 임시 답변 보존이 과거 몸 상태의 재사용을 허용하면 안 된다. 유효한 안전
확인과 실제 처방 저장은 별도이며, 새로운 기록을 가장 빠른 기록으로 자동 선택하지 않는다.

### UX-02 · P2 · 일지를 쓴 뒤 원래 훈련과 완료 확인으로 돌아오지 않는다

DAY 5의 상세 훈련에서 연결 일지를 작성하면 날짜와 계획 링크는 맞게 저장된다.
그러나 완료 후 DAY 1/9, 스크롤 0으로 복귀한다. 일지를 작성한 훈련을 다시 찾고
별도로 완료 표시해야 한다. 오늘의 DAY 1을 기록한 경우에도 홈에서 같은 훈련이
`다음 훈련`으로 남으면서 아래에는 `오늘 기록을 마쳤어요`가 표시됐다.

`journal_result_does_not_auto_mark_progress`는 현재 계약에 명시된 의도다.
따라서 이 검토는 두 데이터를 자동 합치라고 요구하지 않는다. 문제는 사용자에게
둘의 관계와 다음 행동을 알려주는 연결이 없다는 점이다.

근거:
- `specs/reconstruct/PLAN_JOURNAL_LINKAGE_CONTRACT.md` §2.
- `app/src/domain/app-shell-state.ts:100-111,133-147`: 복귀 상태에 원래 세션 위치 없음.
- `app/src/screens/plan-beta/ActivePlan.tsx:306-335`: 일지 버튼과 진행 표시가 별도.
- `reopen-results.json`: 375/320 모두 일지 후 `progress: []`.
- `18-after-journal.txt`, `today-recorded-home-375.png`.

권장 수정: 저장한 DAY·AM/PM으로 복귀하고 `일지를 저장했어요` 아래에
`계획에도 완료 표시`를 선택할 수 있게 한다. 기존 진행 표시가 있으면 중복 요청하지
않는다. 홈에는 연결 일지와 진행 표시 상태를 구분한 문구를 사용한다.

장점: 같은 작업을 두 번 시킨다는 느낌과 완료 누락을 줄인다.
주의: 부분 수행·휴식·통증 기록을 자동 완료로 바꾸지 않는다. 계획 상태와 일지의
사실 구분, 중복 링크 방지, 안전 신호를 유지한다.

정하지 않더라도, 현재 문구는 실제 저장 날짜와 일치해야 한다.

근거: `app/src/screens/log-entry/QuickSessionForm.tsx:360-366`,
`17-journal-saved.txt`, 합성 `synthetic-storage.json`의 날짜·계획 링크.

### UX-04 · P2 · 설명 버튼의 이름과 진입 화면이 다르고 방법이 중복된다

`이 훈련을 하는 이유`를 누르면 `이유·근거`가 아니라 `방법` 탭이 열린다.
방법 화면은 총합 요약, 한 줄 표기, 본운동, 추천 기준, 회복, 준비·정리를 보여준 뒤
다시 운동·회복 순서도를 보여준다. 필요한 정보는 있지만, 처음 읽는 선수는
준비부터 수행까지의 순서를 찾으려고 긴 화면을 훑어야 한다.

실측: 375px에서 순서도 제목은 내용 시작점 아래 약 862px, 내용 창은 553px였다.
320px에서는 약 912px 아래, 내용 창은 402px였다. 가로 넘침은 없었다.
길다는 것 자체보다 같은 처방을 두 번 읽게 하는 배치가 개선 대상이다.

근거: `app/src/screens/plan-beta/SessionExplanation.tsx:29-40,98-114`,
`13-method-reader.png`, `sequence-320.png`, `reopen-results.json`.

권장 수정: 기본 탭 `방법`은 유지하되 진입명을 `훈련 방법과 이유`로 맞춘다.
첫 요약 다음에 준비 → 본운동·사이 회복 → 정리를 하나의 수행 순서로 통합하고,
추천 기준은 숫자 곁에 남긴다. 기존 숫자·회복·근거를 줄이거나 숨겨서 간결함을
만들지 않는다. 긴 학술 설명은 현재처럼 이유·근거 탭에 둔다.

### SUS-01 · 추가 결함 주입 필요

`app/src/domain/plan-beta-flow.ts:153-163`은 상세 템플릿의 런타임 권한 확인이
실패하면 `selectedDetailedTemplateRef`를 `null`로 바꾼다. 후보 화면의 기록 선택
영역은 이 값이 있을 때만 나온다(`PlanCandidates.tsx:103-117`).
사용자의 상세 선택 의도와 실패 이유가 사라지는 경로가 의심된다.

안전한 RPE 폴백 자체는 유지해야 한다. 별도 테스트에서 권한 확인 실패를 주입해
원인·재시도·명시적인 RPE 변경 동의가 남는지 검증한다. 현재 정상 설치에서
자연 발생했다고 주장하거나, 일반 기록 부족과 같은 원인으로 취급하지 않는다.

## 6. 유지해야 할 좋은 흐름

1. 처음 온 사람은 로그인·상세 일지를 강요받지 않고 기록 또는 계획으로 갈 수 있다.
2. 질문을 선택하면 다음 질문으로 이동한다. 좁은 화면과 줄인 모션에서도 기존
   검증이 통과했다. 답하지 않은 RPE를 기본값으로 저장하지 않는다.
3. 빠른 기록을 자세히 쓰면 같은 ID를 수정하며 기록을 하나 더 만들지 않는다.
4. 기준 기록은 명시 선택이며 비가분 초를 포함해 개인 페이스를 보존한다.
5. 상세 설명을 닫으면 같은 DAY 5/9와 원래 선택으로 돌아온다. 문제는 설명 닫기
   자체가 아니라 일지라는 다른 화면으로 갔다 돌아오는 경우다.
6. 몸 상태 이상은 후보 생성 전에 차단되고, 저장 실패에는 재시도 경로가 있다.
7. 현재 처방의 새 순서 저장과 예전 계획의 파생 표시를 서로 다른 문구로 알린다.
8. 다음 계획을 고르는 것과 실제 시작을 분리한다. 새 주기 시작 후 이력 1건,
   주기 순번 2, 새 진행 상태, 새로고침 후 동일 상태를 확인했다.
9. 파일 가져오기는 묵시 병합하지 않는다. 같은 일지 보완 후에도 직접 쓴 주관
   항목은 편집할 수 있고 수입된 객관 값의 출처는 보존한다.
10. 로컬·공개 첫 화면 모두 Pretendard Variable이 실제 로드됐다. 이번 확인에서
    빌드의 폰트 경고를 곧바로 폰트 누락 결함으로 분류하지 않았다.
