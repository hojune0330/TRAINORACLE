## 2. PMR-01: 휴지통 복원 뒤 서로 다른 코드가 섞인다

### 근거

- `app/src/screens/log-entry/PrivateMemoSaveSetup.tsx:24`: 현재 journal/vault만 읽음.
- 같은 파일 `:42`: 현재 vault가 비면 새 코드 생성을 허용함.
- 같은 파일 `:68`: 기존 모든 암호문을 하나의 코드로 복호화해야 준비를 완료함.
- `app/src/domain/journal-store.ts:393`: 삭제할 암호문을 휴지통으로 보관함.
- 같은 파일 `:429`, `:454`: 복원 시 원래 암호문을 새 일지 ID에 붙여 복구함.
- `app/src/domain/journal-trash.ts:1`: 휴지통의 30일 복원 정책은 기존 오너 결정임.

### 실제 재현 순서

1. 코드 A로 비밀 경기 메모를 저장한다.
2. 해당 메모를 삭제한다. 삭제 성공과 휴지통 보관 성공을 확인한다.
3. 세션 코드를 비운다. 새 세션에서 다시 들어온 조건이다.
4. 작성 화면의 새 코드 만들기가 허용된다. 코드 B를 준비하고 새 메모를 저장한다.
5. 휴지통의 A 메모를 복원한다. 이제 현재 vault에 A/B 암호문이 함께 있다.
6. 세션 코드를 비운 후 기존 코드 입력으로 A와 B를 각각 시도한다.
7. 두 경우 모두 준비 실패 안내가 나오고 세션 코드는 설치되지 않는다.

### 영향과 한계

새 작성 화면의 정상적인 준비 경로로는 다음 비밀 메모 저장을 진행할 수 없다.
기존 암호문을 파괴한 것은 아니다. 별도의 합성 시험에서 A로 이전 메모,
B로 새 메모를 각각 복호화할 수 있음을 확인했다. 따라서 '영구 데이터 소실'로
표현하지 않는다. 문제는 앱의 단일 코드 준비 규칙과 실제 복원 가능한 데이터의
코드 구성이 충돌하는 것이다. 현재 키 변경/휴지통 설계의 기존 약점에 이번
인라인 생성과 전체 검증 경로가 연결되면서 드러난 교차 흐름 결함이다.

### 권장 수정

- 현재 목록뿐 아니라 복구 가능한 휴지통 암호문까지 포함해 키 생명주기를 정의한다.
- 단기적으로는 그 데이터가 있는데 빈 금고로 판단해 새 코드를 만들지 않는다.
  정확한 기존 코드 안내를 제공하고, 사용자의 기록이나 휴지통을 자동 삭제하지 않는다.
- 이미 섞인 데이터에는 소유권을 지키는 개별 검증/복구 절차가 필요하다.
  일괄 실패 검사만 완화하거나 임의의 코드로 덮어쓰면 안 된다.
- 삭제 -> 새 세션 -> 새 코드 요청 -> 복원 -> 저장/조회까지 회귀 시험에 넣는다.

## 3. PMR-02: 준비 완료 상태가 현재 코드 상태를 따라가지 않는다

### 근거와 재현

`PrivateMemoSaveSetup.tsx:19`는 최초 코드 존재 여부를 React state에 복사하고,
`:83`에서 ready이면 입력 UI를 없앤다. 이후 코드가 사라져도 ready를 되돌리는
연결이 없다. 반면 `PurposeScopedMemoField.tsx:57`은 저장 시 현재 코드를 다시 읽는다.

유효한 합성 코드를 둔 채 경기 폼을 연 뒤 메모를 입력하고, 기존 함수
`clearSessionRecoveryCode()`로 코드를 제거한 후 저장했다. 결과:

- '복구 코드를 준비해 주세요' 오류가 나온다.
- 동시에 '암호화 준비가 됐어요' 상태도 남는다.
- 기존 코드 입력창과 새 코드 버튼은 없다.
- 작성 텍스트는 남아 있다.

이는 상태 변경을 주입해 재현한 복원력 결함이다. 일반 사용자가 폼에 머무른 채
어떤 계정/잠금 동작으로 항상 이 상태를 만드는지까지 UI 여정을 입증하지는 않았다.
모든 사용자에게 자연 발생한다고 과장하지 않는다.

### 권장 수정

준비 완료를 최초 boolean에 고정하지 않고 현재 계정 범위와 코드 상태에 연결한다.
저장 전 검사에서 미준비가 확인되면 바로 같은 화면의 입력 UI로 복귀시킨다.
코드 제거, 계정 범위 변경, 실패한 코드 교체를 각각 검증하고, 메모를 지워 다시
입력하거나 새로고침해야만 풀리는 경로를 정상 UX로 인정하지 않는다.

## 4. PMR-03: 글을 쓰기 시작하면 입력창이 가려진다

`PurposeScopedMemoField.tsx:141`에서 비어 있던 메모가 처음으로 비어 있지 않게 되면
전체 준비 패널을 textarea 앞에 삽입한다. 저장 버튼을 누르기 전부터 발생한다.

375x667 CSS px, Chromium 모바일 에뮬레이션, 로컬 프로덕션 빌드에서 실측:

| 요소 | 위치/크기 |
|---|---|
| 입력 전 textarea 상단 | y=416.28 |
| 입력 후 textarea 상단 | y=586.25 |
| textarea 높이 | 99.56 |
| 삽입 패널 높이 | 376.97 |
| 저장 바 | y=548.31~623.00 |

textarea는 저장 바/하단 내비게이션과 겹치는 위치로 밀린다. 가로 overflow는 false다.
즉 이전의 '가로 넘침 없음' 검사는 이 수직 가림을 검출하지 못했다.
실제 iPhone Safari와 가상 키보드는 미검증이며, 키보드가 없는 에뮬레이션에서도
이미 재현됐다는 것이 이번 증거 범위다.

### 권장 수정

쓰기 시작할 때 입력창 위에 큰 패널을 삽입하지 않는다. 작고 안정적인 준비 상태
행을 두고, 사용자 선택 또는 최초 저장 시 별도 패널을 연다. 닫으면 같은 텍스트,
선택, 커서로 돌아오게 한다. 코드 생성/입력/보관 확인의 의미는 유지하되 컴포넌트
토큰과 버튼 위계를 통일하고, '복사' 편의 기능도 검토한다. 보관을 자동 확인하거나
훈련 메모로 몰래 변경하는 방식은 금지한다.
