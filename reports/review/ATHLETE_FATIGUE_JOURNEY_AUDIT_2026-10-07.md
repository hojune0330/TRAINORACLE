# 선수 사용 피로 원인과 개선 우선순위

2026-10-07. 직전의 간결함 개선을 포함한 로컬 앱에서도 과도한 메뉴, 반복 판단, 저장 이후의 혼동이 남아 있다. 다음 개선은 문장을 더 접는 작업보다 **사용자가 해야 하는 결정과 완료 절차를 줄이는 작업**이어야 한다.

선수들이 전반적으로 피로와 부담을 느낀다는 것은 오너가 전달한 실제 피드백이다. 아래 화면 관찰과 합성 검토는 그 원인을 찾기 위한 작업이며, 실제 선수의 주저 시간이나 피로도를 측정한 결과는 아니다.

## 가장 먼저 해결할 문제

### 저장했는데 훈련 일지 0건으로 보인다

격리된 브라우저에서 800m 계획을 만들고 첫 오전 훈련에 `계획대로 마쳤어요`, 오전, 힘든 정도 6, 불편한 곳 없음으로 빠른 일지를 저장했다. 저장 성공 후 `완료`로 돌아가 오라클을 열었다.

실제로 나온 화면:

- 최근 8주 훈련 일지 0건 기준
- 직접 적은 거리 기록이 아직 없어요
- 기록은 있지만 분석에 사용할 훈련 목적을 확인하지 못했어요
- 예정 3회 중 완료 표시 0회
- 아래쪽에는 방금 남긴 힘든 정도 6/10 기록이 존재

이 재현에서 데이터가 사라진 것은 아니다. `recentInsightSourceCount`는 일지 전체가 아니라 거리와 훈련 목적 집계에 들어가는 근거의 합집합을 센다. 계획의 완료 표시는 일지와 다른 값이다. 그러나 화면은 이 내부 차이를 사용자가 먼저 이해해야만 납득할 수 있게 만든다.

**우선 개선:** 저장한 기록의 존재를 먼저 인정하고, 분석에 필요한 값과 계획 진행 표시를 분리한다. 이 상태에서는 `오늘 오전 기록을 남겼어요 · 힘든 정도 6/10`이 먼저 나와야 한다. 거리·목적 자료가 없다는 내용은 하나의 짧은 안내로 묶는다. 실제 일지 수를 뜻하지 않는 0에 `훈련 일지`라는 이름을 붙이지 않는다.

**금지:** 계획상의 45분을 실제 운동시간으로 채우거나, 완료 응답만으로 페이스·반복·회복을 수행했다고 판단하지 않는다. 별도 계획 표시를 몰래 완료로 바꾸지 않는다.

근거: [집계 정의](../../app/src/domain/personal-oracle.ts#L40), [표시 라벨](../../app/src/screens/trends/PersonalOraclePanel.tsx#L36), [재현 화면](evidence/fatigue-walkthrough-20261007/plan-oracle-after-one-log.png).

### 저장 후 다시 계획에도 완료 표시를 해야 한다

저장 성공 화면에는 `이 결과를 계획에도 반영`, `완료`, `일지 더 쓰기`, `방금 기록 수정`이 함께 있다. `완료`로 나가면 날짜 상세에서 다시 `계획에도 완료 표시`를 만난다. 선수는 자신의 기록을 마쳤다고 생각하지만 시스템은 두 개의 완료 상태를 요구한다.

**우선 개선:** 일지 저장과 계획 진행 표시가 서로 다른 사실이라는 모델은 유지하되, 저장 직전에 선택적 계획 표시를 함께 확인하는 흐름으로 재설계한다. 기본 경로는 명시적인 `기록 저장`, 선택한 경우만 `저장하고 계획에 완료 표시`처럼 결과를 정확히 표시한다. 두 저장의 성공·부분 실패도 구분한다. 반복·초·회복 달성이나 다음 주기 증량의 근거로 확대하지 않는다.

현재 저장 규칙을 바꾸는 작업이므로 단순 버튼 이름 교체로 처리하지 않는다. [현재 별도 반영 행동](../../app/src/screens/log-entry/JournalPlanProgressAction.tsx#L24), [저장 후 화면](evidence/fatigue-walkthrough-20261007/plan-planned-log-saved.png), [복귀 화면](evidence/fatigue-walkthrough-20261007/plan-return-after-log.png).

## 화면별 잔여 문제

`화면`은 이번 로컬 브라우저 관찰, `소스`는 실행하지 않은 경로의 코드 검토다. 우선순위는 개발 순서이며 모든 항목이 기능 버그라는 뜻은 아니다.

## 소스로 발견한 추가 확인 대상

- 관심 주제와 기록할 요일은 다른 목적이다. 저장한 글을 다시 보는 화면에서 요일 설정까지 할 필요가 있는 것처럼 보일 수 있다. [OracleReturnPanel](../../app/src/components/OracleReturnPanel.tsx#L111).
- 자료 읽기 실패에서 문구는 실패를 알리지만 빈 달력이 함께 나오면 기록 손실로 해석할 수 있다. 미확인 0개는 상태 화면, 확인된 0개는 빈 달력, 이전 자료가 있는 상태는 그 달력과 갱신 상태를 구분해야 한다. 이번에는 운영 장애를 만들어 재현하지 않았다. [JournalArchive](../../app/src/screens/JournalArchive.tsx#L149).
- 다음 주기의 `다음 계획안 만들기`와 `기록 확인·다음 계획 조정`은 진입이 갈린다. 다음 주기 요청 안에서 반영할 자료 확인 → 후보 → 적용으로 이어지게 할 여지가 있다. 완료된 실제 주기·운영 계정으로 끝까지 실행하지 않았다. [ActivePlan](../../app/src/screens/plan-beta/ActivePlan.tsx#L537), [PlanAdaptationFlow](../../app/src/screens/plan-beta/PlanAdaptationFlow.tsx#L267).
- OracleExplore의 예시 진입은 개인 결과가 있으면 개인 모드를 기본 선택할 수 있다. 예시라는 이름과 도착 내용이 일치하는지 해당 상태의 후속 브라우저 확인이 필요하다. [Trends](../../app/src/screens/Trends.tsx#L198), [OracleExplore](../../app/src/screens/OracleExplore.tsx#L33).

## 관찰 수치

375 × 812px 격리 브라우저, 최신 미커밋 UX 변경이 포함된 로컬 앱에서 관찰했다. 기본 페이지의 실제 내용 표시 높이는 758px이었다. 아래 전체 높이는 스크롤 영역의 길이이며 피로 점수나 반드시 읽어야 하는 분량은 아니다.

| 빈 홈 | 921px | 시작 경로가 여러 영역에 분산 |
| 기록 없는 오라클 | 928px | 결과 대신 여러 입력·안내가 이어짐 |

| 계획 생성 결과 | 1509px | 접힌 메뉴 제목 10개. 시작 버튼은 하단 고정으로 보였음 |

전체 4개 스크립트 경로에서 **30개 상태를 수집**했다: 진입 9, 계획·합성 일지 저장·복귀 16, 도구 3, 설문·읽을거리 2. 최종 실행 로그의 페이지 실행 오류는 0개다. 이것은 기능 전체 통과나 좋은 UX의 증거가 아니다. 날짜 상세는 상위 화면이 아닌 실제 대화상자를 수집하도록 보정했다. 초기 로딩 대기·테스트 선택자 오류의 중단 시도는 이 30개에 넣지 않았다.

Luna 최고 추론 작업자 두 개가 계획 영역 12개, 홈·오라클·일지 영역 16개 합성 페르소나 관점으로 소스를 검토했다. 이는 **28명의 실제 사용자도, 28회 브라우저 실행도 아니다**. 최초 독립 검토 뒤 부모의 화면 증거를 공유하여 오탐을 제거했다. 부모가 재현한 저장 후 0건 문제를 독립 작업자가 별도로 재현했다고 세지 않는다.

## 유지할 것과 제외한 오탐

- 계획의 하단 고정 시작 버튼은 화면에서 확인했다. `긴 달력 때문에 시작 버튼이 아예 안 보인다`는 가설은 채택하지 않는다.
- 페이스 계산의 종목 선택, 빠른 기록의 현재 질문 전환, 저장 직전 확인은 비교적 명확했다. 이를 다시 복잡한 새 화면으로 바꿀 근거는 없다.
- 설문 답변 척도를 UX 명목으로 임의 축약하거나 재채점하지 않는다. 모름·상황에 따라 다름·경험 없음과 건너뛰기를 유지한다.
- `RunningProfile.tsx`의 중복 근거 안내는 레거시 경로 발견이다. 이번 브라우저는 V2의 `OracleProfileExperience`를 표시했으므로 현재 V2의 결함으로 합산하지 않는다.
- 실제 달력·요일·월 이동·오전/오후를 없애거나 평범한 글 목록으로 되돌리지 않는다.
- 긴 글이 필요한 상세 화면의 세로 스크롤을 강제로 막지 않는다. 필요한 단계만 먼저 보여주는 것과 내용을 자르는 것은 다르다.
- 기록 없음, 자료 부족, 읽기 실패, 미확인 자료를 같은 상태로 취급하지 않는다. 실제 목표·회복 수치와 통증·저장 오류는 숨기지 않는다.

## 다음 구현의 기준

1. **완료의 의미부터 정리한다.** 저장된 기록, 분석에 쓴 자료, 계획 진행 표시가 다른 사실임을 결과 화면에서 설명 없이 구분할 수 있게 한다.
2. **계획과 오라클의 조립 구조를 정리한다.** 하위 컴포넌트마다 자체 도움말·수정·근거를 추가하는 방식 대신, 상위 화면에서 역할별 진입 하나를 책임진다.
3. **각 화면에 한 가지 주 행동을 둔다.** 안전상 둘 이상의 선택이 필요할 때까지 무조건 버튼 한 개로 줄이라는 뜻은 아니다. 현재 목적과 관계없는 선택은 다음 목적지로 분리한다.
4. **같은 정보를 다시 묻지 않는다.** 확인된 저장 값은 재사용하고 계획상의 값은 명시적인 제안으로만 제공한다. 실제 수행이나 건강 상태를 추정해 입력하지 않는다.
5. **접힌 기능도 발견 가능하게 둔다.** 기능명·목적이 드러나는 진입을 유지하고, 한 메뉴 안에 설명 펼침을 연속 중첩하지 않는다. 자주 쓰는 기능은 첫 관련 화면에서 한 번에 도달하도록 목표를 잡는다.
6. **근거는 결과 가까이, 원문은 상세에 둔다.** 기본 화면에는 기준 기록·자료 부족·중요한 제한을 짧게 유지하고 긴 연구 설명·계산식은 맥락에 맞는 한 곳에서 연다.

첫 수정 묶음은 상태·완료 흐름, 둘째는 계획의 중복 메뉴·질문 주변부, 셋째는 오라클의 첫 결과·중간 소개 화면, 넷째는 기록 재사용·가져오기·읽을거리·더보기다. 이 감사에서 앱 동작을 수정하거나 배포하지 않았다.

## 실제 선수 확인 방법

코드 검사 이후에는 개발자가 클릭할 곳을 말해주지 않고 선수에게 다음 목적만 전달한다. 테스트는 짧은 묶음으로 나누고 불편하면 중단한다. 필요한 동의와 지도 환경을 갖춘 실제 사용자 검토는 별도다.

- 오늘 할 훈련을 찾고, 모르는 단어가 있으면 직접 확인하기.
- 오늘 훈련을 기록한 뒤 앱이 무엇을 저장했는지 자기 말로 설명하기.
- 다른 시간대에 일부만 수행한 훈련을 기록하기.
- 저장한 뒤 오라클에서 자신의 기록이 사용됐는지 찾기.
- 기존 경기 기록으로 계획을 만들고 바꾸고 싶은 한 부분만 수정하기.
- 지난 일지와 저장한 읽을거리를 다시 찾기.

첫 클릭, 잘못 들어간 화면, 도움 요청, 반복해서 읽는 문구, 저장됐다고 이해한 대상, 과정을 끝냈다고 생각한 시점을 관찰한다. 행동 후 어려웠던 지점을 묻되 답을 유도하지 않는다. 개인별 결과를 합성 페르소나 수와 합산하지 않는다. 빠르게 클릭했다는 이유만으로 올바르게 이해했다고 판정하지 않는다.
