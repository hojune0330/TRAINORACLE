## C-1 (치명) 현실적인 기록 대부분에서 상세 처방이 조용히 실패한다

### 증상

같은 종목 현재 기록을 고르고 "이 기록으로 개인 페이스 적용"을 눌러도,
기록 시간이 특정 산술 조건을 만족하지 않으면 상세 처방이 붙지 않고
`"현재 승인 범위에서 상세 처방을 적용할 수 없어요"`라는 **오해를 부르는
폴백 메시지**가 뜬다.

### 실측 재현 (로컬 빌드 + 공개 Pages 모두)

| 종목 | 입력 기록 | 목표 반복 페이스(원시값) | 결과 |
|---|---|---|---|
| 800m | 2:00 (120s) | 30.0s | ✅ 바인딩 성공 |
| 800m | **2:02 (122s)** | 30.5s | ❌ 폴백 |
| 800m | 2:01.5 (121.5s) | 30.375s | ❌ 폴백 |
| 1500m | 4:05 (245s) | 81.67s | ❌ 폴백 |
| 3000m | 10:11 (611s) | 162.93s | ❌ 폴백 |
| 5000m | 18:31 (1111s) | 222.2s | ❌ 폴백 |
| 5000m | 18:30 (1110s) | 222.0s | ✅ 바인딩 성공 |

공개 Pages 실측: 800m 2:02 기록 → `bound notation visible: false`,
`fallback message visible: true`.
증거: `evidence/fable-2026-08-17/24-public-122s-result.png`

바인딩이 성공하는 조건은 사실상 다음과 같다.

- 800m: 기록 초가 **4의 배수** (2:00, 2:04, 2:08…)
- 1500m: 기록 초가 **3의 배수**
- 3000m: 기록 초가 **15의 배수에서 파생된 정수 페이스** (611s 같은 값 탈락)
- 5000m: 기록 초가 **5의 배수**

실제 육상 기록은 초 단위 임의값이고 소수점(전자계측 0.1s)까지 흔하다.
**즉 실사용자 대부분이 이 기능을 영원히 못 받는다.**

### 원인 (코드 경로)

1. `impl/src/prescription/runtime.ts` `calculateSameEventRacePace`는
   `targetRepSeconds`를 **반올림 없이 원시 실수**로 계산한다.
2. `app/src/domain/plan-candidate-prescription.ts:163`은 이 원시값을
   `createStoredPaceTargetPrescription`에 그대로 넘긴다.
3. `app/src/domain/plan-session-schema.ts:249-257`의 저장 스키마 정합
   검사는 `Math.round(anchor × rep / event) !== targetRepSeconds`이면
   저장을 거부한다. **한쪽은 반올림 안 하고, 다른 쪽은 반올림을 강제한다.**
4. `createStoredPaceTargetPrescription`이 `null`을 반환하면 바인더는
   `PACE_TARGET_FALLBACK_AUTHORITY_OR_COMPONENT`로 폴백한다 — **승인이나
   컴포넌트와 아무 상관 없는 실패인데 그 코드를 쓴다.**

`displayRoundingPolicyVersion: "seconds-v1"`라는 정책 이름이 이미
"초 단위 반올림"을 선언하고 있는데, 정작 반올림을 수행하는 코드가
파이프라인 어디에도 없다. 두 저자(런타임 vs 스키마)가 서로 다른 계약을
믿고 작성한 전형적인 봉합선 결함이다.

### 감사가 놓친 이유

- e2e 픽스처: 800→120s, 1500→240s, 3000→600s, 5000→1110s.
  **전부 나누어떨어지는 값.** `multi-event-personalized-prescription.spec.ts`
  20/20 PASS는 "행복한 산술 경로 20개"일 뿐이다.
- 계약 테스트도 동일한 픽스처 습관을 공유한다. 761초, 122초 같은
  "불편한" 값을 넣은 테스트가 0건이다.
- 최종 감사 F3의 "공개 실사용 확인"도 같은 픽스처로 수행됐다.

### 요구 수정

1. `bindDetailedPrescriptionCandidates`에서 `targetRepSeconds`를
   `seconds-v1` 정책대로 **명시적으로 반올림한 정수**로 저장하거나,
   스키마의 재현 검사를 정책 함수 하나로 통일할 것. 반올림 함수는
   단일 소스(예: `applyDisplayRounding(policyVersion, rawSeconds)`)로
   두고 저장·검증·표시가 모두 그것만 쓰게 할 것.
2. 회귀 테스트에 **나누어떨어지지 않는 기록**(122s, 245s, 611s, 1111s,
   소수점 121.5s)을 필수 케이스로 추가할 것.
3. 스키마 정합 실패가 `AUTHORITY_OR_COMPONENT`로 뭉뚱그려지는 것을 분리
   — 저장 스키마 거부는 별도 폴백 코드로 관측 가능해야 한다.

## C-2 (표시 진실성) 홈·계획 목록이 종목과 무관하게 "1000m 페이스"를 표기한다

`app/src/screens/plan-beta/labels.ts:160` `prescriptionLabel`:

```
총 ${totalRepetitions}회 · 품질 거리 ${qualityDistanceM}m · 1000m ${시간}
```

`1000m`이 하드코딩이다. 800m 계획(200m 반복)에서 실측 화면:

> `총 10회 · 품질 거리 2000m · 1000m 0분 30초`

**"1000m를 30초에"라고 읽힌다.** 30초/1000m는 세계기록의 2배 속도다.
실제 의미는 "200m를 30초에"인데, 이 라벨은 홈 화면 "다음 훈련" 카드와
계획 목록 세션 헤더 양쪽에 노출된다(`TrainingHome.tsx:72,77`,
`PlanSessionDetails.tsx:20`, `PlanSchedulePreview.tsx:78`).
증거: `evidence/fable-2026-08-17/17-active-plan-detailed-session.png`

V2-SEED-05(5×1000m) 시절 하드코딩이 다종목 확장(#229) 때 방치된 것이다.
"일지 값은 시간·RPE를 바꾸지 않는다"는 진실성 문구에 그토록 공을 들인
제품이, 정작 처방 숫자 자체를 거짓으로 표기하고 있다.

수정: `1000m` → `${repetitionDistanceM}m`. 그리고 이 라벨을 고정하는
계약 테스트를 800m/1500m/3000m 각각에 추가할 것.

## C-3 (표시 진실성) 실행 안내가 모든 종목에서 "5회 본운동과 4번의 사이 회복"

`labels.ts:201` `sessionExecution`:

```
"준비, 5회 본운동과 4번의 사이 회복, 정리 순서로 진행하세요."
```

역시 V2-SEED-05(5회) 하드코딩. 800m 계획(10회) 화면에 그대로 노출된다.
바로 아래 상세 뷰에는 "10회"라고 정확히 적혀 있어 **같은 카드 안에서
5회와 10회가 동시에 보인다.** 선수가 어느 쪽을 믿어야 하나.

수정: `총 ${totalRepetitions}회 본운동과 ${repetitionRecoveryOccurrences}번의
사이 회복`으로 파라미터화.

## UX/UI 리뷰 (전 화면 워크스루, 모바일 375×667 실측)

### U-1 (높음) 폴백 메시지가 원인을 숨기고 사용자를 자책하게 만든다

C-1이 터졌을 때 사용자가 보는 문구는 "현재 승인 범위에서 상세 처방을
적용할 수 없어요"다. 사용자 입장에서는 방금 **현재·같은 종목·숙련**
조건을 전부 충족하는 기록을 골랐다. 조건을 다 만족했는데 왜 안 되는지에
대한 설명이 0이다. 시스템 내부 실패(저장 스키마 거부)와 자격 미달
(종목·경험·신선도)을 같은 문구로 뭉뚱그리면, 사용자는 "내 기록이 뭔가
잘못됐나"라는 잘못된 결론을 내린다. 폴백 코드별 문구 분리가 이미
`fallbackMessage()`에 부분적으로 있으므로, `AUTHORITY_OR_COMPONENT`를
"앱 내부 문제로 상세 계산을 저장하지 못했어요. 기록 문제가 아니에요"
수준으로라도 분리해야 한다.

### U-2 (높음) 기준 기록 선택 구간이 후보 비교 아래에 묻혀 있다

핵심 개인화 액션(기록 선택→확인)이 화면 순서상 [후보 비교] → [기록 선택]
→ [저장 근거 스트립] → [시작 날짜] → [후보 카드] 중간에 끼어 있다.
"선택 사항"이라는 아이레벨 때문에 그냥 지나치기 쉽고, 지나쳐서 후보를
선택하면 **그대로 RPE-only 계획이 저장된다.** 이 기능이 이번 릴리스의
간판인데 발견 가능성이 우연에 맡겨져 있다. 최소한: (a) EXPERIENCED +
지원 종목 + 사용 가능한 CURRENT 기록이 존재하면 후보 카드 위에 배치
순서를 올리거나, (b) 후보 선택 버튼 근처에 "기준 기록 미선택 — RPE
계획으로 저장됩니다" 상태를 명시할 것.

### U-3 (중간) 확인 후 성공 피드백이 약하고 화면 이동이 없다

"이 기록으로 개인 페이스 적용"을 누르면 후보 전체가 재생성되지만
스크롤 위치는 그대로다. 성공 시 바뀐 것은 작은 체크 문구 한 줄과
멀리 위에 있는 후보 카드 내용뿐. 실패 시(U-1)에는 더더욱 아무 일도
없는 것처럼 보인다. 확인 직후 결과 상태(성공: 어떤 세션에 페이스가
붙었는지 / 실패: 이유)로 시선을 옮겨 주는 스크롤 또는 강조가 필요하다.

### U-4 (중간) "0분 30초" 표기

30초짜리 반복 목표를 "0분 30초"로 표기한다(`DetailedPrescriptionView`
`formatDuration`, `labels.ts` `formatTargetSeconds` 중복 구현 — 이것도
단일화 대상). 육상 선수는 200m 목표를 "30초"라고 부르지 "0분 30초"라고
부르지 않는다. 60초 미만이면 "30초"로, 60초 이상이면 "1분 22초"로.
덧붙여 소수점 기록이 살아나면(C-1 수정 후) 0.5초 단위 표기 정책도
`seconds-v1`에 명문화해야 한다.

### U-5 (중간) 시작·다시 시작 확인 버튼 3개가 위계 없이 나열

`ActivePlan`의 실행 전 확인에서 [시작 확인] [다시 시작 확인] [통증·이상]
3개 버튼이 동일한 시각 위계로 나열된다. "시작"과 "다시 시작"의 차이를
설명하는 문구가 없어 사용자는 아무거나 누르게 되고, 안전 신고 버튼
(통증·이상)이 확인 버튼과 같은 무게라 오탭 위험이 있다. 첫 실행 전이면
"시작"만, 이미 진행 기록이 있으면 "다시 시작"만 노출하는 상태 기반
축소를 권한다.

### U-6 (낮음) 처방 지문 노출 방식

상세 뷰 하단 `처방 지문 · canonical-json...NTROLLED"}` — 내부 JSON
지문 문자열이 잘린 채 그대로 노출된다(스크린샷 19). 무결성 표시 의도는
좋지만 지금 형태는 사용자에게 소음이고, 잘린 JSON 조각(`NTROLLED"}`)은
버그처럼 보인다. sha256 형식 지문으로 바꾸거나 접힌 영역 안에 "기술
정보"로 격리할 것.

### U-7 (낮음) 진행률 표시와 요약 점프의 좋은 점 (칭찬)

인테이크의 "지금까지" 요약 라인 탭 점프, 단계 진행 바, 미리보기 단계의
"아직 계획이 아니에요" 경계 문구, D9 차단·오래된 기록 폴백의 정직한
처리— 이 축은 잘 만들어졌다. 가로 오버플로 0, 콘솔 오류 0도 확인했다.
