## 3. 지금 답할 수 있는 운영 결정 8개

아래 A는 모두 오너 승인되었다. 대안 B는 비교 이력으로 보존한다. 구현 순서는 승인 여부와 별개로 검증 관문을 지킨다.

### 1. 훈련 공개 순서

- A: 검토가 끝난 훈련과 배치부터 순차 공개한다. 나머지도 계속 완성하되 미완료 범위를 명확히 표시한다.
- B: 이번 상세 선택·조정 범위를 모두 갖춘 후 한 번에 공개한다.
- 장단점: A는 실제 피드백을 빨리 얻지만 초기에 선택 폭이 좁을 수 있다. B는 일관된 첫인상을 주지만 전체 공개가 늦어진다. 어느 쪽도 미검토 숫자를 자동 승인하지 않는다.

### 2. 서로 다른 훈련을 한 주기에 조합하는 방식

- A: 첫 버전은 여러 조합을 묶어 검토하고 승인된 조합을 제공한다. 고정 짝으로 제한하지 않는다. 이후 조합을 판단하는 일반 규칙을 별도로 검증해 확대한다.
- B: 조합 규칙을 먼저 완성하고 검증한 뒤, 그 규칙으로 넓은 조합을 제공한다.
- 장단점: A는 현재 계약과 맞지만 검토량이 많다. B는 확장에 유리하지만 처음 규칙을 잘못 만들면 여러 계획에 동시에 영향을 준다. 이 결정은 정확한 각 훈련 채택을 대신하지 않는다.

### 3. COROS 실제 연결 착수

- A: 준비 단계를 넘어 소수 동의 사용자 대상으로 읽기 전용 시험을 준비·수행한다. 사용자가 가져오기를 누르고, 기록을 확인한 뒤 일지에 연결한다.
- B: 신청·설계·자료 준비 상태만 유지한다.
- A의 초기 범위: 활동 ID, 종목, 날짜·시간대, 거리, 의미가 확인된 운동 시간, 수정 정보. 위치 경로·원본 파일·건강 세부 정보·훈련 계획 쓰기·자동 반복 동기화는 별도 단계다.
- 장단점: A는 입력 부담을 줄이지만 동의·중복·철회·삭제·오류 복구를 먼저 갖춰야 한다. 실제 사용자 OAuth 동의나 공급자 지원을 이 승인으로 대신하지 않는다.

### 4. 사용 흐름 개선용 통계

- A: 화면 진입, 기록 저장 성공/실패, 계획 생성·선택 완료 같은 최소 행동 통계만 도입한다. 메모·훈련 수치·위치·화면 녹화는 수집하지 않는다.
- B: 외부 행동 통계 없이 자발적 의견과 테스트만으로 운영한다.
- 장단점: A는 어디서 사용자가 멈추는지 찾기 쉽지만 도구·고지·동의·보관 기간 설계가 필요하다. B는 수집이 적지만 실제 이탈 원인을 알아내기 어렵다. 도구와 정확한 보관 기간은 적용 전 명시한다.

### 5. 콘텐츠 포인트와 방문·일지 포인트

- A: 사용자에게는 하나의 잔액으로 보여주고, 내부에는 획득 이유를 따로 기록한다. 콘텐츠는 기존 승인인 첫 완독 1P·하루 최대 10P를 유지하고 기존 방문·일지 규칙을 임의 변경하지 않는다.
- B: 기존 포인트만 유지하고 콘텐츠 포인트 합산은 계속 보류한다.
- 장단점: A는 꾸미기에 쓰기 쉽지만 중복 지급 방지와 전체 적립량 검토가 필요하다. B는 단순하지만 콘텐츠 보상 연결이 늦어진다. 훈련 거리·강도 보상과 현금성 결제는 포함하지 않는다.

### 6. 다이어리 공유 공개 순서

- A: 먼저 본인이 명시적으로 고른 글을 링크로 공유하게 하고, 팔로워 피드는 권한·차단·신고·삭제 확인 후 공개한다. 기존 글이나 비밀 글을 자동 공개하지 않는다.
- B: 팔로워 피드와 관련 보호 기능까지 함께 준비해서 공개한다.
- 장단점: A는 범위가 작아 운영 확인이 쉽지만 피드 경험이 늦어진다. B는 사회적 경험이 풍부하지만 준비할 권한·운영 기능이 많다. 공유 구현 여부는 재질문하지 않고 공개 순서만 결정한다. 기존 마스터 플랜의 팔로워 방향은 삭제하지 않는다.

### 7. 로그인 제공자 확장 순서

- A: Google·이메일의 실제 운영 안정화 다음은 카카오, 이후 Apple·AthleteTime 연동을 준비한다. 문자·토스·네이버는 필요성과 조건을 확인한 뒤 추가한다.
- B: 문자 로그인도 카카오와 같은 우선순위로 준비한다.
- 장단점: A는 운영 범위와 비용이 작다. B는 전화번호 사용자에게 편하지만 발송비·남용 방지·실수신 시험이 추가된다. 소셜 로그인만으로 실명·법적 책임 문제가 전부 해결된다고 주장하지 않는다.

### 8. 유료 운영 서비스 선택

- A: 이메일 발송·문자·분석·서버의 유료 계약은 항목별 월 예상액과 상한을 먼저 보고받고 승인한다. 그 전에는 현재 승인 범위에서 준비한다.
- B: 오너가 하나의 월 합계 한도를 지정하고 그 안에서 운영 도구 선정을 위임한다.
- 장단점: A는 비용 통제가 명확하지만 확인이 한 번 더 필요하다. B는 빠르지만 한도와 초과 방지 기준이 필요하다. 현재 저장소 문서만으로 실제 청구액은 확인할 수 없으며 결제 기능 공개와도 별개다.

## 5. 승인 없이 먼저 처리할 기술·문서 작업

1. PR #317 실패 로그를 재현하고 수정 범위를 확인한다. 검사 실패를 오너 승인으로 우회하지 않는다.
2. PR #320 최신 head의 모든 검사와 실제 선택→조정→확정→저장→다시 열기→일지→다음 주기 흐름을 확인한다. 합성 시험과 실제 운영 카탈로그를 분리한다.
3. DB V6 계약 적용, 두 계정 데이터 격리, 충돌·삭제·로그아웃 후 접근, 다른 기기 복원을 확인한다. 승인된 서버 저장 구현을 다시 승인 요청으로 돌리지 않는다.
4. 과거 계정 공개 문서의 사업자 미확정·계정 미공개 표현과 이후 실제 공개 기록을 대조한다. 현재 법적 표기와 이메일 발송 상태는 운영 화면에서 별도 확인한다. 과거 증거는 고치지 않고 최신 상태를 연결한다.
5. 가져온 기록은 IMPORTED 출처를 보존한다. 사용자가 확인했다고 직접 입력(EXPLICIT)으로 바꾸자는 제안은 기존 출처 계약과 충돌한다. 사용자 확인과 분석 사용 허용을 별도 속성으로 처리하는 안을 준비한다.
6. Issue #232와 오래된 백로그에 후속 해결 근거를 연결한다. 과거 검사 결과를 최신 코드의 승인으로 재사용하지 않는다.
7. 배포 후 실제 사용자 흐름, 실패 복구, 개인정보 안내·삭제 문의 경로를 확인하고 운영 체크리스트를 만든다.
