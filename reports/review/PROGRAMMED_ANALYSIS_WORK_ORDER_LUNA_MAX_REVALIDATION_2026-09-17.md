### T1. 응답 계약은 여전히 구체화할 가치가 있다

지시서 §5의 방향은 무손실 dual-read와 구형 요청 거절이다. 실제 `app/src/domain/account/account-journal-api.ts`의 요청·응답 종류에는 새 버전 협상이나 업데이트 필요 상태가 없다. 이는 새 기능의 미구현으로 예상되는 상태다. 다만 구현자가 각자 다른 오류를 고르면 구형 앱의 동작이 달라지므로 명세가 필요하다.

완료 조건: capability 없음/V2/V3와 `status/read/list/history/save/delete/restore`별 응답·오류·기존 projection/outbox 유지 결과를 정하고, 실제 구형 빌드에서 손실 없이 실패하는지 실행한다. 정적 소스만으로 자료가 삭제된다고 확정하지 않는다.

### T2. 정정은 일반 편집 허용 범위를 넓히지 않아야 한다

지시서 150행은 같은 기록의 revision 정정과 메모/RPE/계획 링크 보존을 이미 요구한다. `account-journal-record-schema.ts`의 일반 수정 검사는 불변 날짜·객관값·계획 링크·출처 보존을 지키는 기존 방어다. 정정 기능 때문에 이 방어를 제거하면 안 된다.

완료 조건: 같은 operation ID의 같은 요청은 한 번만 반영하고, 다른 본문 재사용·오래된 revision·삭제된 기록·허용 밖 필드는 거절한다. 정정 중 사용자 메모·직접 입력 RPE·계획 링크의 보존을 별도로 단언한다. 정정 API의 존재만으로 완료 처리하지 않는다.

### T3. Luna가 반박한 주장과 실제 Terra 문장을 구분한다

Terra 보고서 57행은 이미 '서비스 기록 ID·원관측 키·내용 수정 지문을 나눈 방향은 반영됐다'고 적었다. 따라서 Luna의 'Terra가 보호 방향 자체를 없다고 보았다'는 요약은 원문과 다르다.

유효한 잔여 조치는 양쪽 리뷰가 같다. 원본 ID 유무, null/누락, 숫자 표현, 시간대, 객체 키 순서, 실제 랩의 순서, parser/profile 버전이 동일 관측 판단에 어떻게 작용하는지 짧은 기대값 표로 정한다. 전체 정체성 설계를 다시 만들거나 유사도 기반 자동 병합을 추가하지 않는다.

### T4. 기존 서버 gate는 실제로 존재한다

총괄이 추가 대조한 소스:

- `supabase/functions/_shared/account-journal-handler.mjs` 252~257행: 요청에서 `repo.enabled(ownerId)` 확인. false는 403, 확정되지 않은 값은 503으로 실패.
- 같은 파일 479~487행: `ACCOUNT`, `ACCOUNT_JOURNAL_V2`를 `service_feature_enabled`로 확인하고 `account_network_access_allowed`도 검사.

기존 계정 접근 제어가 없다는 판정은 잘못이다. 단, Terra 보고서 68행은 이미 '세부 제어가 어디에도 없다고 단정하지 않는다'고 명시했다. 따라서 이번 결과는 Terra의 확정적 부재 주장을 뒤집은 것이 아니라 기존 구현 위치를 더 찾아낸 것이다.

남은 명세는 새 근거 쓰기만 중단할 때 기존 V2/V3 읽기와 일반 일지를 유지하는 조건이다. 기존 계정 gate는 읽기에도 영향을 줄 수 있으므로 새 쓰기 제어를 그대로 대체하지 못한다. 서버에서 검증하고 클라이언트 표시만 끄는 것으로 끝내지 않는다.

### T5. P0는 예정된 선행 작업이며 권한 우회가 아니다

지시서 93행의 좁은 채택표, 99~105행의 용도 표, 246행의 P0→P1 순서가 이미 존재한다. 현행 외부 필드 분석 제외 계약을 그대로 둔 채 새 분석을 공개하는 것은 허용되지 않지만, 그것을 패치하는 일이 현재 계획의 P0다.

이미 선택한 '파일 분석 먼저, 비교와 다음 훈련 선택까지'의 방향을 다시 질문하지 않는다. P0에서 승인 근거와 실제 채택 범위가 일치하는지 문서화한다. 이 검토 자체가 활성화 승인은 아니며, 승인 범위 밖 처방·개인정보 용도가 생기면 그 차이만 별도 결정 대상으로 둔다. 정본 승격은 필요 조건이 아니다.

### T6. 사용자 경로를 새로 발명할 필요가 없다

지시서에는 무기록 시작 경로, 파일 전용 사용자의 기존 계획 입력, 선택·저장·재열기, 무기록·워치 전용 사용자 브라우저 확인이 모두 있다. Terra 보고서 87행도 이를 인정했다.

시험 ID를 더 만드는 것 자체를 새로운 출시 차단 관문으로 삼지 않는다. 기존 P02/U02/§9.2 시험에서 다음 두 입력 상태와 기대 결과를 구분하면 충분하다.

1. 기록도 파일도 없음: 기존 계획 입력으로 진입하고 허용 후보를 선택·저장·다시 열 수 있다.
2. 파일만 있고 적격 경기 기록 없음: 기록 분석은 제공하되 가짜 PB·개인 페이스를 만들지 않고 기존 후보 경로를 완료한다.

## 2. 추가 제시한 코드 경로 두 건의 재검증

### L1. CSV/JSON 숫자 접두부 처리

- 소스: `app/src/domain/import/structured-activity-file.ts` 18~20행은 `Number.parseFloat(text(value))`를 사용한다. 35~44행이 이를 거리·시간·평균 페이스 요약에 사용한다.
- 정적 위험: `5 miles`, `1:30`, `12abc`처럼 전체 형식이 맞지 않는 문자열에서 숫자 앞부분만 읽는 경로가 있다. 이런 값이 정확한 숫자로 안내될 수 있다.
- 중복 여부: 원지시서 §4.3과 N01/N02에서 이미 금지하고 수정 대상으로 정했다. 이번 리뷰로 새 계획 결함이 발견된 것은 아니다.
- 닫는 조건: 정해진 열에서 전체 숫자 문법만 허용하고 누락·0·잘못된 값을 구분한다. CSV/JSON의 실제 파서를 통해 합성 입력을 실행해 정상 소수 정밀도와 잘못된 행의 원인 표시를 검증한다.
- 이번 상태: 소스 재확인만 완료. 파서 실행이나 사용자 화면 재현은 하지 않았다.

### L2. GPX 구간 경계·무효 좌표 연결

- 소스: `app/src/domain/import/activity-file.ts` 130~145행. 하나의 `trk` 아래 모든 `trkpt`를 순회하며 `trkseg`마다 `prev`를 초기화하지 않는다. 비유한 좌표는 `continue`하지만 직전 좌표를 지우지 않는다.
- 정적 위험: 분리된 구간 또는 잘못된 좌표 양옆의 점이 직선으로 이어져 실제 없는 거리가 더해질 수 있다. 이후 평균 페이스 요약에도 영향을 줄 수 있다.
- 중복 여부: 원지시서 §4.3과 R02에 세그먼트 사이를 잇지 않고 무효 좌표에서 연결을 끊도록 이미 명시되어 있다.
- 닫는 조건: 구간별로 연결을 초기화하고 유효성 검사 실패 시 연결을 끊는다. 두 개의 떨어진 구간·중간 무효 좌표·정상 연속 구간을 실제 파서에 넣어 기대 거리와 부분 제외 결과를 확인한다.
- 이번 상태: 소스 재확인만 완료. GPX fixture 실행이나 실배포 분석 결과 검증은 하지 않았다.

두 경로는 현행 가져오기 품질 위험으로 유지하되, 외부 분석이 이미 활성화되어 잘못된 처방을 만들었다고 확장해서 주장하지 않는다. 기존 단계 P8에서 처리하도록 추적하고, 같은 문제를 단계마다 별도 결함으로 중복 집계하지 않는다.

- 코칭 수치·생리학적 효과·개인정보의 새 용도를 이 리뷰로 승인하지 않는다.

## 5. 종료 상태

완료: Luna max 설정 작업의 결과 회수, 이전 여섯 항목 재판정, 코드 두 경로 및 서버 gate 추가 대조, 별도 보고서 작성.

변경하지 않음: 원지시서 v1.1, Terra 보고서, 스펙, 앱, 런타임, 운영 설정. 두 입력 문서의 해시는 검토 기준과 동일하게 유지한다.

미수행: 구형 앱 보존 시험, 정정/중복 합성 실행, GPX/CSV 실제 파서 시험, UI 흐름, Git 원격 최신 확인, 커밋·푸시·배포. 이를 통과 또는 완료라고 보고하지 않는다.

다음 작업: 네 기술 계약을 지시서에 좁게 보완하고, 기존 P0와 연결한다. 사용자 요청이 검토였으므로 이번 턴에서는 실제 계획 패치나 구현을 시작하지 않았다. 리뷰어 종료 요청 완료, 백그라운드에서 검토가 계속된다고 안내하지 않는다.
