## 결론

100개 합성 페르소나의 [원본 검수](PERSONA_100_INTEGRATED_REVIEW_2026-09-30.md)에서
발견한 다음 문제를 실제 코드와 스펙에 반영했다. 실제 사람 100명의 사용성 시험이 아니며,
원본 100개를 수정 후 전부 다시 실행했다고 주장하지 않는다. 반복 실행 횟수와 사람 수를
합산하지 않는다. 운영 계정이나 실제 선수의 일지는 사용하지 않았다.

가장 큰 미완료는 **첫 생성 MAIN의 상세 연결**이다. LT/GLY 강도와 전체 시간의 기존
임시 상한이 검토된 상세 템플릿과 충돌한다. 이 기본값 변경은 오너 답변을 기다리고 있다.
이번 저장 후 직접 교체는 이미 승인된 수동 선택 범위이며 기본 자동 증량의 승인이 아니다.

## 4165380 이후 독립 재검수와 추가 수리

독립 재검수는 기존 W2를 `REQUEST_CHANGES`로 판정했다. 고유 합성 검사 13건 중
10건 통과, 3건 실패였으며 UTC·한국 시간대 반복 실행을 합산하지 않는다. 두 건은
합성 요청/서비스에서 재현한 결함이고, 날짜 경쟁 한 건은 지연 저장 모형에서 재현한
위험이다. 독립 작업자의 추가 PostgreSQL 시도는 준비 단계 503으로 대조군부터 실패해
SQL 재현 증거로 사용하지 않는다.

| 발견 | 분류와 실제 영향 | 추가 수리 | 확인 경계 |
|---|---|---|---|
| F01 이전 계획의 완료 내역 삭제 허용 | P1. 잘못 조합한 요청이 보관되는 이전 항목의 완료 내역을 지워도 통과. 정상 UI가 저절로 지웠다는 뜻은 아님 | 교체 시 이전 항목은 보관 시각만 바뀌도록 정확히 비교 | 삭제·상태 변경·갱신 시각 변경 3개 모두 수정 전 실패, 수정 후 통과. 서버 번들/게이트웨이도 거절 |
| F03 커밋 후 잘못된 응답 | P2. 이미 저장됐지만 `INVALID`로 표시. 데이터 손실이나 이중 적용을 관측한 것은 아님 | 저장 불명 `PENDING` 유지, 동일 영수증 회수 | 실제 API 파서에 잘못된 응답을 넣은 로컬 결합 검사에서 최초 미확인 → 재조회 완료, 커밋은 1회 |
| F02 저장 대기 중 날짜 변경 | P2 위험. 메모리 지연 모형에서 날짜가 바뀐 뒤 커밋. 실제 다중 세션 잠금 대기는 미재현 | 신규 0041 DB 함수에서 잠금 후·중첩 저장 후 날짜 검사, 지난 경우 같은 트랜잭션 롤백 | 로컬 PGlite의 정상 SQL과 결정적 시계 모형으로 이전 날짜 거절·index/receipt 롤백·정상 저장·과거 영수증 회수를 확인 |

후속 서버 검사 **23/23**, 관련 앱 4개 파일 **72/72**, 그 뒤 추가한 실제 API 파서 결합
검사 **1/1** 통과했다. 이전 검사와 중복이 있으므로 전체 합계나 100명 재검수로 표시하지
않는다. SQL 날짜 검사 두 곳을 메모리에서 제거하면 `real PGlite 0037 with gateway and
authenticated repository round trips 18 V3 frames, isolates owners and replays` 검사가
거절 대신 저장되는 HTTP 200/409 차이로 실패했다. 제품 SQL 파일은 변조하지 않았다.

신규 마이그레이션은 로컬에서만 준비했다. 아래 초기 구현 기록의 "신규 DB 마이그레이션
없음"은 독립 재검수 이전 상태이며, 현재 배포 순서는 **0041 → 서버 → 앱**이다.
키 교체·민감한 원문 공개·운영 DB 쓰기는 수행하지 않았다. 아래 F02 후속에서 실제
PostgreSQL 다중 세션 대기는 로컬 실행했고, 운영 계정 검증은 여전히 후속 관문이다.

### 수정 후 독립 판정

F01/F03는 현재 수정본에 한해 **독립 재검수 승인**을 받았다. 고유 검사 12/12 통과,
UTC와 한국 시간대에서 같은 결과였다. 방어문을 메모리에서 제거했을 때 F01의 삭제·변경·
갱신 시각 3건과 F03의 INVALID·실제 API 파서 2건이 이름으로 실패했다. 고유 결함 주입
검사는 5건이며 시간대 반복을 합산하지 않는다. 정상 교체·일반 PROGRESS 수정과 저장 전
확정 입력 오류 대조군도 확인했다. 커밋 후 불명 응답은 원래 작업 ID를 유지하며 재조회로
복구했고 추가 커밋은 없었다.

F02는 독립 작업자가 정적 공격 검토만 수행했다. 서명·소유자 잠금·기존 영수증 우선·
저장 전후 날짜 검사에서 새 차단 결함은 발견하지 못했지만, 주 작업자의 PGlite 결과를
독립 SQL 실행으로 계산하지 않았다. W2 전체 또는 운영 저장·배포 승인은 아직 아니다.

## 공격적으로 다시 확인한 경계

1. **방법군 합침의 과잉 일반화**: 독립 GPT-6.1 Sol ultra 검수에서 단일 자식 그룹의
   반복 회복과 마지막 한 번의 회복이 같은 방법으로 합쳐지는 P2를 찾았다. 단일 자식이라도
   반복 그룹이나 SET이면 경계를 보존하도록 수정했고 같은 독립 6개 검사 모두 통과했다.
   현재 117개 원본에서 실제 충돌 쌍을 발견했다는 뜻은 아니다. 유효한 합성 구조로 재현했다.
2. **서버의 클라이언트 주장 신뢰**: 일지 버전 비교만으로는 요청의 보호 슬롯 목록을
   검증할 수 없다. 서버가 소유자에 한정된 암호화 일지를 25개씩 읽고 실제 날짜·시간대·
   계획 연결과 구조화 근거 지문을 대조하도록 보강했다. 이후 일지 변경이나 누락은 기존
   전체 버전 검사와 계획 CAS를 같은 트랜잭션에서 확인한다. 신규 DB 마이그레이션은 없다.
3. **다른 날짜 수행과 시간대 미지정**: 날짜를 달리해 수행한 일지도 원래 계획 슬롯을
   보호한다. `UNSPECIFIED`/`SINGLE`을 오전·오후가 확정된 기록처럼 취급하지 않는다.
4. **거짓 성공과 원본 유실**: 응답이 불명확하면 재적용을 잠그고 확인 필요로 표시한다.
   원래 계획을 되돌려 덮어쓰거나, 계정 저장 실패를 기기 저장 성공으로 바꾸지 않는다.
5. **검수 증거 오염**: 100개 코어 감사의 기준 SHA와 출력 폴더가 과거 값으로 고정돼
   있었다. 실행 당시 HEAD/dirty 상태와 고유 실행 폴더를 사용하도록 바꿨다. 과거 증거를
   최신 통과 결과로 덮어쓰지 않는다.
6. **진행 결과·날짜의 서버 재확인**: 요청의 보호 목록과 날짜를 그대로 믿지 않는다.
   이전 계획에 완료/휴식/건너뜀 결과가 있거나 통증 확인 상태면 교체 전이를 거절한다.
   변경 영수증의 달력 시간대와 서버 현재 시각으로 날짜를 재계산하고, 날짜가 지난 변경은
   읽기 전과 저장 직전에 다시 막는다. 이미 커밋된 요청의 영수증 재조회는 계속 허용한다.
   시간대는 달력 맥락이며 이용자의 물리적 위치를 증명하지 않는다.
7. **시간 확인란의 거짓 상태**: 이미 확인한 시간을 해제해도 체크가 되살아나는 문제와,
   확인란만 바꾸면 미적용 변경으로 잡히지 않는 문제를 추가로 재현했다. 확인/해제의
   명시적 선택을 별도 보존하고, 구성 변경과 구분해 기존 기준 기록이 사라지지 않게 했다.
   취소하면 기존 확인으로 복귀하며, 운동 초가 달라지면 이전 시간 확인은 재사용하지 않는다.

첫 서버 독립 검수 시도는 도구 중단으로 끝났지만 후속 재검수에서 위 3건을 찾았다.
수정 전 독립 `REQUEST_CHANGES`, 주 작업자의 수정 후 검사, 이후 F01/F03에 한정한
독립 승인을 구분한다. 이를 W2 전체 독립 승인이나 운영 저장 확인으로 표기하지 않는다.

## B03 기존 일지의 교정 연결 수리

- 원래 문제는 현재 후보 ID로만 일지를 찾는 것이었다. 현재 계획에서 수동 교체/수행 교정
  영수증의 정확한 이전 상태를 따라가고, 그 경로에서 수행 대상의 내용이 같을 때만
  원래 일지를 받는다. 원래 비교값과 일지 링크는 바꾸지 않는다.
- 앱 준비 및 적용 직전에 보관 원본을 읽는다. 교정안을 본 뒤 중간 원본이 사라지면 저장을
  멈추고 현재 계획을 유지한다. 저장 후 다시 같은 원래 일지로 다음 검토를 할 수 있다.
- 서버는 신규 요청에 실린 과거 원본을 믿지 않는다. 이전 확정 계정 보관본과 실제 암호화
  일지를 대조하고, 다른 주기·없는 일지·버전 간 중복·통증 신호는 커밋 전에 거절한다.
- 독립 검수 과정에서 A→B→A 내용 복귀 시 ID도 같아지는 추가 결함을 재현했다. 변경
  시각보다 늦게 연결한 현재 일지만 직접 연결하고, 이전/동시각 연결은 원본 경로로 확인한다.
  중간에 수행 대상이 바뀐 오래된 링크는 내용을 되돌려도 받지 않는다. 시간 비교는 구조적
  일관성 검사이며 실제 수행 시각을 인증하거나 클라이언트 시계를 신뢰한다는 뜻은 아니다.
- 수정 전 새 핵심 검사 2건이 이름으로 실패했다. 수정 후 관련 앱 **63/63**, UTC/KST에서
  각각 통과했다. 시간대 반복을 126개 고유 사례로 합산하지 않는다. 관련 서버 **25/25**,
  타입 검사와 생성 검증기 3개 원본 일치도 통과했다.
- 서버 원본 검증만 메모리에서 제거하면
  `execution replan authenticates archived source lineage and rejects forged or duplicate journal sources`
  검사의 `missing-source`가 HTTP 200/422 차이로 실패한다(exit 1). 결함 주입은 제품 파일을
  수정하지 않는다. 앱 브라우저 전체·운영 계정·배포 검증을 수행한 것은 아니다.
- 이번 추가는 원본과 현재 계획을 정확히 잇는 작업이다. B06 다음 주기 준비 정보,

- GPT-6.1 Sol ultra 별도 작업자의 최종 좁은 실행은 **5경계/5통과**, 두 결함 주입은
  지정 이름으로 실패했다. 최초 실패 파일은 시험기 재실행으로 덮어쓰였으므로 보존된

## B06 다음 주기 조정의 늦은 실패 줄이기

- 새 조정안이 실제로 있는지 질문 전에 검사한다. 수동 교체/수행 교정 뒤 미지원 변환,
  카탈로그 변환 미지원, 비교안 누락, 현재 내용 불일치, 지도자 권한을 구별한다.
  같은 후보 ID라도 실제 세션/프레임/범위가 다르면 옛 비교안을 사용하지 않는다.
- 조정할 수 없으면 여러 질문을 거치게 하지 않고 `이번 주기 기록 확인` 한 번으로
  읽기 전용 요약에 진입한다. 조정 가능한 기존 계획은 실제 등록된 사유만 보여준다.

  예외 뒤 무한 대기를 막고, 저장 응답을 모르면 저장 성공/실패를 단정하지 않는다.

  현재 스냅샷 링크 기준이었으며, 아래 `같은 주기 기록 연결 후속`에서 변경되지 않은
  과거 원본까지 확장했다. 모든 장기 누적 분석을 확장했다고 주장하지 않는다.

- 독립 브라우저 문맥의 실제 컴포넌트 **9조합**(320/375px/합성 큰 글자·모션 감소)은

## 장점과 부담

### 같은 주기 기록 연결 후속

- 미래의 다른 훈련을 교체/교정하면 기존 일지가 주기 요약에서 빠지는 문제를 추가로
  재현했다. B03의 정확한 원본 체인 검증을 재사용해 변경되지 않은 수행 대상만 잇는다.
  현재/과거 계획·일지 링크는 수정하지 않는다. 다른 주기·날짜·변경된 대상·누락 원본은
  계속 거절하며, 다음 주기 수치 변환 권한은 추가하지 않는다.
- 같은 날짜·슬롯의 동일한 운동이 후보 버전별로 두 번 집계되지 않게 했다. 서로 다른
  일지가 겹치면 반복 성과가 아니라 충돌 한 건으로 표시한다. 실제 수치·원래 링크만
  사용하며 비밀 메모의 내용이나 존재는 읽지 않는다.
- 주기 요약·오라클·훈련 상세가 같은 근거를 사용한다. 원본 읽기 실패를 일지 없음으로
  표현하지 않고 직접 검증 가능한 기록은 남긴다. 별도의 현재 표시용 참조를 대조하므로
  원래 일지 링크를 새 후보로 덮어쓰지 않는다.
- 실제 브라우저에서 `주기·기록` 바로 열기의 기록이 긴 설명 밑에 묻히는 문제를 확인했다.
  일지에서 직접 들어갈 때만 실제 기록 위치로 즉시 이동한다. 일반 방법 화면과 탭별
  위치 복원은 유지한다. 이 이동에 모션을 강제하지 않는다.
