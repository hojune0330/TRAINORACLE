# 훈련 코칭 30개 페르소나 독립·공격적 검수

## 1. 결론

**REQUEST_CHANGES: 현재 로컬 구현은 수정 후 재검수가 필요하다.**

가장 중요한 문제는 오전 계획을 오후에 수행한 정상적인 변경을 원본 조회 실패로 처리하는 것이다. 그다음은 비교까지 여러 번 펼쳐야 하는 구조, 워치 자료 대기를 숨긴 요약, 탭을 오가면 사라지는 읽기 상태다. 정보량을 줄이는 방향은 좋지만, 필요한 상태까지 숨기거나 같은 행동을 반복하게 만들면 간결함이 아니다.

이번 범위에서 P1 수준의 데이터 유출·임의 계획 변경은 확인하지 못했다. 이것은 전체 제품의 안전 승인이나 무결점 선언이 아니다. 이후 훈련을 실제로 교정하는 엔진도 이번 읽기 전용 코칭 구현만으로 완성됐다고 볼 수 없다.

| 구분 | 결과 |
|---|---|
| 모델 | `gpt-6-luna`, `reasoning_effort: max` |
| 독립 실행 | 새 프롬프트의 검수자 6개, 각 5개 가상 페르소나 |
| 관점 수 | 30개. 실사용자 30명 또는 모델 인스턴스 30개가 아님 |

## 3. 발견 사항

### R01. P2: 오전 계획을 오후에 수행하면 비교가 사라짐

**확인 수준: 합성 브라우저에서 도메인 함수 연결을 직접 실행해 재현.**

같은 계획 링크와 같은 날짜를 유지한 채 실제 수행 시간대만 AM에서 PM으로 변경했다. 변경 관계 계산은 `MODIFIED`를 반환하지만 원본 조회는 `unavailable`, 코칭은 `SOURCE_UNAVAILABLE`, 지표는 빈 배열이 됐다. 사용자에게는 계획을 읽지 못했다는 안내가 나온다.

- 근거: `app/src/domain/journal-original-plan.ts:25`, `app/src/domain/plan-execution-review.ts:44`.
- 대조 근거: `app/src/domain/plan-execution-relation.ts:7`, `app/src/screens/log-entry/QuickSessionForm.contract.test.tsx:263`.
- 재현: [후속 결과](./followup-probes-results.json)의 `AM_PLAN_PM_ACTUAL`.
- 영향: 하루 두 번 훈련하는 선수나 오전 운동을 저녁으로 미룬 사람의 정상 기록이 비교에서 빠진다.
- 수정: 계획의 원래 시간대와 실제 수행 시간대를 구분한다. 검증된 계획 ID·세션 참조·지문을 유지한 경우 시간 변경을 사실로 표시하고, 링크 위조는 계속 차단한다. 조회 함수와 리뷰 함수를 함께 맞춰야 한다.
- 주의: 단순히 검증 조건 하나를 제거하거나 다른 계획으로 대체하면 안 된다. 다른 날짜로 옮긴 경우까지 이번 재현으로 승인하지 않는다.

독립 의견은 갈렸다. A는 정상 변경이 사라지는 문제를 제기했고 F는 기존 테스트의 거부 기대값을 근거로 방어 동작으로 보았다. 통합 검수는 저장 관계 계산과 실제 조회 결과를 대조해 **계약 간 불일치**로 판정했다. 기존 테스트가 통과한다는 이유만으로 현재 동작을 정당화하지 않았다.

### R02. P2: 일지에서 계획과 실제 구성을 함께 보려면 3번 펼쳐야 함

**확인 수준: 코드 확인. 이 경로의 실제 사용자 클릭 시간은 측정하지 않음.**

`계획한 훈련과 비교하기`를 연 뒤 `기록과 설명 더 보기`, 별도의 `당시 계획한 훈련 방법`을 열어야 양쪽 상세를 볼 수 있다. 운동 종류나 구간이 많으면 추가 펼치기도 생긴다.

- 근거: `app/src/screens/journal/JournalOriginalPlan.tsx:43`, `:62`, `:64`, `:67`; `app/src/screens/plan-review/ExecutionReview.tsx:63`.
- 영향: 사용자가 이미 비교를 요청했는데 비교에 필요한 정보가 다시 숨겨진다.
- 수정: 일지의 비교 진입은 하나로 통합하고 `계획·기록`을 같은 화면에서 제공한다. 긴 이유·참고자료와 추가 구간만 선택적으로 펼친다.
- 장단점: 클릭이 줄지만 처음 보이는 정보는 늘 수 있다. 계획과 기록의 핵심 구조를 먼저 보여주고 자세한 설명은 기존 탭에 남기는 방식이 적절하다.

### R03. P2: 워치 자료를 기다리는 상태가 요약에 없음

**확인 수준: 격리 브라우저 UI 재현.**

`objectiveDataState: WAITING`을 넣어도 요약에는 대기가 표시되지 않는다. `이유`로 이동한 뒤 `아직 판단하지 않은 내용`을 펼쳐야 보인다. 현재 비교가 자료 도착 전의 결과라는 중요한 맥락에 두 번의 추가 행동이 필요하다.

- 근거: `app/src/domain/plan-execution-review.ts:100`; `app/src/screens/plan-review/ExecutionReview.tsx:33`, `:55`.
- 재현: `WAITING_VISIBILITY`, `waitingVisibleOnSummary: false`, `visibleAfterTwoActions: true`.
- 수정: 요약에 짧은 상태 한 줄을 둔다. 예: `워치 기록을 기다리고 있어요.` 자세한 의미만 이유 화면에 둔다.
- 금지: 대기를 완료로 해석하거나 입력·저장을 막는 새 확인창을 추가하지 않는다.

### R04. P2: 비활성 탭의 접근성 연결 대상이 DOM에 없음

**확인 수준: 독립 검수 및 부모 검수의 브라우저 DOM 재현.**

세 탭 모두 `aria-controls`를 가지지만 선택된 패널만 렌더링한다. 따라서 두 탭의 대상 ID가 존재하지 않는다. 시각적으로는 전환되더라도 탭-패널 관계가 불완전하다.

- 근거: `app/src/screens/plan-review/ExecutionReview.tsx:110`, `:123`.
- 재현: `TAB_PANEL_REFERENCES`에서 3개 중 2개 `targetExists: false`.
- 수정: 패널 컨테이너와 ID는 유지하고 비활성 패널은 숨긴다. 무거운 내용은 최초 진입 시 생성할 수 있다. 숨긴 영역으로 키보드 포커스가 들어가지 않아야 한다.
- 한계: 실제 VoiceOver 발화나 모든 보조기기의 실패를 확인한 것은 아니다.

### R05. P3: 이유를 읽다가 다른 탭에 다녀오면 펼친 내용이 접힘

**확인 수준: 격리 브라우저 UI 재현.**

`사용한 기록`을 펼치고 요약 탭에 갔다가 돌아오면 닫혀 있다. 스크롤 위치는 따로 저장하지만 펼친 내용이 사라져 높이가 바뀌므로 읽던 맥락을 온전히 복원하지 못한다.

- 근거: `app/src/screens/plan-review/ExecutionReview.tsx:55`, `:84`, `:123`의 `key={view}`.
- 재현: `REASON_DISCLOSURE_RETURN`, `expandedBefore: true`, `expandedAfter: false`.
- 수정: R04와 함께 패널 상태를 유지하거나 펼침 상태를 명시적으로 보존한다. 다른 기록·계정으로 이동하면 이 상태는 초기화해야 한다.
- 구분: 기록 데이터 손실이 아니라 반복 클릭을 만드는 읽기 상태 손실이다.

### R06. P3: 읽고 있던 기록이 삭제되면 포커스가 BODY로 떨어짐

**확인 수준: 다른 탭의 합성 삭제 이벤트를 이용한 브라우저 UI 재현.**

기록이 목록에서 사라지면 리더가 닫힌다. 기존 열기 버튼도 사라져 포커스를 돌려줄 수 없으며 대체 지점 없이 `BODY`에 남는다.

- 근거: `app/src/screens/home/HomeCoachingSummary.tsx:25`; `app/src/hooks/useReaderDialog.ts:35`.
- 재현: `DELETED_OPENER_FOCUS`, `tag: BODY`.
- 수정: 열기 버튼이 없어졌을 때만 코칭 제목이나 삭제 상태 안내로 포커스를 돌린다. 일반적인 닫기는 기존 버튼으로 복귀한다.
- 금지: 삭제 확인창을 추가해 클릭 수를 늘리는 방식으로 해결하지 않는다.

### R07. P3: 화면을 켜둔 채 자정을 넘기면 날짜 기준이 갱신되지 않을 수 있음

**확인 수준: 코드 확인. 자정 런타임 재현은 하지 않음.**

`todayISO()`는 메모 계산 안에서 호출되며 의존성에는 날짜가 없다. 기록 변경이나 다른 재계산 계기가 없으면 오늘까지의 기록 필터가 전날 값으로 남는다.

- 근거: `app/src/screens/home/HomeCoachingSummary.tsx:18`의 메모 및 `:24`의 의존성.
- 수정: 기존 날짜 변경 훅을 재사용해 오늘 날짜를 의존성으로 둔다. 앱 복귀 시 날짜 확인도 고려한다. 잦은 폴링이나 새 전역 타이머는 피한다.

### R08. P3: 중복 기록 두 개를 사용자가 구별하기 어려움

**확인 수준: 코드 확인. 중복 상태의 기술적 동작은 행렬 시험에 포함됐으나 식별성 사용성 평가는 정적 확인임.**

같은 계획에 연결된 두 기록은 날짜·시간대·제목이 같아질 수 있다. `해당 일지`도 기록 ID가 아닌 날짜로만 이동한다. 중복을 확인하라고 하면서 어떤 두 기록인지 식별할 정보가 부족하다.

- 근거: `app/src/screens/home/HomeCoachingSummary.tsx:39`, `:45`; `app/src/domain/plan-execution-review.ts:47`.
- 수정: `기록 1 / 기록 2`와 직접 입력된 시간·거리 등 최소 식별 정보를 표시하고 해당 기록으로 이동한다. 존재하지 않는 수치는 채우지 않는다.
- 금지: 메모나 자유 입력 제목을 노출해서 구별하거나, 임의로 합쳐 중복을 해소하지 않는다.

### R09. P3: 320×568에서 요약이 한 화면을 넘어감

**확인 수준: 30개 브라우저 행렬 실행으로 측정.**

완료 34px, 부분 수행 59px, 통증 86px의 세로 스크롤이 필요했다. 화면 겹침·가로 넘침·버튼 소실은 아니지만 사용자가 요청한 짧은 요약 흐름에는 아직 여유가 없다.

- 근거: `app/src/styles/execution-review.css:13`; `app/src/screens/plan-review/ExecutionReview.tsx:33`.
- 재현: [행렬 결과](./runtime-matrix-results.json), [스크린샷 폴더](./runtime-matrix/).
- 수정: 작은 화면에서는 핵심 지표 2개와 한 줄 단위 표시를 우선하고, 중복 안내를 합친다. 세 번째 지표는 계획·기록에 그대로 둔다.
- 유지: 통증 상태와 중요한 다음 행동은 숨기지 않는다. 글자를 줄이거나 잘라내지 않고 44px 터치 영역을 유지한다. 200% 글자 확대에서는 스크롤 허용이 올바른 대안이다.

### S01. 의심: 계정 기록을 일부만 읽었을 때 일지 비교의 보류 이유가 빠질 가능성

**확인 수준: 미확정. 코드 경로를 확인했으나 통합 계정 상태 재현은 하지 않음.**

불완전 조회에서 비교 목록은 빈 배열을 반환한다. 홈에는 보류 메시지가 있지만 일지 컴포넌트는 원본이 조회되면 원본만 보이고 비교 보류 이유는 드러나지 않을 가능성이 있다.

- 근거: `app/src/screens/journal/JournalOriginalPlan.tsx:40`, `:63`; `app/src/domain/plan-execution-review.ts:127`.
- 다음 확인: 계획 원본은 존재하고 계정 일지 읽기만 불완전한 합성 상태를 주입한다. 재현되면 짧은 보류 상태를 표시한다. 원본 자체를 숨기거나 빈 목록을 0건으로 단정하지 않는다.
- 확인된 결함 9건에 합산하지 않는다.

## 4. 잘 유지된 방향과 아직 없는 기능

- 읽기 전용 경계: 부모 행렬 30건에서 일지·계획 저장 문자열이 바뀌지 않았다.
- 근거 경계: 완료 버튼·시간대만으로 상세 수행 일치를 단정하지 않는 방향은 타당하다. 미기록을 0으로 바꾸거나 남은 반복을 다음 날 더하지 않는다.
- 정보 계층: 요약/계획·기록/이유 분리는 긴 글을 첫 화면에 늘어놓는 것보다 좋다. 다만 상태·필수 비교까지 숨기지 않아야 한다.
- 안전·프라이버시: 검사한 경로에서 메모 원문을 근거로 읽거나 외부에 전송하는 동작, 코칭 열람만으로 계획을 고치는 동작은 확인하지 못했다.
- 아직 없는 것: 실제 운동 구간과 계획 구간의 신뢰 가능한 대응 확정, 그 차이를 반영한 후속 일정 후보 생성·승인·적용은 별도 남은 범위다. 현재 화면을 완성형 재처방으로 홍보하면 안 된다.
