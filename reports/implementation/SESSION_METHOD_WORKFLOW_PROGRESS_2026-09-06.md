## 1. 이번 작업의 의미

사용자가 승인한 상세 훈련 선택·조정·일지 연결 계획을 수행한다. 이전 PR #318의
기반 구현을 전체 기능 완료로 부르지 않는다. 새 방법을 조사하는 일, 실제로 선택하게
하는 일, 조정된 숫자를 저장하는 일, 수행 결과를 해석하는 일은 각각 완료 증거가 필요하다.

현재 공개된 네 가지 정확한 상세 템플릿과 기존 시간·RPE 계획은 유지한다.
이번 변경은 새 훈련량·페이스·회복값·성별 또는 연령별 계수를 만들지 않는다.
일지 메모를 읽지 않으며 기존 청소년·혼자 훈련하기의 승인 범위를 축소하지 않는다.

## 7. M12 후속 구현 및 자체 리뷰

- 추천 입력과 범위 설명을 같은 저장소 읽기 결과에서 만든다. 주입한 테스트 이력에는

- 방법 선택의 `추천에 참고한 이력`을 열면 보관 계획 수, 동일 종목 계획 수,
  종목 불명 과거 계획, 미기록 결과, 매핑 불명 참조를 볼 수 있다.
- 날짜는 명시적으로 UTC 보관 날짜다. 실제 운동 날짜와 연속 관찰 기간 또는
  24주 분석으로 표시하지 않는다. 진행 중인 계획은 여전히 포함되지 않는다.
- 자체 리뷰에서 읽기 실패를 빈 배열로 처리하던 경계를 발견했다. 새 범위 표시에서는
  `coverage: null`로 구분하고 0회 대신 읽기 실패 안내를 표시한다. 원본은 지우지 않는다.
- 결함 주입: 미기록 대신 완료를 세도록 바꿨을 때 최초 테스트는 두 상태가 각각
  1건이라 실패하지 않았다. 서로 다른 개수로 fixture를 보강한 뒤 다음 두 테스트가
  실제 실패함을 확인하고 정상 코드를 복원했다:

전환은 검토된 registry가 있을 때만 활성화하고 시험용 권한을 운영에 넣지 않는다.
기존 네 ref의 청소년/자율 사용자 범위는 그대로 유지한다.

## 13. 조정 적용 host와 단일 snapshot commit 기반

- `revalidateAdjustmentReceipt`가 전달된 before/after, 모든 합계/delta와
  구조 차이를 원래 동작 시점 및 현재 시점의 독립 registry로 재검산한다.
  원래 명시 적용 시각을 현재 시각으로 바꿔 쓰지 않는다.
- `prescription-adjustment-commit.ts`는 후보 계보/MAIN slot/context/revision을
  묶은 workspace snapshot을 CAS 한 번으로 교체한다. 처방, 설명 버전과
  근거 참조, receipt가 한 snapshot에 들어가며 부분 필드 저장을 하지 않는다.
  실제 CAS/lock 구현은 소비 저장소의 책임이며 이 모듈이 localStorage의
  다중 키 원자성을 제공한다고 주장하지 않는다.
- `PrescriptionAdjustmentCommitHost`는 기존 editor의 적용/취소를 이
  controller에 연결한다. 열 때의 base revision을 유지하고, 실패한 draft는
  재시도할 수 있다. 화면 unmount/취소는 대기 중인 write를 무효화한다.
- 안전/context/권한 변경을 write lock 안에서 재확인한다. 중복 적용은
  한 요청으로 합치고, 저장 후 응답 유실은 정확한 receipt를 재검사하여
  write 없이 replay한다. getter 및 허용되지 않은 메모 필드의 유입을 거부한다.
- 합성 registry를 사용하는 app 연결 시험 42 PASS, impl 전체 831 PASS.
  이 수치는 실제 선수를 대상으로 한 처방 검증이나 신규 source 채택이 아니다.
  타입 검사와 build 결과는 아래 실행 기록에 별도로 보존한다.
- 최종 타입 검사/build PASS. 기존 font 경로 및 chunk 크기 경고는 남아 있다.
  [자체 검토 보고서](../review/ADJUSTMENT_COMMIT_HOST_SELF_REVIEW_2026-09-06.md)에
  공격 검토 수정점과 production 연결에서 아직 검증되지 않은 범위를 남겼다.
- **아직 public `PlanBeta`에서 이 host를 열지 않는다.** 실제 적격 전환이
  없는 버튼을 노출하지 않았다. 기존 PACE_TARGET 저장 스키마를 generic
  조정 snapshot으로 대체하지 않았으며, 시험용 권한/용량은 운영 manifest에
  들어가지 않았다. 따라서 M08/M09 공통 host 기반은 구현됐지만 실제 공개
  후보 저장·재조회와 신규 구성 활성화가 완료된 것은 아니다.
- 다음 실제 작업: source configuration과 개인 기록으로 해석된 sequence의
  identity를 구분한 production offer/adapter, 버전별 저장 계약과 정확한
  후보 투영 검증. 현재 4개 고정 baseline에 새 용량을 덧씌우지 않는다.

## 14. 초기 계획 저장의 정확한 재시도

- 저장 성공 후 응답만 놓친 동일 요청은 기존 snapshot을 그대로 반환한다.
  새 generatedAt/주기 계보/설명 receipt를 만들거나 계획·context를 다시 쓰지 않는다.

- 현재 계정·초안·안전·기록·템플릿 권한을 확인한 뒤, 원래 저장 시각으로
  재구성한 전체 예상 상태와 실제 저장 상태를 비교한다. 날짜·후보·근거 변경,
  이미 기록한 진행 상태, 미래 저장 시각은 재시도로 인정하지 않는다.
- 필요한 adaptation context가 없거나 손상되거나 다른 후보를 가리키면
  성공으로 반환하거나 자동 복구하지 않고 `PLAN_STORAGE_STATE_UNCERTAIN`을 유지한다.
- 재시도 회귀 18 PASS. 재시도 성공 반환을 고의로 제거한 변조 실행은
  양성 5건이 모두 실패했다(13건 필터 제외). 변조는 즉시 원복했다.

  변경했다. 원본 저장 내용 불변 검사는 유지한다. 이 변경을 한 뒤 최종 재실행한다.
- 새 빌드의 실제 화면 6 PASS: desktop/320px에서 공유 target, A만, B만의
  선택·기록 확인·저장·새로고침, 원본 222.2초와 슬롯 유지, 가로 넘침 및 pageerror 없음.

  사용했다. 첫 저장 뒤 두 번째 요청이 전체 계획/context를 바꾸지 않음을 확인했다.

신규 훈련 구성/전환 승인, host의 public 연결, 다중 키 원자성, 전체 계획 완료,

## 15. V5 원본 보관과 일지에서의 비교

- 앞으로 보관하는 계획은 기존 최신 18개 한도 안에서 V5 원본과 요약을 함께
  저장한다. 수동 보관·승인된 다음 계획 시작 모두 연결했고, 후자의 요약은 기존

## 18. 원본 조정 전환과 저장 절차 연결

- `prepareSourceAdjustmentOffer`는 현재 원본에서 직접 허용된 모든 전환만
  가져온다. A/B 고정 짝, 역방향·연쇄 변경 허용, 자기 자신으로 바꾸는 가짜
  선택지는 만들지 않는다. 원본의 정책 수명과 근거 참조를 그대로 유지한다.
- 같은 종목의 명시적 RACE_PACE placeholder에 현재 record anchor 참조를
  연결하고 현재 후보/슬롯 revision을 별도 문맥 지문으로 묶는다. 개인 목표 초
  계산·거리/시간 환산·회복값 변경을 이 모듈에서 새로 수행하지 않는다.
- `createSourceAdjustmentCommitAdapter`는 기존 controller/host와 연결한다.
  설명을 정확한 원본 구성에서 가져와 resolved 구성에 결속한다. 운영자가
  제공하는 현재 계정·안전·후보 허용 판정을 진입과 저장 잠금 안에서 재검사한다.
- 저장 직전 원본 authority로 offer/receipt를 다시 계산한다. 기다리는 사이의
  만료·철회·후보 revision·허용 상태 변경은 저장 0건과 기존 snapshot 보존으로
  처리한다. 같은 명시 요청의 재시도는 한 번만 저장한다.
- 합성 구성으로 연결 대상 3파일 50 PASS를 직접 확인했다. 실제 운영 조정값,
  개인 새 페이스, 운영 정책은 추가하지 않았다. owner가 제공할 실제 저장소의
  잠금/원자성이나 공개 조정 여정의 완료를 이 결과로 주장하지 않는다.
- 전체 앱 286파일 / 2,518 PASS, TypeScript 및 build PASS. revision 결속을
  제거하면 2 FAIL로 검출됐고, 정상 복원 후 대상 50 PASS를 재확인했다.
- 전체 회귀 결과와 추가 검수는
  [원본 조정 연결 검토 보고서](../review/SOURCE_ADJUSTMENT_COMMIT_ADAPTER_REVIEW_2026-09-06.md)에 기록한다.

정확한 구성 채택, 사용자 조정·복원·일지 비교의 종단 검증이다. M01~M16의
미완 항목을 삭제하거나 전체 완료로 바꾸지 않는다.

## 19. 임시 조정 초안의 저장·복원

- 버전 1 envelope로 현재 후보의 원본 baseline과 적용된 workspace snapshot을
  현재 탭의 계정별 sessionStorage 한 항목에 보관한다. 확정 계획·archive·서버

- 복원은 현재 후보에서 독립적으로 가져온 baseline 및 현재 authority를 기준으로
  한다. 저장된 policy를 승인 근거로 읽지 않으며, 변경된 상태는 기존 controller의
  정확한 replay 검사로 숫자·설명·receipt·revision을 다시 검증한다.
- 기존 mutation lock 안에서 단일 키 비교/쓰기/재확인한다. 저장 실패는 성공으로
  알리지 않고, 손상·다른 버전·다른 후보의 바이트는 자동 삭제/덮어쓰기하지 않는다.
- 계정 전환은 열린 handle을 무효화한다. 익명 초안의 자동 계정 이전은 없다.

- 연결 4파일 68 PASS. 새 session 계약 시험 18개에는 source offer → source

위치, 이전 원본 지문, 실제 결과별 횟수, 미응답 수, 넘어갈 수 있는 이유를 담는다.
모두 응답한 경우와 표시 기간이 지난 경우를 구분한다. 후자는 미기록을 완료로
바꾸지 않는다. 날짜는 현지 달력으로 비교하고 오전/오후를 별도 슬롯으로 센다.
9.5일 실시간 경과의 검증이나 훈련량 변경 권한으로 해석하지 않는다.

계약 v0.17 §20.4에 반영했다. 신규 8개를 포함한 관련 3파일 32 PASS 및 타입 검사
PASS. 실제 생성 fixture를 확장해 7/9/10일·일 2회 구성을 검증했다. 무저장,
계보 보존, 완료/기간 경과/통증/현재 위험/변경된 원본/근거 없음/미래 시작/과거
시작일/접근자 입력 차단을 확인했다. 합성 fixture는 운영 승인으로 등록하지 않았다.

이 함수는 아직 실제 다음 주기 화면·저장 거래에 연결되지 않았다. 다음 구현은

reader가 초기 주기 전용으로 제한된 부분도 함께 확장해야 한다. 기존 제한을
단순 제거하면 계보 초기화 또는 검증 우회가 되므로 저장/읽기 시험을 함께 요구한다.
운영 resolver/정확한 수치 최종 승인/서버·백업/전체 브라우저 검수도 여전히 남는다.

출력은 일반 generated 결과와 구분되는 adjusted_next_frame_draft이며 전용

## 44. 다음 조정 계획 선택·보관·저장·과거 읽기 거래 (2026-09-07)

selectAdjustedPlanSuccessor와 saveSelectedAdjustedSuccessor를 추가했다. 실제 이전
v4를 보존 근거로 읽고, 예상 지문/현재 안전/기존 통증/종목/진행 횟수 일치와 새
후보의 기록·전체 배치 검토를 재확인한다. 초기 선택 함수는 여전히 successor를
거부한다. 이전 원본 보관과 새 active 저장은 같은 계정 mutation lock 아래에서
수행하고 두 키를 확인한다. 실패 시 자신의 쓰기만 되돌리며, 다른 탭의 값은
덮어쓰지 않고 상태 불확실로 보고한다. 이미 바뀐 predecessor 재요청은 STALE_BASE로
거부하므로 다음 계획의 진행을 초기화하지 않는다(재요청 성공 영수증은 아님).

불변 선택에 continuation을 선택적으로 추가했다. 초기 선택은 기존 형식을 유지한다.
successor는 이전 envelope/selection 지문과 이전 periodization을 보존하고 전진한다.
historical reader는 이 메타데이터와 처방을 재구성한다. 이것이 전체 보관 사슬의
독립 서명 검증은 아니며, 로컬 지문이나 주기 메타데이터는 처방/실행 권한이 아니다.
실제 이전 원본과의 결속은 저장 거래에서 수행한다. 계약 v0.19 §20.6에 명시했다.

AdjustedPlanEditFlow 및 최종 확인 화면에 predecessor 문맥을 전달하는 경로를
연결했다. 다음 계획 저장 문구는 이전 계획 보관/전환임을 알리며, 초기 조정의
"다른 날짜는 그대로" 문구를 잘못 재사용하지 않는다. 화면을 연 뒤 predecessor가
바뀌면 저장을 거부한다. 상위 일정→다음 후보 진입점과 운영 공급자는 아직 남는다.

검증: 관련 11파일 96 PASS, 타입 검사와 production build PASS. 추가로 같은
시험에 새 주기 일지 저장/ACTIVE 원본 읽기를 넣은 후 successor 9 PASS를 재확인했다.
실제 생성→최종 확인 화면→저장, 이전 일지 ARCHIVED 읽기, 새 일지 ACTIVE 읽기,
1→2→3 주기 계보와 두 이전 원본 보관, 보관/active 쓰기 실패, 다른 탭 개입,
취소/계정 변경/검토 철회/안전/손상 보관/초기 API 우회를 검사했다. 시험용 근거는
운영 등록하지 않았다. 전체 앱/실브라우저/배포 검수 완료로 확대해서 주장하지 않는다.

운영 준비 검토 사항: 현재 whole-frame scope는 continuity 결과 횟수와 exposure
ledger fingerprint까지 포함한다. 운영 채택안을 선수별 일지 횟수/날짜마다 다시
승인하는 구조로 만들지 않도록 검토 가능한 구조 범위와 개인별 fresh 검증을
분리해야 한다. 기존 보존 정책 버전의 역사 읽기는 유지하면서 정리할 후속 사항이다.
새 수치 최종 승인, 운영 resolver, 상위 다음 주기 화면 연결, 서버/백업 및 전체
사용자 여정 검수는 남으며 M01~M16 전체 완료/병합/배포를 선언하지 않는다.

## 45. 오너 최종 승인 경로와 재사용 가능한 구성 검수 범위 (2026-09-07)

오너 응답은 `근거 검토 후 내가 최종 승인`이다. 기존 결정 문서의 절차 승인을
재확인했으며, 아직 제시하지 않은 구성의 수치 승인으로 확대하지 않았다.

계약 v0.20 §20.7과 STRUCTURAL_V2 검수 범위를 추가했다. 종목/인구집단/경험/
선택권한/프레임/모든 날짜·오전오후 배치/구성 버전/보조 훈련량/MAIN 횟수는
유지한다. 이전 주기 종류는 유지하되 개인별 완료·휴식 등 횟수와 노출 식별자는
재사용할 구성 검수 지문에서만 제외한다. 전체 후보/스냅샷과 실제 저장 전 검증은
여전히 원본을 결속하므로 이 변경은 개인별 안전 검사나 전진 조건을 생략하지 않는다.
기존 정책은 버전 필드 없이 v1로 읽는다. 새 범위를 적용하려면 명시적 v2 정책과
그 범위의 별도 채택이 필요하며, 알 수 없는 버전/복수 일치 정책은 거부한다.
운영 registry는 계속 비어 있고 신규 활성화는 없다.

§44의 날짜 관련 추정을 정정한다. 실제 현재 exposure 식별자는 주기 내 일자
번호이며 절대 날짜가 아니다. 시작일만 바꾸면 기존 v1 검수 지문도 유지된다.
실제 문제는 이전 결과 횟수가 구성 검수에 포함되는 점이었다. 실패한 합성 테스트의
입력을 실제 후보 스키마와 대조해 확인했으며, 스키마를 느슨하게 바꾸지 않았다.

검증: 관련 11파일 100 PASS, 타입 검사 PASS. 실제 저장된 이전 계획의 한 결과를
COMPLETED에서 RESTED로 바꾸고 기존 생성기로 다음 후보를 다시 만들었다. 새
구성 검수 지문은 같고 개인 후보 지문은 달라짐을 확인했다. 초기/후속 저장 및
과거 읽기 회귀 검사도 포함한다. 중간 실행에서는 저장 테스트 1건이 5초 제한을
초과했다. v1 정책에도 v2 검사를 불필요하게 반복하던 코드를 제거하고, 테스트
제한을 늘리지 않은 동일 명령으로 100개 통과를 확인했다.

남은 작업은 상위 일정에서 다음 후보·편집·확정으로 이어지는 화면 연결, 정확한
구성/대상/한계를 담은 최종 채택 패킷, 승인 후 운영 공급자 연결, 서버/백업,
전체 사용자 여정 및 독립 검수이다. 이번 범위는 전체 계획 완료나 공개 배포가 아니다.

## 46. 실제 일정에서 다음 주기 비교·편집·최종 저장으로 연결 (2026-09-07)

PlanBeta의 조정 일정에 `다음 주기 준비` 진입점을 연결했다. 새 화면은 시작일,
현재 몸 상태, 명시적으로 고른 경기 기록을 받아 실제 successor 생성기를 사용한다.
기존 기록 선택을 자동 재사용하지 않는다. 생성 전/편집 진입 전 계정과 이전 전체
상태 지문을 다시 읽으며, 계정·storage 이벤트는 열린 초안을 닫는다. 후보 비교와
날짜별 오전/오후 처방을 확인한 뒤 검토 공급자가 일치하는 후보만 편집기로 넘긴다.
공급자 없음/불일치 상태는 안내하고 legacy 저장으로 우회하지 않는다.

초기 후보와 다음 후보의 공급자 문맥 비교를 공통 함수로 묶었다. generated,
candidate, intake, athlete evidence, gate, current check, start date가 모두 맞아야
진입한다. 편집 후 별도 최종 저장에서 이전 원본 보관과 새 active 전환 거래를
호출하고, 성공하면 실제 새 일정으로 돌아온다. 취소는 이전 원본을 그대로 보존한다.
기존 smooth scroll/reduced-motion 훅으로 질문·비교 화면 진입과 키보드 초점을 연결했다.

실제 연결 시험 중 화면의 stale 검사에 저장 전 원본 읽기를 넣으면 거래가 자신의
정상 active 쓰기까지 외부 변경으로 오인해 롤백하는 문제가 재현됐다. 화면의
현재성은 계정/마운트/열린 predecessor로 제한하고, 저장 바이트 재검사는 실제
거래의 CAS가 담당하도록 수정했다. 최종 확인 후 다른 writer가 바꾼 값은 여전히
거부하고 보존하는 반례를 추가했다. 거래의 원본 검사 자체를 제거한 것이 아니다.

검증: 실제 PlanBeta 일정→다음 생성→조정 editor→최종 확인→보관/저장→새 일정
통합을 포함해 화면 4파일 17 PASS. 취소, 검토 없음/다른 날짜의 잘못된 provider,
현재 통증, 이벤트 없이 변경된 저장소, 계정 전환, 최종 확인 후 외부 쓰기를 검사했다.
타입 검사 포함 production build PASS. 기존 폰트 unresolved/500kB 번들 경고는 남는다.
실제 브라우저의 320/375px·200% 글자·키보드/모션 전체 검수는 아직 하지 않았으며
컴포넌트 시험을 이를 대체하는 증거로 쓰지 않는다.

M06~M10/M14의 상위 화면 연결은 전진했지만 운영 registry는 여전히 비어 있다.
따라서 현재 공개 사용자에게 새 조정 구성을 제공했다거나 전체 MAIN 다중 구성이
완료됐다고 하지 않는다. 다음 우선 작업은 정확한 채택 패킷/실제 운영 공급자,
검토용 브라우저 시연과 전체 여정, 서버/백업 및 M01~M16 잔여 조건이다.

## 47. 조정 계획 개인 보관 파일과 읽기 검증 (2026-09-07)

기존 일지 공유/전체 백업 형식에는 조정 계획 원본이 없음을 확인했다. 개인 페이스
근거를 기존 공유 파일에 자동 혼합하지 않고 별도 personal-backup.v1을 추가했다.
활성 v4와 최대 18개 보존 archive를 함께 검증·내보낸다. 계정과 두 저장 키를 읽기
전후 대조하고, 손상된 archive는 누락 처리하지 않고 전체 내보내기를 거부한다.
원본과 export 시각/전체 지문을 검증하며 앱 외부로 전송하거나 메모를 읽지 않는다.

파일 읽기는 앱이 별도로 보존한 근거로 각 계획을 재검증한다. 파일 안에 쓰인 검토
문구나 지문만으로 권한을 만들지 않으며 결과는 read_only/NONE/NOT_RESTORED다.

먼저 취급한다. 18개를 넘으면 기존 자료를 잘라내지 않고 거부한다. 쓰기 전후 계정/
active/archive/request를 대조하고 실패 시 자신의 쓰기만 되돌린다. 기존 지문이

동일 선택 재요청 반환 직전에도 검사하도록 수정했다. 실패 시 자기 쓰기만 되돌린다.
수정 후 최초 저장·V3 선택/저장·편집 흐름 3파일 27 PASS.

## 77. 실제 생성된 RPE MAIN의 상세 후보 연결

원본 후보 검증은 유지하면서 QUALITY 주소 확인을 공통화했다. 기존 페이스 경로는
PACE_TARGET 제약을 유지하고 새 RPE 경로는 정확한 구조적 binding review를 따로 요구한다.

다중 후보 조립기는 페이스 또는 RPE 입력을 각각 해당 검증기로 처리한다.

선수 기록 없는 실제 generatePlanFromDraft 결과에서 여러 QUALITY를 가져와 실제 V3
receipt/설명/주소 스냅샷을 만들고 다중 후보로 조립했다. 하위 검증 mock은 사용하지 않았다.
훈련 구성과 binding은 합성 TEST_NOT_APPROVAL이다. 관련 2파일 5 PASS에는 기존 격리
조립 시험도 포함되므로 전부 운영 검증으로 표시하지 않는다. 빈 binding, 만료, 주소 이동,
경험 변경, 중복 주소를 차단했다. 스펙 v0.47.

원래 전체 범위는 유지한다. 다음은 다중 전체 계획의 구조/노출/상호작용 검토와 명시적
저장 형식, 일지/후속 주기 읽기, 여러 MAIN UI, 운영 최종 승인 자료 및 공개 검수다.
RPE 상세 후보 연결은 구현됐지만 저장과 공개 완료는 아니다.

## 81. 다중 계획의 일지 원본 보관과 조회
