# ACCOUNT_STORAGE_PREKEY_READINESS_2026-09-08.md

## 범위

- 기준 커밋: `2509a173e564b7924d07903d138ff3603c150956`
- 이번 지시: 복구키 전에 가능한 대용량·모바일·동시 저장·PR/CI·독립 검수·운영 인수 준비를 끝까지 진행.

- 원본/미전송 자료 자동 삭제, 훈련 수치·강도·적격성·안전 기준 변경 없음.

## 개발 변화

1. 과거 이력 읽기에서 이미 검증한 원본을 물리 저장소에서 다시 읽는 단계를
   제거했다. 각 참조의 전체 논리 검증, 고유 ID/현재 포인터 확인, 순서가 있는
   전체 문서 해시는 유지한다. 3개 계획 회귀 시험에서 물리 저장소 읽기는
   18회에서 12회로 줄었다. 이것을 응답 속도 33% 향상으로 해석하지 않는다.
2. 마지막에 모든 원본을 한 번에 다시 파싱하는 단계를 없애고 계획별 검증 후
   전체 해시를 대조한다. 부분 결과는 전체 기록으로 공개하지 않는다.
3. `historyProgress`와 `cancelHistory()`를 추가했다. 중단은 조회 세대를 폐기하며,
   현재 계획·기기 암호화 자료를 삭제하지 않는다. 늦은 실패/성공은 무시한다.
   이미 시작한 HTTP 요청이 즉시 중단된다고 보장하지 않는다.
4. 대용량 무손실 검사에는 실제 100개 원본 생성·기존 파서 검사가 포함된다.
   CI 병렬 부하를 감안해 해당 검사 한정 제한을 120초에서 240초로 조정했다.
   검사 개수·본문 단언은 유지했고, 제한 변경 자체는 성능 개선이 아니다.
5. 새 Edge 함수의 설정 누락을 보완했다. 기존과 같이 함수 내부 `auth.getUser`
   검증을 사용하며, 익명·만료·계정별 RPC 권한 검사를 우회하지 않는다.

첫 fault config는 배열 병합으로 불필요한 다른 파일까지 수집하여 중단했다.
include를 정확한 한 파일로 제한한 뒤 위 두 결함을 다시 실행해 확인했다.

## 최종 결과 연결

### 추가 독립 검수 발견

- P1: SDK가 세션을 다시 읽는 사이 저장 시작 계정과 전송 토큰의 계정이
  달라질 수 있었다. collection API의 검증된 토큰 고정과 stage 의도 계정
  대조를 추가했고 같은 일지 API 경로도 수정했다. 실제 SDK와 gateway를 잇는
  합성 경합 시험 2건도 통과하며, 위 155건에 포함된다.
- P2: 취소된 이력의 HTTP 응답을 기다리느라 직렬 작업이 다음 조회를 막았다.
  조회 AbortSignal과 취소 경쟁 처리로 오래된 요청의 완료 전에도 재시도가
  시작되도록 보완했다. 네트워크 자체 취소와 늦은 응답 무시는 별도 방어다.
- P2: 부품 저장 후 manifest를 만드는 사이 중단되면 복구 요청이 숨겨졌다.
  모든 암호화 부품과 작업 의도를 먼저 단일 IndexedDB 트랜잭션으로 준비하는
  보완을 구현했다. 단편 부품만 존재하는 것을 완전한 복구본으로 표시하지 않는다.

독립 검수 담당자는 위 재현 관측을 전달했으나 이후 도구 오류로 최종 보고서를
완성하지 못했다. 따라서 이를 최종 독립 APPROVE로 표기하지 않는다. 수정 후
실행 결과와 추가 코드 검토는 별도로 기록한다.

### 모바일 및 실제 DB 증거

  현재 계획 유무별 취소 후 재시도, 늦은 계정 응답, 10개씩 렌더링을 확인했다.
- 100개 합성 V3 단순 이력은 약 2.92/2.91초였다. 복잡한 V6 100개와 실제
  저사양 휴대폰의 성능을 보장하는 수치가 아니다. 부모 작업자가 320px 캡처를
  직접 확인했다. 상세 실행/한계는 [모바일 보고서](ACCOUNT_PLAN_MOBILE_HISTORY_2026-09-08.md).
- 실제 PostgreSQL 시험은 부모 작업자도 독립 재실행했다. 서로 다른 writer
  PID 24012/22388와 observer 29068, 실제 advisory lock 대기 상태를 확인했다.
  CAS 단일 승자·동일 요청 재전송·기존 writer 전후 전환·소유자 격리 5건이다.
  임시 서버는 종료됐으며 설치된 서비스나 운영 DB는 변경하지 않았다.
- SQL 변조 5종과 실행 보호 시험은 [DB 실행 보고](../../supabase/tests/concurrency/RESULTS_2026-09-08.md)에 별도로 남겼다.

### 원자적 기기 준비본 검증 범위

전체 작업 의도와 모든 암호화 부품을 하나의 IndexedDB 트랜잭션에 기록한다.
원본 부품 게시 후 계정 전환으로 중단된 경우, 같은 계정으로 다시 열면 같은
operation ID의 PENDING 상태가 복원됐다. quota·transaction abort·scope close는
완전한 준비본 수용 전에 모든 payload/key 쓰기를 취소했다. 암호문 변조를 빈
기록으로 처리하지 않고 오류로 보존하며, 다른 탭은 기존 작업을 덮지 못한다.
실제 Chrome에서 100개 V3 계획의 202개 암호화 행이 각 물리 한도를 지키고
복구됨을 확인했다. 브라우저 저장소 강제 축출이나 물리 전원 차단 시험은 아니다.

### 추가 P2: Web Locks 없는 경합 경로

독립 검토에서 준비본 저장 중 다른 탭이 기준 manifest를 갱신하면 안전하게
충돌을 감지하지만 진행을 회복하지 못하는 저수준 재현을 발견했다. 자동 덮어쓰기나
원본 삭제를 추가하지 않고 production의 unlocked fallback을 제거했다.
모든 서비스 작업은 같은 owner Web Lock 안에서 전체 완료를 기다린다.
없는 API와 잠금 획득 실패는 요청/저장 전에 차단하며 명시적 브라우저 안내를
표시한다. 격리 단위 시험만 명시적인 runExclusive port를 주입한다.

실제 두 탭에서 A의 잠금 동안 B의 client 호출 0건과 대기 lock을 확인했고,
A 완료 후 B가 EMPTY로 정상 진입했다. 없는/거절된 잠금 각각 요청 0건,
새 IndexedDB 생성 0건을 확인했다. 재접속 복구도 저수준 read만 아니라 실제
서비스 hydrate에서 같은 PENDING 작업으로 확인했다. 최초 서비스 복구 시험은
합성 서버의 원본 부품 응답을 빠뜨려 INVALID였으며, 실제 서버 응답을 모사하도록
fixture를 고친 뒤 통과했다. 런타임 검증을 완화하지 않았다.

이 준비본 코드는 아직 미배포다. 저수준 buffer 직접 동시 접근은 지원 계약
밖이며, 이후 새 호출부는 반드시 서비스의 owner lock을 통과해야 한다.

최종 브라우저 통합 23건은 위 두 runner의 실제 실행이다. 독립 검수·원격 CI
결과는 해당 실행 뒤 PR에 SHA와 함께 기록한다.
첫 원격 브라우저 실행은 실패했다. 새 Vite 전용 시험 3파일이 일반 정적
preview runner에도 수집돼 시험 경로가 없는 서버에서 실행된 설정 누락이다.
기존 전용 시험과 같은 testIgnore 분리에 3파일을 추가했으며, 기존 CI의
전용 runner 실행은 유지했다. 일반 desktop 목록 163건과 전용 23건은 별개다.
라우팅 계약 5건으로 일반 runner 제외, 전용 runner 포함, CI 호출 연결을
고정했다. 실패 실행을 성공으로 재표시하지 않고 수정 SHA로 다시 검사한다.
서로 겹치는 검사 수를 합산하지 않는다. 빌드의 기존 폰트 경로·큰 청크 경고는
남아 있으며 이번 계정 저장 변경의 공개 화면/실기기 배포 증거가 아니다.
