## 2. 정확한 처방 연결

[새 4개 검토안](../review/DISTANCE_PRESCRIPTION_ADOPTION_2026-09-30.md)을 기존
`OWNER_REVIEWED_OPERATIONAL_ADOPTION` 경로로 연결했다. 새 우회 권한은 만들지 않았다.
현재 실제 생성 아티팩트는 `PREPARED_AWAITING_OWNER_DECISION`이다.

| 구성 | 목표 | 회복 | 본운동 거리 |
|---|---|---|---:|
| 5×800m | 현재 5000m RP | 반복 사이 120초 조깅 | 4km |
| 8×400m | 현재 5000m RP | 반복 사이 90초 조깅 | 3.2km |
| 2×(3×800m) | 현재 5000m RP | 반복 120초 / 세트 240초 조깅 | 4.8km |
| 4×1000m | 현재 5000m RP | 반복 사이 180초 조깅 | 4km |

목표 초는 `현재 5000m 기록 초 × 반복 거리 / 5000`이다. 목표 기록, 다른 종목,
전체 일지 평균 페이스를 대입하지 않는다. 내부 소수점을 보존하고 표시에만 반올림한다.
같은 목적의 기존 MAIN을 대체할 뿐 추가 세션을 만들지 않는다. 기존 4개 경기 페이스
상세 처방과 기존 LT 파일럿 등의 승인 상태는 별도로 유지한다.

새 구간의 60~300초·본운동 5000m 상한은 이번 제품 검토 범위이며 생리학적 경계가 아니다.
현재 사용자의 최근 주간량을 분석해 최적 반복 수를 산출한 것은 아니다. 가능 시간을
받으면 준비·정리까지 포함해 필터링하는 함수는 있으나 현행 간편 입력에서 시간이
전달되지 않으므로 모든 사용자에게 시간 적합성을 확인했다고 주장하지 않는다.

세트형은 회복을 늘려 재시작을 돕는 별도 대안이다. 총 회복 720초를 검증했고,
세트 경계에서 반복 회복을 추가로 더하는 오류를 막았다. 회복을 늘렸다고 효과가
같거나 누구에게나 쉬워졌다고 표시하지 않는다. 전체 소요시간은 기존 안보다 길 수 있다.

## 3. 실제 수행 기록과 평가

빠른 기록과 상세 기록에 선택식 `반복별 기록 남기기`를 연결했다.
세 구간씩 넘기며 실제 거리·초·회복·회복 방식을 남긴다. 빈 칸은 원래 계획값으로
채우지 않는다. 회복 0초는 직접 입력한 때만 0이며, 빈 값은 미기록이다.

비교에는 당시 계획 ID와 내용 지문이 필요하다. 계획과 같은 거리의 실제 구간만
목표 초와 비교한다. 전체 조깅 평균, 다른 거리나 누락된 구간은 대신 사용하지 않는다.
모든 반복을 기록했을 때 앞뒤 같은 개수의 평균을 제공한다. 홀수 가운데 반복은
앞뒤 평균에서 제외하되 전체 목표 비교에는 포함한다.

평가 예:
- `목표 222.3초, 앞 2회 평균 221초, 뒤 2회 평균 230초`는 관찰 사실이다.
- `목표보다 빠르게 출발한 뒤 뒤 구간이 길어졌으므로 첫 반복 속도를 확인`은 행동 안내다.
- `해당계 능력 부족 / 산화 능력 우수`는 이 자료만으로 판정하지 않는다.
- 회복을 바꿨다면 같은 조건의 결과로 취급하지 않는다. 당일 피로·날씨·코스는 확인할 항목이지 검출된 원인이 아니다.

통증·겹친 기록·원본 검증 미완료가 수행 해석보다 우선한다. 실제 수행 평가 화면의
계획·기록 탭과 이유 설명에 연결했으며, 반복 수치 수정은 남은 일정 교정의 근거
지문을 바꿔 예전 근거로 만든 변경안의 적용을 막는다. 새 능력 점수나 자동 증량은 없다.

## 4. 저장·프라이버시

- 기존 `exerciseLog`에 선택적 구조화 필드를 추가했다. 구형 일지는 그대로 읽는다.
- 다른 계획 지문, 동일 반복 번호 중복, 음수·무한대·원문 필드, 원본보다 큰 반복 번호를 차단한다.
- RESTED/SKIPPED와 수행 기록의 동시 저장을 거부한다. 원본을 찾지 못해도 이미 적은 기록은 보존하고, 사용자가 명시적으로 지울 수 있다.
- 운동 구성 편집은 반복 기록을 보존한다. 메모·제목·자유 운동명은 평가 및 교정 근거 지문에서 제외한다.
- 서버 일지/계정 상태/계획 저장 검증기를 같은 소스로 재생성했다. 원본과 서버 검증기 모두 소수점·0초·잘못된 연결을 시험했다.
- 운영 DB나 계정에 실제로 저장한 시험은 아니다. 프런트만 먼저 배포하면 새 필드를 구 서버가 거부할 수 있으므로 서버 검증기와 함께 릴리스해야 한다.
