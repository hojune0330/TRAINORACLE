# 종목별 기록 기반 페이스 추천·계획 갱신 구현 현황

상태: `IMPLEMENTED_IN_PART_NOT_RELEASED`

이 보고서는 구현과 검증의 범위를 구분한다. 전체 계획 완료, 운영 DB 적용,
실계정 저장 성공, 공개 배포를 의미하지 않는다. 기존 동시 작업의 변경 파일은
삭제하거나 되돌리지 않았다.

## 1. 구현한 흐름

1. 7개 종목의 실제 기록·목표를 구분해 저장한다. 날짜를 모르면 null을 보존한다.
2. 최근 실제 경기, 최근 12개월 최고, 입력된 기록 기준 개인 최고를 구분한다.
   같은 날 다른 기록은 순서를 발명하지 않는다. 목표는 실제 최고 집계에 넣지 않는다.
3. 직접 환산은 원본 소수값을 유지한다. 신규 하프 계산 거리는 21097.5m다.
4. 구간별 기준 기록과 버전을 카탈로그 입력에 연결한다. 수동 고정값과 충돌하는
   이중 기준은 사용하지 않는다. 검토되지 않은 종목-훈련 조합을 자동 활성화하지 않는다.
5. 남은 훈련의 전후 초를 비교하고 명시적으로 적용한다. 반복·세트·거리·회복·일정은
   페이스 변경을 이유로 함께 바꾸지 않는다. 적용 가능한 미수행 슬롯만 변경한다.
6. 되돌리기는 당시 저장한 처방을 복원한다. 원본 경기 기록의 삭제·수정 때문에
   과거 처방을 다시 계산하지 않는다. 새 수행·일지가 생긴 슬롯은 보호한다.
7. 기록 저장 성공과 계획 비교 실패를 구분한다. 서버 확인 전 저장 성공을 표시하지 않는다.
8. Riegel 1.06은 실제 원본 기록에서만 계산하는 비교 기능이다. 예측을 다시 예측의
   원본으로 사용하거나 실제 PB/SB로 저장하지 않는다.

## 2. 현재 처방 연결 범위

| 기준 종목 | 직접 환산 계산 | 현재 숫자 처방 연결 |
|---|---|---|
| 800m | 구현 | 기존 MD-800-01 실제 기록 기반 10×200m |
| 1500m | 구현 | 기존 MD-1500-01 실제 기록 기반 3×500m |
| 3000m | 구현 | 기존 MD-3000-01 실제 기록 기반 4×800m |
| 5000m | 구현 | 기존 V2-SEED-05 및 카탈로그 LT/VO2 참조 |
| 10km | 구현 | 동일 종목 RP 3개 구성 연결 구현, 전체 여정·운영 확인 전 |
| 하프 | 구현 | 동일 종목 RP 3개 구성 연결 구현, 21097m 계획 입력·21097.5m 계산 호환 확인 |
| 마라톤 | 구현 | 동일 종목 RP 3개 구성 연결 구현, 전체 여정·운영 확인 전 |

기존 legacy PACE_TARGET 경로의 목표기록 적용은 아직 미완료다. 새 카탈로그의
목표 참조는 5km LT/VO2와 새 동일 종목 장거리 RP 구성에 연결했다. 이것은 다른 종목 예측의 채택 문제와
다르다. 직접 기록 연결을 더 구현해야 하는 항목이며, 예측 승인 대기로 설명하지 않는다.

장거리 RP는 기존 117개와 별도로 9개를 추가해 총 126개로 생성한다. 기존의
2×4분·3×7분·5×1km 구성과 반복 사이 60초 조깅을 재사용하며, 해당 속도를
LT 또는 VO2 강도라고 재분류하지 않는다. 첫 계획에서 총시간이 달라지면 적용 전에
변경 전후 시간을 표시한다. 새 구성은 미수락 초안에서만 제안하고, 기존 계획의
기록 갱신으로 구성·회복·운동량을 함께 바꾸지는 않는다.

## 3. 화면 검수에서 추가 수정한 점

- 첫 추천 요약에 RP 약어뿐 아니라 실제 반복 목표 초를 표시한다.
- 계획에 `기준 기록·페이스 바꾸기` 진입점을 제공한다.
- 기존 경기 기록에서도 변경 미리보기를 열 수 있다.
- 변경 미리보기 중 입력 폼과 기록 목록을 함께 펼치지 않는다.
- 상세 일정·일지·계획 요약의 목표 표시를 0.1초로 맞춘다. 원본 계산값은 보존한다.
- 접힌 상세 화면에도 기준 종목·기록 종류·시간을 한 줄로 표시한다.
- 구간 순서도에서도 실제·목표기록 환산을 `직접 정한 목표`로 오표시하지 않는다.
  구간 초는 0.1초, km 페이스는 초 단위로 표시하며 저장한 원본 값은 바꾸지 않는다.
- 오래된 표시 자릿수 설명을 현재 표시 정책과 구분해 수정한다.
- 기록 화면의 padding으로 발생한 가로 넘침을 수정한다.
- 실제 계산값이 달라지지 않는 기록 재선택은 불필요한 변경 알림을 만들지 않는다.

## 4. 검증 증거와 경계

후속 장거리 연결의 집중 검사: 초기 추천 27개와 동일 종목 RP 계산 21개,
총 48/48 통과. 실제·목표기록, 3개 장거리 종목, 원본 소수값, 회복 불변,
잘못된 기준 종목 거부, 하프 별칭, 적용 전 시간 변경 자료를 포함한다.
새 RP 환산에도 기존 직접 입력의 120~1800초/km 허용 범위를 적용하며,
범위 밖의 실제·목표 기록은 적용 불가로 처리한다. 이 수치는 제품 입력 경계이지
개인의 생리학적 적합성이나 경기 기록의 진위를 판정하는 기준이 아니다.
이는 24개 전체 브라우저 여정이나 운영 저장 성공을 뜻하지 않는다.
아래 전체 타입 검사·빌드 결과는 이 후속 변경 전의 결과다. 목표기록·서버 통합이
진행 중이므로 최신 전체 타입 검사·빌드·배포 결과로 재사용하지 않는다.

부모 작업에서 실행한 집중 검증:

- 기록 계산·선택·카탈로그·초기 연결·계획 갱신·기존 편집·입력·확인 UI: 373/373.
- 첫 추천 요약과 실제 실행 표시: 13/13.
- 훈련 표기와 페이스 변경 확인 UI: 22/22.
- 경기 기록 입력 및 기존 경계: 21/21. 날짜 미입력 및 하프 정확 거리 포함.
- 추천 근거·훈련 설명·실행 표시: 34/34.
- 로컬 PostgreSQL 호환 실행(PGlite): 4/4. source revision 충돌, 재시도,
  삭제 원본, 권한 제한, collection commit을 검사했다. journal guard가 없는
  신규 계획의 pace-only guard도 적용하며, 두 guard가 모두 없거나 journal guard가
  현재 자료와 다르면 거부한다. 원본 기록 수정 뒤 lost-ACK 재시도도 중복 반영하지 않는다.
- 서버·스키마·계정 API 최종 묶음: 144/144.
- 계정 source revision 전달·재시도 담당자 최종 묶음: 156/156.
- 갱신·되돌리기·캐시 충돌 담당자 최종 묶음: 115/115.
- 앱 전체 타입 검사: 통과. 프로덕션 모드 빌드: 통과(운영 배포 아님).
  기존 폰트 URL 빌드 경고와 큰 청크 경고는 남아 있으며, 이 빌드로 실제 폰트 제공이나
  운영 환경 설정·로그인 저장을 검증했다고 주장하지 않는다.

검증 묶음 사이에 중복 테스트가 있다. 이 숫자를 합쳐 고유 테스트 총수로 보고하지 않는다.
구간 표시 최종 패치 이후 카탈로그 기준·갱신 집중 검증은 162/162 통과했다.
오늘 미수행 슬롯 허용 및 당일 진행 기록 보호를 추가한 단일 회귀 사례도 통과했다.
후자의 선택 실행은 1개 통과·98개 미실행이며 전체 재실행 통과를 뜻하지 않는다.

브라우저의 합성 게스트 기록으로 확인한 실제 경로:

`800m 2:01.5 입력 → 10×200m 생성 → 30.375초 원본/30.4초 표시 →
800m 2:04 등록 → 30.4초→31초 비교 → 적용 → 되돌리기 → 다시 적용 →
달력 상세에서 31초와 기준 기록 확인`.

320px에서 main/기록 화면의 scrollWidth와 clientWidth가 같았다. 375px에서도
적용 성공 및 상세 훈련 표시를 확인했다. 이는 운영 계정, 200% 글자 확대,
24개 전체 브라우저 여정, 실제 선수 검증을 대신하지 않는다.

## 5. 완료로 합산하지 않는 남은 항목

1. 10km·하프·마라톤의 새 동일 종목 RP 연결을 전체 초기 생성·갱신·일지 여정에서 확인.
2. legacy 중거리 PACE_TARGET의 목표기록 전용 저장·근거 어댑터는 구현했다.
   게스트 목표 저장과 다음 주기 파서도 연결했으며, 전체 브라우저 여정 재확인은 남아 있다.
3. 24개 합성 페르소나의 입력→수정→일지→다음 주기 전체 여정 검수.
   기존 24개 초기 연결 단위 사례를 전체 여정이라고 부르지 않는다.
4. 온라인 최초 계획·다음 주기·PACE_REFERENCE 갱신은 source revision 검사를 연결했다.
   그 외 catalogReplacement·executionReplan·일반 편집이 새 기준을 도입·변경·이동하는
   경우에도 source guard 전달과 서버 검사를 구현했다. 최신 스키마로 생성한 서버
   validator와 통합 검사는 진행 중이며, 운영 적용을 완료한 것으로 합산하지 않는다.
   역사적 처방의 같은 위치 조회·진행 기록·정확한 복원은 별도로 취급한다.
5. 운영 SQL0046 및 관련 서버 함수 적용, 실제 로그인 계정의 저장·재열기 확인.
6. 현재 동시 변경 묶음과 통합한 정확한 릴리스 커밋 검수, PR·병합·공개 배포.

새 종목 간 예측 처방 채택 목록은 0개다. 비교 제공과 처방 활성화는 별도 상태로 유지한다.

오늘의 슬롯은 날짜만으로 제외하지 않는다. 아직 시작하지 않았다는 명시적 확인과
진행·일지 보호 검사를 모두 통과해야 적용한다. 과거 날짜·수행 기록이 있는 슬롯은
보존한다. 실행 계약의 오래된 `오늘도 제외` 문장은 현재 구현 및 승인 방향에 맞게 고쳤다.

## 7. 통합 후속 수정

- 게스트 목표기록을 실제 경기와 분리 저장하고, 새 하프 기록은 21097.5m로 보존한다.
- 계획에서 경기 기록 입력으로 이동하면 해당 계획 종목을 초기 선택한다.
- 새 기록을 저장했지만 구성·시간 조건 때문에 적용하지 못하는 경우, 이유와 제외한
  훈련을 보여준다. 기록 저장 성공과 계획 갱신 성공을 혼동하지 않는다.
- 표시 초가 같아도 실제 기록에서 목표기록으로 바꾸는 명시적 선택은 근거 변경으로
  취급한다. 레거시 참조가 없는 경우도 정상 처리한다.
- 후속 집중 검사: pace-plan-update 111/111, 적용 불가 안내 UI 2개 각각 1/1.
  계정 기준 기록 UI 파일도 통과했다. 서로 다른 시점의 묶음은 총수로 합산하지 않는다.
- 24개 전체 여정의 직전 실행은 13개 통과·11개 실패였다. 목표 저장·하프 거리 결함을
  수정했지만 아직 재실행 전이다. 장거리의 느린 새 페이스가 기존 시간 예산을 넘는
  사례는 정상 적용 여정과 별도 거부 여정으로 구분해야 한다. 시간 제한을 완화해서
  테스트를 통과시키지 않는다.

## 8. 2026-10-03 릴리스 통합 체크포인트

- 최신 확인 main `64774e30` 기준의 `codex/multi-event-pace-release-20261002`
  작업폴더로 기능 변경을 분리했다. 이미 병합된 달력·꾸미기는 유지하고, 별도 진행 중인
  RestoreBackup 및 DeviceJournal 보완은 이 릴리스에 복사하지 않았다.
- 공유 node_modules 경로의 파일 소실로 검증이 중단되어, 릴리스 app에 lockfile 기준
  독립 의존성 404개를 설치했다. 다른 작업폴더의 연결이나 의존성은 변경하지 않았다.
- 독립 설치 후 릴리스 타입 검사 및 diff 검사 통과. GitHub 기존 인증 유효 확인.
- 승인된 현재 시간 예산보다 짧은 RP 갱신을 오거부하던 정책을 수정했다.
  해당 담당자의 관련 182개 검사와 전용 KST 17개 검사가 통과했다. 숫자는 중복 합산하지 않는다.
- 일반 CATALOG 편집 재검증에도 기존 승인 시간을 재사용하게 수정했다.
  실제 증가 여부와 추가 동의 검사는 계속 유지한다. 서버 validator 3종 재생성과
  일치 검사가 통과했다. 릴리스 작업폴더에서 source guard 28/28, 계정 기록 서비스
  55/55, gateway 선별 18/18이 UTC·KST 각각 통과했다. 이는 합성 검증이며 운영
  데이터 저장이나 로그인 왕복 증거를 대신하지 않는다.
