## 1. 무엇을 개선했나

새 상세 계획은 준비운동, 가속, 본운동, 반복/세트 사이 회복, 정리운동의
순서를 처방 안에 함께 저장한다. 저장 후 다시 열거나 백업에서 읽어도 같은
구조를 사용한다. 화면의 순서도와 실제 처방 숫자가 서로 달라지는 것을 막는
후속 기반 작업이다. 기존 네 종목의 반복 수, 페이스, 회복량은 바꾸지 않았다.

이번 증분을 '서로 다른 MAIN 두 방법 완성'이라고 부르지 않는다. 새 템플릿의
정확한 구성과 적용 범위를 채택하고 연결하는 작업은 여전히 남아 있다.

## 2. 스펙과 구현 경계

- [처방 계약](../../specs/reconstruct/TRAINING_SESSION_PRESCRIPTION_CONTRACT.md)
  §12.5를 먼저 추가했다. 독립 처방을 하나 더 저장하는 것이 아니라 원래 처방과
  정확히 일치해야 하는 V2 구조를 같은 fingerprint에 묶는다.
- `PaceTargetPlanPrescription.sequence`는 하위호환을 위한 선택 필드다.
  신규 생성은 저장하며, 기존 계획을 읽거나 진행 상태를 남긴다고 소급 추가하지 않는다.
- 앱 저장 검증과 코어 후보 선택 검증 모두 구조 파서와 원본 대조를 수행한다.
  확인값을 다시 계산했더라도 승인 구성과 달라지면 거부한다.
- 기존 네 템플릿에는 별도 본운동 종료 회복이 없어 NOT_APPLICABLE로 명시한다.
  거리 회복을 시간으로 바꾸거나 회복 거리를 본운동 거리에 합하지 않는다.
- 설명 receipt와 후보 식별자는 기존 전체 처방 fingerprint를 통해 새 구조까지 묶는다.
  예전 처방, 식별자와 설명 receipt는 그대로 읽는다.
- START/RESTART의 기존 안전·승인 재확인을 유지한다. 구간별 타이머나 반복 완료
  체크 기능을 새로 만든 것은 아니다.
- 비공개 계정 백업 payload는 구조를 유지하고, 공개 요약 카드에는 구조나 기록
  참조를 추가하지 않는다. 계정/서버 기능은 새로 활성화하지 않는다.

## 3. 실제로 잡은 연결 문제

첫 통합 실행에서 저장 스키마는 새 필드를 허용했으나 코어 후보 파서의 엄격한
키 목록이 이전 형식만 받아 신규 계획 선택이 거부됐다. 코어에도 선택 필드를
명시적으로 연결하고 동일한 구조 대조를 넣었다. 조건을 느슨하게 풀어 통과시킨
것이 아니며, 알 수 없는 다른 키는 계속 거부한다.

기존 MAIN 비교 테스트는 비활성 비교용 숫자를 바꾸면서 이전 snapshot을 유지해
불일치가 됐다. 이 테스트 입력만 레거시 비저장 구조로 명시했다. 실제 저장 구조를
바꾼 경우의 거부 테스트는 별도로 추가했다. 과거 판정을 그대로 통과시키려고
제품의 불일치 검사를 제거하지 않았다.

### 결함 주입

반복 수, 운동 거리, 회복 시간/방식/단위, 종료 회복, 기록 참조, 준비/정리,
라벨 원문 10종을 바꾼다. 구조 문법은 유효하고 처방/후보 확인값도 다시 계산한
입력이다. 앱과 코어가 각각 거부하며 START/RESTART도 차단한다.

1. 앱의 원본 구조 대조를 일시 제거하자 10개 이름의 테스트가 실제 실패했다.
2. 원복 후 코어의 대조만 제거하자 동일 10개가 코어 판정 단언에서 실패했다.
3. 두 변경을 원복하고 집중 48개를 다시 실행해 전부 통과했다.

이 밖에 종료 회복 누락, V1/알 수 없는 버전, 알 수 없는 키, 빈 본운동을
거부한다. 잘못된 저장 파일은 원본 bytes를 남기며, 추정한 계획으로 덮어쓰지 않는다.
Terra의 코어 V1 주입도 7개 실패 후 원복/통과로 보고됐으나 부모의 위 두 실측과
별도 기록이며 합산하지 않는다.
