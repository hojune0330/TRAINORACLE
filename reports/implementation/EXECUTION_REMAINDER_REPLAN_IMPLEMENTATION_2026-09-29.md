## 2. 실제 구현

| 구간 | 구현한 동작 | 하지 않는 동작 |
|---|---|---|
| 진입 | 홈 훈련 코칭에서 실제 수행 기록을 연 뒤 `남은 일정 조정` | 읽기만으로 일정 변경 |
| 확인 | 통증·이상 여부를 기본 선택 없이 확인, 이상/불확실이면 일지로 돌아가기 | 사용자의 한 번 확인으로 기존 D9 위험 해제 |
| 유지 | 원래 일정으로 복귀, 쓰기 없음 | 불필요한 계획 버전 추가 |
| 시간 줄이기 | 남은 RPE 시간형 훈련의 기존 시간 범위 최솟값을 선택 | 임의의 10% 감량이나 상세 반복 수치 발명 |
| 저강도로 교체 | 원래 계획의 저강도 구성을 재사용, 시간·RPE 상한이 증가하지 않을 때만 제시 | 거리형 처방을 추정 시간으로 환산 |
| 뒤로 옮기기 | 같은 오전/오후의 기존 운동 슬롯으로 이동, 원래 날짜는 휴식, 도착 날짜의 기존 저강도 운동 제거 | 쉬는 날에 추가 운동을 끼워 넣거나 두 주요 훈련을 같은 날 배치 |
| 비교 | 날짜·요일·오전/오후, 변경 전후의 시간·강도, 펼쳐 보는 남은 일정 | 바뀌지 않는 모든 설명을 첫 화면에 나열 |
| 적용 | 사용자가 적용을 눌러야 저장, 원래 계획/진행/일지 보존 | 미리보기 시점의 낙관적 저장 성공 표시 |

현재 정책은 조건을 만족하는 각 행동의 첫 변경안을 제공한다. 모든 날짜를 자유롭게 편집하는 도구나 현재 주기 전체를 최적화하는 알고리즘은 아니다. 같은 기록에서 체력 부족·과훈련·회복 완료를 추론하지 않는다.

## 3. 코드와 불변 조건

- [변경 규칙](../../app/src/domain/execution-replan-policy.ts): 버전이 있는 영수증, 정확한 재실행 대조, 오늘/과거/이미 기록한 슬롯 보호, 운동 횟수 보존 또는 감소, 주요 훈련 간격 및 오전·오후 동반 구성 보존.
- [변경안 생성](../../app/src/domain/execution-replan.ts): 현재 계획의 정확한 일지 연결, 중복·불완전·통증·과거 연결 거절, 실제 구조화 근거만 지문화. 자유 메모/제목/운동 이름은 내용이나 길이도 사용하지 않는다.
- [저장](../../app/src/domain/execution-replan-store.ts): 적용 직전 계정·날짜·계획·일지·통증·상세 처방 권한 확인. 계정 사용자가 기기 저장으로 우회하지 않는다.
- [화면](../../app/src/screens/plan-review/ExecutionReplan.tsx): 명시적 선택, 전후 비교, 저장 확인 후 성공. 저장 중 중복 클릭 방지. 계정이 바뀌면 닫는다.
- 변경 전 설명 영수증을 제거하고 새 처방으로 과거 설명을 위조하지 않는다. 기존 주기 계보·선택 권한·인테이크는 유지한다.
- 기기 보관함은 먼저 원본을 보관하고 현재 계획을 쓴다. 두 저장 키의 원자적 트랜잭션이라고 주장하지 않는다. 저장 실패 시 원본을 보존하며 보관함이 가득 차면 삭제하지 않고 멈춘다.
- `REPLAN` 보관본은 과거 일지 확인에 사용하지만 새 훈련 주기나 방법 수행 횟수로 중복 집계하지 않는다.

## 4. 온라인 저장 보호

추가 파일: [0040 마이그레이션](../../supabase/migrations/0040_execution_replan_journal_guard.sql).

1. 기존 HMAC 서명·계정 소유권·원자적 계획 저장 체계를 유지한다.
2. 계정에서 확인한 모든 일지 문서 ID와 버전 집합을 변경안에 묶는다. 원문 일지는 이 검사에 전달하지 않는다.
3. 서버는 일지 쓰기와 같은 계정 잠금을 잡고 일지 버전 집합을 대조한 후 계획을 저장한다.
4. 다른 기기의 새 기록·수정·삭제가 끼어들면 기존 제안 적용을 거절한다.
5. 이미 적용된 요청의 응답만 유실됐다면 이후 일지가 바뀌어도 같은 영수증을 확인한다. 중복 적용하지 않는다.
6. 현재 계획이 변경됐을 때 이전 계획과 진행을 보존하고, 새 스냅샷은 정확한 허용 변환인지 서버 검증기로 재검사한다.

서버 함수나 SQL이 미배포된 상태에서 웹만 올리면 계정 저장이 성공하지 않을 수 있다. 그러므로 프론트만 먼저 공개하지 않는다.

## 6. 자체 검토에서 반영한 개선

- 변경한 뒤에도 기존 비교 화면이 `계획은 변경되지 않았어요`라고 단정하던 문구를 `읽기만 해서는 일정이 바뀌지 않아요`로 수정했다.
- 현재 일정 버튼과 변경 버튼이 둘 다 주요 버튼으로 보이지 않도록 우선순위를 분리했다.
- 변경 전후에는 시간·RPE를 간결하게 표시하고, 중복 목적 문구와 긴 한계 설명은 접었다.
- 통증 선택 후 설명만 띄우는 막힌 흐름을 해당 일지로 돌아가는 행동으로 연결했다.
- 보관본을 새 주기/새 수행으로 세는 중복 집계를 제외했다.
- 화면에서 본 일지 버전만 믿는 클라이언트 검사에 그치지 않고 서버 트랜잭션 안의 버전 대조를 추가했다.
- 저장을 보낸 뒤 읽기 확인만 실패한 경우에는 원복하거나 실패로 단정하지 않고 재확인이 필요한 상태로 처리했다. 실제 저장은 남고 원본 일지도 해석되는 결함 주입 시험을 추가했다.
- 점프 접지 수와 좌우 구분의 변경도 근거 변경에 포함했다. 자유 운동 이름은 여전히 제외한다.

## 8. 수동 서버 배포 기록

- 대상: 기존 운영 웹이 사용하는 Supabase `texspxlpjungyarkvtkc` 프로젝트. 새 프로젝트나 자격증명을 만들지 않았다.
- SQL Editor에서 0040을 적용해 `Success. No rows returned`를 확인했다. 이후 함수/권한 조회는 `true / true / false`(존재/인증 사용자/익명 사용자)다.
- Edge Functions 기존 코드 편집기로 두 함수를 배포했다. 기존 환경변수·키·JWT 설정은 변경하지 않았다.
- 실제 배포 ZIP을 대조하자 기존 일지 핸들러와 레코드 검증기 두 파일도 main보다 오래된 상태였다. 이미 저장소에 반영된 현재 소스로 함께 맞췄다.
- 최종 배포 ZIP은 함수마다 8/8 파일이 로컬 소스와 일치했다. 파일 내용을 로그나 보고서에 복제하지 않고 일치 여부만 확인했다.
- 0039는 COROS 전용 변경으로 이번 기능의 선행 조건이 아니며 이 배포에 포함하지 않았다. 번호가 작다는 이유로 별도 데이터 수신 기능을 활성화하지 않았다.
- 운영 선수 기록의 조회·수정·삭제, 메모 원문 열람, 키 값 조회는 수행하지 않았다. 배포 성공과 실제 로그인 계정의 저장 왕복 검증은 서로 다른 증거다.
