## 2. G-1 — 삭제된 일지의 부활 결함 (수정 완료)

### 2.1 결함을 먼저 증명했다

기획서를 믿지 않고 재현 테스트를 먼저 썼다. 결과:

```
AssertionError: expected [ { id: 'a', …(11) } ] to have a length of +0 but got 1
```

**원인**: `mergeEntries`가 "한쪽에만 있으면 보존"하도록 되어 있어서,
로컬에서 지운 일지의 서버 사본이 다음 동기화에 그대로 되돌아왔다.
사용자가 지운 기록이 돌아오는 것은 **삭제권 위반**이다.

### 2.2 수정

| 파일 | 변경 |
| --- | --- |
| `domain/account/tombstone.ts` (신규) | 삭제 기록부. 키 `trainoracle.sync.tombstones.v1`, 상한 500건 |
| `domain/journal-store.ts` | `deleteEntry`가 **로컬 삭제 성공 시에만** tombstone 기록 |
| `domain/account/sync.ts` | `mergeEntries`에 `deletedIds` 예외 추가 (LWW보다 삭제가 우선) |
| `domain/account/sync.ts` | `syncNow` 5단계 — 서버에도 삭제 전파, `SyncOutcome.deleted` 노출 |

**최소 수집**: tombstone에는 `{id, deletedAt}`만 남긴다. 날짜·수치·메모는
남기지 않는다 — 지운 기록의 내용을 삭제 기록부에 다시 적으면 삭제한 의미가 없다.

**실패 가시화**: 서버 삭제가 실패하면 조용히 성공으로 처리하지 않고
"지운 일지를 서버에서도 지우지 못했어요. 이 기기에서는 그대로 지워진
상태예요."라고 사실대로 알린다.

**마이그레이션 불필요**: `0001_journal_sync.sql`에 이미 `own rows delete`
RLS 정책이 있어 서버 스키마 변경 없이 동작한다.

### 2.3 검증

- 신규 계약 테스트 14건 (부활 방지 4 / `deleteEntry` 연동 3 / 최소 수집 1 / 저장 견고함 6)
- 기존 동기화 테스트 17건 전부 그대로 통과

## 3. G-2 — 백업 되돌리기 (구현 완료)

### 3.1 문제

앱은 JSON 백업을 **두 종류** 내려주고 "이 기기에만 저장돼요"라고 안내한다.
그런데 그 파일을 **다시 넣을 경로가 없었다.** 백업을 권하면서 복원을 주지
않는 것은 지키지 못할 약속이다.

### 3.2 발견한 더 나쁜 사실

안전 백업(`trainoracle.journal.v1`)은 `memo`/`note`/`memoPurpose`를 **일부러**
제거한다. 그런데 일지 스키마는 `memo`(또는 `note`)를 **필수**로 요구한다.
즉 앱이 첫 번째로 권하는 백업 파일은 **애초에 100% 복원 불가**였다.

`withEmptyTextFields`로 해결했다. 하는 일은 "빠진 텍스트 자리를 빈 문자열로
되돌리는 것"뿐이다 — 없는 메모를 만들어 채우지 않고, 숫자·날짜·강도는
절대 손대지 않으며, 이미 값이 있는 필드도 덮어쓰지 않는다.

### 3.3 안전 설계

| 원칙 | 구현 |
| --- | --- |
| 지금 데이터를 날리지 않는다 | 기본 모드 `keep-existing` — 겹치는 일지는 손대지 않음. 덮어쓰기는 사용자가 라디오로 **직접** 골라야 함 |
| 지운 일지는 백업으로도 안 살아난다 | tombstone id는 복원 대상에서 제외 (동기화와 같은 규칙) |
| 검증 우회 금지 | 복원도 `parseJournalEntryForWrite`를 그대로 통과해야 저장됨 |
| fail-visible | 읽지 못한 항목 수·제외된 개수·실패 건수를 모두 화면에 표시 |
| 기기 로컬 | 파일은 이 기기에서만 읽고 어디로도 올리지 않음 |
| id 중복 방지 | 덮어쓰기는 append가 아니라 `replaceAllEntries` 교체 |

### 3.4 진입점 3곳 — 특히 빈 상태

복원이 **가장 필요한 순간은 일지가 비었을 때**(브라우저 정리·기기 변경)인데,
기존 내보내기 UI는 데이터가 있을 때만 렌더링된다. 그래서 빈 상태에도 넣었다.

| 위치 | testid | 이유 |
| --- | --- | --- |
| `EmptyJournalHome` | `open-restore-empty` | **핵심** — 브라우저를 지우고 온 사람이 처음 보는 화면 |
| `DeviceJournal` 내보내기 옆 | `open-restore` | 내보내기와 되돌리기를 같은 자리에 둠 |
| `Account` | `open-restore-account` | 로그인 여부와 **무관하게** 노출 (지우고 온 사람은 로그아웃 상태) |

### 4.3 이번 작업이 만든 새 후속 과제

1. **tombstone 상한 500건 초과 시** 가장 오래된 것부터 버린다 → 아주 오래
   전에 지운 일지가 다른 기기의 오래된 사본에서 되살아날 이론적 여지가 있다.
   실사용 규모에서는 도달하기 어렵지만 기록해 둔다.
2. **안전 백업 복원의 메모 공백**은 의도된 동작이다. 사용자가 "메모가
   사라졌다"고 느낄 수 있어 화면에서 미리 알리지만, 문구 효과는 미검증이다.
3. `SyncOutcome.deleted`는 값만 노출했고 **`Account` 화면 문구에는 아직 반영
   안 됨** — 동기화 결과 메시지에 삭제 전파 건수를 넣을지 판단 필요.
