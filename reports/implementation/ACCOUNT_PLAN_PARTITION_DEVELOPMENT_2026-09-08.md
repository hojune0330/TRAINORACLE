# ACCOUNT_PLAN_PARTITION_DEVELOPMENT_2026-09-08.md

## 이번 작업의 목적

복구키 보관은 오너가 다음 날 진행하기로 했다. 오늘은 운영 서버·실제 키를
변경하지 않고, 장기 훈련계획 보관의 개발을 진행한다. 키 보관 결정을 기다려야
코드를 만들 수 있는 것은 아니다.

## 구현 범위

| 구분 | 이번 구현 | 아직 연결하지 않은 것 |
|---|---|---|
| 데이터 분리 | 계획 원본, 진행 버전, 현재 계획·과거 참조 목록 | 실제 온라인 문서 저장 경로 |
| 복원 | V3/V4/V5/V6 기존 독자와 정확한 해시 대조 | 새 기기의 실제 로그인·온라인 복원 |
| 전송 순서 | 먼저 보관·재조회·대조, 마지막 참조 목록 전환 요청 | 서명 gateway와 실제 SQL 트랜잭션 |
| 충돌·재시도 | 같은 작업/계정/버전/전체 요청 영수증 대조 | 암호화 outbox의 새 작업 형식 연결 |
| 기존 문서 이전 | 원본 내용과 revision을 담는 정확 복사 요청 | 서버가 실제 원본 revision을 대조하는 구현 |

새 파일은 기존 운영 경로에서 import하지 않는다. 현재 앱 서비스의 단일 PLAN
문서 제한은 아직 그대로이며, 이 문서를 근거로 계정 저장 기능을 공개하지 않는다.
현재 스냅샷의 물리 한도는 올리지 않았고 과거 계획도 삭제하지 않는다.
기존 논리적 100개 이력 한도를 유지한다. 무한 보관을 구현했다고 표시하지 않는다.

## 구현 파일

- `app/src/domain/account/account-plan-collection-schema.ts`: 순수 분리·재조립과 무결성 검사.
- `app/src/domain/account/account-plan-collection-transfer.ts`: 전송 요청 고정, 계정 epoch 확인,
  재조회와 영수증 검증, 변경 전 현재 계획·목록 버전 대조 요청.
- 같은 이름의 `*.contract.test.ts`: 실제 버전별 합성 계획과 실패 경로 검사.

내용 해시는 인증이 아니다. 서버는 사용자 JWT, 소유자, 불변 부품, 정확한 참조,
이전 목록 revision, 이전 현재 계획, 기존 문서 revision을 다시 검증해야 한다.
전송 중 남은 부품만으로 현재 계획을 바꾸지 않으며, 읽어온 과거 근거만으로
훈련을 수행할 권한을 만들지 않는다.

## 검수와 발견

독립 코드 리뷰가 ACK 유실 후 재조회 실패를 일반 연결 실패로 내리던 결함을
찾았다. 영수증 조회가 끝나지 않았으면 `outcome_unknown`으로 유지하도록 수정했다.
동일 작업의 재조회가 성공해야만 계정 저장 확인을 반환한다.

`stale`도 서버 롤백 증거가 아니다. 계정 변경 후 응답을 버렸다는 뜻이며,
전송된 작업은 원래 계정의 outbox에 남겨 나중에 영수증을 재확인해야 한다.
로그아웃이 이미 전송된 서버 커밋을 취소했다고 표시하면 안 된다.

최초 전송 테스트는 18개 성공, 대량 V4/V5/V6 3개는 30초 제한을 넘었다.
같은 전체 계획을 중복해서 파싱하던 경로를 줄였다. 대량 합성 데이터 시험의
시간 제한은 120초로 분리했으며, 이를 UI 성능 합격 기준으로 사용하지 않는다.
실제 클라이언트 통합에서는 현재 계획 우선·과거 이력 지연 조회·백그라운드
검증이 필요하다. 한 번에 모든 근거를 UI 스레드에서 검증하도록 연결하지 않는다.

## 실행 증거

- 분리/재조립 42개와 기존 문서 스키마 10개: 52/52 통과. V4/V5/V6 각각 18개,
  V3/V4/V5/V6 각각 100개의 실제 버전별 합성 fixture를 포함한다. 새 키나 실사용
  일지는 사용하지 않았다. 기본값이 있는 필드 삭제도 해시 대조에서 검출한다.
- 전송 절차 테스트: `account-plan-collection-transfer.contract.test.ts` 23/23 통과.
  18프레임 V4/V5/V6 전체 복원, 중간 전송 중단, 두 기기의 같은 revision 경합,
  A-B-A 계정 전환, 진행만 변경, 정확한 이전 요청, 잘못된 영수증을 포함한다.
- TypeScript 전체 검사: `npm run typecheck` 통과.
- 최종 한국 시간대 검사: 위 세 파일 75/75 통과, 실패 0, 보류 0.
  명령은 `node node_modules/vitest/vitest.mjs run -c vitest.config.kst.ts`
  뒤에 위 세 테스트 파일 경로와 `--maxWorkers=1 --reporter=json`을 전달했다.
  기기 로컬 실행 결과는 `app/test-results/account-plan-partition-kst.json`에 있다.
  이 파일은 Git에 포함하지 않는다. 전체 앱 테스트나 공개 배포 검증을 대신하지 않는다.
- 결함 주입: 영수증 조회 미완료 보호 조건을 제거하자
  `lost ACK followed by unavailable receipt lookup stays outcome_unknown`가 실제 실패했다.
  조건을 복원한 후 같은 테스트가 통과했다. 단순 테스트 개수 비교가 아니다.
- 테스트 저장소는 프로토콜 double이다. 실제 SQL 원자성, JWT, 서버 암호화,
  운영 두 기기 왕복을 검증한 것으로 읽지 않는다.

18개 상세 계획의 로컬 측정값: V4 논리 문서 1,112,646B / 최대 부품 61,770B,
V5 939,684B / 52,161B, V6 954,516B / 52,985B. 목록은 각각 8,100B다.
이는 fixture 결과이며 모든 실제 계획의 크기를 보장하지 않는다. 분리와 재조립은
각각 약 2.5~3.9초가 걸려, 이 결과를 모바일 성능 통과로 표시하지 않는다.

## 다음 개발 순서

1. 서버 부품 저장과 목록 전환 계약: 계정 귀속·불변 부품·서명·영수증을 포함한다.
2. 하나의 실제 DB 트랜잭션: 참조와 원본 revision 검증 후 목록/현재 계획/영수증을
   원자적으로 기록한다. 여러 클라이언트 쓰기를 원자성으로 가장하지 않는다.
3. 암호화 outbox 및 기존 서비스 연결: 요청 재사용, 중단·재시작, 계정별 복구를 연결한다.
4. 과거 이력의 단계별 읽기와 성능 검수: 현재 계획부터 표시하고 원본은 필요할 때 검증한다.
5. 기존 문서 복사·대조·전환: 원본을 삭제하지 않고 실제 경쟁 수정과 중단을 시험한다.
6. 복구키·운영 서버 준비가 끝난 뒤 실제 계정 시험, CI, 병합·배포를 진행한다.

위 1~5는 추가 개발이다. 오너의 미승인 때문에 남은 작업으로 표현하지 않는다.
실제 키 등록과 운영 변경은 이번 작업에서 수행하지 않았다.
