## 목적

서로 다른 컴퓨터와 에이전트가 작업할 때 다음 두 가지 누락을 매일 자동으로 찾는다.

1. 감시 시작 이후 커밋된 작업 브랜치에 PR이 없거나, 미병합 종료·PR 이후 재푸시가 있는 상태
2. 공개 GitHub Pages가 최신 `main`이 아닌 버전을 제공하는 상태

## 자동 실행

`.github/workflows/repository-freshness.yml`이 매일 09:15(KST)에 실행된다.
필요할 때 GitHub Actions에서 수동 실행할 수도 있다.

실패하면 Actions 실행 요약에서 다음을 확인한다.

- 현재 `main` 전체 SHA
- Pages 배포 영수증의 원본 `main` SHA
- 열린 PR 번호
- PR이 없거나 닫힌 채 미병합됐거나 PR 이후 다시 푸시된 최신 브랜치와 커밋

## 기존 작업자 규칙

아래 다섯 항목은 기존 최신 상태 점검 규칙이다. **기본 작업 방식은
[`AGENTS.md` §6](../../AGENTS.md#6-커밋공개-규칙)의 main 직접 작업**이며,
3번은 별도 승인된 작업 브랜치/PR 흐름에 적용한다. 이 문서로 새 브랜치 생성을
허용하거나 모든 기존 브랜치를 병합 대상으로 바꾸지 않는다.

1. 작업 전에 `git fetch origin`으로 원격 상태를 갱신한다.
2. `origin/main`에서 시작한다.
3. 원격 브랜치에 커밋을 푸시했다면 같은 작업 안에서 PR도 만든다.
4. 병합 후 `TrainOracle CI`의 배포 작업이 끝날 때까지 확인한다.
5. Pages의 `trainoracle-deploy-receipt.json`에서 `sourceSha`가 `main`과 같은지 확인한다.

감시를 도입한 2026-08-14 20:10(KST) 이전의 보관 브랜치는 경고하지 않는다. 그 이후
커밋된 브랜치는 `main`이 더 최신이 되어도 계속 추적한다. 새 작업에 PR이 없거나,
PR이 닫힌 채 미병합됐거나, PR 이후 다시 푸시한 경우와 배포가 뒤처진 경우만
실패시켜 불필요한 경보를 줄인다.

## 여러 작업자가 시작·인계할 때

1. **작업 장소부터 확인한다.** 실제 저장소 경로, Git 공통 저장소, 현재 브랜치,
   HEAD, 갱신한 `origin/main`, 추적·미추적 변경을 확인한다. 폴더 이름에 `main`이
   있어도 최신 main이라는 뜻은 아니다. Git 저장소가 여러 개면 각각의 worktree를
   확인하며, 한 저장소의 목록만으로 모든 작업실을 확인했다고 하지 않는다.
2. 열린 PR과 해당 영역의 기존 작업을 확인하고, 작업 인계에 **통합 담당자·기준 SHA·
   소유 파일·현재 상태·다음 작업**을 남긴다. 승인된 9월 지시서의 방식대로 한 작업의
   최종 커밋·푸시는 한 통합자가 맡고 구현자는 겹치지 않는 파일을 담당한다.
3. 같은 파일을 여러 명이 동시에 편집하지 않는다. 공통 계약·공유 화면을 넘길 때는
   검수 패치 또는 PR, SHA와 남은 쟁점을 함께 전달한다. 기존 변경은 되돌리지 않고,
   내 작업과 관계없는 변경·스크린샷·미추적 자산을 함께 커밋하지 않는다.
4. 커밋·게시 직전에 원격 기준을 다시 확인한다. 다른 작업으로 main이 전진했으면
   변경 내용을 확인하고 통합 기준을 갱신한다. 미커밋 자료를 잃을 수 있는 강제
   전환·초기화·덮어쓰기를 최신화 수단으로 사용하지 않는다.
5. [기존 상태 보고 계약 §11](../plans/PROGRAMMED_TRAINING_ANALYSIS_IMPLEMENTATION_WORK_ORDER_2026-09-17.md#11-완료인계중단-보고)을
   재사용한다. 구현·검증·main 반영·배포·실계정 확인을 분리하고 정확한 SHA,
   변경 파일, 실행 검사와 결과, 독립 검수, 미완료 사항과 다음 행동을 남긴다.
   문서가 공유되었다는 사실을 다른 작업자가 이미 읽었다는 뜻으로 보고하지 않는다.

## 브랜치와 작업실 정리 전 확인

정리는 다음처럼 분류한 뒤 진행한다. 이 안내 자체는 삭제·병합 승인이 아니다.

| 분류 | 먼저 확인할 것 | 처리 원칙 |
|---|---|---|
| 열린 작업·초안 PR | 최신 head, 담당 범위, 진행 중 변경, 검수와 필수 검사 | 초안을 정식 릴리스로 취급하지 않음. 다른 작업과 분리해 유지 |
| 연결된 PR이 병합됨 | PR head와 현재 branch tip, squash/cherry-pick 반영, 현재 main의 실제 내용 | `MERGED`나 커밋 조상 관계만으로 현재 tip까지 반영됐다고 판단하지 않음 |
| PR 미병합 종료·PR 없음·PR 이후 재푸시 | 남은 변경의 목적, 최신 main에서의 결함, 소유자·보존 자료 | 무조건 병합하지 않음. 필요한 최소 변경만 별도 승인 범위에서 통합 |
| 미커밋·미추적·ignored 자료가 있는 작업실 | 코드·이미지·증거의 소유자와 보관 위치 | 원격 브랜치나 PR이 있어도 이 자료가 보관됐다는 보증은 아님 |

실제 반영 여부는 현재 tree·파일 내용·패치와 함께 대조한다. `git cherry` 결과나
폴더 날짜만으로 미반영 또는 삭제 가능을 단정하지 않는다. 브랜치·worktree 삭제는
정확한 대상, 보존 여부와 명시적 승인을 확인한 후의 별도 작업이다.

## 현재 배포 확인과 경계

- 주 사용 주소는 [정식 TrainOracle](https://hojune0330.github.io/TRAINORACLE/) 하나다.
  버전별 preview는 보존된 검토 자료이지 별도 정식 제품이 아니다.
- `codex/**`·PR 검사 실행과 앱 공개를 구분한다. 소스 main, 빌드한 원본 SHA,
  `gh-pages` 게시 커밋, GitHub Pages의 `built`, 공개 매니페스트·영수증을 따로 확인한다.
  CI 성공·브랜치 수·Pages HTTP 응답 하나로 모든 기능을 검증했다고 하지 않는다.
- 수동 게시가 별도로 승인된 경우 기존 [수동 게시 보존 방식](../implementation/COACHING_REVIEW_REMEDIATION_2026-09-29.md#배포-준비)을
  따른다. 최신 `gh-pages` 위에 정상 커밋으로 게시하고 force push하지 않는다.
  preview와 이전 해시 자산, 기존 사용자 자료·저장 키를 삭제하지 않는다.
- 현재 정식 주소 통합에는 기존 공개 설정을 보존하고 `--account-held`를 적용한다.
  비회원 Oracle V2 기본 공개와 명시적 false·kill 설정을 유지한다. 계정 공개,
  DB·Edge·provider 적용 및 실계정 왕복은 별도 [계정 공개 관문](../../docs/ACCOUNT_PUBLIC_RELEASE_GATE.md)이다.
- 전체 검사 반복 대신 변경 범위와 릴리스 위험에 필요한 검사를 선택한다.
  필수 관문을 임의로 약화하지 않는다. 승인된 수동 게시의 미실행·실패·skip 검사는
  통과로 적지 않는다. 배포 요청이 없는 문서 공유를 앱 배포로 확대하지 않는다.

### 아직 자동으로 보장되지 않는 부분 — 2026-10-07 코드 확인

아래는 **수정 완료가 아니라 운영상 주의할 공백**이다. 이번 문서 정리로 workflow,
운영 변수·계정 권한·배포 도구를 변경하지 않았다.

1. `.github/workflows/ci.yml`의 자동 게시에는 root 전체 교체가 남아 있어 `previews/`와
   이전 해시 자산을 지울 수 있다. 승인된 보존형 수동 게시와 같은 동작이 아니다.
   현재 계정 보류·오라클 공개 설정의 일치도 자동 게시를 사용하기 전에 확인해야 한다.
2. [보존형 수동 게시 도구](../implementation/PARALLEL_RELEASE_GUARDS_2026-10-07.md)는
   원격 main·Pages를 빌드 전후와 게시 직전에 확인하고, 파일 무결성과 이전 자산
   보존을 검사한다. 다른 게시자가 먼저 올렸으면 재시도 없이 거절한다. 과거 수동
   명령과 자동·롤백 workflow에는 이 보호가 강제되지 않으며, 자동·수동 공통 게시
   잠금이 생긴 것은 아니다. 한 게시 담당자가 경로를 선택하는 운영 규칙은 유지한다.
3. 최신 상태 감시는 `gh-pages`의 영수증을 main SHA와 비교한다. 실제 공개 사이트의
   파일·설정·`built`까지 검증하거나 현재 브랜치 변경의 내용 반영을 증명하지 않는다.
4. 문서·증거만 추가된 main은 공개 앱의 런타임 SHA를 바꾸지 않을 수 있다.
   [기존 운영 인계](BETA_RELEASE_HANDOFF_2026-08-02.md)의 구분대로 변경 범위를 확인한다.
   현재 감시는 이 예외를 자동 구분하지 못한다. 경고를 성공으로 바꾸거나,
   SHA만 맞추려고 영수증을 수정하거나 불필요하게 재배포하지 않는다.
   문서 전용 차이를 확인해도 감시의 SHA 불일치·실패 상태는 그대로 기록하고,
   확인한 변경 범위와 판단 근거를 함께 남긴다.

다음 운영 개선은 자동·수동 공개 설정/자산 보존을 맞추고, 게시 직전 기준과
문서 전용 변경을 감시 도구에서 어떻게 확인할지 정하는 것이다. 현재 자동 배포를
끄거나 활성화했다고 보고하지 않으며, 이 안내로 운영 변경 승인을 대신하지 않는다.
