# Garmin 상태 확인과 기록 보존 구현

확인일: 2026-11-04 KST. 통합 기준 main: `a840dc2ef41e6b75ba9762fdbb273266ff2e82e3`.
사용자 승인 범위는 Garmin 회신·실제 권한 확인, 승인 대기 중 가능한 보존·연동·상세 화면 개발이다.
코드 구현·계정 함수 배포·공개 화면 게시·실제 Garmin 수신을 별도로 확인한다. API 키·사용자 건강 자료·사업자 증명서·비공개 공식 문서 원본은 저장소에 넣지 않았다.

## 현재 외부 상태

- 회사 메일의 Garmin 검색(스팸·휴지통 포함)에서 10월 29일 개발자 프로그램 승인 원문을 확인했다. 이번 검색 범위에서는 자체 호스팅 LLM 문의에 대한 별도 허용 회신을 찾지 못했다. 검색 결과를 전체 메일의 부재 증명으로 해석하지 않는다.
- 사용자가 로그인한 공식 개발자 포털에서 회사 등록과 Starter 앱 생성 화면에 접근했다. **Apps 목록은 0개**였다. 따라서 TrainOracle 앱 Client ID·Secret 발급과 앱별 Activity·Training 권한을 확인한 상태가 아니다.
- API Tools는 Client ID·Secret 로그인을 요구했다. 키를 추출·생성하거나 약관을 대신 동의하지 않았다. 앱 등록은 아직 제출하지 않았다.
- 후속 확인에서도 Apps는 0개였다. 신청 화면에는 TrainOracle, `https://trainoracle.io/?garmin_callback=1`, Activity API만, 식별 가능한 본인 계정, 자료 판매 없음, Starter 및 회사 정보를 입력하고 재읽기했다. 설명에는 pre-production, 수신 호스트/최종 처리업체 고지 미확정, AI 비활성·서면 허용 대기를 명시했다. 신청 초안 입력은 완료했으나 `Add app`은 누르지 않았다. 실제 처리업체와 공개 정책을 확정한 뒤 제출해야 하며 키 발급·권한 확인 영수증이 아니다.
- 후속 작업에서 회사 메일의 검색·보냄·초안과 연결된 Gmail 검색을 대조한 뒤, 11월 4일 19:42 KST 회사 메일로 공식 조건 문의를 발송했다. 제목은 `TrainOracle: written clarification on self-hosted inference and Starter Activity API`, 수신자는 `connect-support@developer.garmin.com`이다. 회사가 관리하는 자체 호스팅 LLM의 추론 전용 설명/코칭, 파생값·로그·동의철회, 처리업체, 일반 Activity/향후 Training 허용 범위를 질문했다. 모델 학습·평가·개선 및 허용 전 AI 사용은 하지 않는 조건을 명시했다. [Zoho 발송 기록](https://mail.zoho.com/zm/#mail/folder/sent/p/1793788942940155300)에서 `전달됨`을 확인했으며, 이는 Garmin의 허용 회신이 아니다.
- 발급된 공식 OAuth2 PKCE 2.0, Activity API 2.1, Starter 안내와 Rev.H 라이선스를 확인했다. 원문은 비공개 로컬 작업 자료에만 보관했다. Starter의 PUSH 중심·과거 조회 제외 범위를 구현에 적용했다. 일반 OAuth scope와 `ACTIVITY_EXPORT`를 구분한다.
- 자체 호스팅은 AI 허용의 자동 근거가 아니다. Garmin 자료와 파생값의 모델 학습·평가·개선 및 코칭 허용을 별도로 확인해야 한다. 현재 AI 관련 권한은 열지 않았다.
- Supabase `trainoracle-beta-staging`은 `ACTIVE_HEALTHY`였고, `account-journal` v17, `account-plan-collection` v15, COROS 관련 함수 등이 존재했다. Garmin 수신 함수는 목록에 없었다. 새 DB를 만들지 않았으며 기존 프로젝트를 재사용하도록 설계했다. 회사 Node 실행 환경의 실제 배포 주소는 미확정이다.

## 구현한 파일 경로

1. TCX·GPX의 실제 센서 표본·위치·랩·기기 메타데이터를 보존한다. 공식 `@garmin/fitsdk@21.221.0`으로 FIT 바이너리·CRC·세션·랩·정지 이벤트와 지원 센서 필드를 읽는다. CSV·JSON도 일반 가져오기에서 관측값을 저장한다.
2. 파일 저장과 분석 허용을 분리한다. 상세 표시를 위해 저장했다고 AI·훈련 근거로 승격하지 않는다. FIT 분석은 닫혀 있다. 파일 제조사 표기는 `FILE_METADATA`이며 제공자 인증이 아니다.
3. 저장 전 상세 미리보기, 일지 상세의 요약·전체 수치·랩·센서 차트·원본 표, 외부 지도 요청 없는 경로 개요를 제공한다. 원본 시각, 단위, 누락, 구간 경계와 0값을 구분한다. 차트 표시량을 줄여도 저장 표본은 삭제하지 않는다.
4. 같은 파일 재수입은 기존 기록 확인으로 처리하며 수정된 원본은 기존 일지를 덮지 않는다. 상세 없는 기존 V1과 새 상세 관측이 만나는 경우 명시적 확인을 요구한다. 삭제한 기록을 동일 키로 조용히 되살리지 않는다.
5. 계정 일지는 상세/새 FIT에 V5를 사용하고, 서버 지원을 먼저 확인한다. 구버전 서버·클라이언트는 명시적으로 거부하며 상세를 제거해 저장하는 대체 경로가 없다. 계정 변경·늦은 응답은 이전 지원 여부를 재사용하지 않는다.
6. 개인용 전체 백업 V7은 상세를 보존한다. 공유용 내보내기와 기존 분석 투영에는 센서·GPS 원본을 넣지 않는다. 원천 수정 경로로 기기 표기를 바꾸거나 상세 전체를 제거할 수 없다.
7. 기존 계정 게이트웨이의 655,360 UTF-8 byte 요청 한도를 지키면서 상세 FILE 문서만 무손실 gzip으로 전송·보관한다. 압축 데이터는 400 KiB, 펼친 상세 문서는 3,500,000 bytes, 펼친 요청은 4 MiB로 제한한다. 메모 등 상세 외 필드는 기존 600,000 byte 범위를 유지한다. SHA-256·정확한 바이트 수·스트리밍 해제 한도·사용자/문서에 결속된 AES-GCM을 확인한다. 구버전은 명시적으로 거절하며 원본을 줄여 성공 처리하지 않는다. 기기의 암호화 전송 대기열에도 같은 방식을 적용하고, 실패하면 기존 자료를 유지한다.

## 구현한 Garmin 경로

- 회사 서버의 OAuth2 PKCE 교환, 별도 활동 제공 권한 확인, 암호화된 토큰·회전 CAS, 사용자·세션·연결 세대 결속.
- 공식 PUSH → 검증한 제공자/프록시 경계 → 암호화된 영속 대기열과 ACK → 작업자 → 사용자별 수신함.
- 사용자가 검토한 원본 revision을 일지로 확정한다. 일지 저장과 수신함 확인은 같은 SQL 트랜잭션이며 응답 소실 재시도에 같은 처리 결과를 돌려준다.
- provider 원천은 `import:provider-activity`이다. 파일 업로드로 위장하지 않는다. RPE·페이스·계획 완료·AI 허용을 만들지 않는다.
- `read(documentId)`와 분할 상세의 순서·개수·SHA-256 확인 후 원본을 표시한다. 바뀐 원본을 과거에 저장한 일지의 원본으로 대신 보여주지 않는다.
- 수신 중단, 원격 권한 해제 대기, 실제 권한 미허용, 처리 중·충돌을 별도로 표시한다. 보관 동의 철회와 기존 계정 삭제 RPC의 같은 처리 안에서 토큰·수신함·상세·대기열을 지우는 SQL 후보를 포함했다.
- 브라우저 콜백 `?garmin_callback=1`을 Supabase 로그인 코드보다 먼저 캡처·제거한다. 키는 브라우저에 넣지 않는다. 인증 SDK 자체가 멈추거나 계정이 삭제돼도 요청을 종료한다.

서버 실행·환경 변수·SQL 적용 전제·복구 방법은 [서버 README](../../server/garmin-integration/README.md)를 따른다.
웹 설정은 `VITE_GARMIN_INTEGRATION_URL`, `VITE_FEATURE_GARMIN_INTEGRATION`,
`VITE_KILL_GARMIN_INTEGRATION`, `VITE_GARMIN_AUTHORIZATION_ORIGIN`이다. 기본 OFF를 유지한다.

## 검증 근거와 한계

- 파서: 기존 67, 새 상세/FIT 8, 기존 관측 계약 47개 통과. 10만 점 GPX 약 2.9초, TCX 점수 경계 약 2.0초. live collection 이차 순회를 수정했다.
- V5 capability·UTF-8 용량·owner 전환: 16개 통과.
- 파일 보존/기존 파일 확인/원천 수정/백업/용량 실패: 새 6개 통과. 일반 파일·계정 가져오기 53개 묶음도 통과했으며 겹치는 검사 수를 합산하지 않는다.
- 화면·저장·백업 기존 108개 묶음은 초기 화면 문구/파일 형식 기대 2개가 실패했다. FIT 형식 추가와 파일 제목 비보존 계약에 맞춰 해당 fixture를 수정했고, 해당 화면과 비동기 파서 32개 재검사가 통과했다. 나머지 4개 파일은 최초 실행에서 통과했다.
- Garmin UI·클라이언트·공통 상세: 서로 다른 34개 통과. 375px, 320px 및 큰 글자에서 가로 넘침·브라우저 오류·외부 지도 요청 0건을 확인했다.
- 공식 Encoder의 합성 FIT 319 bytes를 실제 파일 선택 → 전용 Worker → 저장 전 센서 차트 → 기기 일지 1건 저장 → 달력에서 일지 원문 열기 → 새로고침 후 재조회로 검증했다. 심박 `123/0/145`, 파워 `240/0/미기록`, 타이머 중단 구간 `0/0/1`, 거리 100m와 타이머 30초가 유지됐다. 새로고침 전후 관측 JSON이 같았으며 브라우저 오류·외부 요청은 0건이었다. 실제 개인 운동이나 Garmin API 수신 증거는 아니다.
- Garmin 서버: 실제 루프백 HTTP·AES-GCM·폐기용 PGlite의 28개 통과. 새 토큰 회전 후 권한 조회 실패 복구와 실제 계정 삭제 RPC 경로 포함. 운영 Supabase 왕복은 아니다.
- 수신 작업자 CLI: 기본 OFF·고정 loopback 대상·서명·제한시간·재시도·종료의 5개 검사 통과. 명시적으로 실행할 `worker.mjs`를 제공하며 운영 스케줄을 등록하지 않았다.
- 공유 서버 검증 번들·기존 자체 호스팅 코칭: 119개 통과. 최종 원천 표기를 바꾼 코칭 입력 차단 검사는 별도로 13개 통과했다.
- TypeScript 및 Vite 운영용 빌드 통과. 기존 대형 chunk 경고는 남는다. 결과는 로컬 후보 검증이며 전체 hosted CI·공개 배포·실기기 증명이 아니다.
- 최초 원격 CI의 계약 검사는 통과했다. 품질 검사에서 양사 모두 승인 대기라는 과거 안내를 요구하던 기대가 실패해, Garmin 프로그램 승인·실제 수신 준비·COROS 대기를 각각 검사하도록 바로잡았다. 관련 Node 검사 11개는 다시 통과했다. 최신 원격 CI 결과는 해당 커밋의 Actions 실행에서 별도로 확인한다.

합성 1시간 TCX(1Hz, 심박·GPS·파워 3,600점)는 JSDOM 5 MiB 저장 제한과
격리 Chromium 149의 실제 reload에서 저장 1건/실패 0건이었다. 재읽기와 V7 백업
왕복 후 3,600점 및 내용 지문이 같았다. 원본 1,181,389 bytes, 관측 JSON
842,194 bytes, localStorage 3개 키 총 843,522 UTF-8 bytes, 백업 1,717,387 bytes였다.
Chromium 단일 측정은 파싱 195ms, 저장 459ms, 재읽기 154ms, 백업 생성·재파싱
206ms였다. 최초 계정 문서 842,902 bytes는 당시 600,000 byte 한도를 넘어 거절됐다.
후속 무손실 저장으로 이 병목을 수정했다. 별도 합성 계정 문서 842,851 bytes가
HTTP 요청 92,282 bytes와 암호화 봉투 122,683 bytes로 저장됐고, 실제 handler/AES
재읽기와 V7 백업 원문이 같았다. 4시간·14,400점 표본은 문서 3,383,336 bytes,
요청 361,707 bytes, 로컬 저장 처리 1,206ms/CPU 1,515ms였다. 이는 로컬 Node의
단일 측정이며 Supabase의 요청당 2초 CPU 내 처리를 운영에서 보장하는 수치가 아니다.
7.6MB 표본은 CPU 한도를 넘었으므로 허용하지 않는다. 실제 Chromium의 암호화
IndexedDB 새로고침·계정 격리·전체 백업도 검증했다. 장기간 누적이나 저장 공간이
적은 휴대전화, 실제 사용자 계정의 hosted 왕복은 별도 검증 대상이다.

## 후속 운영 준비

- 단일 Node 실행 진입점과 기본 OFF 상태의 `/healthz`, 공개 경로 제한, loopback 작업자, 종료 처리를 추가했다. 운영 키가 없으면 `PREPARATORY_DISABLED`를 보고한다. DB/Garmin 연결 여부는 `NOT_PROBED`로 구분한다.
- 정식 Garmin migration 후보와 기존 SQL 후보가 같은 바이트임을 확인했다. 새 테이블 9개와 제한된 RPC/철회 트리거만 추가하며 기존 계정 함수·키·동의·승인값을 변경하지 않는다. Node 24.22.1의 관련 HTTP/PGlite/암호화/작업자/배포 검사 39개가 통과했다.
- 원격 권한 해제는 즉시 해제 요청과 여러 작업자가 같은 DELETE를 보내지 않도록 DB lease를 적용했다. 늦은 중복 DELETE가 새 연결을 해제하는 경합을 검사했다.
- 기존 Supabase에 해당 migration을 적용하려던 도구 호출은 자동 승인 검토가 거절했다. 이유는 운영 DB 영구 DDL 변경에 대한 명시적 승인 부족이다. 이 호출로 DB는 변경되지 않았으며 사용자에게 정확한 파일과 적용 범위를 제시해 승인을 요청했다.
- Render 작업공간은 `호준's workspace` 한 곳이 확인됐으나 선택 확인을 기다린다. 무료 준비 설정은 실제 수집 운영 설정이 아니다. Render의 무료 인스턴스는 유휴 중지와 재기동 시간이 있어 Garmin PUSH 응답 요건을 충족하는 상시 수신으로 표시하지 않는다.
- FIT SDK 21.221.0의 개별 FIT Protocol License Agreement를 일반 오픈소스와 구분했다. 정확한 버전·라이선스 표기·LICENSE.txt SHA-256을 검사하고 다른 미확인 라이선스의 일괄 허용은 하지 않는다. 관련 고지 검사 5개 통과.
- 계정 일지·계획 원문 연결·자료 내려받기·자체 호스팅 코칭의 저장 문서 읽기 경로를 같은 무손실 형식에 맞췄다. 압축은 보관 방식이며 AI 활용 권한을 만들지 않는다. 코칭 서버의 실제 AES 복호화/잘못된 계정·문서 거절/변조 거절을 포함한 17개 검사가 통과했다.
- 긴 기록의 수정은 실제 CPU 측정 결과에 따라 실행 환경을 분리했다. 기존 Supabase Edge는 요청당 CPU 2초 제약 때문에 상세 정정의 원본·제안 각각 1,200,000 bytes를 사전 제한한다. 회사 Node의 `/api/account-journal`은 같은 handler/repository·기존 Supabase DB·사용자 JWT·동의 revision·키·서명 검사를 그대로 사용하며 3,500,000-byte 범위까지 처리한다. 클라이언트는 별도 회사 URL이 설정된 경우에만 이 경로를 사용하고, 동의 확인은 기존 Supabase에서 수행한다. 회사 경로는 기본 OFF이며 새 DB나 별도 서비스 구매를 요구하지 않는다.
- 회사 Node의 실제 loopback HTTP·기존 SQL·AES 시험에서 4시간 14,400점/3,383,337-byte 문서 저장 → 상세 정정 → 같은 값 재읽기, commit ACK 유실 후 같은 작업 재시도에서 revision 2 유지가 통과했다. 로컬 측정은 저장 wall 1.531초/CPU 1.875초, 정정 wall 3.911초/CPU 4.813초였으며 운영 성능 보장이 아니다. 기본 OFF·origin·다른 계정·만료 세션·오래된 동의·철회 소거와 배포 경로 검사를 포함해 7개 통과. 회사 서버에 실제 게시한 결과는 아직 아니다.
- 수정 이력은 크기를 제한한 페이지로 조회하고 정확한 대상 리비전만 읽어 복원·응답 소실 재시도를 처리한다. 많은 수정본 때문에 모든 원문을 먼저 펼치거나 이미 완료한 저장을 중복 실행하지 않도록 한다.
- ActivityDetails의 공식 구조화 요약 22개 필드(기기 이름 포함)를 허용 목록에 따라 암호화 대기열·수신함·확정 일지 상세에 보존한다. 평균/최대 심박, 속도·페이스, 종목별 케이던스, 칼로리, 위치, 걸음 수, 상승·하강 고도를 원래 단위와 null/0/미보관 상태로 표시한다. 별도 `allowedSummaryFields`는 기본 빈 목록이며 설정 지문에 결속돼 기존 승인 범위를 묵시 확대하지 않는다. 새 UI/API 관련 26개 검사 통과. 자유 제목·설명과 별도 FIT/MoveIQ는 포함하지 않는다.
- 정식 도메인 게시기가 최신 원본을 10월 9일 Garmin 심사 중단 안내로 다시 바꾸는 결함을 수정했다. `TRAINORACLE-DOMAIN`의 `b9ca876`에 반영했고, 실제 최신 원본의 정책·상태 보존을 포함한 게시기 검사 14개가 통과했다. 이 커밋 자체는 사이트 게시 영수증이 아니다.
