## 실제 적용

Supabase CLI `2.111.0`으로 시험 프로젝트를 연결하고 `db push`를 실행했다.
`migration list`에서 로컬과 원격 모두 `0001`부터 `0020`까지 20개가 같은
순서로 표시됐다. `0019`는 시험 중 발견된 익명 사용자의 고권한 함수 실행권을
회수하고, `0020`은 로그인 사용자가 다른 선수의 보호자 필요 여부를 추측하지
못하도록 조회 대상을 본인 계정으로 제한한다.

현재 적용 절차의 정본은 `docs/SUPABASE_SETUP.md`다. 이전 구현 보고서와 무료
베타 인계서는 각 문서가 작성된 시점의 이력을 보존하며 최신 적용 목록으로
사용하지 않는다.

## RLS 재현 결과

`supabase/tests/trial_rls_rehearsal.sql`을 시험 DB에서 실제 실행했다.

- 성인 A와 B의 베타 좌석 등록: 통과
- B가 A의 일지와 암호화된 개인 메모를 조회: 0건
- B가 A의 계정으로 일지를 쓰는 시도: 권한 거부
- B가 A의 보호자 필요 여부를 직접 조회하는 시도: `false`
- B가 본인의 성인 상태를 확인하는 조회: `true`
- 보호자 확인 없는 만 14세 미만 계정의 네트워크 저장: 권한 거부
- 삭제 요청 직후 기존 일지 접근: 0건
- 분석 테이블의 메모·통증·기분·몸 상태 원문 컬럼: 0개
- 시험 종료 뒤 합성 사용자·일지·개인 메모 잔존: 각각 0건

시험 중에만 트랜잭션 안에서 `ACCOUNT`와 `SYNC`를 켰고 마지막에 모두
되돌렸다. 시험 후 다섯 기능 제어값은 전부 `false`, revision은 모두 `1`이다.

## 함수 권한 점검

초기 보안 점검에서 과거 마이그레이션 일부가 `PUBLIC`만 회수하고 `anon`을
회수하지 않아 익명 사용자가 몇몇 `SECURITY DEFINER` 함수를 호출할 수 있는
문제를 발견했다. 이어서 로그인 사용자가 3인자 보호자 확인 함수를 다른 선수
ID로 호출하면 나이 구간을 추측할 수 있는 문제도 발견했다.
`0019_function_execute_privilege_hardening.sql`과
`0020_guardian_helper_rpc_hardening.sql` 적용 후 다음을 실측했다.

- 익명 사용자가 실행 가능한 `SECURITY DEFINER` 함수: 0개
- 로그인 사용자가 직접 실행 가능한 트리거 함수: 0개
- 앱에서 필요한 로그인 전용 함수는 `authenticated`와 `service_role`만 유지
- 폐기된 2인자 보호자 확인 함수는 직접 실행 불가
- 3인자 보호자 확인 함수는 로그인한 본인 선수 ID에만 결과를 반환

공개용 API key만 사용해 `request_account_deletion`을 익명 호출한 결과도
HTTP `401`, PostgreSQL `42501` 권한 거부로 끝났다.

Supabase 보안 점검기는 로그인 사용자가 의도적으로 호출하는 서버 함수에도
일반 경고를 표시한다. 각 함수는 사용자 식별자와 RLS·기능 스위치를 내부에서
재검사한다. 이 경고는 공개 승인으로 간주하지 않으며 실제 로그인 시험에서
다시 확인한다.

## 공개 상태

이 영수증은 시험 DB 구조와 기본 권한 경계를 확인한 기록이다. 공개 사이트의
계정·동기화·공유·계획 제안·제품 분석은 모두 계속 꺼져 있다. 저장소와
`github-pages` 환경에도 Supabase 공개 변수나 secret을 등록하지 않았다.
계정 공개는 개인정보 안내, 가입 동의, 실제 이메일 로그인, 삭제 작업과
서로 다른 두 계정·두 기기 시험을 마친 뒤 서비스 운영자가 별도로 결정한다.
