**사용자가 훈련을 설계하게 하지 않는다. 이미 완성된 훈련을 받고, 마음에 안 드는 부분만 쉽게 바꾼다.**

기본 흐름은 `오늘 훈련 확인 → 필요하면 다른 훈련/조절 → 이 훈련으로 변경 → 수행·기록`이다. 아무것도 바꾸고 싶지 않은 사람은 조절 화면을 거치지 않는다. 사용자의 선택은 빠르게 반영하되, 그것이 저장·실행·실제 수행을 뜻하는지는 분명히 구분한다.

이번 문서는 기존 계획을 대체하거나 축약하지 않는 추가 설계다. 새 훈련 수치의 채택, 구현 완료, 병합·배포의 증거로 쓰지 않는다. 상세 계획 확정 후 오너가 구현을 지시했다. 실제 이행과 남은 공급 경계는 [구현 보고서](../implementation/WORKOUT_CHOICE_AND_TUNING_IMPLEMENTATION_2026-09-28.md)로 구분한다.

### 이번 계획의 핵심 결정안

1. 처음에는 **완성된 훈련 하나**를 보여준다. A/B 비교나 긴 설문을 필수로 만들지 않는다.
2. `다른 훈련`을 누르면 **같은 목적에 맞는 다른 방법**을 바로 미리 보여준다. 전체 주기를 다시 만들지 않는다.
3. `조절`에서는 현재 훈련에 맞는 항목만 제시한다. `횟수`, `한 번 거리`, `달리는 시간`, `쉬는 시간`, `속도`, `나눠 하기`를 한꺼번에 펼치지 않는다.
4. 조절 중에는 카드 숫자·순서도가 즉시 바뀐다. **마지막 적용 한 번 전까지 원래 계획은 그대로**다.
5. 재미는 빠른 반응·탐색·되돌리기에서 만든다. 더 빠르게/많이/자주 하는 행동에 점수나 보상을 주지 않는다.
6. 간단하게 보여도 거리·시간·강도·반복·세트·회복 방식은 누락하지 않는다. 설명은 숨겨도 **따라 하는 데 필요한 숫자는 숨기지 않는다.**
7. UI 개발과 함께 실제 훈련 공급을 완성한다. 바꿀 훈련이 없는데 새로 뽑는 애니메이션만 보여주는 기능은 출시하지 않는다.

## 4. 기본 화면: 훈련 하나를 곧바로 이해

### 4.1 화면 구성

순서는 `날짜·오전/오후 → 훈련명 → 핵심 방법 → 준비·정리 → 주 행동 → 바꾸기`다. 긴 이력·검수 과정·원문 지문은 처음에 표시하지 않는다.

다음은 기존 상세 처방을 표시하는 예이며 새 용량 제안이 아니다. 개인 페이스는 합성 5000m 18분31초의 기존 계산 예다.

```text
9월 28일(월) 오후
1km 인터벌

1km × 5회
1회 약 3분 42초 / 사이 2분 30초 조깅

준비 15분 + 20초 점진 가속 4회
가속 사이 40초 걷기·조깅 / 정리 10분

[훈련 순서 보기]                  이유 보기
다른 훈련                        조절
```

- 실제 날짜·회복·준비는 저장 데이터에서 읽는다. 위 예시를 하드코딩하지 않는다.
- 현재 몸 상태 문제·적용 실패·온라인 반영 전 상태는 짧게 바로 보인다.
- `훈련 순서 보기`는 안내를 여는 동작이다. 실제 측정기가 없다면 `측정 시작`이라고 하지 않는다.
- 여러 세트라면 `4회씩 3세트 · 총 12회`와 세트 사이 회복을 함께 표시한다.
- 시간형이면 `2분 달리기 × 6회`, 복합형이면 `빠르게 달리기 → 회복주`처럼 순서를 표시한다. 이 숫자는 채택된 구성에서만 온다.
- 구성상 필요한 회복은 한 줄을 늘려서라도 보인다. 한눈에 보이게 하려고 세트 회복을 숨기지 않는다.
- `기록 없음`은 수행 화면의 장식 문구로 반복하지 않는다. 기록을 써서 목표를 만든 경우에만 짧은 출처 표식을 둔다.

### 4.2 시각 요약

- 준비 / 반복 묶음 / 정리를 얇은 순서 도식으로 제시한다. 운동과 회복을 텍스트·패턴으로 구분한다.
- 같은 크기 칸은 **순서 도식**이다. 시간 비례처럼 보이지 않게 명시한다. 실제 시간을 모두 알 때만 비례 도식을 쓴다.
- 거리를 초로 임의 환산하거나 에너지 기여율을 임의 퍼센트로 만들지 않는다.
- 큰 반복 수를 작은 막대 수십 개로 펼치지 않고 `한 묶음 × N`으로 접는다. 펼치면 전체 반복을 볼 수 있다.
- 간단한 설명과 정확한 숫자는 동일한 처방 원본을 읽는다. 홈·달력 상세·비교·일지에 별도 문구 계산기를 만들지 않는다.

## 5. 다른 훈련: 재생성이 아니라 빠른 대안 탐색

### 5.1 사용 동작

1. `다른 훈련`을 누르면 현재 카드 자리에 다음 적격 방법을 미리 보여준다.
2. 상단에 작은 `바꿔보는 중` 상태와 `원래 훈련` 되돌리기를 남긴다. 기존 계획은 아직 변경하지 않는다.
3. 차이는 `한 번에 달릴 거리`, `쉬는 방법`, `반복 구성` 중 실제 달라진 내용부터 보여준다.
4. 마음에 들면 `이 훈련으로 변경`. 후보 계획 편집이면 `이 일정에 넣기`로 표시한다.
5. 마음에 안 들면 다시 `다른 훈련`, 또는 `직접 고르기`에서 최대 두 개를 먼저 비교한다.

**다른 안 미리보기는 한 번, 실제 변경까지는 정상 경로 두 번의 명시적 행동**을 목표로 한다. 안전·권한·저장 충돌 해결을 탭 수 목표 때문에 생략하지 않는다.

### 5.2 추천의 규칙

- 훈련 풀은 목적·적격성으로 묶는다. A라는 훈련 뒤에는 항상 B만 나오는 고정 짝을 만들지 않는다.
- 동일한 context/version에서 순서는 재현 가능하다. 테스트에서 무작위 클릭을 하더라도 운영 추천 자체를 난수로 뽑지 않는다.
- 현재 방법과 구조적으로 같은 것, 반복 수만 다른 것은 `다른 훈련`의 새 방법으로 세지 않는다. 이것들은 `조절`에 속한다.
- 현재 탐색 묶음에서 이미 본 방법을 제외해 순회하고, 모두 보았으면 `다른 방법을 모두 봤어요`와 `본 방법 비교`를 제공한다. 없는 새 방법을 꾸며내지 않는다.
- 적격 방법이 하나라면 `다른 훈련`을 작동하는 것처럼 보이지 않는다. 이유 한 줄과 `조절` 또는 `조건 바꾸기`를 제공한다. 0개라면 개인 훈련인 척 예시를 내놓지 않는다.
- 새 방법으로 바꿀 때 이전 방법의 거리·속도·회복 변경을 가져가지 않는다. 새 방법의 완전한 구성으로 시작하고, 이전 초안으로는 되돌릴 수 있다.
- 시간이 더 길거나 다른 부담이 늘면 그 차이를 **적용 버튼 위**에 표시한다. 같은 목적이라고 같은 부담/효과라고 부르지 않는다.
- 기록·날짜·안전·규칙이 바뀌면 후보를 다시 계산한다. 탐색 커서만 다음으로 넘겨 오래된 후보를 적용하지 않는다.
- 기록 횟수가 적다는 이유로 능력이 부족하다고 판단하지 않는다. 반복/다양성 선호는 선택 옵션이고 기본은 중립이다.

### 5.3 지연과 연속 클릭

검토된 풀과 입력으로 후보를 미리 계산해 두고 카드 교체는 로컬에서 수행하는 방향이다. 서버 왕복과 LLM 문장 생성을 매번 기다리게 하지 않는다. 단, 적용 전 현재 권한·계정·계획 버전은 다시 확인한다.

탐색 버튼은 빠른 탭마다 다음 안으로 이동할 수 있지만, 이전 요청이 뒤늦게 도착해 최신 카드를 덮어쓰면 안 된다. 결과는 현재 context와 요청 순번이 모두 일치할 때만 표시한다. 긴 누르기의 자동 연속 동작은 사용하지 않는다.

성능 목표는 입력 반응 100ms 이내, 준비된 후보의 표시 p95 300ms 이내로 제안한다. 목표이지 현재 실측값이 아니다. 1초 이상 지연하면 현재 카드를 유지하고 `다른 훈련을 찾고 있어요`를 표시한다. 멈춘 화면을 가리기 위한 가짜 회전 애니메이션은 금지한다.

## 6. 조절: 무엇을 바꾸는지 먼저 분명하게

`조절`을 누르면 별도 거대한 설문이 아니라 같은 훈련을 보면서 조작하는 편집 화면을 연다. 모바일은 전체 화면 편집, PC는 넓이를 제한한 편집 영역을 사용한다. 중첩 팝업과 이중 스크롤은 만들지 않는다.

기본은 `횟수 / 쉬는 시간 / 더 조절`처럼 **현재 훈련에서 자주 쓰고 실제 가능한 항목 2~3개**다. 더 조절 안에서 전체 지원 항목을 볼 수 있다. 운동 유형이 바뀌면 항목도 달라진다.

| 사용자가 원하는 것 | 화면의 정확한 이름 | 한 번 누르면 일어나는 일 | 주의할 오해 |
|---|---|---|---|
| 갯수 줄이기/늘리기 | `반복 횟수` + 현재 값 + −/+ | 다음 검토된 전체 구성으로 미리보기 | 이름만 바꾼 새 방법으로 세지 않음 |
| 거리 늘리기 | `한 번 달릴 거리` 또는 `오늘 달릴 거리` | 어느 거리를 바꾸는지 명시한 구성 선택 | 반복형에서 총거리와 1회 거리를 섞지 않음 |
| 더 짧게 달리기 | `한 번 달리는 시간` 또는 `달리는 시간` | 시간형의 운동 구간 길이 변경 | 준비·정리까지 자동 압축하지 않음 |
| 강도 낮추기 | `덜 힘들게` 진입 후 `속도 늦추기` / `횟수 줄이기` 등 | 의미가 분명한 가능한 방법을 고름 | RPE 숫자만 내려 같은 처방을 쉬워졌다고 하지 않음 |
| 더 빠르게 달리기 | `목표 속도`의 `느리게 / 빠르게` | 채택된 개인 목표 변경만 제공 | 초/km의 +가 더 느리다는 부호 혼동 금지 |
| 더 쉬기 | `반복 사이 쉬는 시간` | 검토된 회복 구성으로 변경 | 조깅과 정지 회복은 같은 것으로 취급하지 않음 |
| 나누어 쉬기 | `나눠 하기` | `6회씩 2묶음` 등 검토된 세트 구조 선택 | 12회를 나눴으니 같은 자극이라고 단정하지 않음 |
| 세트 사이 더 쉬기 | `묶음 사이 쉬는 시간` | 해당 경계만 바뀐 구성 선택 | 반복 회복과 중복 합산 금지 |

`덜 힘들게`는 쉬운 진입어이지 정확한 생리학적 판정이 아니다. 승인된 낮춤 구성이 하나이고 실제 변화가 단순하면 바로 미리보기한다. 여러 방식이면 가장 관련 있는 두 선택만 보여준다. `느리게`, `짧게`, `적게` 중 무엇을 했는지 결과에 적는다.

실제로 속도를 낮추는 버튼이면 처음부터 `속도 늦추기`, 반복을 줄이는 버튼이면 `횟수 줄이기`라고 쓴다. 범용 `강도 낮추기` 버튼을 모든 훈련에 붙이지 않는다. 목적을 유지하는 낮춤 구성이 없다면 '덜 힘든 같은 훈련'을 발명하지 않고 다른 적격 방법이나 별도 목적 변경으로 안내한다.

### 6.1 플러스·마이너스의 계약

- 버튼은 숫자를 마음대로 더하는 계산기가 아니라 **현재 훈련에서 허용된 다음 구성**을 선택한다. 예: 5회에서 다음 허용값이 7회면 `+2회`라고 보이고 `+1`처럼 오해시키지 않는다.
- 크기·의미가 일정한 한 단계일 때만 −/+를 쓴다. 여러 항목이 함께 바뀌면 `4회 구성` 같은 명시적 구성 선택으로 보여준다.
- 반복 거리 증가와 목표 속도/회복 변경이 함께 필요하면 함께 바뀌는 항목을 숨기지 않는다. UI 한 버튼은 가능하지만 내부적으로는 완전한 구성 한 개다.
- 정해진 상·하한에서는 멈춘다. 최대에서 최소로 돌아가는 순환, 자동 보정(clamp), 길게 눌러 계속 증가하는 동작은 없다.
- 편집을 닫고 다시 열거나 저장한 뒤 다시 늘려도 제한을 우회할 수 없어야 한다. 기준은 매 클릭의 직전 값만이 아니라 원래 승인 구성·현재 전체 일정이다.
- `−`의 역으로 `+`가 허용된다고 추정하지 않는다. 허용 변화가 방향별로 다르면 버튼도 그대로 따른다.
- 조절 가능한 값이 없으면 클릭을 유도하는 빈 도구를 만들지 않는다. `이 훈련은 현재 횟수로 제공해요`처럼 짧게 설명하고 다른 가능한 행동을 제시한다.
- 단, 지원하지 않는다고 기본/선수 사용자 전체를 막지 않는다. 같은 화면에서 가능한 조절은 계속 쓸 수 있다.

### 6.2 세트 구조와 합계

균등 세트는 운동 횟수 `S×N`, 세트 내부 회복 `S×(N−1)`, 세트 사이 회복 `S−1`을 별개로 센다. 일반적인 세트 경계에서는 마지막 반복 회복을 세트 회복으로 대체한다. 마지막 회복이 따로 규정된 복합 구조는 그 원본 의미를 따른다.

사용자 예시 `2×(10×400m), r60초, R3분`의 산술은 총 20회·8000m, 반복 회복 18회·세트 회복 1회·합계 1260초다. **이는 표기/산술 검증 예이며 지금 누구에게나 제공하는 새 처방이 아니다.**

홀수 반복을 세트로 나눌 때 임의로 버리거나 올림하지 않는다. 5+4처럼 불균등 구성이 검토돼 있으면 그대로 제안하고, 없으면 나눔 선택을 제공하지 않는다. 마지막 이후 회복·정리를 중복하거나 지우지 않는다.

## 7. 정보량: 없애는 것이 아니라 정확한 위치로 이동

### 7.1 항상 보이는 것

날짜·오전/오후, 실제 수행 방법, 목표 속도/노력, 반복·세트 회복, 변경된 핵심 값, 현재 오류/안전/저장 상태, 주 행동이다. 길면 세로로 확장한다.

### 7.2 눌렀을 때 보이는 것

- `이 훈련을 하는 이유`: 목적·대사 특성·구성 이유·회복 이유·이번 주기 역할·기대와 한계·근거.
- `기준 기록`: 실제 적용 기록, 날짜, 모델과 적용 범위. PB를 썼으면 PB, 목표만 저장했으면 개인 페이스 근거라고 하지 않음.
- `전체 구성`: 준비·운동·모든 회복·정리의 정확한 합계와 미산출 항목.
- `주기에서 위치`: 실제 날짜 달력, 전후 훈련, 오전·오후. 오늘 세션만 바뀌고 다른 날짜가 유지됨을 확인.
- `계산 상세`: 전문가를 위한 원본 초·단위·버전·계산 근거. 해시/JSON은 일반 설명에 출력하지 않음.

### 7.3 문구 교체 원칙

| 현재 어렵거나 모호한 표현 | 제안 |
|---|---|
| 시간 기준 / 본운동 기준 | 선택 항목에서 제거. 실제로 `2분씩 달리기` / `400m씩 달리기`를 보여줌 |
| 시간·RPE 기준으로 받기 | 필요한 분기에서만 `기록 없이 받기`; 결과에는 구체적 방법과 체감 노력 |
| 본운동 안내 방식과 방법 | `오늘 할 훈련` 또는 `다른 훈련 고르기` |
| 본운동 반복 단위 | 단순 반복이면 `달리는 횟수`; 복합형은 `이 묶음을 N번` |
| 처방 조정 / 변경안 적용 | `훈련 조절` / `이 훈련으로 변경` |
| 총 시간 | `준비·마무리 포함`을 값 옆 짧게 표시. 일부만 알면 전체라고 하지 않음 |
| 산출 불가 | `전체 시간은 아직 알 수 없어요` 등 무엇이 없는지 풀어 씀 |
| 허용되지 않은 엣지 / 검토 기준 만료 | `이 훈련으로 지금 바꿀 수 없어요. 원래 계획은 그대로예요.` + 사유·다음 행동 |
| 검토된 구성 보기 | `다른 방법 보기` |

`본운동`, RPE, LT 등 단어를 문서와 전문가 화면에서 전부 삭제하지 않는다. 첫 화면에서는 자연스러운 수행 표현을 쓰고 물음표·용어집에 정확한 개념을 둔다. `존2`는 개인 구간이 확인되지 않았는데 BASE의 동의어처럼 무조건 붙이지 않는다.

## 8. 맥락에 맞는 추천과 주기 보존

### 8.1 처리 순서

1. 현재 계정/선택 권한/안전 상태 확인.
2. 정확한 훈련 identity·버전·채택 범위 확인.
3. 종목·경험·목적·기록 요구·장소/도구 요건으로 필터.
4. 사용자 시간 상한·기존 날짜/오전오후·전후 훈련·주기 역할에 대한 채택된 정책 검토.
5. 사용자가 이미 고른 방법은 적격성이 유지되는 한 보존.
6. 기본 중립 순서, 명시적 다양성/반복 선호가 있으면 해당 규칙 적용.
7. 같은 구조 중복 제거 후 대안 표시. 원래 처방 대비 차이와 실제 사용 근거 생성.
8. 적용 시 현재 맥락·전체 일정·저장 버전 재확인.

현재 코드가 모두 이 순서를 구현한 것은 아니다. 실제 미사용 맥락은 `반영함`으로 표시하지 않는다. 우선순위를 생리학적 점수로 발명하지 않으며, 시간표·목적의 사실과 과학적 타당성 판단을 나눈다.

### 8.2 중요한 상황

- **기록 없음:** 기록이 없어도 수행할 수 있도록 채택된 구체적 시간형/노력형을 공급한다. 막연한 `RPE 7로 50분`이 인터벌의 대체 완료가 아니다.
- **PB/SB:** 같은 기록이라도 경험·현재성·주기 맥락은 다를 수 있다. 빨라진 기록을 발견해 자동으로 목표·양을 올리지 않는다.
- **목표 기록만 있음:** 목표는 보존하지만 현재 능력으로 계산하지 않는다. 현재 기록을 넣으면 달라질 항목을 짧게 안내한다.
- **청소년/자율 사용자:** 이번 범위를 그대로 유지한다. 임의의 연령/성별 배율이나 코치 연결 강제를 새로 만들지 않는다. 실제 COACH_REQUIRED 상태는 우회하지 않는다.
- **하루 두 번:** 오전/오후를 명확히 표시하고 편집 대상 하나만 바꾼다. 오후를 무조건 회복 전용으로 되돌리지 않으며 하루 고강도 노출 정책은 현재 계약을 따른다.
- **7일씩 보기:** 표시 기간 끝을 주기 리셋으로 삼지 않는다. 이전 주기·다음 주기에 이미 확정된 근거를 보존한다.
- **긴 주기:** 에너지 목적의 예정 횟수·실제 수행·관찰 변화는 별개로 누적한다. 9.5일 관례를 9일/10일 달력과 자동 동치 처리하거나 과학적 우위라고 주장하지 않는다. 중·대주기에서의 목적 편중 표시를 후보 조절 때문에 지우지 않는다.
- **경기·테이퍼:** 적용할 정책이 있는 경우만 반영. 근접한 경기일을 새로 확인했는데 기존 후보를 그대로 유효하다고 하지 않는다. 검토되지 않은 축소율을 적용하지 않는다.
- **거리형↔시간형:** 새로 검토된 방법으로 교체할 수는 있지만 단순 단위 표시 변경인 척하지 않는다. 모델 없이 거리/시간을 환산하지 않는다.
- **ATP-PC 등 짧은 고출력:** ‘덜 힘들게’가 무조건 느리게 뛰기일 수 없다. 목적을 바꾸는 변화와 같은 목적의 분량 변화는 다른 제안이다. 60m 미만 경기페이스 환산 금지 유지.
- **환경:** 더위/경사/바람에 사용자 요청을 받을 수 있으나 미채택 수식으로 페이스를 보정하지 않는다. 위치정보 수집을 새로 필수화하지 않는다.
- **전문 선수/기본 보기:** 동일한 수행 처방을 공유한다. 전문 보기는 출처·세부수치·주기 설명을 더 보여주고, 기본 보기에도 하루 두 번 등 필요한 기능을 남긴다.
- **휴식일:** OFF의 `다른 훈련`이 새 MAIN 추가 버튼이 되지 않는다. 쉬는 날을 훈련일로 바꾸는 것은 별도 일정·노출 변경으로 다룬다.
- **근력·점프·대체 운동:** 실제 수행한 여러 활동은 일지에 별개로 보존한다. 러닝 처방 조절 때문에 다른 활동을 거리/시간으로 환산하거나 지우지 않는다.
- **자정·여행·시간대:** 현지 날짜가 달라져도 열어 둔 세션의 identity는 유지한다. 표시 날짜·오전오후가 변경되면 짧게 알리고 적용 맥락을 재확인한다. 다른 날짜로 몰래 옮기지 않는다.
- **좋아하는 방법:** 즐겨찾기나 탐색 선호는 효과·실제 수행·안전의 증거가 아니다. 매번 다른 안을 요구하지 않고 원래 훈련을 그대로 수행하는 흐름도 정상 성공이다.

### 8.3 항목별 변화 설명

어떤 버튼도 '전체 부하 점수 10% 감소'처럼 근거 없는 단일 점수로 변화를 요약하지 않는다. 운동 거리/운동 시간/목표 속도 또는 노력/반복·세트 회복/전체 예상 시간/주기 노출을 별개 차원으로 비교한다. 실제로 변한 항목 중 핵심 1~3개만 앞에 두고 전체는 펼쳐 본다.

`횟수는 줄고 목표 속도는 빨라짐`처럼 서로 다른 방향이면 그대로 표시한다. 모르는 차원은 모르는 상태로 두며 '동일', '더 안전', '동등 효과'로 채우지 않는다. 같은 목적을 유지한다고 판정할 수 없는 변경은 `목적이 다른 훈련`으로 분리하고 현재 슬롯의 빠른 교체로 적용하지 않는다.

## 9. 저장·실행·뒤로가기: 가볍게 조작해도 기록은 정확하게

| 상태 | 가능한 행동 | 금지되는 오해 |
|---|---|---|
| 현재 훈련 | 그대로 보기, 다른 방법/조절 열기 | 열었다고 계획이 바뀜 |
| 변경 미리보기 | 다른 방법, 값 조절, undo/redo, 원래대로 | 미리보기가 온라인 확정됨 |
| 적용 확인 | 핵심 차이와 대상 날짜를 보고 한 번 적용 | 비교·적용·저장을 의미 없이 세 번 반복 |
| 저장 중 | 중복 클릭 방지, 기존 계획/변경안 보존 | 애니메이션 종료를 저장 성공으로 취급 |
| 미전송/응답 불명 | 미전송 표시, 정확한 요청 재확인 | 자동으로 다른 구성 재시도 또는 성공 처리 |
| 충돌 | 최신 계획과 내 변경안 유지, 선택 복구 | 기기 시각으로 덮어쓰기 |
| 반영 완료 | 적용된 계획 보기, 필요한 후속 변경 | 과거 수행·일지를 새 계획 수치로 재작성 |
| 시작/기록 완료 | 당시 계획과 실제 기록 보기 | 이미 한 운동의 계획을 소급 변경 |

### 적용 단위

활성 계획의 변경은 현재 계약대로 새 버전/후속안으로 처리한다. 내부 원본·변경안을 나누되 사용자에게 불필요한 개발 단계까지 여러 번 승인하게 하지 않는다. 기존 후보 편집과 활성 계획 변경의 확인 단계를 합칠 수 있는 범위는 소유 계약에서 먼저 명시한다.

이미 시작했거나 결과가 기록된 세션은 과거 계획을 유지한다. 남은 수행 중 조정 기능은 별도 설계이며 이번 편집기로 조용히 열지 않는다. 계획을 바꾼 이유와 실제 수행한 수치를 구분해 일지로 연결한다.

### 되돌리기와 내비게이션

- 편집 중 undo/redo는 숫자·회복·설명·선택 구성을 함께 되돌린다. 새 편집을 하면 redo 가지는 제거한다.
- `원래대로`는 편집 시작 시점으로, `취소`는 편집을 끝내고 그 이전 화면으로 돌아간다.
- 저장 이후의 `되돌리기`는 서버 기록을 과거로 되감는 동작이 아니다. 기존 구성으로 복원하는 새로운 요청이며 현재 권한·안전·버전 확인이 필요하다.
- 도움말/근거를 열었다 닫으면 같은 날짜·오전오후·초안·스크롤·포커스로 돌아온다. 홈으로 보내지 않는다.
- 통증 신호나 규칙 철회 뒤 undo를 눌러도 이전의 '적용 가능' 상태가 복구되지 않는다. 콘텐츠 복원과 현재 권한 검증은 다르다.
- 계정 변경은 편집을 분리한다. 늦은 저장 응답을 다른 계정의 성공으로 표시하지 않는다.
- 삭제된 계획에 늦은 변경 요청이 도착해도 부활하지 않는다. 삭제 및 실제 일지 보존 계약 유지.

계정 사용자는 서버 반영을 기준으로 한다. 기기는 미전송 작업 보호에 사용하며 온라인 저장 완료를 앞당겨 표시하지 않는다. 게스트는 기존 기기 저장 범위를 유지한다. 현재 탭의 pending editor와 계정 outbox를 임의로 같은 저장소로 합치지 않는다.

저장 여부가 불명한 동안에는 다른 변경을 덮어쓰거나 '원래대로'로 서버를 되돌리려 하지 않는다. 초안 변경과 전송한 변경 요청을 따로 보존하고 먼저 그 요청의 확정 결과를 조회한다. 저장 중 뒤로가기를 막는 시간도 무제한으로 늘리지 않는다. 안전하게 나가되 pending 상태와 결과 확인 경로가 남아야 한다. 세부 처리는 기존 계정 버퍼 계약을 따른다.

## 10. 게임 같은 조작감, 운동량 경쟁 없는 재미

- 후보를 넘기면 카드 내용만 짧게 교체되고 다음에 누를 위치는 안정적으로 유지된다.
- −/+를 누르면 해당 숫자와 도식의 달라진 부분이 함께 바뀌고 `횟수 5 → 4회`처럼 변화가 잠깐 강조된다.
- 한 단계 전으로 되돌리는 아이콘은 항상 같은 위치에 둔다. 손가락이 익숙해질 수 있게 버튼이 들쑥날쑥 이동하지 않는다.
- 적용 성공 후 작은 체크 피드백을 보여준다. 오래 떠 있는 축하 팝업이나 수동 닫기 요구는 없다. 저장 상태 자체는 짧은 애니메이션이 사라져도 확인 가능해야 한다.
- 스와이프는 후보 넘김의 보조 경로다. 보이는 버튼과 키보드 경로가 반드시 있다. 브라우저 가장자리 뒤로가기와 충돌시키지 않는다.
- 숫자 조절에는 드래그 슬라이더를 기본으로 쓰지 않는다. 젖은 손·작은 화면·정확한 수치에 불리하다.
- 더 많은 운동, 더 빠른 페이스, 짧은 회복, 더 많이 새로 뽑기에 보상·출석·포인트를 연결하지 않는다.
- `도전하세요`, `이 정도는 해야죠`, 불꽃 등 증가 유도 표현을 쓰지 않는다. 줄이기·쉬기·같은 훈련 반복도 동일한 품질로 다룬다.
- 다른 훈련 탐색 횟수 자체를 성공 지표로 삼지 않는다. 많이 눌렀다는 것은 선택이 어려웠다는 신호일 수도 있다.

## 11. 접근성·화면 크기·성능 예산

- 현행 Pretendard·색/간격 토큰·lucide·hairline 사용. 그림자·좌측 색띠·큰 장식 카드 재도입 금지.
- 일반 375×667에서 현재 방법·주요 회복·주 행동을 첫 화면에서 이해하도록 설계한다. 320px·200% 글자에서는 세로 스크롤 허용. 무스크롤을 위해 글자를 줄이거나 자르지 않는다.
- 시각 아이콘은 작아도 터치 영역 최소 44px. WCAG 2.2의 24 CSS px 최소 기준과 제품의 44px 기준을 혼동하지 않는다.
- 숫자 수정 시 화면이 위로 튀지 않고 버튼에 포커스가 남는다. 바뀐 값은 스크린리더에 간결하게 알린다.
- 단순 방향키 이동·라디오 포커스만으로 화면 이동하지 않는다. 다음 화면으로 가는 항목은 명시적 행동 버튼이다.
- 모션은 기존 200~350ms 토큰과 짧은 이동 범위 사용. 모션 감소에서는 이동 없이 상태 변화 전달. 화면 흔들림·무한 바운스 금지.
- 키보드, TalkBack/VoiceOver, 굵은 글자·확대, 낮은 화면 밝기, 네트워크 지연을 별도 확인한다.
- 도식은 동일한 텍스트 대안이 있고 색만으로 강도/회복을 구별하지 않는다.
- 원본 연구 문서·전체 근거를 매 클릭마다 불러오지 않는다. 설명 상세는 지연 로딩하되 숫자와 설명 버전은 고정한다.

## 12. 기존 코드 활용과 필요한 계약 패치

새 '게임 엔진'이나 LLM 추천 엔진을 만들지 않는다. 현재 구조 위에 행동 의미를 정확히 매핑한다.

| 영역 | 재사용할 실제 경로 | 후속 변경 내용 |
|---|---|---|
| 후보 풀 | `app/src/screens/plan-beta/plan-template-options.ts`, `impl/src/prescription/method-recommendation.ts` | 문맥별 후보 목록·구조 중복 제거·탐색 커서. 계산과 화면 순서를 분리 |
| 조절 | `PrescriptionAdjustmentEditorV3.tsx`, `impl/src/prescription/prescription-adjustment-v3.ts` | 허용된 행동만 노출. 바뀌는 필드·복합 변화 표시. 새 수치 직접 계산 금지 |
| 설명 | `DetailedPrescriptionView.tsx`, `SessionExplanation.tsx`, `PrescriptionStructureV3.tsx` | 한 처방을 읽는 수행 요약·근거·순서 도식 |
| 원본/결속 | `source-adjustment-offer.ts`, `adjusted-method-resolution-v3.ts`, `rpe-adjusted-slot-v3.ts` | 실제 채택 공급 연결. 원본 ID와 개인 목표 결과를 분리 |
| 적용/저장 | `prescription-adjustment-commit.ts`, `adjustment-workspace-session.ts`, `selected-multi-adjusted-plan-v3.ts` | 기존 lock/revision/safety/account 경로 활용. 미리보기와 활성 계획 분리 |
| 일정/일지 | 현재 날짜 리더·계획-일지 결속 | 같은 세션의 당시 처방과 실제 기록 보존. 전후 비교로 연결 |

상세 함수의 변경 위치는 실행 직전 최신 코드로 다시 확정한다. 파일이 존재한다는 사실만으로 해당 모든 기능이 공개 경로에 연결돼 있다고 판단하지 않는다.

### 조절 버튼을 만드는 정보

새 저장 스키마를 이 문서로 확정하지 않는다. 기존 offer에서 UI가 읽을 투영에는 적어도 대상 세션/초안 revision, 변경할 필드와 단위, 전후 전체 구성 참조, 연동 변경 필드, 현재 사용 가능 여부/사유, 규칙·설명 버전이 필요하다. 버튼이 직접 템플릿이나 숫자 범위를 만들지 않고 코어가 제공한 전이만 요청한다. `더 많은 반복` 같은 화면 라벨을 파싱해 실제 변경 대상을 추정하지 않는다.

| TRAINING_SESSION_PRESCRIPTION_CONTRACT | 운동/회복 산술, 설명 버전, 실제와 계획 분리 | compact 실행 요약 계약, 조절 후 설명 동시 변경 |

| TRAINING_PLAN_FORMATION_AND_ADAPTATION_SPEC / PLAN_CYCLE_RESPONSE_AND_ADAPTATION_CONTRACT | 계보·노출·다음 주기 제한 | 단일 세션 미리보기와 실제 successor 변경의 책임 분리 |
| UX_UI_VISUAL_STANDARD | 점진 공개·44px·기존 토큰·동작 필요 정보 상시 표시 | 편집 상태의 고정 동작 위치·모션·정보 예산·내비게이션 복귀 |

규칙형 폭넓은 조절로 전환하는 것과 유한 검토 구성을 버튼으로 고르는 것은 다르다. **첫 구현은 후자**다. Cartesian 조합 폭발을 줄이기 위해 근거 검토는 구성·공통 요소·배치 정책으로 재사용하되, 개별 구성 채택만으로 모든 동시 조합이 승인됐다고 하지 않는다.

## 13. 훈련 공급 계획: 버튼이 아니라 실제 선택지를 완성

### 공급 단위

훈련마다 `방법 정체성 / 정확한 구성 / 적용 대상 / 목적 / 주기 역할 / 기록 요건 / 설명 / 근거 / 조절 가능한 변화 / 전체 배치 검토 / 승인 버전`이 연결돼야 한다. 새 ID 발급만으로 새 방법 수를 늘리지 않는다.

### 우선순위

1. 기록 없는 사용자가 실제 따라 할 수 있는 구체적 MAIN. 기존 검토안에서 정확한 운동/회복/노력과 대상이 준비된 것부터 채택 묶음을 만든다.
2. 현재 상세 4종목의 **같은 목적에서 구조가 다른 두 번째 방법**. 다른 종목의 템플릿을 그대로 가져와 숫자만 바꾸지 않는다.
3. 장거리·마라톤과 각 에너지 목적, 오전·오후를 포함한 실제 전체 일정 조합.
4. 각 방법의 횟수/시간/회복/세트 변경. 모든 버튼을 모든 훈련에서 억지로 열지 않고 검토된 변화부터 제공.

위 작업은 준비를 병렬로 할 수 있다. 유한 검토안을 오너에게 한 개씩 질문하지 않고 **정확한 수치·대상·변경 범위·근거 한계가 있는 묶음**으로 제시한다. 이미 승인된 범위는 재승인 요청하지 않는다. 미해결 조건은 보류 목록에 남기고 전체 기능을 무기한 멈추는 핑계로 쓰지 않는다.

출시 범위표는 `종목 × 경험 × 기록 유무 × 목적 × 주기 역할`별로 다음을 기록한다: 수행 가능한 기본안 수, 구조가 다른 방법 수, 조절 항목, 미지원 이유, 적용 정책, 실제 저장·재열기 확인. 연구 카드 수나 코드 파일 수를 제공률로 쓰지 않는다.

첫 사용자 공개 묶음은 적어도 **한 실제 사용자 범위에서 서로 다른 적격 방법 2개, 한 가지 유용한 조절, 저장·재열기·일지 연결**이 끝나야 한다. 이것을 전 종목 완성이라고 광고하지 않는다. 동시에 기록 없는 경로의 공급을 별도 필수 작업으로 추적한다.

## 14. 다각 검토와 랜덤 탐색

[24개 페르소나·무작위 순서 검토](WORKOUT_CHOICE_PERSONA_REVIEW_2026-09-27.md)를 함께 읽는다. 동일 작성자가 수행한 설계 검토이며 독립 모델·실제 선수 인터뷰·브라우저 실행으로 표시하지 않는다.

- 24개 프로필: 입문 마라톤, 중고등 중거리, 코치 확인, 대학/실업급 일2회, 트랙 없는 러너, 시간 제한, 복귀, 통증, 접근성, 오프라인, 계정 전환 등.
- seed 20260927의 96개 무작위 순서, 768개 행동 요청, 32종 행동을 생성해 설계 규칙과 대조했다. 화면에서 실행한 768클릭이 아니다.
- 무작위 순서는 현실적인 정상 흐름을 대신하지 못한다. 별도 정상/경계 시나리오를 함께 작성했다.
- 무작위 결과는 초안 종료 후 조작, 삭제 뒤 적용 등 불가능한 요청도 포함한다. 이것은 허용 UI가 아니라 **늦은 응답·잘못된 호출을 받았을 때 무슨 일이 없어야 하는지** 검토하는 자료다.

### 실제 구현 때 필요한 결함 주입

1. 이름/반복만 바꿔 새 방법 수를 부풀리기.
2. 횟수를 줄이면서 속도를 올리고도 '덜 힘듦'으로 표시하기.
3. 회복을 줄였는데 전체 합계·설명을 그대로 두기.
4. 기록 ID는 같고 내용만 바뀌었는데 과거 페이스 적용하기.
5. 다른 훈련을 고른 뒤 이전 훈련의 회복값이 남기.
6. 세트 경계에 반복 회복과 세트 회복을 중복하기.
7. 새 안전 신호 뒤 undo로 차단 해제하기.
8. 두 번 적용·응답 유실·새 계정에서 늦은 응답 성공 처리하기.
9. 이미 작성된 일지를 변경된 미래 계획의 수치로 덮기.
10. 연구 검토안/테스트 fixture를 운영 풀로 읽기.
11. 거리 회복의 시간을 0으로 세어 시간 상한을 통과시키기.
12. 전체 가능 시간에 맞추려고 준비·정리를 몰래 삭제하기.

성공 경로도 함께 검사한다. 모든 변경을 거부해서 실패 케이스만 통과하는 검증기는 반려한다.

## 16. 작업 구역·순서·완료 조건

초안 작성 당시에는 전 단계 미착수였다. 2026-09-27의 구현 지시 후 계약 패치와 선택·조절 구현을 시작했다. 이미 존재하는 기능을 새로 만든 것처럼 세지 않고 구역별 차이와 검증 결과를 구현 보고서에 남긴다. 아래 완료 조건은 그대로 유지한다.

| 단계 | 작업 | 책임 구분 | 완료 조건 |
|---|---|---|---|
| W0 | 실제 공급/버튼/저장 경로·스펙 충돌 목록 | 코어 담당 + 독립 읽기 검수 | 준비/승인/운영 연결/배포 상태가 구분된 표 |
| W1 | 정확한 공급 묶음·변경 규칙·설명·대상 채택 준비 | 근거/코어 담당, 오너 최종 내용 결정 | 시작 경로와 대안·조절의 실제 채택 목록. 외부 독립 전문가 승인으로 위장하지 않음 |
| W2 | 행동 의미·후보 순회·편집 상태·기존 계약 패치 | 코어 담당 | 단일 원본·방향별 변화·권한/안전·중복 저장·계보 검사 |
| W3 | 수행 카드·다른 훈련·조절·비교·undo | UI 담당, Fable UX 검수 | 정상 두 동작 변경, 짧은 수행 문구, 같은 위치에서 응답 |
| W4 | 활성 계획 successor·계정 저장·달력·일지 | 저장/도메인 담당 | 새로고침·다른 기기·충돌·삭제·일지 원본 보존 |
| W5 | 실제 페르소나 동선·랜덤 상태 전이·접근성 | 독립 검수 담당 | 구현 테스트 + 결함 주입 실패 증명 + 화면 증거 |
| W6 | 범위별 공개·배포·운영 확인 | 릴리스 담당 | 정확한 소스/배포 일치, 실제 제공 목록, 공개 흐름 확인 |

W0 후 W1의 내용 준비와 W3의 비운영 프로토타입은 병렬 가능하다. 실제 숫자 활성화는 W1·W2 이후다. UI·코어·저장 담당은 같은 파일을 동시에 수정하지 않도록 소유 범위를 먼저 고정한다. 짧은 문구 변경 때문에 승인 의미나 숫자 계약을 바꾸지 않는다.

### 출시 전 평가표

- 사용자가 “무엇을, 몇 번, 어느 정도로, 어떻게 쉬면서 할지” 말할 수 있는가?
- 다른 훈련을 받았을 때 실제로 달라진 방법을 한 가지 이상 짚을 수 있는가?
- 조절 뒤 어떤 수치가 바뀌었고 무엇이 유지됐는지 알 수 있는가?
- 적용 전 원래 계획, 적용 뒤 새 계획과 저장 상태를 구분하는가?
- 일정·일지·근거에 같은 처방이 표시되는가?
- 실제 이용자 평가에서 이해율/탭 수/취소 회복/수행 시작 시간을 측정하되 가상 페르소나 결과로 대체하지 않는가?
- 운영 지표는 오류·저장 실패·의도치 않은 변경·대안 없음 비율 중심인가? 고강도·거리 증가량을 성공으로 삼지 않는가?

운영 지표에는 기본적으로 세션 메모, PB 원본, 통증 내용, 전체 개인 처방을 보내지 않는다. 집계에 필요한 동작 종류·실패 범주·시간 구간을 최소화하고 기존 동의/보관 정책을 따른다. `바꾼 이유`는 선택 사항이며 탐색마다 질문하지 않는다.

## 17. 외부 기준과 이번 검토의 한계

- Apple [Steppers](https://developer.apple.com/design/human-interface-guidelines/steppers): 조절하는 값이 무엇인지 명확해야 한다. TrainOracle의 `한 번 거리/총거리` 분리 근거로 사용했다.
- Apple [Undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo): 되돌릴 수 있는 탐색의 방향을 참고했다. 저장·안전·처방 권한의 근거는 아니다.
- W3C [On Input](https://www.w3.org/WAI/WCAG22/Understanding/on-input): 선택 탐색만으로 예상치 못한 화면 전환이 일어나지 않도록 한다.
- W3C [Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html): 터치 크기·모션 대체를 확인했다.
- UI/UX 스킬 검색의 스포츠용 붉은색·새 폰트·큰 블록 제안은 기존 디자인 시스템과 맞지 않아 채택하지 않았다. 점진 공개·접근성 관점만 참고했다.

조회일은 2026-09-27이다. 이 자료들은 인터페이스 참고이며 훈련 용량·효과를 승인하는 스포츠과학 근거가 아니다. 초안의 책상 검토는 실제 앱 시험이 아니다. 이후 실제 실행 증거는 별도 구현 보고서에 기록하며 새로운 운동량·강도·회복의 채택과 혼동하지 않는다.
