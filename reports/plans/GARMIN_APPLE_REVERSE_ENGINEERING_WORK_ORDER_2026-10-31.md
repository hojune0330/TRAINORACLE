- 작성일: 2026-10-31 KST
- 대상: 다음 역설계 담당 작업자
- 산출물 지위: **후속 상세 개발 계획의 근거를 만드는 조사 지시서**
- 오너 요구: Garmin·Apple에서 확인하던 세부 기록과 조작을 TrainOracle에서도 빠뜨리지 않아야 한다. 요약 카드나 디자인 분위기만 조사하고 끝내지 않는다.
- 진행 순서: **이 지시서 전달 → 실제 관찰·데이터 대조 → 미확인 항목 정리 → 상세 구현 계획 확정**.

## 0. 맡은 일과 완료의 의미

Garmin Connect와 Apple Fitness·Health·Watch에서 사용자가 운동과 건강 데이터를 확인하는 구조를 역설계한다. 그 결과를 현재 TrainOracle의 수집·변환·저장·조회·표시 경로와 대조한다.

각 기능에 대해 다음 질문에 근거로 답해야 한다.

1. 사용자는 어디서 진입하며 무엇을 읽고 어떤 조작을 하는가?
2. 화면의 각 값은 무엇을 뜻하며, 단위·시간 범위·출처는 무엇인가?
3. 공식 API·HealthKit·사용자 내보내기 중 어느 경로에서 어떤 필드로 받을 수 있는가?
4. 현재 계정에서 실제 수신한 증거가 있는가? 문서상 후보인가?
5. TrainOracle의 어느 단계가 그 정보를 유지·변경·누락하는가?
6. 원본과 같은 의미로 보여주려면 어떤 데이터 계약과 UI 동작이 필요한가?
7. 표시·일반 분석·자체 호스팅 LLM 추론 등 목적별 허용은 어디까지 확인됐는가?

**다음 개발자가 화면, 데이터 구조, 예외 처리, 검증 대상을 다시 추측하지 않고 개발 작업으로 옮길 수 있어야 한다.** 화면 수나 문서 분량으로 완료를 판정하지 않는다.

이번 담당 범위는 조사·대조·설계 입력 작성이다. 제품 코드 수정, 새 연동 활성화, 병합·배포는 후속 구현 작업으로 둔다. 조사용 파일과 비식별 증거는 전용 산출물 폴더에 작성한다.

## 1. 시작 자료와 저장소 상태

### 1.1 작업 위치

현재 확인한 체크아웃:

```text
D:\admin\Documents\ChatGPT\트레인 오라클\TRAINORACLE-garmin-selfhosted-20261030
```

이 지시서 작성 시 HEAD는 `f6d19aef9cb0635aee77a42c93e97ea8ddc41a36`이다. 착수 시 현재 경로·HEAD·브랜치·작업 트리 상태를 다시 기록한다. 해당 SHA를 최신 상태라고 가정하지 않는다.

현재 체크아웃에는 `LogDetail.tsx` 변경과 미추적 상세 컴포넌트·연구·검증 자료가 있다. 다른 작업자의 변경과 `tmp/`를 보존한다. 다른 체크아웃에는 아직 이 자료가 없을 수 있으므로 존재 여부부터 확인한다. 미추적 파일을 포함해 무작정 add·reset·clean·stash·checkout하지 않는다.

없는 자료는 검색 가능한 정확한 저장소 위치를 찾고, 끝내 확보하지 못한 파일을 목록에 남긴다. 다른 작업자의 기존 승인을 자료 부재만으로 다시 요청하지 않는다.

## 2. 조사 범위와 우선순위

### 2.1 주 대상

| 대상 | 반드시 분리해서 조사할 표면 |
|---|---|
| Garmin | Connect 모바일, Connect 웹, 활동 상세, 차트·구간·경로, 관련 건강·회복 상세 |
| Apple | iPhone Fitness의 운동 상세, iPhone Health의 지표·출처, Watch의 운동 화면·종료 후 요약 |

같은 제공자여도 플랫폼별로 화면·조작·지원 지표가 다를 수 있다. 한 플랫폼의 관찰로 다른 플랫폼을 채우지 않는다. 앱 버전·OS·기기·언어·지역·표시 단위·유료 기능 여부를 함께 기록한다. 확인할 수 없는 항목은 미확인이다.

### 2.2 조사 순서

1. **P0 — 실제 기록을 자세히 읽는 핵심 경로**: 운동 목록 → 해당 운동 → 요약 → 랩/스플릿 → 심박·페이스 등 차트 → 경로 → 출처 → 원래 목록 복귀.
2. **P0 — 데이터가 손실되는 경로**: 같은 운동의 원 화면·내보낸 파일·API/HealthKit 응답·현재 파서 출력·저장 계약·재조회·표시 비교.
3. **P1 — 종목과 상태 확장**: 실내, 인터벌, 걷기, 자전거, 수영·멀티스포츠의 데이터 구조 차이와 조건부 화면.
4. **P1 — 일별 건강·회복**: 수면·심박·HRV·활동량·부하·회복 및 제공자 고유 점수의 표시·기간·출처·외부 제공 여부.
5. **확장 메모**: COROS, 삼성 Health Connect 및 다른 회사에 공통으로 적용할 부분과 별도 어댑터가 필요한 부분. 이번 Garmin·Apple 직접 관찰을 타사 검증으로 확대하지 않는다.

둘 중 접근이 가능한 대상부터 진행한다. 네이티브 접근이 막혀도 웹·공식 자료·제공된 내보내기·현재 코드 조사는 계속한다. 네이티브 조사 결과는 미확인으로 남긴다.

## 3. 증거 규칙

모든 주장에는 아래 증거 종류와 연결 ID를 붙인다. 하나의 단일 ‘확인됨’ 체크로 합치지 않는다.

| 종류 | 입증하는 범위 |
|---|---|
| `native-observed` | 실제 네이티브 화면에서 재현한 표시·동작 |
| `web-observed` | 실제 웹 화면에서 재현한 표시·동작 |
| `official-static` | 공식 문서·영상·정적 이미지에서 확인한 내용 |
| `api-documented` | 공식 API/SDK의 타입·필드·조건 설명 |
| `payload-observed` | 실제 승인된 경로에서 받은 자료의 필드·값 |
| `repo-traced` | 현재 소스의 함수·스키마·호출 경로에서 확인한 내용 |
| `roundtrip-observed` | 같은 기록을 수신→저장→재조회→표시까지 대조한 내용 |
| `inferred` / `unknown` | 추론 또는 미확인. 판단 근거와 다음 확인 방법을 명시 |

증거마다 `evidenceId`, 확인 시각, 대상 버전/기기, 접근 경로, 재현 단계, 출처 URL 또는 로컬 상대 경로, 입증 범위·한계를 적는다. 파일 증거에는 해시를 기록한다. 자료가 개정되면 버전도 남긴다.

- 스크린샷 한 장은 눌렀을 때의 동작을 증명하지 않는다.
- SDK에 타입이 있다는 사실은 해당 기기·운동에 표본이 있다는 뜻이 아니다.
- 프로그램 승인·OAuth 성공·HTTP 200은 실제 활동 필드 수신이나 저장 왕복 완료와 별개다.
- 추정한 레이아웃 수치와 직접 측정한 수치를 구분한다. 화면 px를 기기의 pt/dp라고 쓰지 않는다.
- 실제 기록 캡처와 합성 예시는 분리한다. 합성 예시는 눈에 띄게 표시한다.
- 외부 공개 보고서에는 개인 경로·건강 원본·계정 정보·토큰을 넣지 않는다. 대조에 필요한 비식별 표본과 증거 ID를 사용한다. 민감한 원본은 기존 승인된 보관 위치를 유지한다.

## 4. 화면과 상호작용을 전부 목록화

### 4.1 화면 단위

각 대상의 화면 ID를 부여하고 다음을 채운다.

```text
screenId / 제공자 / 앱·플랫폼·버전 / 종목·데이터 조건
진입 경로 / 뒤로 가기 대상 / 재진입 시 유지되는 필터·스크롤
영역 순서 / 고정·스크롤 영역 / 접힘·펼침 / 상세 진입점
표시 필드 ID / 기본 선택 / 단위 / 도움말·출처 접근
기본·빈값·부분값·로딩·실패 상태
관련 evidenceId / 미관찰 상태 / TrainOracle 대응 화면 후보
```

활동 상세는 스크롤 아래까지 조사한다. 제목과 첫 요약만 캡처하고 상세 전체를 조사했다고 쓰지 않는다. 메뉴·상세 패널·툴팁·단위 설정·날짜 선택 등 결과를 바꾸는 조작을 포함한다.

### 4.2 동작 단위

버튼·탭·차트마다 `초기 상태 → 입력 → 결과 상태 → 복귀·취소`를 기록한다. 실제 실행한 것과 설명서에 나온 것을 분리한다.

| 영역 | 확인할 동작 |
|---|---|
| 목록 | 날짜·종목·제공자 필터, 같은 날 복수 운동, 더 읽기, 상세 후 복귀 |
| 요약 | 기본 지표 우선순위, 더 보기, 단위 변경, 종목별 항목 차이 |
| 랩·스플릿 | 정렬·원순서, 수동/자동 랩, 워크/회복 구간, 스플릿 거리 단위, 선택과 차트 연결 |
| 차트 | 지표 선택, 시간/거리 축, 시점 조회, 확대·축소·초기화, 범위 선택, 오버레이, 스크롤과 터치 충돌 |
| 차트 보조 | 단위·축 범위·범례, 평균선/구간선, 누락 표본, 일시정지, 원자료 표 접근 |
| 경로 | 전체 경로, 시작/종료, 확대, 구간·차트 시점 연결, GPS 누락·실내 상태 |
| 건강 상세 | 일/주/월/연 변경, 날짜 이동, 기간 집계, 측정 구간·출처·기기 확인 |
| 상태 변경 | 새로고침, 늦게 도착한 자료, 정정, 연결 해제, 재연결 후 중복 |

관찰되지 않는 기능은 ‘없음’이라고 단정하지 않는다. 위치를 찾지 못한 것과 해당 버전에 없는 것을 구분한다.

## 5. 필드 단위 데이터 사전

기존 57개 묶음을 출발점으로 실제 표시·수신 필드로 분해한다. 예를 들어 ‘심박’ 하나로 끝내지 말고 평균, 최대, 시계열, 구간 경계, 구간별 체류시간, 회복 심박을 서로 다른 항목으로 만든다.

각 행은 **제공자 × 플랫폼 × 지표 × 수신 경로**를 구분할 수 있어야 한다.

| 열 묶음 | 필수 열 |
|---|---|
| 식별 | fieldId, 한국어 이름, 원래 명칭, provider, platform, sport, screenId |
| 의미 | quantity, unit, statistic, observationWindow, timeBasis, nullMeaning |
| 원천 | originProvider, writer/sourceRevision, device, transport, nativeActivityId, revision |
| UI 근거 | uiStatus, uiEvidenceIds, 표시 위치, 반올림/정밀도 |
| 수신 근거 | route, endpoint 또는 SDK type, 정확한 payload path, 최소 OS/기기/권한 조건, apiEvidenceIds |
| 실제 확인 | accountScopeStatus, payloadStatus, sampleEvidenceIds, 실제 샘플 유무 |
| 처리 | 원본값 또는 계산값, 변환식·근거, parser 위치, normalized path, 저장 위치, 조회 위치, UI 위치 |
| 목적별 사용 | 수신·보관·표시·일반 분석·LLM 추론·모델 학습·계획 전송의 각 상태와 근거 ID |
| 실행 판단 | 현재 손실 지점, 의존성, 우선순위, 미확인 질문, 검증 방법 |

`uiStatus`, `payloadStatus`, 목적별 허용을 하나의 boolean으로 합치지 않는다. `미조사`, `문서상 있음`, `직접 확인`, `해당 조건에서 없음`, `명시적으로 제공 불가`, `확인 불가`를 구분한다.

### 반드시 세분화할 항목

- 신원·시간: 운동 ID, 수정 버전, 시작·종료, 원 offset/시간대, 일지 날짜, 기록 기기·작성 앱·전달 경로.
- 운동량: 거리, 타이머 시간, 이동 시간, 경과 시간, 멈춤 구간, active/total calories.
- 속도: 평균/순간/최대 속도·페이스, 랩 평균, 거리 스플릿, 표시용 평활화 여부.
- 심박: 평균/최대/시계열, 구간 설정과 적용 시점, 구간별 시간·비율, 휴식·회복 관련 값.
- 달리기 자세: 케이던스 단위, 보폭, 수직 진폭·비율, 지면 접촉 시간·균형, 지원 기기 조건.
- 파워·고도: 평균/최대/시계열, 파워 구간, 누적 상승·하강과 고도 표본, 보정 출처.
- 경로·구간: GPS 좌표·정밀도·시각, 원본 랩, 자동 스플릿, 인터벌 워크/회복, 이벤트 마커.
- 종목 특화: 자전거의 센서·기어 등 조건부 필드, 수영의 길이·풀 길이·스트로크, 멀티스포츠 전환 구간. 존재와 접근이 확인된 범위까지 조사.
- 일상·회복: 걸음·활동량·휴식 심박·HRV·수면 단계·측정 창·주간 부하 등.
- 고유 점수: Garmin의 Training Effect/Load/Status, Recovery, Body Battery, Stress 등과 Apple의 노력·훈련 부하 등. 표시 여부, 정확한 정의, 외부 제공 여부를 각각 확인.

### 의미가 달라지기 쉬운 항목

1. `duration`이라는 이름만으로 이동 시간이라고 정하지 않는다. 원천의 정의를 확인한다.
2. 원본 랩과 거리로 재구성한 스플릿을 같은 것으로 처리하지 않는다. 시간 경계가 없는 랩은 차트 선택 범위를 확정하지 못할 수 있다.
3. 시간÷거리로 계산한 페이스와 기기가 보고한 평균 페이스가 다를 때 적용 시간·정밀도·평활화 차이를 추적한다. 한쪽을 조용히 덮어쓰지 않는다. 거리÷시간은 속도로 구분한다.
4. 케이던스의 steps/min·strides/min·rpm을 구분한다.
5. HRV의 SDNN·RMSSD와 순간·야간·기간 평균을 구분한다.
6. 수면은 취침 시간, 실제 수면, 단계, 겹친 샘플, 자정 이후 날짜 귀속을 분리한다.
7. 결측, 실제 0, 빈 배열, 일부 표본, 늦은 도착, 비공개 권한 상태를 다른 상태로 다룬다.
8. Garmin → Apple Health → TrainOracle처럼 원 제공자와 전송 경로를 따로 유지한다. 작성 앱과 원 측정 제공자가 항상 같다고 가정하지 않는다.
9. 제조사 점수의 표시 권한과 고유 계산식 재현 가능성을 구분한다. 확인되지 않은 자체 계산을 제조사 점수명으로 제안하지 않는다.
10. 회사 관리 서버의 자체 호스팅 LLM 도입은 전제다. 이것만으로 각 제공자 자료의 추론·학습 허용이 확인됐다고 쓰지 않는다. 기존 문의·약관 근거를 목적별로 연결한다.

## 6. 같은 기록으로 데이터 경로 대조

가능한 경우 다음 경로를 동일한 실제 운동에 대해 연결한다. 제공자·내보내기·HealthKit·TrainOracle의 ID가 서로 다를 수 있으므로 각 경로의 원천 ID·revision 대응표와 동일 운동으로 판단한 근거를 남긴다. ID 문자열 자체가 같아야 하는 조건은 아니다. 연결이 불확실하면 중복 후보로 남긴다.

```text
제공자 원 화면
  → 공식 API / HealthKit / 사용자가 내보낸 파일
  → 파서 출력
  → 정규화·출처·중복 판정
  → 현재 저장 계약
  → 재조회 결과
  → TrainOracle 상세 표시
```

모든 화살표마다 입력·출력 근거와 유지/변환/누락 필드를 기록한다. 아직 구현되지 않았거나 실제 접근이 없는 단계는 끊어진 지점 그대로 표시한다.

내보내기는 사용자 조작부터 조사한다. 앱/웹 중 어디서 어떤 메뉴로 내보내며, 단건·일괄·압축 파일 여부, 생성 대기와 파일 선택 이후 과정이 어떠한지 기록한다. FIT·TCX·GPX·CSV·JSON·Apple 건강 내보내기 등은 **실제로 제공되거나 확보한 형식만** 지원표에 넣고, 형식마다 보존되는 랩·표본·좌표·출처와 현재 TrainOracle의 직접 처리 가능 여부를 비교한다. 한 형식의 성공을 다른 형식의 성공으로 확대하지 않는다.

### 6.1 비교 기록

대조표에는 최소한 원본 값, 파서 값, 저장·재조회 값, 표시 값, 단위·시간 의미, 차이, 설명 가능한 반올림, 판정, 증거 ID를 포함한다. 직접 수신하지 않은 필드는 공개 fixture로 보충할 수 있지만 별도 비교 행으로 둔다.

차이가 있을 때 원인을 `원천 미제공 / 권한 또는 조건 / 파서 손실 / 변환 차이 / 저장 제한 / 조회 누락 / 표시 반올림 / 미상`으로 특정한다. 허용 오차를 임의로 넓혀 일치로 판정하지 않는다.

### 6.2 대표 시나리오

| ID | 사례 | 특히 확인할 것 |
|---|---|---|
| S01 | 야외 달리기 | 요약·심박·페이스·GPS·랩의 연결 |
| S02 | 일시정지 포함 | 경과/타이머/이동 시간, 차트의 시간 축 |
| S03 | 인터벌 | 워크/회복, 원본 랩, 자동 스플릿의 차이 |
| S04 | 실내 달리기 | 경로 없음, 거리 보정, 센서 조건 |
| S05 | 센서 일부 누락 | 심박/파워 없는 상태, 표본 중간 단절 |
| S06 | 같은 날 복수 운동 | 목록→정확한 ID 상세→복귀·일지 연결 |
| S07 | 자정·시간대 변경 | 운동 시작일, 일지 날짜, 여행·DST 자료가 있을 때 처리 |
| S08 | 같은 기록의 복수 경로 | 파일/API/HealthKit 중복 후보, 원천 보존 |
| S09 | 정정·재수신·늦은 경로 | 동일성, 버전, 부분 자료 갱신 |
| S10 | 긴 기록·많은 랩 | 실제 표본·랩 수, 크기·렌더링·페이지 처리 |
| S11 | 일별 수면·HRV | 기간·방법·출처·겹침·날짜 귀속 |
| S12 | 미연결·읽을 자료 없음·연결 해제 | 구별 가능한 상태와 사용자에게 설명 가능한 범위 |
| S13 | 걷기·자전거·수영·멀티스포츠 | 공통 모델로 표현되지 않는 종목별 필드 |

실제 보유 자료에 없는 시나리오를 만들기 위해 사용자에게 운동을 시키거나 기록을 변경하지 않는다. `실자료 재현 / 합성 대조 / 문서만 확인 / 접근 불가 / 해당 없음`과 이유를 남긴다.

이번 조사는 기존 승인된 계정·자료 접근 범위를 따른다. 새 기록 저장·삭제·권한 변경 등 상태 변경이 필요한 검증은 이미 그 행동까지 승인된 경우에만 실행하고, 그 외에는 재현 절차와 필요한 상태를 남긴다. 계정 승인 문제 때문에 독립적인 파일·소스 조사를 중단하지 않는다.

권한 거부와 읽을 자료 없음이 앱에서 실제로 구분 가능한지는 SDK·응답 계약을 확인한다. 구분할 근거가 없는 빈 결과에 ‘사용자가 권한을 거절했다’는 상태를 임의로 붙이지 않는다.

## 7. 디자인·사용성 계약 추출

목표는 사용자가 익숙한 정보 구조와 조작을 TrainOracle에서 충분히 사용할 수 있게 하는 것이다. 기능 요구와 시각 표현을 함께 조사한다.

### 7.1 측정 항목

- 주요 수치·단위·라벨·보조값의 위계, 숫자 정렬·자리수·줄바꿈.
- 첫 화면의 정보량, 상세 진입 횟수, 반복 탐색 시 유지되는 위치.
- 여백·그리드·표 열 너비·분리선·그룹 경계. 수치마다 측정/추정 여부.
- 차트 축·범례·선·점·구간 색·선택 상태·툴팁 위치·커서 동기화.
- 터치와 스크롤 충돌, 포커스 이동, 화면 읽기 라벨, 숫자를 읽는 대체 표.
- 작은 화면·큰 글자·긴 값·결측·오류 문구에서 핵심 값과 조작이 유지되는지.
- 밝은/어두운 테마 및 플랫폼 차이 중 직접 관찰 가능한 범위.

### 7.2 TrainOracle로 옮기는 대응표

각 동작에 다음을 작성한다.

```text
원 화면/동작 ID
사용자가 해결하는 질문
필요한 필드·데이터 조건
유지해야 할 정보·조작
TrainOracle 기존 컴포넌트/토큰/동선 후보
새 컴포넌트 또는 계약이 필요한 이유
빈값·부분값·미지원에서의 표시와 다음 행동
수락 시나리오와 관찰 증거
```

기존 RecordUI·시각 토큰·일지 동선을 우선 대조한다. 브랜드 자산을 가져오는 작업과 정보 구조를 구현하는 작업을 혼합하지 않는다. 관찰한 레이아웃을 설명할 필요가 있으면 주석 달린 와이어프레임을 만들고 ‘분석용 재구성’으로 표시한다.

## 8. 현재 TrainOracle의 손실 지점 추적

기존 소스 경로를 출발점으로 사용하되 현재 파일·함수·줄 번호를 재확인한다.

| 후보 | 조사 질문 |
|---|---|
| `app/src/domain/import/activity-file.ts` | TCX Trackpoint·GPX 좌표·각 센서가 실제로 어디까지 남는가? |
| `app/src/domain/import/structured-activity-file.ts` | JSON/CSV 등 구조화 입력의 지원 필드·한계는 무엇인가? |
| `app/src/domain/import/file-observation.ts` | 스키마·확인값·원본값·제한·fingerprint가 무엇을 포함하는가? |
| `app/src/domain/import/file-analysis.ts` | 분석용 투영에서 시간·출처·세부 항목이 떨어지는가? |
| `app/src/domain/import/account-import.ts` | 계정/기기 경로·형식·플래그별로 보존되는 자료가 다른가? |
| 계정 일지 projection/schema/validator | 저장 전·후의 타입·버전·마이그레이션·구형 자료 호환은 무엇인가? |
| `supabase/functions/_shared/account-journal-handler.mjs` | 요청 크기·권한·검증·저장·재조회 경계는 무엇인가? |
| `app/src/components/ImportedActivityDetail.tsx` | 로컬 후보가 표시할 수 있는 값과 저장하지 않는 값은 무엇인가? |
| `app/src/screens/LogDetail.tsx` | 실제 일지 ID 연결·재방문·편집·출처 표시에 어떤 계약이 있는가? |
| 차트·내보내기·백업·동기화 소비자 | 새 필드/표본을 추가할 때 함께 바뀌어야 하는 경로는 무엇인가? |

추적 범위는 실제 관련 코드로 한정한다. 전체 저장소를 의미 없이 재검사하지 않는다. 파일을 열기 전 AGENTS의 도메인별 선행 문서를 따른다.

각 손실 지점은 `입력 필드 → 함수 → 출력 필드 → 소비자 → 사용자 영향 → 필요한 계약 변경`으로 기록한다. 기존 정보 보존, 구형 자료 읽기, 수정 이력, 삭제, 계정 격리, 백업/복구, 중복 판정에 영향을 주는 공유 계약은 별도로 표시한다.

대용량 시계열을 기존 일지 JSON에 넣을 수 있다고 가정하지 않는다. 현재 제한을 실제 코드에서 읽고, 확보한 대표 자료의 bytes·표본 수·랩 수와 비교한다. 원자료 보관·청크/manifest·다운샘플 표시 후보는 필요한 경우만 제시한다. 측정하지 않은 처리 시간·메모리·저장 비용을 성능 달성치처럼 쓰지 않는다.

## 9. 도구 선택과 접근 불가 시 처리

- 화면 구조·사용자 동작에는 실제 브라우저/네이티브 관찰이 우선이다. 소스 경로 추적에는 일반 저장소 도구를 사용한다.
- 사용자가 제공한 설치 패키지·허용된 실행 대상에서 정적 리소스나 런타임 근거가 필요한 경우 REA의 실제 사용 가능한 도구를 선택한다. 설치된 스킬 이름을 실행 성공으로 취급하지 않는다.
- 바이너리·네트워크 내부를 조사할 이유가 없으면 해당 조사를 강제하지 않는다. 조회한 비공개 엔드포인트를 곧바로 제품 연동 경로로 제안하지 않는다. 제품 수신 경로는 공식 API/SDK/사용자 내보내기와 대조한다.
- 필요한 도구가 없으면 정확한 미지원 단계를 남기고 가능한 관찰을 계속한다. 불필요한 도구 설치·시스템 설정 변경으로 범위를 늘리지 않는다.
- 로그인 세션·토큰·서명 URL을 보고서나 공개 fixture에 복사하지 않는다. UI와 필요한 데이터 필드의 근거를 최소한으로 남긴다.

실기기 또는 특정 화면에 접근하지 못하면 다음 형식으로 **작은 추가 관찰 요청 목록**을 만든다.

```text
대상 앱·버전·기기:
열어야 할 정확한 경로:
필요한 조작 한 가지:
캡처할 전/후 상태:
가려야 할 개인 정보:
이 관찰로 결정할 구현 질문:
대체 근거로 이미 확인한 범위:
```

‘가민 화면을 전부 보내달라’ 같은 넓은 요청은 피한다. 같은 질문에 답하는 증거가 있으면 재요청하지 않는다.

| `ui-contract.md` | 측정된 시각·동작 계약, 접근성·상태, 기존 컴포넌트 대응 |

문서 간 같은 표를 복제하지 말고 ID로 연결한다. 필드 이름과 증거 ID가 바뀌면 참조도 함께 갱신한다. 최종 보고 전에 링크·JSON 문법·중복 ID·누락된 참조를 확인한다. 조사 문서만 작성한 경우 앱 전체 빌드·CI를 돌릴 필요는 없다.

## 11. 수락 기준

### 11.1 조사 결과를 받을 수 있는 조건

- Garmin·Apple의 주 대상 표면마다 접근/버전/관찰 범위가 명시되어 있다.
- P0 경로의 각 화면·조작에 직접 증거 또는 구체적인 미확인 사유와 다음 확인 방법이 있다.
- 세부 필드마다 UI, 공식 수신 경로, 실제 payload, 계정 범위, 저장/조회, 표시, 목적별 허용을 별도로 판정했다.
- 대표 기록 비교는 가능한 단계까지 실제로 이어지고, 끊긴 지점이 명확하다.
- 차트·랩·경로·시간·결측·중복·정정의 핵심 의미 차이를 설명한다.
- 구현 후보마다 현행 코드 근거, 필요한 입력, 영향을 받는 계약, 검증 방법이 연결된다.
- 접근 불가로 남은 항목이 개발 계획에서 어떤 결정을 막는지 구체적으로 적혀 있다.

### 11.2 완료 표현

보고서 작성 완료와 네이티브 직접 관찰 완료를 구분한다. 제공자별·표면별·시나리오별로 `완료 / 부분 / 미확인 / 해당 없음`을 판정한다. 접근 불가 항목을 적었다는 이유만으로 해당 역설계가 완료된 것은 아니다.

다음 결과만으로 ‘역설계 완료’ 또는 ‘제품 사용 가능’이라고 쓰지 않는다.

- 공식 문서 링크와 화면 몇 장만 정리함.
- 57개 묶음을 그대로 옮기고 세부 필드·수신 경로를 확인하지 않음.
- 요약값만 일치하고 랩·표본·시간대·출처를 대조하지 않음.
- 합성 데이터의 예쁜 화면, 빌드 성공, 개발자 계정 승인, OAuth 성공만 있음.
- TrainOracle에서 현재 버리는 필드를 특정하지 않고 ‘어댑터 개발 필요’라고만 씀.

## 12. 후속 상세 개발 계획으로 넘길 형식

역설계 담당자는 확인된 격차를 아래 형식의 **작업 후보**로 넘긴다. 최종 우선순위·작업 분담·실행 계획은 이 결과를 받은 주 담당자가 현재 진행 중인 구현과 통합해 확정한다.

```text
작업 ID / 사용자에게 가능해질 행동
근거 screenId·fieldId·scenarioId·evidenceId
현재 동작과 정확한 결손
선행 작업 ID / 외부 의존성 / 미확인 결정
변경 후보 파일·컴포넌트·스키마·API
입력·출력 계약 / 단위·시간·출처·null 규칙
원본·구형 기록·중복·정정·삭제에 미치는 영향
필수 정상 사례 / 핵심 실패·경계 사례
완료를 확인할 실제 사용자 경로와 증거
후속 계정·실기기 검증 필요 여부
독립 구현 가능한 범위와 공유 계약 책임자 후보
```

‘차트 구현’처럼 큰 이름으로 끝내지 않는다. 예를 들어 시간축 표본 계약, 결측 구간 표현, 시점 조회, 랩 선택 연동은 입력·검증 조건이 다르면 별도 후보로 나눈다. 반대로 같은 계약과 검증으로 끝나는 작은 변경은 묶는다.

최종 요약에는 **다음 계획의 순서를 바꾸는 발견**, **먼저 합의해야 하는 공유 데이터 계약**, **실제 기기·계정이 있어야 닫을 수 있는 항목**을 앞에 둔다. 근거 없는 완료율이나 개발 일수를 쓰지 않는다.
