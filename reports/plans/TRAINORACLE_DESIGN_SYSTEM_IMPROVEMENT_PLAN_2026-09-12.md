## 1. 목표

**이미 개발된 제품을 유지하면서, 각 페이지가 같은 앱답게 정교하고 아름답게 보이도록 만든다.**

디자이너 제안은 미감·에셋·컴포넌트 표현의 재료다. 제안 속 단어, 화면 이동, 훈련 수치, 저장 방식, 새 기능을 그대로 복사하지 않는다. 원래 있던 기능을 빼거나 단순화하는 계획도 아니다.

사용자가 체감할 결과는 다음 다섯 가지다.

1. 훈련계획을 열면 날짜·주요 훈련·수행 수치가 먼저 읽힌다.
2. 일지를 빠르게 쓰거나 자세히 쓰는 기존 방식이 그대로 편하다.
3. 꾸미기에서는 종이와 재료가 잘 보이고, 안내창이 조작을 막지 않는다.
4. 분석·오라클은 수치·근거·상태의 시각적 구분이 또렷하다.
5. 홈부터 로그인·설정까지 폰트·아이콘·간격·버튼의 밀도가 일관된다.

### 1.1 검토 근거

[선행 검토 보고서](../review/TRAINORACLE_DESIGN_SYSTEM_REUSE_REVIEW_2026-09-12.md)의 D-01~D-08을 해결 대상으로 삼는다. 선행 리뷰의 40개 캡처는 기준 상태 자료이지 이번 개선의 통과 증거가 아니다. 실제 구현 후 다시 검수한다.

신규 디자인 PR은 아직 특정하지 못했다. 확인된 시안은 main의 `design_handoff_plan_beta_extension/`이다. 실제 PR이 다르면 그 diff를 추가 대조하되, 이미 확인한 현행 앱 결함의 수정 준비까지 멈추지는 않는다.

### 1.2 이번 요청의 결과물

이번에는 상세 계획을 작성한다. 앱 구현, 작업자 실행, 커밋·푸시, 병합·배포는 시작하지 않는다. 아래의 파일 변경·PR·검사 항목은 향후 실행 범위다.

### 1.3 후속 실행 승인 (2026-09-12)

위 §1.2는 계획 작성 당시의 범위로 보존한다. 이후 오너가 "작업 쭉 진행해 멈추지 말고 모두 끝날 때까지"라고 승인하여 구현 단계에 착수했다. 제품 의미를 변경하지 않는 본 계획의 구현·검수·공개 반영이 실행 범위이며, 정확한 단계 상태와 증거는 [실행 보고서](../implementation/TRAINORACLE_DESIGN_SYSTEM_IMPROVEMENT_EXECUTION_2026-09-12.md)에 기록한다. 계획의 최초 작업표는 착수 전 기준으로 유지하고 실행 완료로 소급하지 않는다.

### 2.1 불변 목록

- 원본 일지·비밀 메모·계정 토큰을 시각 fixture나 스크린샷 증거에 넣지 않는다.
- `D9` 판정, 처방 허용 목록, 개인 기록 사용 범위, 적응 제한을 바꾸지 않는다.
- 시작·미리보기·선택을 훈련 완료로 처리하지 않는다.
- 날짜·오전/오후·소중대주기 연결을 화면 정리 과정에서 합치지 않는다.
- 미기록을 0으로 바꾸거나, 출처·불확실성 표시를 삭제하지 않는다.
- 서버 확인 전 저장 완료 표시, 계정 전환 후 다른 사용자의 초안 노출을 허용하지 않는다.
- 장식의 소유·구매·24개 상한·기존 레거시 파싱·undo/redo·자유 배치를 보존한다.
- 기본·전문 보기는 같은 처방이다. 기본 보기를 정보가 부족한 버전으로 만들지 않는다.

### 2.2 화면 표현 변경과 기능 변경의 경계

같은 정보의 글자 크기·정렬·간격·구분선·색상 역할을 조정하는 것은 허용한다. 기존 섹션 안에서 표현을 묶는 것도 허용한다. 그러나 필수 경고를 새로 접거나, CTA를 다른 단계로 옮기거나, 클릭 후 목적지를 바꾸는 것은 기능 검토로 분리한다.

현행 문구 자체의 오류를 발견하면 별도 항목으로 기록한다. 디자인 개선을 핑계로 고치지 않으며, 실제 안전·저장 오해가 발생하면 해당 부분만 멈추고 영향과 수정안을 제시한다.

## 3. 디자인 결정

### 3.1 기존 디자인 시스템을 유지한다

- 값의 원본: `colors_and_type.css`, `colors_and_type_journal.css`.
- 서체: self-hosted Pretendard Variable. 코드가 아닌 한글 라벨을 다른 mono 서체로 바꾸지 않는다.
- 아이콘: 현재 Lucide 사용. 버튼의 의미는 아이콘·현재 라벨·접근 가능한 이름으로 유지한다.
- 앱 바깥: 중립 배경, 청록 강조, 절제된 구분선.
- 일지 안쪽: 종이·잉크·재료의 표현. 전체 앱을 종이색으로 덮지 않는다.
- 기존 컴포넌트를 먼저 확장한다. 새 UI 프레임워크·아이콘 팩·애니메이션 라이브러리는 도입하지 않는다.
- 시안의 `shared/tokens.css`는 앱에 import하지 않는다.

### 3.2 글자와 크기 기준

| 역할 | 적용 기준 |
|---|---|
| 앱 제목 | 기존 `--fs-app-title` 유지. 페이지마다 별도 대형 제목을 만들지 않음 |
| 섹션 제목 | 기존 앱 섹션/소제목 토큰을 컨테이너 크기에 맞춰 사용 |
| 주요 훈련 숫자 | 컴포넌트 전용 고정 크기 variant로 강조. 값·단위를 함께 읽을 수 있어야 함 |
| 수행 설명 | 기존 본문 토큰을 기준으로 유지. 한 화면에 맞추려고 축소하지 않음 |
| 상태·근거 라벨 | 읽어야 하는 문장은 12px 캡션을 기본 후보로 정리. 숨은 정보처럼 만들지 않음 |
| compact 탭 | 현재 보이는 높이32px/터치44px 구분 유지. 본문·입력 항목까지 compact 적용하지 않음 |
| 터치 타깃 | 실제 클릭 영역 최소44px. 그림만 크게 하거나 영역만 겹치게 확장하지 않음 |
| 숫자 | tabular-nums, 오른쪽 또는 동일 축 정렬. 다른 단위를 같은 숫자 행에 혼합하지 않음 |
| 한글 | 자간0, 자연스러운 줄바꿈. 긴 단어와 200% 확대에서 잘림 금지 |

페이지 전체 폰트를 비율로 한꺼번에 줄이거나 늘리지 않는다. 글자 크기를 viewport 너비에 따라 축소해 문제를 감추지 않는다. 모바일 입력 시 자동 확대와 키보드 가림은 실제 브라우저로 검수한다.

### 3.3 한눈에 보인다는 것의 정의

모든 설명을 한 화면에 압축한다는 뜻이 아니다. 현재 단계에서 판단할 제목, 주요 값, 선택 가능 행동이 먼저 읽히고, 아래 내용이 이어진다는 단서가 있어야 한다. 긴 설명은 기존 상세 보기로 읽으며, 스크롤을 금지하지 않는다.

## 5. DS-00: 기준·보존 목록 확정

### 목적

새로운 디자인을 적용하다가 기존 기능을 지우거나, 오래된 디자인 규칙을 최신 승인처럼 따르는 일을 방지한다.

### 수행

1. 시작 시 현재 main·열린 PR·수정 파일을 재확인한다. 다른 작업자의 변경은 유지한다.
2. 선행 리뷰와 증거 파일이 실제로 존재하는지 확인한다. 기준 해시가 달라졌으면 영향받은 화면만 다시 비교한다.
3. 신규 디자인 PR을 식별하면 head SHA·변경 파일·에셋을 기록한다. 미식별이면 신규 에셋 도입만 대기하고 DS-01은 진행 가능하다.
4. 기존 `SKILL.md`, `DESIGN.md`, 시각 기준의 각 조항에 현행 앱/대시보드/레거시/제안 범위를 정리한다.
5. 현재 저장 상태와 동작하는 문구를 기준 snapshot으로 남긴다. 제품 의도와 충돌하는 코드는 정상으로 고정하지 않고 별도 이슈로 분리한다.
6. UI 아이콘 크기, 모션, 이모지 고정 슬롯/현행 자유 배치의 혼재를 관련 채택 기록과 대조한다. 단순히 코드가 최신이라는 이유로 스펙을 바꾸지 않는다.

### 변경 범위

- 기존: `SKILL.md`, `DESIGN.md`, `docs/UX_UI_VISUAL_STANDARD.md`의 안내·연결·범위 표시.
- 기존: 본 계획과 선행 검토 보고서의 진행 상태.
- 신규 예정: 해당 구현 브랜치의 증거 폴더에 화면/문구/동작/보호 파일 manifest. 아직 생성된 것으로 취급하지 않는다.
- 금지: `PRODUCT_NORTH_STAR.md`의 정책 변경, 원본 문서 삭제, 도메인 코드 수정.

### 완료 기준

- 모든 수정 대상에 적용할 디자인 원본과 보호할 기능이 연결돼 있다.
- 겹치는 이전 규칙은 원문을 보존한 채 적용 범위가 설명돼 있다.

## 6. DS-01: 공통 스타일·겹침 수정

### DS-01A · 누락된 색상 연결

- `--accent`, `--line-dark`, `--accent-ink` 사용 위치별 의미를 분류한다.

### DS-01B · 범례 공간

- `plan-beta.css`의 기본 범례와 `AccountPlanStorage.css`의 덮어쓰기 규칙을 한 곳이 책임지도록 정리한다.

### DS-01C · 모달과 저장 안내

- 일반 저장 성공, 지속 확인이 필요한 경고, 모달 내부 상태 알림의 표시 위치를 구분한다.

- 현재 문구와 알림 의미는 유지한다. 확인이 필요한 경고를 성공 toast처럼 자동 소거하지 않는다.
- 모달로 인계할 경우 원래 알림과 중복 낭독하지 않고 같은 상태를 한 번 전달한다.
- 저장과 인증의 상태 전이를 바꾸지 않는다. AppShell 변경이 필요하면 오직 표시 위치/전달 범위로 한정한다.

### DS-01D · 글자와 밀도

- 실제 읽혀야 하는 8.5~11px 상태·설명을 우선 정리한다.
- 탭·보조 코드·본문을 구분한다. 전체 글자를 무조건12px 이상으로 바꿔 기존 compact 동작을 무너뜨리지 않는다.
- 폰트 파일과 glyph source는 유지한다. 줄바꿈·caption 토큰·weight를 함께 조정한다.

## 7. DS-02: 훈련계획·수행·근거

### 목표 화면

계획 입력 → 후보 비교 → 선택한 계획 → 날짜/오전·오후 → 훈련 방법 → 이유·근거 → 주기·기록. 현재 경로를 유지한다.

### 수행

1. 계획 입력의 제목·선택지·보조설명 간격과 눌린 상태를 통일한다. 질문·기본값·선택 수를 바꾸지 않는다.
2. A/B 비교는 현재 제공되는 값의 라벨·순서를 일치시킨다. 서로 다른 수치를 하나의 점수로 합치지 않는다.
3. 저장된 계획은 기존 날짜·주기·범례·훈련 흐름의 공간을 조정해 일정이 먼저 읽히도록 한다. 새로운 일정 화면을 만들지 않는다.
4. `DetailedPrescriptionView`에서 실제 값과 단위의 위계를 강화한다. 표시용 숫자를 만들기 위해 계산 코드를 복제하지 않는다.
5. `PrescriptionStructure`의 준비/본운동/회복/정리 블록을 같은 규칙으로 정돈한다.
6. `SessionExplanation`의 세 탭, 전문 보기, 설명 닫기 뒤 원래 위치를 유지한다. 긴 근거는 문장 삭제가 아니라 본문 조판을 개선한다.
7. 시안의 카운트다운·고정 6×1000m·시작=완료 연결은 가져오지 않는다.

### 대상

- `app/src/screens/plan-beta/PlanIntake.tsx`, `PlanCandidates.tsx`, `CandidateSection.tsx`, `MainWorkComparison.tsx`.
- 같은 폴더의 `PlanSchedulePreview.tsx`, `ActivePlan.tsx`, `PlanSessionDetails.tsx`.
- 같은 폴더의 `DetailedPrescriptionView.tsx`, `PrescriptionStructure.tsx`, `SessionExplanation.tsx`.
- `app/src/styles/plan-beta.css`, `app/src/styles/session-explanation.css`.

V3·다중 조정 화면은 시작 시 공개 경로 여부를 확인한다. 열린 Draft PR의 기능을 디자인 작업으로 활성화하지 않는다. 현행 public renderer와 draft renderer를 통째 합치지 않는다.

### 보호 영역

`impl/`, 처방 계산·allowlist·저장 스키마·`labels.ts`의 의미/수치 형식은 수정 대상이 아니다. UI 연결 때문에 보호 파일 변경이 필요하면 그 사유를 분리 보고한다.

### 완료 기준

- 준비·본운동·총 시간·반복 회복·세트 회복이 혼동되지 않는다.
- 모든 숫자와 단위, 처방 식별자, 저장 payload가 기준 fixture와 동일하다.
- RPE 안내를 상세 숫자 처방처럼 보이게 하지 않는다.
- 거리/시간/복합형, 비가분 기록, 데이터 없음, 오래된 기록, 설명 실패, 긴 훈련명에서 잘림이 없다.
- 1일2회 세션과 7/9/10일 화면을 유지한다. 전문 보기에서도 동일 처방을 읽는다.
- 같은 버튼을 통해 같은 상세 화면으로 이동하고 닫기 뒤 선택/스크롤/포커스가 복원된다.

## 8. DS-03: 홈·빠른 기록·일지

### DS-03A · 홈

- 현재 첫 방문/계획 보유/기록 보유 상태 구분과 CTA를 유지한다.
- 첫 방문 홈의 최소 높이와 `margin:auto` 조합으로 생긴 과도한 빈 공간을 줄인다.
- 기존 민지 예시 진입에 실제 예시 일지 미니어처를 활용한다. 예시 데이터만 사용하고 사용자의 사적 일지를 홈 광고처럼 노출하지 않는다.
- 미니어처는 읽기 전용 표현이며 내부 수정/삭제/구매 버튼이나 중복 ID를 렌더하지 않는다.
- 일지 표면 컴포넌트를 안전하게 분리할 수 없으면 새 프레임워크를 만들지 말고 기존 검증된 예시 이미지/에셋을 사용한다.
- 재방문 홈은 다음 훈련의 날짜·슬롯·수행 핵심값을 같은 축으로 정렬한다. 오늘 기록한 사람에게 새 작성 요구를 추가하지 않는다.

### DS-03B · 기록 작성

- 빠른 기록의 질문·건너뛰기·완료 경로는 그대로 둔다.
- 선택 상태와 단계 전환 방향, 저장 완료 영수증의 타이포를 정리한다.
- 상세 작성은 입력을 삭제하지 않고 관련 필드 간 간격·라벨·단위를 통일한다.
- 바닥 저장 버튼과 모바일 키보드가 입력·오류를 가리지 않는지 확인한다.
- 화면을 짧게 만들기 위해 필수 정보를 임의 accordion으로 바꾸지 않는다.

### DS-03C · 일지 읽기

- 목록의 날짜·종류·주요 값을 정렬하고 읽기/수정 진입점의 기존 의미를 유지한다.
- 예시/실제 일지의 다음 장 이동과 상단 접힘을 유지한다.
- 종이 안의 숫자·설명·장식 경계를 정리한다. 사용자 텍스트를 요약하거나 바꾸지 않는다.
- 계획과 연결된 일지는 연결 표시·원래 계획 상세·수정 경로를 보존한다.

## 9. DS-04: 분석·오라클·용어·콘텐츠

### 수행

1. 오라클의 제목·현재 상태·핵심 수치·근거를 네 역할로 구분하고 작은 글자와 불필요한 간격을 정리한다.
2. 거리/기간/건수는 공통 정렬을 사용하되, 같은 의미가 아닌 값을 범용 카드로 강제 통합하지 않는다.
3. 기록이 없는 화면은 부재 안내의 문구와 근거를 유지하며 시각적으로 묶는다. 허구의 예시 수치를 실제 분석 영역에 넣지 않는다.
4. 에너지 원장은 색·한글·영문·결측·제외 정보를 유지한다. 장식 그림이나 더 강한 색으로 의미를 바꾸지 않는다.
5. 용어집은 현재 검색·분류·상세·전문 보기·출처를 재사용한다. 다른 FAQ/용어 원본을 만들지 않는다.
6. 훈련법 콘텐츠는 현재 읽기 기능을 유지하고 제목·그림·출처 행·본문 밀도를 정리한다. 훈련 추천으로 바꾸지 않는다.

### 대상

`app/src/screens/trends/PersonalOraclePanel.tsx`, `CumulativeDistancePanel.tsx`, `EnergySystemLedgerPanel.tsx`, `MonthlyTrendBars.tsx`, `AccessibleTrendTable.tsx`, `app/src/screens/TrainingLexicon.tsx`, `TrainingContent.tsx`, 관련 기존 CSS.

### 완료 기준

- 원래 집계 수치·제외 건수·기간·표 데이터가 그대로다.
- 그래프 길이와 데이터 비례가 동일하며, 읽기 쉬움을 이유로 막대 길이를 부풀리지 않는다.
- 색을 제거해도 값과 분류를 구분할 수 있다.
- 지표 표시와 표로 보기의 값이 일치한다.
- 전문가·초보 모두 현재 뜻/이름의 이유/출처로 이동할 수 있다.
- 기록이 적다는 이유로 낮은 능력 점수나 결핍 판단을 추가하지 않는다.

## 10. DS-05: 꾸미기·재료 표현

### DS-05A · 도구와 종이

- 기존 전체화면 편집을 유지하고 모달 안의 상태 메시지와 작업 공간을 정리한다.
- 모바일 서랍의 제목·분류·가격 행 높이를 정돈한다. 카테고리와 구매 확인의 동작은 유지한다.
- 타일마다 그림이 비슷한 크기로 느껴지도록 광학 크기·투명 여백을 검토한다. 모든 이미지를 같은 픽셀로 잘라 해결하지 않는다.
- 기본 삽입 위치는 실제 현재 여백을 우선 활용할 수 있는지 검토한다. 기존 좌표를 바꾸지 않으며, 자유 배치를 막는 강제 보호 영역은 새로 만들지 않는다.
- 데스크톱은 종이 읽기 폭과 도구 작업공간을 구분한다. CSS transform으로 종이를 축소하기 전에 저장 좌표·포인터 변환을 검증한다. 안전하게 분리할 수 없으면 기존 좌표 모델을 유지한 채 도구 폭부터 정리한다.
- 손잡이의 시각 크기와 터치 영역, 선택 경계·레이어 도구가 본문을 필요 이상 가리지 않도록 한다.

### DS-05B · 에셋 선별

1. 현재 제공 중인 자산부터 새 조판에 재사용한다.
2. 신규 시안은 원본 PR/커밋·파일·제작/라이선스·기존 유사 재료를 한 표로 만든다.
3. 후보는 단색 도장과 테이프부터 비교한다. 후보 수를 출시 수로 고정하지 않는다.
4. 178 BPM, V2 등 그림 속 수치·용어를 실제 사용자 데이터나 현재 명칭처럼 노출하지 않는다.
5. 귀여운 입체 소재는 기본 문구 재료와 무리하게 섞지 않고, 현행 선택형 컬렉션 구조에서 검토한다.
6. 새 자산은 안전성·출처·작은 크기·대비 검토 후에만 등록한다. 기존 파일이나 ID를 덮어쓰지 않는다.
7. 신규 가격·구매 방식은 이 디자인 작업에서 발명하지 않는다. 현행 컬렉션 정책으로 정할 수 없으면 자산 준비 상태로만 남긴다.

### 완료 기준

- 열기→재료 선택→서랍 숨김→이동→크기/회전→완료→새로고침이 기존 데이터로 이어진다.

- 320px에서 필터와 구매 확인을 누를 수 있고, 중첩 알림이 재료를 가리지 않는다.
- 소유하지 않은 재료를 시각 preview만으로 구매·저장 처리하지 않는다.
- 계정 A의 자산/배치가 계정 B에서 보이지 않는다. 기존 account-decoration 서비스 fixture를 재사용한다.
- 장식은 일지 프레임 내부에 머무르고 분석·안전 표시 위로 침범하지 않는다.

## 11. DS-06: 로그인·계정·관리

### 수행

- 로그인 수단 버튼·필드·동의·처리 중·오류의 기존 단계와 문구를 유지한다.

- fixture를 먼저 사용하고, 검수 목적으로 실제 이메일·문자·초대·삭제를 자동 수행하지 않는다.

- 오류 발생 위치와 다음 가능한 행동을 현재 안내로 식별할 수 있다.
- 처리 중 중복 제출 방지·재전송 제한·입력 보존·취소 동작이 유지된다.
- 계정 전환·오프라인·충돌·복구·삭제 확인에서 시각 상태와 실제 상태가 일치한다.
- 키보드가 열린 작은 화면에서도 입력·오류·주요 행동이 가려지지 않는다.
- 민감한 작업은 전송하지 않는 시험 환경에서 먼저 검수하고, 실제 provider 연동이 검증됐다고 과장하지 않는다.

## 12. DS-07: 통합 검수·병합·배포

### 12.1 단계별 검수 방식

각 작업 묶음마다 다음 순서를 지킨다.

1. 변경 전 기준 상태와 결함을 재현한다.
2. 해당 묶음만 구현한다.
3. 보호한 문구·동작·데이터와 실제 diff를 대조한다.
4. 관련 계약/단위/e2e를 실행하고 명명된 실패를 분석한다.
5. 화면을 직접 확인하고 실제 조작을 수행한다. 스크린샷 파일 생성만으로 검수 완료로 처리하지 않는다.
6. 독립 코드 검수와 디자인 검수를 구분해 기록한다.
7. 수정 뒤 head가 바뀌면 변경된 범위의 검수를 갱신한다.

### 12.2 화면 환경

| 환경 | 확인 대상 |
|---|---|
| 320×568 | 좁은 화면, 긴 제목, 도구 서랍, 작은 글자 |
| 375×667 | 주 기준 화면, 첫 화면 우선순위, 하단 탐색·알림 |
| 768px 폭 | tablet에서 과도한 늘어남/빈 공간 |
| 1440×900 | 읽기 폭과 편집 작업공간, 도구 배치 |
| 200% 확대 | 글자 축소 없이 reflow, 버튼·본문 겹침 없음 |
| 키보드 | 초점 순서, 모달 진입/복귀, 숨은 요소 초점 없음 |
| reduced-motion | 의미·완료·오류 전달과 동일한 조작 가능 |
| 폰트 지연/실패 | fallback에서 읽기·선택 가능, 정상 로딩 후 큰 이동 없음 |
| 실제 모바일 Safari/Chrome | 폰트·safe area·키보드·touch·viewport 동작 |

브라우저 확대, 시스템 글자 확대, pinch zoom은 구분해 방법을 기록한다. CSS로 폰트 하나만 바꾼 검사를 전체 200% 접근성 검수라고 보고하지 않는다.

### 12.4 미감 검수 질문

- 가장 중요한 정보가 작은 보조 글자보다 먼저 보이는가?
- 같은 의미의 요소가 페이지마다 같은 크기·색·간격으로 보이는가?
- 읽는 영역과 조작하는 영역이 구분되는가?
- 종이/장식은 적절한 영역에만 있고 데이터와 상태를 가리지 않는가?
- 여백이 정보를 묶는 데 쓰이는가, 단순히 빈 화면을 만드는가?
- 데이터 없음과 실제 0, 진행 중과 완료가 다른 상태로 보이는가?
- 그림이 없어도 정확히 쓸 수 있고, 그림이 더해지면 더 즐겁고 이해하기 쉬운가?

임의의 총점으로 미감 승인을 대신하지 않는다. 항목별 화면·관찰·결정으로 남긴다.

### 12.5 공개 반영

- 승인된 실행 단계에서 PR별 검수 후 병합한다. 디자인 제안 PR 자체를 먼저 병합해야 한다고 가정하지 않는다.
- CSS 공통 변경은 전 페이지에 영향이 있으므로 해당 PR은 전체 주요 경로를 다시 확인한다.
- 배포 직전 main SHA와 검수 head, 배포 대상 환경을 맞춘다. 오래된 빌드를 나중에 덮어쓰지 않는다.
- 배포 뒤 공개 URL에서 새 사용자·계획·일지·꾸미기·분석의 핵심 화면과 자산 로딩을 확인한다.
- 인증·계정 화면은 시험 환경 검수와 운영 검수를 따로 기록한다. 운영 검수의 개인정보/실제 전송은 별도 허용된 경로로만 수행한다.
- 출시 실패 시 사용자 데이터·DB를 롤백하지 않는다. 문제를 만든 앱 변경을 되돌리거나 바로 수정하되 다른 작업자의 후속 변경을 삭제하지 않는다.
- 모든 상태가 끝나야 `PUBLICLY_VERIFIED`다. CI 통과·병합 완료와 구분한다.

## 13. 작업자·모델·파일 소유권

현재 로컬 `terra-sol-router` 스킬의 이름은 유지돼 있지만 정책은 Astra/Sol로 갱신돼 있다. 새 작업을 과거 Terra/Luna 설정으로 발주하지 않는다.

| 역할 | 예정 모델/추론 | 범위 |
|---|---|---|
| 기획·지시·충돌 판정·독립 코드 검수 | Astra / medium | 이번 상세 계획과 정확한 diff 기준 검수 |
| 일반 구현·수정·의미 있는 테스트 | Sol / xhigh(매우 높음) | DS-01~06의 한정된 묶음 |
| 확정된 파일 목록·링크·해시 확인 | Sol / medium | 판단이 없는 기계적 지원만 |
| 미감·모바일 독립 검수 | Fable 또는 별도 지정 디자이너 | 실제 변경 화면과 에셋 검수 |

이 표는 향후 배정이다. 이번 계획 작성으로 모델이 바뀌거나 작업자가 실행된 것은 아니다. 지원되는 위임 기능이 없으면 대체 모델로 몰래 진행하지 않고 알린다.

### 병렬 규칙

- DS-00/01은 단일 소유자가 처리한다.
- `app.css`, 루트 토큰, `compact-tabs.css`, AppShell은 통합 담당자만 수정한다.
- 이후 별도 페이지 파일은 독립 작업 가능하되, 공통 CSS 변경 요청은 통합 담당자에게 모은다.
- 에셋 원본 조사·모음 시트는 코드 작업과 병렬 가능하다. 카탈로그 등록은 코드 검수 후 별도 커밋으로 통합한다.
- 한 작업자가 남의 dirty 파일을 정리하거나 덮어쓰지 않는다.

### 하위 작업자용 공통 지시

```text
목표: 지정받은 DS 작업 묶음 하나만 구현한다.
우선 읽기: PRODUCT_NORTH_STAR.md, AGENTS.md, 본 계획, 선행 디자인 리뷰,
          대상 모듈에 연결된 현행 스펙과 채택 결정.
기준: 시작 시 확인한 main SHA와 정확한 작업 브랜치 head.
허용: 지정 UI/CSS/표현용 컴포넌트와 해당 테스트.
보호: 문구, 라우팅, 입력 단계, 저장 모델, 훈련 숫자, 의미, 계정/안전 경계.
재사용: 현재 토큰, Pretendard, Lucide, 기존 renderer와 제스처/모션.
금지: 시안 전체 복사, 신규 기능 활성화, 이전 자료 삭제, 검수 전 병합.
증거: 수정 전후 실제 화면, 관련 테스트, 결함 재현, 보호 항목 diff.
종료: 맡은 묶음 구현과 자체 검수가 끝나면 검수 가능한 head를 남긴다.
      다른 묶음이나 운영 작업을 임의로 시작하지 않는다.
```

| 계정/DB 변경 필요 | UI 범위를 넘어선 사유와 영향 보고 | 해당 변경만 보류 |
| 실제 모바일 접근 불가 | 시뮬레이션 결과와 실기기 미검수를 구분 | 완료 판정에 잔여 항목 명시; 확인 없이 검수 완료 주장 금지 |
| 다른 작업자의 신규 main | 현재 변경과 비교 후 최신 기준으로 재검수 | 영향받은 범위만 |

추가 결정을 매 화면마다 사용자에게 묻지 않는다. 이 계획 안에서 정해진 시각 결정은 작업자와 리뷰어가 처리하고, 권한·정책·제품 의미가 바뀌는 경우에만 구체적인 선택을 요청한다.

## 15. 산출물·진행 보고·완료 정의

### 15.1 필요한 산출물

- 적용 범위가 정리된 현행 디자인 문서.
- 기존 컴포넌트 기반 UI/CSS 변경과 제한된 자산 변경.
- 페이지별 before/after·상태 목록·검수 결과.
- 테스트 실행 및 결함 주입/기준 코드에서 실패한 기록.
- 정확한 PR·head·병합·배포 SHA·공개 확인 결과.
- 미수용 시안 항목과 사유, 남은 결정·환경 검수 목록.

신규 문서·테스트·스크린샷 경로는 생성 후에만 실제 파일 목록에 올린다. 실행 전에는 `PLANNED`로 표기한다.

### 15.2 보고 상태

`NOT_STARTED → IN_PROGRESS → IMPLEMENTED → REVIEWED → MERGED → DEPLOYED → PUBLICLY_VERIFIED`

부분 검수는 `REVIEWED`로 올리지 않고 어떤 범위가 남았는지 적는다. 다른 작업자에게 지시만 보낸 것을 `IN_PROGRESS`라고 하지 않고 실제 시작 여부를 확인한다.

작업 보고는 기술 파일 나열보다 먼저 다음을 설명한다.

1. 사용자가 볼 때 무엇이 좋아졌는가.
2. 기존 기능·데이터가 그대로인지 무엇으로 확인했는가.
3. 현재 로컬/PR/병합/배포 중 어디까지인가.
4. 다음에 무엇을 하며, 기다리는 것이 있다면 누구의 어떤 행동인가.

### 15.3 최종 완료 기준

- DS-00~07의 적용 대상에 상태 누락이 없다.
- 현행 문구·이용 흐름·도메인 동작을 보존한다.
- D-01~D-08은 수정·범위 정리·명시적 비적용 중 하나로 근거가 남는다.
- 중요한 정보는 읽을 수 있고, 주요 행동은 가려지지 않는다.
- 계획 수치·설명·일지·저장 상태가 기존 의미와 일치한다.
- 적용한 에셋은 출처·버전·소유·이전 배치 호환성이 확인됐다.
- 독립 코드 검수와 미감 검수가 구분돼 있다.
- 실제로 병합·배포하고 공개 화면까지 확인한다. 남은 관문이 있으면 미완료로 보고하며, 문서 작성이나 CI 통과로 전체 완료를 대신하지 않는다.
