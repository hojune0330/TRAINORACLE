### 3.1 현재 기본 생성 경로의 정적 예

다음은 기존 함수를 읽어 계산한 예이며 새 권장 처방이 아니다. 상세 방법 교체·후속 조정을 적용하기 전 경로다.

현재 문제는 반드시 "2회를 3회로 바꿔야 한다"가 아니다. **이 선수에게 왜 이 횟수이고, 왜 이 날짜·강도·방법인지 계산과 설명이 연결되어 있지 않은 부분**이다.

## 4. 조건부 질문 흐름: 필요한 질문에 한 액션

### 4.1 공통 원칙

- 한 화면에는 질문 1개, 주 선택 영역 1개, 다음 행동 1개를 둔다.
- 뒤로가기·도움말은 보조 기능이다. 큰 CTA를 여러 개 나란히 놓지 않는다.
- 숫자를 입력해야 하는 질문은 숫자 입력 하나와 확인 버튼만 둔다. 한 터치 원칙 때문에 입력 완료를 추측하지 않는다.
- 단일 답 선택은 "이 답으로 다음" 의미의 명시적 버튼으로 한 번에 이동할 수 있다. 라디오 선택·방향키 탐색만으로 갑자기 화면을 바꾸지 않는다.
- 여러 날짜 선택, 기록의 최종 적용, 안전 확인, 저장·삭제는 선택과 최종 확인을 구분한다.
- 모든 정보를 필수로 만들지 않는다. 다만 핵심 개인화 입력을 기본값으로 몰래 대신하지 않는다.
- 이미 있는 기록·설정은 출처와 날짜를 짧게 보여주고 한 번 눌러 사용한다. 원문 일지를 다시 작성하게 하지 않는다.
- 4문항으로 끝내는 것을 목표로 삼지 않는다. 필요한 쉬운 질문으로 나누되 불필요한 질문은 생략한다. 완료 시간은 실측 전 광고하지 않는다.

### 4.2 제안 화면 순서

기본 경로는 `기록/목표의 작은 구조화 입력 → 필요한 사실만 보완 → 기본 추천 하나`다. 종목·분·초는 기록 한 건을 표현하는 입력 묶음이며 각각 별도 페이지를 강제하지 않는다. 기준 날짜와 적용 요건은 있는 자료를 재사용하고 부족한 경우만 확인한다.

아래는 가능한 질문의 목록이다. 모든 사용자에게 모든 단계를 강제로 보여주는 고정 15단계 설문이 아니며, Q1부터 Q13까지의 순회도 기본값이 아니다. 답이 적격성·숫자·일정에 영향을 주는 경우만 호출하고, 직접 고치려는 사용자는 해당 질문으로 들어간다. 여러 질문을 한 화면에 몰아 넣어 추가 질문 수를 적게 센 것으로 보고하지 않는다.

| 단계 | 실제 질문 초안 | 화면에 남길 것 | 다음 처리 |
|---|---|---|---|
| Q1 종목 | "어떤 종목을 준비하나요?" | 종목 버튼. 많은 선택지는 중거리/장거리/마라톤의 같은 화면 내 그룹 전환 | 800m~마라톤 기존 지원 유지. 100~400m 전문 계획을 새로 열지 않음 |
| Q2 기록 | "훈련 속도를 정할 기록이 있나요?" | 저장된 같은 종목 기록 요약, 직접 입력, 기록 없이 시작 | 기록이 있으면 생성 전에 연결 |
| Q3 기록 입력 | "기록이 몇 분 몇 초인가요?" | 시간 입력. 종목은 Q1 값 표시. 소수 초 보존 | 기록 없는 사용자는 생략 |
| Q4 기록 시점 | "언제 세운 기록인가요?" | 날짜 입력 또는 확인 가능한 시점 선택 | 모르면 날짜 미확인으로 저장. 임의의 최근 날짜 금지 |
| Q5 기록 성격 | "이 기록을 지금 훈련의 기준으로 쓸까요?" | PB/SB/최근 기록의 실제 정보와 적용 가능성. 목표 기록은 실제 기록과 구분 | 이미 확인된 저장 기록이면 Q3~Q5를 짧은 확인 한 번으로 대체 가능 |
| Q6 현재 훈련 | "최근에는 얼마나 훈련했나요?" | 승인된 구조화 이력 요약을 사용하거나 횟수 질문, 모름 | 주당 횟수와 최근 이력의 기간을 구분 |
| Q6a 필요 시 | "한 번에 보통 얼마나 달리나요?" | 거리 또는 시간 중 사용자가 아는 단위 하나 | 원자료 보존. 미입력을 0 또는 평균 선수 값으로 채우지 않음 |
| Q7 이번 목적 | "이번 계획에서 무엇을 준비할까요?" | 경기 준비 / 평소 훈련 이어가기 / 다시 시작 / 특정 훈련 선택 | 목적에 필요한 후속 질문만 표시. 기존 에너지 목적 직접 선택은 마지막 선택 안으로 이동 |
| Q7a 조건부 | "경기는 언제인가요?" 또는 기존 경험 확인 | 해당 답 하나만 | 경기일 기반 처방이 미지원이면 그 사실을 표시하고 적용된 것처럼 쓰지 않음 |
| Q8 계획 기간 | "며칠 계획을 볼까요?" | 7일·9일·10일, 기존 선택 재사용 | 표시에 쓰는 기간이며 주기 전체를 초기화하지 않음 |
| Q9 시작 날짜 | "언제 시작할까요?" | 오늘 / 내일 / 날짜 선택 | 기본 날짜를 명시적으로 확인. 계정 시간대 기준 날짜 |
| Q10 가능일 | "이번 9일 중 언제 훈련할 수 있나요?" | 실제 날짜, 매일 버튼, 날짜 직접 선택 | 기간 문구는 동적. 주당 횟수를 프레임 횟수로 오인하지 않음 |
| Q11 하루 횟수 | "하루에 몇 번 훈련할까요?" | 한 번 / 오전·오후 두 번 | 두 번 선택 시 기존 승인된 두 슬롯 유지. 선택했다고 두 번 모두 고강도가 되지 않음 |
| Q12 몸 상태 | 기존 안전 질문의 직관적 표현 | 꼭 답해야 하는 신호와 명확한 선택 | D9 등 기존 상태를 덮거나 자동으로 안전 답을 선택하지 않음 |
| Q13 생성 결과 | "9일 계획을 만들었어요" | 기본 추천 하나의 기간·부담·미니 일정·시작 버튼 | 저장 전 최종 확인. 다른 안은 사용자가 비교를 열었을 때 제공 |

### 4.3 최소 입력과 선택 입력

- **처방 연결에 필요한 입력:** 종목, 사용 가능한 기록 또는 기록 없음, 최근 훈련 맥락, 이번 목적, 날짜/가능일, 안전 상태. 필요한 경험·적격성 정보는 기존 프로필에서 재사용하거나 하나씩 확인한다.
- **나중에 바꿔도 되는 입력:** 꾸미기, 부문 표시, 세부 설명 보기 수준, 선호하는 방법 탐색. 이것들을 앞의 필수 문항으로 추가하지 않는다.
- **개인 기록만으로 알 수 없는 것:** 최근 훈련을 감당하는 정도, 통증, 쉬었다가 복귀한 상태. PB가 빠르다고 횟수와 양을 자동으로 올리지 않는다.
- **기록이 없는 경우:** 생성 자체를 막지 않는다. 검토된 시간·노력 기준 구성을 제공하고, "기록 없이 만든 계획"을 짧게 표시한다. 임의의 초/km를 개인 페이스라고 만들지 않는다.
- **타 종목 기록만 있는 경우:** 저장은 가능하되 현재 채택된 변환 모델이 있는 경로에서만 참고 페이스를 계산한다. 모델이 없는 종목을 슬쩍 외삽하지 않는다.
- **추천 페이스:** 기존 승인된 참고 모델이 있으면 숨기지 말고 `참고 페이스` 표식과 함께 제안한다. 적용 기록·계산 모델·오차와 사용 범위는 눌러서 확인한다. 목표 기록만으로 현재 능력을 확정하지 않는다.

### 4.4 중단·수정·복귀

- 종목을 바꾸면 호환되지 않는 기록/템플릿/페이스 바인딩만 무효화한다. 시작 날짜 같은 무관한 답은 유지한다.
- 기록이 바뀌면 페이스·설명·예상 시간·후보 비교를 함께 갱신하고, 기존 적용 확인은 다시 받는다.
- 뒤로가기는 직전 질문 또는 열었던 상세로 돌아간다. 도움말을 닫으면 같은 답과 스크롤·포커스로 돌아온다.
- 질문 초안과 활성 계획을 별도 상태로 둔다. 새 계획을 만들다 취소해도 원래 계획이 사라지지 않는다.
- 계정 전환 시 다른 사람의 기록과 초안을 재사용하지 않는다. 민감한 입력을 URL·분석 로그에 넣지 않는다.
- 진행률은 답변 분기를 반영한다. 처음에는 `기록 → 일정 → 확인` 그룹 표시를 사용하고 정확하지 않은 "총 4단계"를 약속하지 않는다.

## 5. 언제든 삭제: 보관과 다른 기능으로 만들기

### 5.1 사용자 동작

`계획 상단 더보기 → 계획 삭제 → 무엇이 남는지 확인 → 삭제`

진행 중·완료·보관 계획 모두 같은 경로로 접근한다. 위험 신호나 미완료 세션이 있다는 이유로 계획 삭제 자체를 막지 않는다. 삭제가 안전 신호 해제나 실제 운동 기록 삭제를 뜻하지는 않는다.

확인 문구 초안:

> 이 훈련계획을 삭제할까요?
> 일정에서 사라져요. 작성한 일지는 남아요.
> 삭제한 계획은 30일 동안 휴지통에서 복구할 수 있어요.

30일 복구는 기존 계정 저장 방향에 맞춘 권장 설계다. 실제 휴지통·복구·만료 정리 기능을 구현하기 전 이 문구를 노출하지 않는다. 당장 완전 삭제한 것처럼 표시하지 않는다.

### 5.2 데이터와 동기화 계약

| 상황 | 동작 |
|---|---|
| 후보를 보기만 함 | `나가기`로 초안 취소. 활성 계획과 기존 기록은 그대로 |
| 활성 계획 삭제 | 휴지통 전환과 currentPlanId 해제를 원자적으로 처리. 다른 과거 계획을 자동 활성화하지 않음 |
| 완료·보관 계획 삭제 | 같은 휴지통 처리. 보관은 나중에 보기, 삭제는 일반 목록에서 제거라는 차이 유지 |
| 연결된 일지가 있음 | 일지·실제 수행량 보존. 일지의 당시 처방 스냅샷과 불투명 참조는 필요한 범위에서 유지, `삭제한 계획` 표시 |
| 앞으로 예정된 훈련 | 오늘 할 일·알림·미래 계획 집계에서 제거. 실제 수행한 기록을 지운 것처럼 처리하지 않음 |
| 주기 연결 | 과거 실제 수행 이력과 다음 주기에 이미 확정된 근거를 임의 재작성하지 않음. 삭제한 미래 세션을 다음 추천의 예정 부하로 계속 세지 않음 |
| 다른 기기 | 계정 서버의 삭제 버전 확인 후 동일 상태로 수렴 |
| 인터넷 끊김 | 삭제 요청을 보존하고 `온라인 연결 후 삭제돼요` 표시. 로컬 실행 진입은 막고 서버 삭제 완료라고 말하지 않음 |
| 오래된 저장 요청 도착 | 삭제 표식·revision과 충돌 검사. 오래된 outbox가 계획을 부활시키지 않게 함 |
| 복구 | 사용자가 직접 선택. 복구만으로 활성화하지 않음. 다시 활성화하려면 현재 날짜·안전·적격성 검토 |
| 실제 완전 삭제 | 계정 보존 정책과 암호화 본문·인덱스·기기 캐시·백업의 삭제 범위를 구분. 데이터 전체 삭제 메뉴와 계획 삭제를 혼동하지 않음 |

기존 서버 확인, 암호화, 계정 격리, CAS/revision, pending/conflict 모델을 재사용한다. 서버 확인 없이 로컬에서만 지운 것을 계정 삭제 성공으로 포장하지 않는다. 비로그인 계획도 해당 저장 범위에서 삭제할 수 있어야 하며 삭제를 위해 로그인하도록 강요하지 않는다.

## 6. 후보 선택: 접혀 있어도 일정부터 보이게

이 절의 일정 요약은 기본 추천 하나에도 적용한다. 후보 둘을 반드시 비교하고 고르게 하는 절차는 아니다.

### 6.1 정보 순서

1. 실제 기간: `9월 21일(월)~29일(화) · 9일` 같은 날짜 표시.
2. 실제 계획 차이를 담은 짧은 제목.
3. **항상 보이는 일정 미리보기. 접기 대상이 아님.**
4. 주요 훈련 횟수·총 운동 횟수·오전/오후 여부 중 중요한 정보 최대 3개.
5. 다른 안과의 실제 차이 한 줄.
6. `이 계획 선택` 주 버튼. `자세히 보기`는 보조 버튼.

긴 베타 안내, 전체 RPE 설명, 모든 근거와 용어 도움말은 첫 화면에서 제거하고 아래 `계획 정보` 또는 상세 화면으로 이동한다. 저장 실패·기록 미확인·통증·현재 적용 불가 사유는 감추지 않는다.

### 6.2 일정 표현

- 날짜·요일·훈련 종류가 실제 세션 데이터에서 나온다. 장식용 달력 이미지를 만들지 않는다.
- 작은 화면 기본은 **5일씩 두 줄로 배치한 날짜형 일정**을 권장한다. 각 칸에 날짜/요일과 `인터벌`, `지속주`, `기초`, `회복`, `휴식` 등 실제 훈련 이름을 짧게 표시한다. 달력의 주 구분처럼 오해하지 않도록 `첫 5일 / 다음 4일` 구분과 실제 요일을 유지한다.
- 7열 주간 달력 보기를 제공할 경우 320px에서 터치·글자가 작아지면 읽기 전용 요약으로 쓰고, 접근 가능한 일별 선택 목록을 별도로 제공한다. 한 칸을 억지로 작은 터치 버튼으로 만들지 않는다.
- 오전/오후 두 번이면 같은 날짜 안에 두 줄로 표시한다. 한 칸의 색만 바꿔 두 번을 숨기지 않는다.
- MAIN은 역할 표식으로 구분하되 한글 훈련명을 우선한다. 에너지 약어는 상세나 짧은 병기로 둔다. 색만으로 MAIN/회복을 구분하지 않는다.
- 고강도 범위가 본운동에만 해당하면 전체 세션을 같은 강도로 칠하지 않는다. 비례 막대는 실제 산출 가능한 시간에만 사용한다.
- 전체 시간 미산출을 0분으로 합산하지 않는다. `시간이 정해진 훈련 N개` 또는 `전체 시간은 일부 미산출`로 정직하게 요약한다.
- 훈련 횟수와 훈련일 수를 구분한다. 하루 두 번 사용자에게 `18회`를 `18일`로 표시하지 않고, 필요하면 `9일 · 18회`로 병기한다. MAIN 세션과 MAIN 노출 원장의 집계 단위도 명시한다.
- 일별 셀을 누르면 그날의 오전·오후를 한 화면에서 보되 상세 수치와 근거는 별도 펼침/페이지로 연결한다.

### 6.3 두 안 비교

기본 결과에서는 추천 하나를 보여주고 `다른 계획 보기`를 보조 행동으로 둔다. 비교를 연 모바일 화면에서는 상단에 `계획 A / 계획 B` 전환을 두고 한 번에 한 개의 명확한 미리보기를 보여준다. 스와이프는 추가 수단이며 버튼 없이 제스처만 요구하지 않는다. 데스크톱은 비교를 연 경우 두 미리보기를 같은 기준으로 나란히 표시할 수 있다.

각 후보의 요약 모드는 달력을 항상 보존한다. 전환 시 현재 탭·진행 위치를 고정하고 화면 높이가 튀지 않게 한다. 처음부터 후보 상세 둘을 세로로 길게 펼치지 않는다.

두 안의 차이가 일반 달리기 시간뿐이라면 **"주요 훈련은 같고, 일반 달리기 시간이 달라요"**라고 쓴다. 서로 다른 에너지 전략이나 두 개의 상세 MAIN 방법인 것처럼 부풀리지 않는다.

```text
계획이 준비됐어요                       더보기
9월 21일~29일 · 9일

[ 계획 A ] [ 계획 B ]
일반 달리기 시간을 직접 조절

[날짜·요일별 실제 훈련 미리보기, 항상 표시]
[오전 / 오후 구분, 주요 훈련 표시]

주요 훈련 N회 · 전체 N회
두 계획은 일반 달리기 시간이 달라요

                 [ 이 계획 선택 ]
                     자세히 보기
```

위 예시는 사용자가 비교를 연 상태다. 기본 결과에는 A/B 탭 대신 추천된 프로그램의 이름과 부담을 표시한다. N과 날짜·훈련은 화면 구조용 자리표시자다. 검토된 실제 배치를 렌더링할 뿐 새 처방을 이 문서에서 생성하지 않는다.

## 7. 추상어를 실제 차이로 바꾸기

| 현재/피할 표현 | 교체 방향 | 주의 |
|---|---|---|
| 최소 시간 계획 | `일반 달리기 N분으로` | 실제 하한 고정이 맞을 때만. 전체 계획 최소·최적이라고 주장하지 않음 |
| 기본 보조훈련 | `일반 달리기 N~M분` 또는 실제 활동명 | BASE/REC를 똑같이 부르지 않음 |
| 쉬운 날은 내가 조절 | `일반 달리기 시간을 고를 수 있어요` | 범위와 조정 가능 항목을 실제 제공 기능에서 읽음 |
| 쉬운 훈련 | `기초 지구력 달리기`, `회복 걷기` 등 실제 세션명 | 한글 목적+필요한 RPE를 방법 상세에 제공 |
| 일주일에 며칠 움직일 수 있나요? | `이번 9일 중 언제 훈련할 수 있나요?` | 선택한 기간·실제 날짜와 일치 |
| 권장 / 추천 | `선택한 조건에 맞는 안` + 근거 진입 | 실제 추천 순위 규칙이 없으면 추천 배지 삭제 |
| 개인 맞춤 | `5km 기록으로 속도 계산` / `기록 없이 시간·노력 기준` | 어떤 항목이 개인화됐는지 구체화 |
| 강도 8 · 50분 | `전체 예상 50분 · 본운동 노력 8` | 실제 전체 시간이 산출됐을 때만. 준비·회복 강도 별도 |
| 균형 있는 계획 | 실제 배치·비율 요약 | 모든 시스템 동일 비율이 최적이라는 의미 금지 |

위 문구는 복사한 정적 숫자로 만들지 않는다. 제목·비교·상세·홈 카드가 같은 처방을 읽는다. 용어 정의는 기존 용어집을 사용하고 각 화면에 별도 정의를 복제하지 않는다.

## 8. 훈련 배치와 개인화: 화면 아래의 코어 개선

### 8.1 먼저 정리할 것

`계획 요청 → 적용 가능한 방법 → 배치 → 실제 세션 → 노출 원장 → 달력 → 설명 → 일지 연결`을 하나의 추적표로 만든다.

원장과 달력에 별도의 MAIN 배치 알고리즘을 유지하지 않는다. 역할 정의가 다르다면 다른 이름·필드로 분리하고 왜 다른지 계약에 적는다. 같은 개념이면 **실제 확정된 세션 배치에서 원장·표시·근거를 함께 산출**하도록 바꾼다. 기존 원장값에 화면을 억지로 맞추거나 단순히 3회로 증량하는 패치는 금지한다.

### 8.2 배치 결정에 쓰는 입력

| 입력 | 허용하는 역할 | 하면 안 되는 추론 |
|---|---|---|
| 확인한 기록·날짜·종목 | 채택된 공식의 목표 페이스·반복 시간 | 빠른 기록이면 높은 훈련량을 감당한다고 단정 |
| 최근 구조화 수행 이력 | 실제 빈도·양·이전 MAIN·휴식 확인 | 미기록을 휴식 또는 0km로 처리 |
| 이번 목적·주기 단계 | 검토된 세션 목적·배치 정책 선택 | BASE/REC 목적을 무시하고 고강도 강제 |
| 가능 날짜·하루 횟수·시간 상한 | 실제 일정과 수행 가능한 구성 제한 | 매일 가능=매일 주요 훈련, 두 번=두 번 고강도 |
| 직전·다음 주기 경계 | 이미 한 주요 훈련과 겹치지 않는 연속성 | 7일·9일 화면을 새 주기로 보고 매번 리셋 |
| 안전·통증 신호 | 기존 중단/검토 경로 | 계획 삭제·일지 성실성·PB 갱신으로 자동 해제 |
| 에너지 원장 | 어떤 목적의 훈련을 했는지 기술 | 횟수가 적은 시스템을 개인의 생리적 약점으로 진단 |

### 8.3 중강도·고강도 구성을 풍부하게 하는 방법

1. 현재 채택된 목적·템플릿·대상·정확한 숫자·페이스 모델을 런타임 목록과 대조한다. 준비 문서를 곧 활성화 목록으로 읽지 않는다.
2. 각 MAIN의 목적을 먼저 정하고, 그 목적 안에서 검토된 서로 다른 방법을 제안한다. 특정 방법을 고르면 다음 방법이 항상 고정되는 짝은 만들지 않는다.
3. 9.5일 Formation의 기존 MAIN 2~3회 방향, 7/9/10일 표시, 장기 주기와 실제 수행 이력을 함께 검토한다. 현재 품질 세션 2회 코드를 그대로 전체 과학적 근거로 삼지 않는다.
4. 중강도 목적이 필요한 범위에서는 LT 등 해당 검토 구성을 실제 운동·회복 단위로 제공한다. MIX나 "중강도" 라벨 하나로 대신하지 않는다.
5. 세 번째 MAIN, 새로운 복합 구성, 기존보다 높은 양·강도·빈도는 **정확한 대상·배치·지원·시간·한계가 승인된 정책 범위에서만** 선택 가능하게 한다. 이번 UI 승인이나 "매일 가능" 선택을 훈련 증량 승인으로 확대하지 않는다.
6. 자기 선택·청소년 지원·매일 훈련·하루 두 번 방향은 유지한다. 나이나 코치 미연결만으로 과거 승인 범위를 다시 닫지 않는다. 반대로 해당 방향 승인을 모든 용량의 승인으로 해석하지 않는다.
7. 이력 부족 사용자를 무조건 BASE만 하는 사용자로 고정하지 않는다. 검토된 입문 구성이 있으면 제시하고, 없으면 무엇이 부족한지 구체적인 적용 범위로 남긴다.
8. 동일 훈련 반복은 허용한다. 다양성은 매번 다른 이름을 강제로 만드는 기능이 아니라 같은 목적의 실제 선택지를 제공하는 기능이다.

중점 목적을 하나 골랐다고 모든 MAIN을 같은 에너지 목적의 복제로 만들지 않는다. 기존 주기 정책에 따라 다른 날의 역할을 정하고, 이번에 강조하는 목적과 유지하는 목적을 구분한다. 다만 다양하게 보이기 위해 모든 에너지 시스템을 9일 안에 반드시 넣거나 같은 비율로 맞추는 규칙은 만들지 않는다.

### 8.4 구현할 결정 순서

```text
선수가 확인한 입력 + 기존 주기 + 실제 수행 이력
  → 안전 상태와 사용 가능한 근거 확인
  → 승인된 대상/주기 정책 선택
  → 실제 날짜와 시간 상한 안에서 MAIN·일반·회복 역할 배치
  → 각 MAIN 목적에 맞는 검토된 방법을 독립적으로 제안
  → 사용자가 고른 기록으로 지원 모델의 숫자 계산
  → 전체 구성·회복·앞뒤 주기·시간 상한 재검토
  → 확정 세션으로 원장·달력·설명·비교를 함께 산출
  → 사용자 선택과 서버 확인 후 활성 계획으로 저장
```

배치 정책은 버전, 적용 대상, 필요한 입력, MAIN/강도/회복 조건, 출처, 적용 한계를 갖춘다. 정책이 사용하지 않은 기록이나 수면을 설명에 끼워 넣지 않는다. 가능한 날짜에 검토된 배치를 만들 수 없으면 몰아서 넣거나 앞뒤 주기 밖으로 밀지 말고, 바꿀 수 있는 조건 하나를 구체적으로 제안한다.

주당 가능 횟수와 프레임 가능일의 수정은 **새 요청 버전**으로 구분한다. 기존 저장 계획과 과거 답을 새 의미로 조용히 다시 해석하지 않는다. 새로 생성하거나 수정하는 시점에 실제 날짜로 확인받는다.

### 8.5 개인화 완료 표시

각 세션에서 다음을 내부적으로 구분하고 필요 시 사용자가 확인할 수 있게 한다.

- 개인 기록으로 계산된 값.
- 사용자가 직접 고른 값.
- 검토된 기본 구성에서 가져온 값.
- 아직 산출하지 못한 값.
- 적용한 템플릿·숫자·설명·근거 버전.

전체 계획에 `개인 맞춤` 배지 하나를 붙여 일부 MAIN만 개인화된 사실을 가리지 않는다. 상세 방법 선택·수치 조정 후 설명과 달력도 같은 버전으로 갱신한다.

## 9. 인터랙션·접근성·시각 기준

### 9.1 토스에서 가져올 원칙

쉬운 말, 분명한 행동, 앞뒤 흐름의 일관성, 답하기 쉬운 질문, 한 화면의 한 핵심 메시지를 적용한다. 토스의 색·카드·브랜드를 복제하거나 클릭 수 자체를 늘리는 보상 설계를 가져오는 것이 아니다. [Toss Product Principles](https://toss.im/tossfeed/article/tossproductprinciples)

긴 입력을 논리적인 단계로 나누고 선택 단계를 건너뛸 수 있게 하며 진행 상황을 알려주는 구조를 사용한다. [W3C 다단계 폼 지침](https://www.w3.org/WAI/tutorials/forms/multi-page/)

### 9.2 화면 전환

- 기존 `screen-motion.ts`·단계 모션·디자인 토큰을 재사용한다. 새 애니메이션 라이브러리는 추가하지 않는다.
- 답 선택 후 다음 질문은 짧게 전환하고 질문 제목/첫 선택 영역이 즉시 보이게 한다. 이전 답 요약 박스가 새 질문 위를 차지하지 않는다.
- 뒤로가기는 반대 방향. 도움말은 별도 읽기 화면으로 열고 정확한 진입점으로 돌아온다.
- 모션 도중 연속 탭해 두 단계가 건너뛰어지지 않도록 이벤트와 상태를 하나의 전이로 묶는다. 값 커밋 전에 화면부터 넘기지 않는다.
- 키보드가 열렸을 때 하단 확인 버튼이 가려지지 않게 한다. iOS 주소창·안전 영역·가상 키보드를 고려한다.
- 생성 완료 효과는 한 번만 짧게 재생하고 자동 종료한다. 서버 저장이 안 됐는데 저장 완료 축하를 하지 않는다.
- `prefers-reduced-motion`에서는 움직임을 없애도 단계·선택 결과가 명확해야 한다.
- 입력이나 포커스 변화만으로 뜻밖의 문맥 이동을 일으키지 않는다. 단일 선택 후 이동은 명확한 명령 버튼으로 구현하고 폼 컨트롤 자동 이동과 구분한다. [W3C On Input](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html)

### 9.3 스크롤 최소의 정확한 의미

**스크롤을 없애려고 글자를 작게 하거나 선택지를 자르면 실패다.**

- 기본 375px 모바일 질문 화면에서 질문과 주요 선택 영역, 다음 버튼이 첫 화면에 들어오게 한다.
- 320px·200% 글자 확대·가로모드·키보드 상태에서는 필요한 세로 스크롤을 허용한다. 양방향 스크롤·텍스트 잘림은 금지한다. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- 많은 선택지는 목적별 그룹/검색/자세히로 나눈다. 찾을 수 없는 숨김 메뉴나 스와이프만 가능한 긴 캐러셀로 대체하지 않는다.
- 작은 일정은 HTML 텍스트와 실제 데이터로 렌더링한다. 이미지 안에 글자를 굳혀 확대·스크린리더·번역을 막지 않는다.
- 아이콘은 뒤로가기·도움말·더보기·상태처럼 역할이 있을 때만 둔다. 모든 행에 서로 다른 장식 아이콘을 붙이지 않는다.
- 기존 Pretendard·종이/잉크·색/간격 토큰을 사용한다. 그림자·좌측 굵은 색띠·카드 안 카드 회귀는 만들지 않는다.
- 클릭 가능한 항목은 기존 44px 터치 기준을 유지한다. 시각적인 크기 감소와 터치 영역 감소를 같은 일로 취급하지 않는다.

## 10. 유지할 기존 기능과 스펙 패치 대상

### 10.1 절대 축소하지 않을 기능

- 각 MAIN의 서로 다른 실제 방법 선택, 검토 범위 내 조정, 같은 방법 반복 선택.
- 거리형·시간형·복합형과 반복/세트 회복 구분.
- 방법 / 이유·근거 / 주기·기록 상세, 공통 용어집.

### 11.1 작업 분담 제안

- 디자인 작업자 또는 Fable: W2 및 W3 동작·카피·좁은 화면 검수. 훈련량·안전 의미는 독자 변경하지 않음.
- 독립 리뷰어: W0의 판정, W1의 계정 경계, W4의 산술/날짜/근거, W6 실제 사용 시나리오 확인.

v1.0 작성 시 작업자나 새 대화를 실행하지 않았다. v1.1에서 기존 상대 세션에 읽기 전용 분담 확인을 요청했고 답변을 받았다. 개발 실행은 지시하지 않았다. 실제 코드 소유는 통합 검토 §6의 파일별 작성자 표를 우선하며, 이 절의 역할명만 보고 같은 파일을 병렬 수정하지 않는다.

변경 모듈의 단위/계약 테스트와 핵심 브라우저 경로를 PR마다 실행한다. CSS·문구만 바꾼 PR에 전체 생리학 검수를 반복하지 않고, 저장/배치 변경에는 해당 경계 테스트를 생략하지 않는다. 최종 통합 시 필수 CI와 공개 배포 smoke를 한 번 연결한다. 미실행·환경 문제·실패를 PASS에 포함하지 않는다.

결함 주입은 대표 원인마다 1개 이상으로 제한해 실효성을 확인한다. 예: 기록 입력을 다시 null로 덮기, 달력을 다시 숨기기, 삭제 뒤 오래된 저장 재생, 9일을 주간 횟수로 잘못 변환하기, 설명 버전을 이전 값으로 남기기. 불필요한 전수 검증 반복을 성과로 세지 않는다.

- 생성에 쓰지 않은 값을 쓴 것처럼 설명하지 않는다.
- 접힌 후보만 보고도 실제 기간·주요 훈련 날짜·회복/휴식·하루 두 번 여부를 알 수 있다.
- 이름을 읽지 않고도 두 후보의 실제 차이를 일정/수치에서 확인할 수 있다.
- 달력·상세·원장·설명·일지가 같은 세션 배치를 참조한다.
- 기존 상세 방법 두 안, 조정, 근거, 장기 주기 기능이 유지된다.
- 생성 후 언제든 계획 삭제를 요청하고 상태를 확인할 수 있다. 일지는 별도로 남는다.
- 질문 하나를 답하면 다음 질문이 바로 보이며, 뒤로가거나 도움말을 열어도 답이 유지된다.
- 모바일·확대·키보드에서 잘림 없이 완료할 수 있다.
- 개발·검수·병합·배포·공개 사용 확인 상태를 따로 보고한다.

### 15.2 이번에 새로 임의 결정하지 않는 사항

UX 간소화, 삭제 동선, 기록 우선, 일정 상시 요약은 이번 요청에 따른 계획이다. 기존 청소년·자기 선택·하루 두 번·MAIN별 방법 다양성 방향을 재승인 문제로 돌리지 않는다.

다만 **새 훈련 구성이나 강도·양·빈도를 실제로 확대하는 정확한 정책**은 현재 승인 목록 대조 후 정한다. 이미 승인된 것은 재질문하지 않는다. 정말 미결정인 조합만 선수 유형·변경 전후·근거·한계를 한 표로 모아 최종 확인받는다. 모델이 마음대로 9일 3회 또는 두 번 모두 고강도를 기본값으로 켜지 않는다.
