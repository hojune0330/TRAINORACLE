## 1. 이번 요청과 완료 경계

기록을 찾으러 들어왔는데 빈 이번 달부터 넘겨야 하는 수고를 줄인다. 날짜와 기록의
관계를 바로 알아보고, 한 번 누를 때마다 선택 결과와 다음 행동을 알 수 있게 한다.
아무 기록도 없는 사용자는 기록이 쌓였을 때의 모습을 실제 달력처럼 탐색할 수 있다.

0.1~0.2 산출물은 현재 코드 대조, 상세 구현안, 계획 모델 시험과 독립 페르소나 리뷰다.
0.3은 아래 §13의 색상·공통 모션만 구현한 역사 단계다. 0.4의 추가 구현과 검증은
§14에 구분한다. 전체 앱 구현·실사용자 시험·공개 배포를 완료했다고 주장하지 않는다. 현재 처방 수치,
주기 길이, D9, 메모 공개 권한, 외부 달력 연동을 변경하지 않는다.

사용자의 "조금 과해도 됨, 로블록스처럼"은 반응과 발견성을 강화할 근거다.
앱을 3D 게임으로 바꾸거나, 운동량 경쟁·연속 출석 압박·무한 모션을 넣는 근거가 아니다.

## 3. 사용자가 보게 될 흐름

### 3.1 기록이 있는 일지

첫 방문에는 가장 최근의 실제 일지가 있는 달과 날짜를 선택한다. 예: 오늘이 9월 29일이고
최근 운동일이 8월 18일이면 8월 달력에 `최근 일지 · 8월 18일`과 선택 표시가 먼저 보인다.
월 제목·요일·오늘 버튼은 계속 보인다. "오늘"이라고 과거 날짜를 소개하지 않는다.

선택일 아래에는 `8월 18일 화요일 / 훈련 1 · 일상 1`처럼 한 줄 요약과
`이날 기록 보기`를 둔다. 메모·체중·통증·개인 제목을 자동으로 펼치지 않는다.
날짜를 누르면 기존 큰 하루 리더를 연다. 정보가 없는 칸을 클릭해도 허용하며
`이날 기록하기`로 이동할 수 있다. 자동 선택은 큰 리더를 자동으로 열지 않는다.

### 3.2 진행 중 계획

명시적 세션 진입이 없으면 오늘의 계획 날짜, 앞으로 남은 계획 날짜, 종료된 계획의
마지막 날짜 순으로 보여준다. 오늘의 예정 휴식도 있는 그대로 보여준다. 지난 미완료
훈련을 오늘 해야 할 일처럼 끌어오거나, 최근 일지 날짜로 계획 달력을 이동하지 않는다.
오전·오후 표시는 실제 세션 슬롯을 사용하고 작성 시각으로 추측하지 않는다.

### 3.3 예시

준비된 데이터에 실제 기록이 하나도 없을 때 `아직 일지가 없어요`와 짧은 예시
미리보기를 먼저 보여준다. 빈 실제 달력과 큰 예시 달력을 연속으로 두 개 쌓지 않는다.
미리보기에는 실제 연월·요일을 지킨 축약된 한 주와 가상의 기록일 표시를 넣고
`예시 · 내 기록에 저장되지 않아요`를 항상 붙인다. `예시 둘러보기`로 월 달력을 확대해
가상의 세 날짜(훈련, 가벼운 활동, 쉬는 날 기록)를 누를 수 있다. 실제 빈 달력과
과거 날짜 기록 경로도 `내 달력`에서 접근 가능해야 한다.

예시 화면의 주요 행동은 `내 첫 기록 남기기`, 보조 행동은 `달력으로`다.
예시 날짜는 예시 전용 시계로 생성하고 실제 날짜·요일은 일치시킨다.
예시 조회·완료 누르기로 계정 저장, 일지 통계, 계획 완료, 포인트가 발생하지 않는다.
실제 데이터와 예시를 같은 배열에 합치지 않는다. 건강 점수·가짜 기록 향상은 넣지 않는다.
로딩·오류·오프라인 미확인·다른 계정 전환 중에는 "기록 없음"으로 단정하거나 예시를 띄우지 않는다.
예시 확대 중 실제 데이터가 도착하면 예시 화면을 강제로 닫지 않는다. 별도 예시 컨텍스트를
고정한 채 `내 기록도 도착했어요 · 내 달력으로`를 제공한다. 실제 데이터는 뒤에서 갱신하되
예시의 날짜·표시 데이터로 합치지 않는다. 계정 전환은 예외로 즉시 예시 포함 모든 이전 컨텍스트를 비운다.

## 4. 날짜 결정 규칙

### 4.1 우선순위

동일 계정·동일 화면 인스턴스에서 한 번만 초기 선택한다.

1. 현재 탐색 의도가 담긴 유효한 명시적 날짜/세션 요청.
2. 뒤로가기 시 복원하는, 계정과 화면 및 계획 ID가 일치하는 위치.
3. 이번 화면에서 직접 고른 날짜·월. 새 데이터 도착이나 자정은 이를 덮어쓰지 않음.
4. 첫 데이터 준비 시 아래 화면별 기본값.
5. 데이터가 없다고 확인되면 오늘 또는 후보 시작일, 상태에 맞는 안내.

위 순서는 매 렌더마다 실행하는 정렬이 아니다. 이미 사용자가 탐색한 화면에 이전
링크를 다시 적용하지 않도록 명시적 요청에는 소비되는 navigation token을 둔다.
미래의 실제 새 사용자 요청은 현재 수동 선택보다 우선한다.

| 화면 policy | 첫 기본 위치 | 자동으로 하지 않을 일 |
|---|---|---|
| JOURNAL | 오늘 이하 유효한 실제 기록 날짜의 최댓값 | 과거 기록의 수정일(savedAt/updatedAt)로 날짜 선택, 미래 오입력으로 이동 |
| ACTIVE_PLAN | 오늘이 계획 범위에 있으면 오늘, 시작 전이면 첫 일정, 종료 후면 마지막 일정 | 과거 미완료를 오늘 일정으로 승격, 끝난 계획을 활성 처방으로 재생성 |
| PLAN_CANDIDATE | 후보의 실제 시작일 | 사용자 과거 기록으로 후보 달 이동 |
| INTAKE_PREVIEW | 사용자가 입력한 시작일 | 시작일 자동 수정, 안전 판정 전 실제 처방 생성 |
| CYCLE_JOURNAL | 보존된 앵커에서 최근 일지가 속한 주기 index와 그 기록 월 | 앵커를 최근 기록 날짜로 교체하거나 처방의 주기 규칙 변경 |
| EXPLICIT_RANGE | 호출자가 지정한 날짜·주기 | 다른 달의 기록이 많다고 범위 자동 교체 |

기록 정책은 `entry.date`의 의미를 따르고 서버 업로드 시각을 운동 날짜로 쓰지 않는다.
삭제·휴지통·미승인 가져오기·타 계정·예시는 자동 선택 후보가 아니다.
미래 날짜의 기록만 있으면 오늘을 보여주고 `미래 날짜의 기록`을 보조 제공한다.
미래 날짜라는 사실만으로 예정 경기나 계획된 훈련이라고 해석하지 않는다.
가까운 기록 이동은 현재 선택일 전후의 실제 날짜 인덱스로 이동한다. 동률은 과거 우선.
`최근 일지`는 항상 최댓값, `가까운 기록`은 현재 선택일 기준으로 이름과 기능을 구분한다.

계획 범위의 마지막 날짜는 저장된 계획의 시작일과 기간으로 결정한다. 마지막 운동 세션이나
가장 최근 일지를 종료일로 쓰지 않는다. 마지막 날이 예정 휴식이거나 세션 없는 날이어도 보존한다.
`예정 휴식`, `기록한 쉼`, `일정 없음`, `기록 없음`, `예시`를 같은 OFF/완료 문구로 합치지 않는다.
인테이크 날짜 미입력/invalid는 `날짜 예시`로 오늘을 잠시 사용할 수 있지만 입력값을 확정하지 않는다.
같은 시작일의 후보 A/B도 candidate ID/version이 다르면 별도 scope다. 동일 계획 revision 갱신은
선택 날짜를 보존하되 달력에서 선택한 세션이 제거되면 제거 사실과 새 상세 진입을 안내한다.

주기 일지의 날짜→index 역매핑은 아직 기존 API에 없다. 신규 표시 전용 helper는
`trainingCycleWindow(anchor,index)`가 내는 창을 기준으로 음수 index까지 찾는다.
앵커 2026-09-29, 기록 2026-09-28은 기존 index -1 창(9월 20~28일)이어야 한다.
과거 날짜라고 0으로 clamp하지 않고 onAnchorChange도 호출하지 않는다. 검색 범위를 기존
유효 날짜 한계로 제한하고 창 생성 횟수 상한을 둔다. 계산 불가 시 명시적 월 보기로만 이동하며
앵커를 대체하지 않는다. 이 helper와 경계 시험은 단계 A 완료 조건이다. 9/10일 아카이브 묶음을
정확한 반나절 처방 엔진이나 승인된 과학적 주기 효과로 격상하지 않는다.

### 4.2 자동 이동이 멈추는 시점

날짜/월/주기 직접 변경, 키보드 그리드 탐색, 목록 스크롤, 필터 변경, 리더 열기,
입력 시작 중 하나라도 수행하면 그 탐색 세션의 자동 이동 권한을 소모한다.
로딩 중 먼저 달력을 조작했으면 늦게 기록이 도착해도 이동하지 않는다.
명시적 `최근 일지` 또는 `오늘` 버튼만 다시 이동한다.

마지막 보이던 기록 삭제 시 날짜는 유지하고 그 날의 빈 상태와 삭제 취소를 보여준다.
새 기록 동기화 시 `새 일지 1개`를 보조 동작으로 제공할 수 있으나 강제 이동하지 않는다.
계정 전환 시 리더·날짜 컨텍스트·원문·pending transition을 즉시 버리고 새 계정 준비를 기다린다.
이때 비밀 메모/건강 내용을 애니메이션 퇴장 레이어에 남기지 않는다.

## 5. 데이터·탐색 상태 설계

새 도메인 후보 `calendar-context.ts`는 날짜 선택만 결정한다. 저장·동기화·처방 API를 호출하지 않는다.
기존 날짜 헬퍼와 주기 매핑 함수를 재사용한다. 달력 날짜는 civil-date이고 UTC slicing으로
다시 계산하지 않는다. 로컬 today 변경은 "오늘" 표시만 갱신한다.

```ts
type CalendarLoadState = 'LOADING' | 'READY' | 'STALE' | 'ERROR'
type CalendarAnchorReason = 'EXPLICIT' | 'RESTORED' | 'MANUAL'
  | 'RECENT_RECORD' | 'PLAN_TODAY' | 'PLAN_START' | 'PLAN_END' | 'EMPTY_TODAY'
// Scope: owner identity/epoch + page policy + plan/range id + navigation instance.
// Context: visible month, selected civil date, optional AM/PM, return focus key,
// scroll target, consumed navigation token, manual-interaction epoch.
```

위 상태는 제안이며 기존 API가 이미 제공한다고 주장하지 않는다. 실제 계정 hydrate와
동기화 오류 상태를 조사해 adapter로 연결한다. 일정 시간 기다렸다는 이유만으로 READY로
바꾸지 않는다. STALE에 보관된 실제 기록이 있으면 `저장된 기록`으로 탐색 가능하되
서버 최신 확인 완료로 말하지 않는다. 실패 때 기존 기록을 빈 배열로 바꾸지 않는다.

같은 계정에서도 역순 응답이 올 수 있다. scope epoch만 확인하는 것으로 부족하므로
읽기 요청 generation과 적용한 snapshot revision을 함께 다룬다. 이전 요청 결과가 늦게
도착해 최신 날짜 인덱스를 비우거나 되돌리지 못하게 한다. 기존 동기화 서비스의 revision을
우선 사용하고 UI만을 위한 별도 저장·재시도 엔진은 만들지 않는다.

### 5.1 실제 기반과 연결

현재 account projection의 LOADING/READY/PENDING/REJECTED/FAILED/CONFLICT는 준비 상태와
다른 축이다. 기존 status를 삭제하거나 READY 하나로 덮지 않는다. 새 읽기 결과에는
`readiness + syncStatus + ownerEpoch + snapshotRevision`을 각각 둔다.

| 실제 조건 | 달력 처리 |
|---|---|
| 익명 기기 snapshot 및 ownership index 정상 | 확인된 기기 기록으로 탐색, 진짜 0건이면 예시 허용 |
| 계정 scope 일치, hydrate 성공, 소유권 확인 | READY, 실제 0건일 때만 첫 기록 예시 |
| 동일 계정의 확인된 cache 존재, 서버 재확인 중/실패 | STALE, 기존 기록 탐색 유지, 서버 최신 완료 주장 금지 |
| cache 없음, 해당 계정 hydrate 진행 중 | LOADING, 예시/기록 없음 단정 금지 |
| 필수 저장소 또는 ownership index 판독 불확실 | ERROR, 모르는 기록을 다른 계정 것으로 추정 금지 |
| PENDING/REJECTED/CONFLICT 쓰기 상태 | 기존 저장/충돌 표시 유지. 준비 상태와 함께 전달 |

`loadJournalEntriesSnapshot`, 기존 account projection, storage event/service queue를 재사용한다.
ownership manifest certainty를 노출하는 작은 read accessor는 필요하지만 별도 동기화 서버를
만들 이유는 없다. 현행 useCalendarEntries는 동기 읽기라 same-owner 역순 응답이 실제로
발생했다는 증거는 없다. 향후 비동기 읽기를 추가할 때만 request generation 방어를 연결하며,
이미 직렬화된 서비스 옆에 중복 fetch 계층을 만들지 않는다.

기존 owner=null 기기 기록은 여러 로그인 계정에서 보일 수 있는 현재 계약이다.
이를 계정 전용 데이터라고 부르지 않는다. 이번 권장안은 로그인 상태의 자동 첫 위치에는
명확한 현재 계정 소유 기록만 사용하고, 연결 안 된 기기 기록은 별도 `이 기기의 기록` 진입을
유지하는 것이다. 기기 기록이 있다고 새 계정에 자동 귀속/삭제하지 않는다. 해당 기록이 남아
있는데 전체 기록이 0이라고 안내하지 않는다. 기존 열람 권한 자체의 변경은 이 달력 작업에
섞지 않고 별도 결정으로 남긴다.

### 5.2 복귀 계약

- 월/날짜만이 아니라 진입원점 `CALENDAR_MODAL / FULL_READER / ARCHIVE_LIST`와 owner epoch를 보존한다.
- 현재 탭 재탭뿐 아니라 다른 탭을 거쳐 돌아올 때도 같은 계정의 마지막 월·날짜를 복원한다.
  새로 앱을 시작하면 최근 데이터 기본값으로 시작하며 영구 추적 history는 만들지 않는다.
- 전체화면 원문 리더도 달력 modal과 같은 Back 계약에 연결한다. 한 번 Back은 원래 달력/리더
  한 단계로 돌아간다. 월 이동마다 history를 추가하거나 새 router를 도입하지 않는다.
- 작성 취소는 원점으로 돌아간다. 저장 성공은 원래 날짜의 리더로 돌아가 갱신된 요약을 보여준다.
  달력에서 썼으면 달력 리더, 전체 원문에서 썼으면 전체 원문으로 복원한다. 실제 저장 상태는 유지한다.
- 닫을 때 현재 선택 날짜에 포커스를 복원한다. 버튼이 없어졌으면 월 제목, 그마저 없으면
  해당 화면 제목으로 이동한다. 계정이 달라졌다면 이전 화면으로 포커스를 복구하지 않는다.
- A→B→A도 새로운 epoch다. 계정 ID가 다시 같다고 옛 작성 복귀 ref를 살리지 않는다.
- 날짜 변경 낭독은 날짜 한 줄만 한 곳에서 한다. 월 live region과 dialog 제목·focus가
  중복해서 세 번 읽히는 구조는 피한다. 실제 VoiceOver/TalkBack 확인은 구현 후 별도 관문이다.

계정 격리된 navigation state에 달/날짜/slot을 저장한다. 민감 원문을 URL/history에 넣지 않는다.
기존 AppShell, reader history entry, draft return을 확장하며 또 다른 router를 만들지 않는다.
월 이동은 history entry를 매번 늘리지 않는다. 리더 열기/닫기와 화면 뒤로가기만 기존 규칙대로 처리한다.
날짜 팝업·키보드·스와이프·최근 기록 버튼은 같은 reducer에 의미 있는 이벤트를 보낸다.
렌더용 month와 archive의 월별 상세 단계(selectedMonth)를 분리해 Back 의미가 바뀌지 않게 한다.

## 6. 안내와 모션

### 6.1 화면 밀도

- 월 제목 한 줄, 보조 컨텍스트 한 줄, 달력, 선택일 요약, 주요 동작 한 개가 기본 구조다.
- `오늘`과 `최근 일지`는 기능이 다르므로 접근 가능하게 유지한다. 월 화살표는 Lucide와 툴팁.
- 별도 온보딩 팝업·설명 문단·매번 뜨는 튜토리얼은 만들지 않는다.
- 기존 44px 터치 영역을 유지한다. 320px/200% 글자 확대는 필요한 세로 스크롤을 허용한다.
- 스와이프는 선택적 편의이고 화살표·키보드 대체 경로를 없애지 않는다.
- 일지 리더에 `기록 있는 날` 이동을 제공하되 기본 하루 이동과 구분한다. 빈 날짜 기록 기능은 유지한다.

### 6.2 동작별 반응

| 순간 | 기본 효과 | 정직성·중단 조건 |
|---|---|---|
| 초기 최근 기록 표시 | 첫 프레임부터 맞는 월. 선택일 테두리/짧은 색 강조 한 번 | 여러 달을 순서대로 자동 넘기지 않음. 강제 focus 없음 |
| 날짜 탭 | 눌림 색 + 선택 테두리, 리더 내용 짧은 fade | 탭 즉시 상태 결정. 모션 끝을 기다려 클릭을 차단하지 않음 |
| 월/날짜 넘김 | 기존 ease-out, 방향이 일관된 opacity/작은 이동 | 200~350ms, 새 입력이 오면 최신 목표로 합침. 수동 스크롤과 경쟁 금지 |
| 기록 저장 뒤 | 저장 확인 후 해당 칸의 기록 표시가 한 번 나타남 | 로컬 임시/서버 완료의 기존 구분 유지. 애니메이션이 저장 완료를 대신하지 않음 |
| 새 데이터 도착 | 제자리 보조 안내, 원하면 새 날짜로 이동 | 보고 있는 날짜를 빼앗지 않음 |
| 예시 탐색 | 선택 칸과 연결된 요약이 즉시 바뀜 | 실제 기록/포인트/완료 효과와 다른 `예시` 표시 고정 |
| 다음 행동 | 한 개 CTA의 명확한 pressed/selected 반응 | 운동량·통증 숨김·공유·삭제를 보상하지 않음 |

"더 살아 있는" 느낌은 이 반응을 빠짐없이 이어서 만든다. 우선 기존 Pretendard,
잉크·종이 토큰, Lucide, screen-motion/useOrderedStepMotion을 재사용한다.
반복 점멸·3D 회전·폭죽·자동음악·진동·필수 대기시간은 이번 범위 밖이다.
동작 감소 설정은 OS 우선으로 모든 translate/smooth-scroll/강조 반복을 제거한다.
색과 즉시 상태 변경으로 같은 정보를 제공하며 앱 내 `동작 줄이기`도 접근 가능하게 둔다.
모션 선택은 기본/줄이기의 두 가지면 충분하다. 사용자에게 복잡한 설정부터 묻지 않는다.

앱의 동작 줄이기는 화면 애니메이션과 JS scroll 모두가 읽는 하나의 설정으로 구현한다.
유효값은 `OS reduce OR 앱 reduce`다. 앱에서 기본을 골라도 OS의 줄임 선호를 해제하지 않는다.
이 기기의 비민감 표시 환경설정으로만 저장하고 계정/훈련 데이터와 묶지 않는다.

구체적인 기본 화면은 `연월 + 오늘/월 이동 → 최근 일지 날짜 안내 → 달력 → 선택일 요약`이다.
작은 화면에서 마지막 요약이 접히면 선택 시 리더로 바로 이어져야 하며, "아래로 찾아서
다시 누르기"를 요구하지 않는다. 핵심 탐색의 1탭 목표는 달력 날짜 탭이며, 보조 CTA는
같은 목적의 접근성 경로다. 날짜 선택의 테두리 반응, 요약의 짧은 교체, 리더 전환이 이어져
선택이 반영됐다는 것을 이해시킨다. 저장 성공이 아닌 단순 조회에 축하나 성과 점수를 붙이지 않는다.

### 6.3 기술 보호

첫 화면을 오늘로 그렸다가 기록 월로 튀기보다 준비 상태를 그린 후 목표 월을 배치한다.
늦은 animation callback은 owner epoch/navigation token 확인 후 무시한다.
연속 탭의 중간 transition은 취소하고 마지막 의도만 반영한다. Pointer 취소, 세로 스크롤,
브라우저 가장자리 Back 제스처를 월 넘김으로 훔치지 않는다. swipe 구현 시 기존 검증된
gesture 경로를 재사용하고 임계값은 실측으로 결정한다. 가상 물리 엔진을 추가하지 않는다.

policy/identity를 명시해 기존 초기화 소유권을 resolver 쪽으로 옮기고 중복 경로를 제거한다.

독립 구현 가능 부분은 B/C지만 공용 calendar-context/AppShell/CSS는 담당을 하나로 둔다.
하위 작업자는 달력 보기 문제를 해결하려고 실제 훈련 일정·서버 데이터·권한을 수정하지 않는다.
새 runtime library 설치 없이 시작한다. 렌더마다 전체 이력을 날짜마다 재검색하지 않고
검증된 날짜별 인덱스를 owner/revision별 memoize한다. 1만 기록 fixture의 성능은 구현 후 측정한다.

## 10. 검증 계약

### 10.1 최소 확정 시나리오

- 오늘, 어제, 1년 전, 몇 년간 드문 기록, 같은 날짜 여러 종류, 미래 오입력만, 휴지통만.
- 로딩 중 수동 월 이동 후 도착, stale offline, load error, A 계정 요청이 B 로그인 뒤 도착.
- 오늘 없는 미래 계획, 종료 계획, 오늘 휴식, 오전 완료/오후 예정, 명시적 세션 링크.

- 두 번 빠른 탭, swipe 중 세로 스크롤, pointercancel, 리더 Back, 작성 취소/저장 후 복귀.
- 기록 삭제/복구, 가져오기 검토 전후, 동기화 반복, 예시 탐색 중 실제 데이터 도착.
- 스크린리더/키보드/320·375px/200% 글자 확대/OS와 앱의 줄인 모션.

### 10.2 랜덤 공격

seed를 기록하는 pure state-machine 모델로 enter, load, select, month, refresh, account,
midnight, open/back, delete, demo 이벤트를 섞는다. 불변값: 수동 의도 유지, scope 격리,
잘못된 날짜 금지, 예시 쓰기 0, 자동 리더 열기 0, 실제 기록/처방 변경 0.
이 시험은 설계 모델 시험이며 앱 실행을 대체하지 않는다. 모델에 owner check 제거,
매 refresh 재정렬, empty와error 혼합 결함을 넣어 시험이 실패하는지도 확인한다.

### 10.3 독립 검토

Luna 최고 지원 추론(max)의 독립 6패스, 각 5페르소나로 총 30관점을 검토한다.
실제 사용자 30명 시험이 아니라 모델에 의한 관점 분리 검토다. 추측·코드 사실·실측을 구분한다.
각 리뷰는 해당 소스 근거, 예상 공격 순서, 장점/단점, 구체적인 보완안과 우선순위를 남긴다.
문서만 근거로 무조건 APPROVE하지 않으며 새로운 문제는 본 문서 수정 이력에 연결한다.

### 10.4 구현 후 관문(0.2 당시 미실행, 최신 결과는 §14)

처음부터 목표 달이 보이고 사용자가 최근 일지를 여는 데 한 번의 명시적 탭이면 된다.
기존 월 이동을 연타해야 하는 횟수와 비교한다. 입력 지연·animation frame·CLS는
실기기/CPU throttle로 측정하며 측정 전 "60fps"라고 쓰지 않는다. 키보드 포커스, 화면
폭 초과, 타깃 겹침, 날짜 요일, AM/PM, 안전 안내가 스크린샷과 상태에 모두 맞아야 한다.
계획 수치·일지·계정 storage snapshots는 UI 탐색 전후 동일해야 한다(탐색 환경 설정 제외).

## 11. 외부 근거와 적용 판단

2026-09-29 공식 문서 웹 검색 확인. Agent Reach doctor는 Exa 미설정으로 공개 웹 검색을
사용했다. 외부에 선수 데이터는 보내지 않았다. 자동 디자인 검색 도구의 랜딩페이지·금색·
Syncopate 제안은 기존 제품과 맞지 않아 채택하지 않고 접근성·즉시 피드백 원칙만 참고했다.

- [Roblox UI/UX](https://create.roblox.com/docs/production/game-design/ui-ux-design):
  행동 결과를 이해시키는 피드백을 참고. 월 이동·선택·저장 반응으로 번역한 것은 본 계획의 판단.
- [Roblox adaptive design](https://create.roblox.com/docs/production/publishing/adaptive-design):
  입력 방법과 접근성 선호에 맞는 경로. 게임패드나 3D 구현을 복제하지 않음.
- [Apple Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback):
  상태 근처 피드백과 중요한 문제의 명확한 안내. 모든 상태를 팝업으로 만들지 않음.
- [W3C animation from interactions](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions):
  비필수 동작을 줄이거나 끌 수 있어야 함. 해당 SC는 AAA이며 AA 의무라고 잘못 주장하지 않음.
- [W3C C39](https://www.w3.org/WAI/WCAG22/Techniques/css/C39):
  CSS prefers-reduced-motion과 실제 설정별 확인. CSS만으로 JS smooth scroll을 해결했다고 보지 않음.
