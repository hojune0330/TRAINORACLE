# 구형 앱과 새 몸 기록의 기기 저장소 분리

```yaml
status: OWNER_APPROVED_IMPLEMENTED_VALIDATION_IN_PROGRESS
owner_approval: 2026-10-12 저장소를 분리해 보호한 뒤 배포 준비
baseline_commit: ccf0c00d1a838c72a1bcbb12a057c3a793771a9a
release_authority: 준비만 승인, 이번 작업에서 운영 배포하지 않음
```

## 목적과 변경하지 않는 것

이미 설치된 옛 앱은 `trainoracle.journal.v1`의 전체 배열을 저장하면서 새 몸 기록
필드를 지울 수 있다. 새 클라이언트의 필드 보존 검사만으로 옛 바이너리를 보호할 수
없으므로 **새 앱이 사용하는 기기 저장 주소를 분리**한다.

- `JournalEntry` 구조와 기존 `bodyPartMetadata` companion은 그대로다. 별도 부위
  데이터베이스나 severity 중복 사본을 런타임 원본으로 추가하지 않는다.
- 계정 JOURNAL v4, 서버 식별자, 백업 v1–v6 형식 이름, 훈련·안전 수치와 처방은 바꾸지 않는다.
- 계정 삭제 요청이 기기 기록을 보존하는 기존 계약은 유지한다. 기기 지우기는 별도다.
- 전역 `Storage`를 덮어쓰지 않는다. 일지 관련 소비자만 명시적 접근 어댑터를 사용한다.

## 저장 경계

`journal-storage-keys.ts`가 유일한 주소 계약이다. 일지, 암호화 메모, 소유권,
휴지통, 삭제 기록, 계정별 동기화 복구는 `to-local-journal.*`로 이동한다.
구형 `trainoracle.*` 일괄 정리에도 새 저장소가 함께 지워지지 않도록 별도 접두사를 사용한다.
이는 **호환성 보호**이며, 같은 출처에서 실행되는 악성 스크립트에 대한 보안 격리는 아니다.
브라우저의 사이트 데이터 삭제로부터 보호한다고 주장하지 않는다.

이관은 Web Locks로 새 앱끼리 직렬화한다. 기존 바이트의 고정 사본을 보관하고,
현재 저장 주소에 복사한 뒤 모든 값과 옛 원본을 다시 읽는다. 완료 표시는 마지막에 쓴다.
검사·용량·읽기 확인 실패 시 원본을 지우거나 빈 일지로 초기화하지 않는다.
지원하지 않는 버전이나 설명할 수 없는 새 저장 영역도 보존하고 멈춘다.

복구 코드는 `sessionStorage` 안에서만 옮긴다. 기기 원본 사본이나 로그에 포함하지 않는다.
탭별 이관 표시로 로그아웃·잠금 후 옛 복구 코드가 다시 불러와지는 일을 막는다.

## 옛 앱의 후속 쓰기

옛 일지 수정뿐 아니라 키 삭제, 휴지통·암호화 메모·소유권 변경, 새로운 계정별 복구 키도
감지한다. 새 일지를 덮어쓰거나 양쪽을 시간순으로 합치지 않는다.

1. 새 저장을 막고, 안전 판단용 읽기는 `uncertain`으로 유지한다.
2. “이전 앱에서 기록이 바뀌었어요”와 `현재 기록으로 계속 / 다시 확인`을 보여준다.
3. `현재 기록으로 계속`은 표시 당시 양쪽 상태를 다시 확인한다. 바뀐 옛 바이트를
   보관한 뒤 비교 기준만 갱신한다. 현재 기록은 수정하지 않는다.
4. 그 사이 또 변경됐으면 이전 확인을 사용하지 않는다. 새 상태를 다시 확인해야 한다.

화면 뒤의 폼은 언마운트하지 않는다. 모달은 키보드 포커스를 유지하고, 해결 후 원래
입력으로 돌아간다. 실패 메시지·이벤트·URL에 기록 내용이나 소유 계정 ID를 넣지 않는다.
이 작업은 원본을 보관하는 경계까지다. 서로 다른 기록을 비교·합치는 새 UI를 만들지 않는다.
기존 개인 백업은 현재 소유자에게 보이는 현재 기록만 내보내며 혼합 계정 사본을 자동 포함하지 않는다.

## 삭제·복원

- 휴지통 복구는 기존대로 새 ID를 만든다. 복구가 실제 저장되기 전에는 옛 사본을 지우지 않는다.
- 영구 삭제·30일 만료·개수 한도로 버리는 기록은 고정 사본과 옛 저장소에서도 같은 stable ID를 정리한다.
- 현재 소유권과 과거 소유권이 서로 다른 계정을 가리키면 임의 추정하지 않는다.
  과거 미귀속 사본은 같은 stable ID에 대한 현재의 명시적 계정 귀속을 따른다.
- 이름·날짜·메모 유사도로 대상을 찾지 않는다. 다른 소유자 기록은 보존한다.
- 기기 전체 지우기는 옛 키, 현재 키, 원본 사본과 이관 중 임시 자료를 포함한다.
  기본 삭제 이력 보존은 ID·시각과 필요한 소유권만 남기며 본문·몸 이름·메모를 남기지 않는다.
- 중간 실패는 완료로 표시하지 않는다. 승인된 정리 작업의 고정된 전후 값과 대상을 보관하여
  재시도할 수 있게 하고, 그 사이 달라진 값을 자동 삭제하지 않는다.
- 복원 실패의 되돌리기는 대상 데이터에만 적용한다. 이관 표시나 다른 탭의 새 값을 되돌리지 않는다.

## 보장 범위와 배포 경계

`localStorage` 여러 키는 하나의 원자적 데이터베이스 트랜잭션이 아니다. 새 앱의 이관은
Web Locks로 직렬화하지만 옛 앱은 그 잠금을 모른다. 정확한 바이트 비교, 완료 표시,
재시도 가능한 정리 의도와 쓰기 차단으로 실패를 감지하고 보존하며, 완전한 교차 탭
직렬화를 주장하지 않는다. Web Locks가 없는 환경에서는 신규 이관을 열지 않는다.

기존 캐시의 옛 앱이 새 저장 주소를 읽는 것으로 되돌릴 수 없다. 문제가 생겼다고 새 주소를
옛 주소로 복사하거나 DB·개인 사본을 지우지 않는다. 최신 읽기 지원은 남기고 새 쓰기만
보수적으로 막는다. CI·운영 배포·실제 계정 왕복 확인은 각각 별도 증거가 필요하다.

## 검사 자료 정비와 검증 인수

초기 검색의 `app/src` 테스트 39개·E2E spec 49개·별도 script/audit 6개는 수정 전
옛 리터럴 발견 수다. 현재 남은 작업 수나 실행·통과 수로 사용하지 않는다. 의도적인
구형 seed와 부정 대조군이 포함되므로 전체 문자열 치환도 하지 않는다.

E2E의 각 맥락을 검토해 **33개 spec + 6개 script/audit + 12개 fixture, 총 51개 파일**의
소스 정합 정비를 완료했다. 부팅 전 구형 합성 seed·원본 보존 확인·백업 형식 이름은
유지하고, 부팅 후 현재 일지·vault·귀속·휴지통 접근은 새 저장 주소로 바꿨다. 정상 앱의
관문을 거치지 않는 독립 브라우저 fixture에는 production initializer와 실제 Web Locks를
명시적으로 적용했다. fresh JSDOM/CJS fixture loader에만 격리된 test-only inline lock runner를
사용하며 async 초기화를 기다린다. 제품 guard와 소유자·계정 삭제 계약을 완화하지 않는다.

초기 손상 구형 목록은 일부 행만 표시하지 않고 원문을 그대로 보존하며 진입을 막는
`SOURCE_CORRUPT` 경계로 검사한다. 이미 확인한 현재 저장소의 읽기 호환성과 최초 이관의
전체 목록 보존 조건을 같은 기대값으로 취급하지 않는다.

이 정비 담당은 테스트·Git·커밋·배포를 실행하지 않았다. 정비 동결 뒤 통합 담당의
`typecheck:e2e` 통과 보고는 있지만, 이는 실제 브라우저 행동·전체 E2E·CI·운영 검증을
대신하지 않는다. 대표 후행 후보는 `private-memo-save.spec.ts`, `journal-trash.spec.ts`,
`journal-drop-observability.spec.ts`이며 실제 결과는 별도 실행 로그로 확정한다.

후행 확대 48파일 배치에는 통과, assertion 실패, worker 시작 실패가 함께 남아 있다.
영향 fixture 5묶음과 pace 관련 4검사는 통합 담당이 보정 중이며 현재 전체 성공이나
배포 준비 완료를 선언하지 않는다. 후행 worker 실패·fixture 재실행도 호스트의 worker
시작·종료 timeout으로 결과 없이 중단되어 원래 부분 통과·실패 증거를 유지한다.
순환참조 보정 뒤 기존 pace 검사 112/112와 최종 app 타입 검사는 통과했다. 별도 신규 import
순서 회귀는 worker 시작 timeout으로 실행되지 않았다. 수정 fixture 재실행과 최종 통합
릴리스 검증은 남아 있으므로 전체 검증 완료로 처리하지 않는다.
중간 수치·최종 재실행 결과·E2E 정확한 변경 목록은
[구현 인수 보고서](../review/CANONICAL_LOCAL_JOURNAL_IMPLEMENTATION_2026-10-12.md)에
구분하여 기록하고, 겹치는 실행을 합산하지 않는다. 미시작 worker와 skip도 통과로 세지 않는다.

현재 작업 결과와 실행한 검사/미실행 검사의 최종 확정은 통합 담당의 검증 인수 단계에 남아 있다.
