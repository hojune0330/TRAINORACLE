## 3. 사용자에게는 하나의 제품으로 보이게

### 3.1 일반 진입

```text
기록 또는 목표 한 건 입력 / 저장된 기록 사용
  → 실제로 필요한 누락 사실만 확인
  → 추천 하나: 기간·부담·첫 훈련·미니 일정
  → 이 일정으로 시작
  → 준비·본운동·회복·정리가 이미 보이는 오늘 수행
```

`기록/목표 + 종목 + 분·초`는 하나의 기록을 표현하는 묶음이다. 각각을 반드시 다른 페이지로 나누지 않는다. 추가 질문이 필요하면 그때 한 가지에 집중하도록 보여준다. 안전 관련 여러 사실을 한 문장에 묶어 "질문 1개"라고 보고하지 않는다.

기록 보유자만을 대상으로 결과를 완성하지 않는다. 기록이 없는 사용자에게는 승인된 기록 비의존 시작 프로그램을 제공할 수 있어야 한다. 목표 기록은 현재 가능한 반복 페이스로 간주하지 않는다.

### 3.2 제작자 프로그램 진입

```text
허용된 제작자 프로그램 소개
  → 내게 맞춰 보기
  → 같은 입력/누락 사실/적격성 경로
  → 선택한 제작자·원본 관계가 남는 개인 결과
  → 같은 저장·오늘 수행·일지 연결
```

공개 프로그램 원본은 별개 데이터이지만 개인 적용 후에는 기존 계획 체계를 사용한다. 별도 달력, 별도 수행 기록, 별도 삭제 기능을 만들지 않는다.

### 3.3 상세를 원하는 사용자

추천 결과의 `다른 계획 보기`, `시작일·훈련일 바꾸기`, `훈련 방법 고르기`, `왜 이 훈련인가요?`에서 상세로 진입한다. 이 기능은 숨겨 없애는 것이 아니라 기본 생성의 필수 관문에서 빼는 것이다.

- 계획 A/B와 MAIN별 두 방법은 다른 종류의 선택이다. 섞어 계산하지 않는다.
- 같은 목적의 방법들은 독립적으로 선택할 수 있고 같은 방법을 다시 선택할 수 있다.
- 수행에 필요한 반복·페이스·회복은 오늘 화면 기본 정보다. 긴 근거만 접는다.
- 상세에서 돌아오면 같은 추천·기록·스크롤·선택이 유지된다.

### 3.4 홈과 재방문

전역 허브에는 기존 다이어리·분석·학습 접근을 유지한다. 계획 탭 또는 계획을 받으러 들어온 맥락에서는 추천/진행 중 계획이 먼저 보인다. 계획 유무 하나만으로 모든 사용자의 앱 첫 화면을 강제로 바꾸지 않는다.

시작 전 / 오늘 예정 / 오늘 수행 보고 / 같은 날 남은 오후 / 휴식 / 공백 후 복귀 / 프로그램 완료 / 저장 실패 상태를 구분한다. 하루 첫 세션 완료로 오후까지 완료 표시하지 않으며 미기록을 미수행으로 단정하지 않는다.

- 입력 컴포넌트가 정보 부족을 건강 정상·최근 기록·평균 훈련량으로 보충하지 않는다.
- 기본 추천은 실제 선택 규칙과 안정적인 동률 처리로 정한다. 첫 배열 항목에 근거 없이 추천 배지를 붙이지 않는다.
- 프로그램 하나뿐이면 불필요한 순위 모델을 만들지 않는다. 선택 가능한 안이 없으면 상태·대안이 명확해야 한다.
- 개인본은 같은 저장 ID·세션 ID 체계를 따른다. 원본 ID와 개인본 ID를 같게 쓰지 않는다.
- 제작자 철회/리콜, 사용자의 삭제, 계정 전체 삭제는 별개 상태다. 사용자 삭제가 원본 상품을 지우거나 원본 철회가 수행 일지를 지워서는 안 된다.
- 입력/프로그램/안전 상태가 바뀌면 오래된 결과 적용을 막는다. 화면 전환을 위해 새 값이 저장되기 전에 성공을 표시하지 않는다.
- 기존 승인 범위의 수치를 사용한다. 기록 입력 UI를 추가했다고 새로운 대상·용량이 자동 활성화되지 않는다.

### 작업 충돌 방지

1. 실제 앱 저장소의 같은 기준 main SHA에서 별도 작업트리/브랜치를 사용한다. 이번에는 만들지 않았다.
2. C1~C5의 최소 타입·행동 계약을 먼저 공통 커밋으로 고정한 뒤 각 작업이 그 커밋을 기준으로 시작한다.
3. I가 공통 경로, P가 독립 경로를 수정한다. 소유 밖 변경이 필요하면 담당자에게 작은 변경 요청을 전달한다.
4. P의 컴포넌트를 앱에 import하고 기존 흐름과 연결하는 패치는 I만 작성한다.
5. 앱 build, 서버 schema, migration 순서와 문서 출처를 I가 한 번에 조정한다. 브랜치를 통째 복사해 맞추지 않는다.
6. 동일 기능을 두 PR에서 다시 구현하지 않는다. 아래 ID 대응표로 완료를 한 번만 센다.
7. 필수 리뷰·병합은 한 줄기로 진행한다. 두 세션이 서로 다른 main을 동시에 배포하지 않는다.

## 8. 구현 순서와 출시를 나누는 기준

### 단계 0. 개발 준비 통합

- A/B 원문을 실제 저장소로 보존 편입하고 B의 수정 사항을 실행 지시에 반영한다. 두 문서가 서로 다른 UI를 지시한 채 남지 않게 한다.
- C v1.1과 이 문서의 소유/우선순위를 함께 연결한다.
- 현재 활성화된 정확한 훈련·기록 모델·대상·버전을 다시 확인한다. 오래된 범위표 숫자를 현재 전체 공급량이라고 쓰지 않는다.
- 배치/원장·주당/프레임 의미와 공통 저장 계약을 확인한다. 의심 항목은 재현한 뒤 확정한다.
- 최소 3화면의 기존 토큰 기반 구조를 합의한다: 입력, 최초 결과, 오늘 수행. 별도 디자인 시스템을 만들지 않는다.

### 단계 1. 독립적으로 먼저 고칠 수 있는 것

I: 삭제/계정 상태, 추상어의 실제 값 표시, 달력 요약 유지, 확인된 가능일 의미 오류를 작은 변경으로 진행한다.

P: C1~C5를 소비하는 간편 입력·결과·오늘 수행 컴포넌트와 프로그램 자료를 준비한다. 가짜 처방을 운영 데이터처럼 사용하지 않는다.

이 단계의 UI 편의 수정은 따로 공개할 수 있으나 전체 간편/제작자 제품 완성으로 보고하지 않는다.

### 단계 2. 하나의 실제 경로 연결

이미 지원되는 기록 보유자 경로로 입력→기본 추천→미니 일정→계정 저장→오늘 수행→일지→삭제를 끝까지 연결한다. 이는 기술 통합 기준선이며 첫 파일럿 전체 완료가 아니다.

원장·개인 근거·달력의 불일치는 이 경로에서 해결한다. 단순한 기본 추천 랭킹과 새로운 훈련 정책 개발을 한 변경에 섞지 않는다.

### 단계 3. 첫 파일럿의 네 경로 완성

| 진입 | 현재 기록 있음 | 목표만 있음 |
|---|---|---|
| 일반 추천 | 지원 모델로 개인 페이스, 정확한 기준 표시 | 검토된 기록 비의존 시작 프로그램, 목표와 실제 역할 구분 |
| 제작자 프로그램 | 해당 원본의 허용된 변환만 적용 | 대표 프로그램 최소 1개의 검토된 목표-only 버전 |

네 경로 모두 같은 저장·오늘 수행·일지·삭제를 사용한다. 이름만 제작자 버전이고 실제로 몰래 일반 계획을 주는 경우는 실패다. 권한이 확보된 대표 상품이 없으면 없는 것으로 표시하고 그 공급 업무를 남긴다. 가짜 선수 협업을 만들지 않는다.

### 단계 4. 검수·병합·배포

계약/수치와 UX 과업을 나눠 검수하되 같은 시나리오를 양쪽에서 전수 반복하지 않는다. 프로그램별 새 용량의 실제 채택은 별도 근거이고 UI 검수 통과로 대체하지 않는다.

병합 전 필수 검수 → 한 통합 경로로 병합 → 배포 → 공개 화면과 계정 상태 확인을 연결한다. 앱 화면 변경과 실제 프로그램 활성화가 다른 단계면 보고서에서 분리한다.

## 10. 공통 검수: 한 번의 증거를 함께 사용

P는 시각 컴포넌트 단위 입력/오류/모션/접근성을 확인한다. I는 계획·기록·서버 상태와 연결된 통합 경로를 확인한다. 동일한 모바일 E2E를 각 브랜치가 별도 이름으로 복제하지 않는다.

| 통합 과업 | 통과 조건 |
|---|---|
| 최소 입력 | 실제 응답한 사실 수와 수정 횟수 기록. 여러 필드를 한 질문이라고 숨기지 않음 |
| 첫 결과 이해 | 기간·훈련 횟수·부담·주요 훈련 날짜를 상세 펼침 없이 파악 |
| 실제 수행 준비 | 기본 화면에서 반복/페이스 단위/회복 순서를 파악 |
| 선택권 | 그냥 시작 가능, 원하면 A/B·MAIN 방법·일정을 수정하고 원위치 복귀 |
| 네 진입 | §8의 일반/제작자×기록/목표 전부 실제 경로 제공 또는 정확한 미완료 표시 |
| 숫자 정합 | 소수 초 보존, 목적/실제 MAIN/원장/달력·개인 근거 일치 |
| 저장·삭제 | 계정 전환·오프라인·재시도·다른 기기·늦은 쓰기·삭제 후 링크 검증 |
| 제작자 | 원본/개인본 버전과 권한·철회·리콜, 거짓 협업/몰래 대체 없음 |
| 재방문 | 오전 완료/오후 남음, 휴식, 공백, 종료, 실패의 실제 상태 표시 |
| 모바일 | 320/375px·키보드·200% 글자·reduced motion·뒤로가기. 무스크롤 위해 글자/터치 축소 금지 |

계약 위반 0과 사용자 이해를 별도로 확인한다. 사용성 관찰이 적으면 다수 사용자 선호나 성과 향상을 입증했다고 하지 않는다. 실제 기록 값·메모·건강 세부를 분석 이벤트에 넣지 않는다.

## 11. 장단점과 최종 권고

**장점:** 상대 계획이 첫 사용·추천 부담을 줄이고, 이 계획이 실제 코칭 정보·배치·삭제·계정 정합성을 채운다. 제작자 프로그램도 같은 엔진에 붙으므로 유지보수가 두 배가 되지 않는다. 기존 고급 기능을 버리지 않고 일반 사용자에게 먼저 단순한 결과를 줄 수 있다.

**비용:** 공통 연결을 한 작성자가 맡아 일부 통합이 순차적이다. 프로그램 원본·권한·목표-only 버전 공급은 UI보다 늦을 수 있다. 이 비용을 줄이려고 두 엔진을 만들거나 검토되지 않은 용량을 켜면 더 큰 되돌림이 발생한다.

**권고:** 두 프로젝트를 경쟁시키거나 하나를 폐기하지 않는다. 상대 세션은 **간편 제품과 제작자 경험**, 이 세션은 **공통 엔진·계정·통합**을 맡긴다. 같은 파일을 나눠 고치는 대신 합의된 입력/결과 계약으로 연결한다.

현재는 원문 대조, 충돌 해소, 읽기 전용 상호 확인, C v1.1 수정, 통합 문서 작성까지 완료했다. 개발·branch/PR 생성·원격 반영·배포는 수행하지 않았다. 다음 실행은 새로운 무제한 리뷰가 아니라 **단계 0의 문서 보존·정확한 파일 소유·최소 계약 고정**이다.
