## 2. 제안 A: 앱 버전이 달라도 기록을 보존한다

### 권장 방식

새 클라이언트는 읽고 쓸 수 있는 문서 버전을 명시한다. 버전 정보가 없는 요청은 구형 클라이언트로 다룬다. 버전 주장은 인증·소유권·분석 자격이 아니며 서버는 문서와 권한을 별도로 검증한다.

| 요청 | capability 없음/V2만 지원 | V2와 V3를 모두 지원 |
|---|---|---|
| status | 기존 API 가용 상태의 응답 의미를 유지. 계정 전체 데이터가 V2라는 보증으로 사용하지 않음 | 가용 상태와 지원 버전 정보를 정해진 응답 형식으로 확인 |
| read | V2는 기존 응답. V3는 업데이트 필요 오류 | V2/V3 모두 읽기 |
| list/history | 요청한 결과에 해석 불가 문서가 있으면 실패. 해당 문서만 몰래 빼고 성공하지 않음 | 기존 페이지 크기·커서로 두 버전 모두 반환 |
| save | V2 일반 수정 유지. 현재 V3인 문서를 V2로 덮어쓰는 요청 거절 | 새 기능이 없으면 V2 그대로 저장 가능. 검증된 목적에만 V3 생성/승격 |
| delete/restore | 일반 V2 경로 유지. V3 대상은 호환되는 클라이언트 필요 | 기존 소유권·revision·삭제/이력 정책 유지. 형식 강등이나 무검증 새 근거 복원 금지 |

`UPGRADE_REQUIRED`는 권장 오류 코드이며 HTTP 426을 후보로 둔다. 신형 클라이언트는 명시적으로 안내하고, 이미 배포된 구형 클라이언트는 이를 일반 오류로 볼 수 있다. 구형 앱에 새 문구가 저절로 생긴다고 가정하지 않는다. 기존 오류 처리에서 projection·초안·outbox가 보존되는지 실제 구형 빌드로 시험한 뒤 코드를 확정한다.

목록은 기존 페이지 나눔을 유지한다. '전체 목록 반환'은 무제한으로 한 번에 내려준다는 뜻이 아니라, 지원하지 않는 문서를 조용히 누락하지 않는다는 뜻이다. 중간 페이지가 실패하면 동기화 완료나 삭제로 처리하지 않는다.

원칙:

- 새 앱도 기존 V2 기록을 강제 변환 없이 편집할 수 있다.
- V3가 된 기록은 구형 요청으로 V2로 낮추지 않는다.
- V2 이력 복원과 V3 현재 문서의 관계를 별도 표에 넣는다. 사용자 확인 없는 새 근거 삭제나 알 수 없는 필드 절삭을 허용하지 않는다. 손실 없는 복원 규칙이 준비되지 않은 조합은 오류로 보존한다.
- 어떤 오류도 빈 기록 목록·삭제·저장 완료로 위장하지 않는다.
- `status`마다 계정 전체 문서를 스캔하는 구조는 만들지 않는다. 요청 대상의 실제 형식은 각 동작에서 검증한다.

장점은 구형 사용자 자료와 새 기능을 함께 보존하는 것이다. 비용은 일부 구형 사용자가 업데이트 전 새 기록을 읽지 못할 수 있다는 점이다. 빈 화면을 성공처럼 보여 주는 것보다 오류 상태에서 기존 내용을 유지하는 쪽을 택한다.

## 3. 제안 B: 가져온 기록 정정은 전용 동작으로 처리한다

같은 account-journal 경로 안에 `action: correctImportedObservation`를 두는 안을 권장한다. 새 서버 서비스나 별도 정정 DB는 만들지 않는다. 기존 `save`에 `writePurpose`를 추가하는 방식도 원리상 가능하지만, 이번에는 일반 편집의 불변 규칙과 정정의 허용 필드를 분명히 분리하기 위해 전용 action을 선택한다.

최소 요청 필드:

`documentId`, `operationId`, `expectedRevision`, `previousContentRevisionFingerprint`, `replacementObservation`, `confirmedChangedFields`.

| 조건 | 권장 결과 |
|---|---|
| 같은 operation ID, 같은 정규 요청 | 최초 처리 결과 재사용. 두 번 반영하지 않음 |
| 같은 operation ID, 다른 내용 | 재사용 충돌 오류 |
| 현재 revision 또는 이전 지문 불일치 | 최신 내용을 확인하도록 충돌 반환 |
| 삭제된 기록 | 정정으로 복구하지 않음. 기존 복원 경로를 거친 후 새 요청 필요 |
| 허용하지 않은 필드 변경 | 요청 거절. 일반 저장으로 우회하지 않음 |
| 정상 정정 | 같은 일지 ID의 새 revision. 변경 이력과 기존 정보 보존 |

소유 계정은 본문 주장이 아니라 현재 인증 정보로 결정한다. 정정 가능한 것은 명시된 구조화 관측 필드뿐이다. 원출처를 직접 입력으로 바꾸거나 다른 원관측으로 바꾸는 권한은 없다. 일지 ID·소유자·서비스 날짜·메모·직접 입력 RPE·불변 계획 링크·완료 상태·legacy 식별자는 변경하지 않는다. parser 버전 등 처리 메타데이터는 서버 검증 대상이며 임의 신뢰도 승격 값은 받아들이지 않는다.

서버가 새 내용 지문을 계산한다. 해당 관측을 보던 비교 연결은 '이전 관측 기준'으로 표시하고 새 값에 자동 재사용하지 않는다. 날짜가 틀린 기록의 처리 경로는 기존 명시적 삭제/새 기록 정책을 유지하며 자동 재배치하지 않는다.

**형식 승격을 정정 action 하나에만 묶지 않는다.** 원지시서에는 새 가져오기 근거 추가와 비교 관계 추가도 있다. V2→V3은 이 세 목적의 검증된 명령에서만 무손실로 허용하고, 일반 저장에서 임의 필드를 붙여 승격하지 못하게 한다. 각 목적의 허용 변경 필드는 분리한다.

## 4. 제안 C: 같은 운동·수정된 기록·다른 운동을 구분한다

다음 세 값을 계속 분리한다.

1. `journalEntryId`: 서비스 안에서 유지되는 일지의 ID.
2. `sourceObservationKey`: 어느 원관측인지를 나타내는 키.
3. `contentRevisionFingerprint`: 해당 관측 내용이 바뀌었는지 확인하는 지문.

| 상황 | 권장 처리 |
|---|---|
| 안정적 원본 ID가 있음 | 계정·출처/형식 프로필 범위와 원본 ID로 관측 키 구성 |
| 같은 관측 키, 내용 동일 | 명확한 재시도는 중복 반영하지 않음 |
| 같은 관측 키, 내용 변경 | 같은 운동의 정정 후보. 자동 최신본 덮어쓰기 금지 |
| 원본 ID가 없음 | 같은 요청 재전송은 operation ID로 처리. 별도 재가져오기는 기존 후보와 대조하고 모호하면 사용자 확인 |
| 같은 날 거리·시간이 비슷함 | 같은 운동으로 자동 병합하지 않음. AM/PM 두 운동 보존 |
| 파일 행 순서만 바뀜 | 바깥 행 순서는 관측의 정체성에 넣지 않음 |
| 실제 랩 순서가 바뀜 | 내용 변화. 구간 배열 순서는 보존 |
| parser 코드만 업데이트됨 | 원관측 키를 바꾸지 않음. 실제 정규 값/의미가 달라질 때만 변경 후보 |

정규 숫자 `5`, `5.0`, `5.00`은 같은 수치로 비교하고 표시용 반올림값으로 지문을 만들지 않는다. 입력의 소수 자릿수와 센서의 실제 정확도를 동일시하지 않는다. null·누락·실제 0의 구분 규칙을 고정한다. 시각이 없으면 자정이나 임의 UTC 시각을 만들지 않는다.

객체 키 순서는 정렬하고 랩·세그먼트 순서는 유지한다. 지문 규격 버전은 명시한다. 파서 구현 버전은 처리 이력으로 남기되, 의미가 바뀌지 않은 코드 업데이트로 기존 지문을 대량 재생성하지 않는다. 호환되지 않는 지문 규격 변경은 별도 마이그레이션으로 다룬다.

정규 입력 허용 필드에 메모 원문·파일명·GPS 경로·토큰·임의 자유문장을 넣지 않는다. 관측 키나 지문을 공개 분석 이벤트로 자동 전송하지 않는다. 숫자·시간·랩의 정규 내용만으로도 비교 가능한 범위를 먼저 완성한다.

## 5. 제안 D: 새 기능에 문제가 나도 기존 일지는 유지한다

기존 서버의 `repo.enabled(ownerId)`, `ACCOUNT`, `ACCOUNT_JOURNAL_V2`, 계정 접근 자격 검사를 그대로 사용한다. 그 위에 새 구조화 근거/비교 관계 쓰기를 허용하는 좁은 서버 조건을 둔다. 새 원격 설정 플랫폼은 필요하지 않다.

| 동작 | 새 기능 쓰기 중단 시 |
|---|---|
| 기존 V2/V3 읽기·목록·이력 | 기존 계정 권한이 유효하면 유지 |
| 기존 일반 일지 작성·허용된 수정 | 새 구조화 근거를 변경하지 않는 범위에서 유지 |
| 신규 근거 추가·정정·V2→V3 승격·신규 비교 관계 변경 | 서버에서 중단 |
| 일반 save로 새 근거를 몰래 변경 | action 이름과 무관하게 실제 변경 필드를 검사해 거절 |
| 삭제·복원 | 기존 권한·이력 계약 유지. 복원으로 새 쓰기 제한을 우회하지 못하게 조합 시험 |

서버 조건이 false이면 명시적인 기능 중단 오류, 상태를 확인할 수 없으면 일시적 오류로 신규 쓰기를 막는다. 클라이언트의 분석 버튼 표시 여부는 별도이며 권한 증거가 아니다. 사용자가 화면을 우회하거나 오래된 앱으로 직접 요청해도 같은 서버 검사가 적용된다.

새 기능 중단은 이미 성공한 저장을 지우거나 정상 계정 일지 전체를 끄는 동작이 아니다. 단, 계정 자체의 권한 철회·인증 실패는 기존 보안 규칙이 우선한다.

정상 입력에서는 다음 흐름을 권장한다.

`파일 선택 → 인식한 기록 확인 → 저장하고 분석 보기 → 계획·이전 수행 비교 또는 다음 훈련 고르기`.

기술 버전·출처 정책·계산 자격을 각각 사용자에게 승인받지 않는다. 사용자는 같은 운동인지, 단위/시간 의미가 무엇인지처럼 실제 본인이 알 수 있는 모호한 항목만 확인한다. 기본 설명은 짧게 두고 계산 정의·제외 이유·출처는 펼쳐 볼 수 있게 한다. 이미 입력한 일지·선수 정보를 다시 요구하지 않는다.

### 부분 실패 권장안

| 상황 | 화면과 저장 처리 |
|---|---|
| 정상 활동과 오류 활동이 함께 있음 | 사용자가 정상 활동만 먼저 저장할 수 있음. 제외·미해결 수를 명시 |
| 시간의 의미만 불분명 | 관측과 유효 날짜·거리는 보존. 불확실한 시간을 쓰는 페이스/시간 합계/준수 비교만 제외 |
| 숫자 문법이 잘못됨 | 숫자 앞부분을 채택하지 않음. 해당 필드/항목의 문제를 보여주고 임의 0 대입 금지 |
| 동일 운동 후보가 모호함 | 해당 기록만 연결/별도 저장/제외 선택. 다른 정상 기록은 진행 가능 |
| 일부 서버 저장 성공 | 성공한 기록은 유지. 나머지는 대기/실패/재시도로 구분하고 전체 완료로 표시하지 않음 |
| 인증·계정 전환·호환성 오류 | 진행 중인 관련 새 쓰기를 중단하고 선택·초안·전송 대기 상태 보존. 이미 서버 확인한 성공은 취소하지 않음 |
| 파일 구조 자체가 깨짐·전체 크기 제한 초과 | 저장 전 해당 파일 전체 중단. 조용한 잘라내기 금지 |

개별 제한과 전체 제한을 구분한다. 단지 시간 의미가 불명확하다는 이유로 일지 전체를 막지 않는다. 반대로 계정 소유자가 바뀐 상태에서 '정상 항목만 계속 저장'하지 않는다.

무기록·무파일 사용자는 기존 계획 입력으로 곧바로 갈 수 있다. 파일만 있고 적격 경기 기록이 없는 사용자는 실제 기록을 분석하되, 가짜 PB·개인 페이스를 만들지 않고 기존 시간/RPE 후보를 고른다. 청소년·혼자 훈련하는 사용자·AM/PM 선수 범위는 기존 계약대로 유지한다.

## 7. 실행 순서와 검수 종료 조건

후속 실행 때 원지시서를 v1.2로 패치하되 기존 장을 축약하지 않고, 네 결정표와 필요한 예제만 추가한다. 기존 관련 스펙의 조항을 좁게 수정하고 이미 존재하는 27개 시험 항목에 연결한다. 새 보고서나 시험 카탈로그를 단계마다 늘리지 않는다.

| 순서 | 실제 산출물 | 다음으로 넘어갈 조건 |
|---|---|---|
| 1 | P0 채택표 + 네 기술 계약 표 | 승인 범위·현행 스펙과 충돌 없음. 요청/응답·정정·식별 예제가 서로 일치 |
| 2 | P1 TCX 정밀 관측 + P2A 기존 해설·비교·용어집·복귀 흐름 보완 | 인터페이스 확정 후 병행. TCX 숫자·시간·중복 예제 통과, 기존 가져오기 퇴행 없음, P4/P5에서 재사용할 화면 흐름 확인 |
| 3 | P2B 호환 저장·정정·서버 제어 | 구형/신형 앱의 자료 보존, 계정 전환·충돌·재전송 확인 |
| 4 | P3~P5 분석·비교·다음 선택 | 계정에 저장된 실제 근거로 화면 연결, 후보 선택·저장·재열기 완료 |
| 5 | P6~P7 독립 검수·TCX R1 공개 | 정확한 릴리스 기준 테스트와 공개 흐름 확인 |
| 6 | P8~P9 CSV·JSON·GPX 확장 | 형식별 동일 계약과 지원 필드 확인 후 전체 완료 |

위 표는 실행 순서를 묶어 보여 준 것이며 원지시서의 P2A/P2B를 포함한 11개 변경 묶음을 삭제하거나 합친 것이 아니다. 특히 P2A의 사용자 흐름 보완과 P9의 최종 검수·인수인계를 별도 상태로 추적한다.

### 기존 시험과 연결

| 기존 항목 | 확인할 것 |
|---|---|
| N01/N02/T01/T02/D01~D04/R02 | 전체 숫자 문법, 정밀도·시간 의미, 동일 관측/정정/다른 운동 구분 |
| S01~S04/C01/C02/R03 | 대기열 보존, 버전 호환, 형식 강등 거절, 정정 재전송, 요청 크기 |
| A01/A02/L01~L03/R01 | 표본·제외 이유, 원계획과 관측 지문, 정정 후 오래된 비교, 원문 비노출 |
| P01~P03/U01/U02 | 기존 후보와 안전 제한, 무기록·파일 전용 경로, 모바일·뒤로 가기·저장·재열기 |

이 시험 이름들은 형식 공통이다. TCX R1에도 숫자·시간·대용량 검사가 필요하며 N01/N02/R02를 전부 R2로 미루지 않는다. 이미 지목된 CSV 접두 숫자와 GPX 구간 연결의 형식별 수정은 P8에서 추적한다.

정적 검토 반복만으로 통과시키지 않는다. 결함 주입 시 실패하는 시험, 실제 구형/호환 빌드, 동일 계정의 다른 브라우저, 최종 공개 화면 증거를 순서대로 확보한다. 자료 손실·다른 계정 쓰기·잘못된 중복 합산·승인 밖 처방 변화가 발견되면 해당 기능 공개를 멈춘다. 한 형식이 안 된다고 검증된 다른 형식까지 무조건 되돌리지 않는다.

## 9. 종합 과정에서 보정한 Terra 세부안

Terra ultra 제안을 그대로 복사하지 않고 원지시서와 대조해 다음을 보정했다.

1. 신형 클라이언트도 새 기능이 필요 없는 V2 기록은 V2로 저장한다. V3만 저장하도록 강제하지 않는다.
2. V2→V3을 정정 action 하나에만 허용하면 새 근거/비교 관계 추가가 막힌다. 목적별 명시적 쓰기에 무손실 승격을 허용한다.
3. 의미 불명확한 시간은 관련 계산만 제외할 수 있다. 전체 활동을 반드시 보류시키지는 않는다.
4. N01/N02/R02는 공통 시험이므로 TCX 적용 부분까지 P8로 미루지 않는다.
5. status를 계정 전체 형식 검사로 바꾸거나 목록을 무제한 반환하지 않는다. 기존 API 의미·페이지 나눔을 보존한다.

이는 새 제품 범위를 더한 것이 아니라 기존 약속의 손실과 불필요한 차단을 줄인 통합 보정이다.

## 10. 오너 결정과 현재 상태

현재 제안 안의 통신 형식·정정 action·지문 규칙·서버 쓰기 조건은 작업자가 책임지고 정할 기술 선택이다. 이미 선택한 파일 우선·다음 후보 선택까지의 방향을 다시 묻지 않는다. P0에서 기존 승인 근거를 정확히 연결하되, 새 개인정보 용도·새 처방 수치·자동 활성 범위가 추가되는 경우에만 그 차이를 별도 결정받는다.
