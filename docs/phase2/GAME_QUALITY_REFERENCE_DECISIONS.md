# 게임 품질 기준과 레퍼런스 적용 결정

작성: 2026-10-16. 기준 소스: `3f08bf1fe900e688df2b8e0b60fe56b51856e273`.

이 문서는 사용자 지정 영상과 공개 사례를 실제로 확인한 범위, 이번 제작 결정, 이후 게임별 수용 기준을 구분한다. 아래 수용 기준은 **검사할 조건**이며 통과 보고가 아니다. 구현·브라우저 검수·배포 증거는 통합 담당자의 릴리스 기록에서 별도로 확인한다.

## 1. 이번 결정

첫 대상은 기존 **숲길 방어전의 한 판 전체**다. 6웨이브, 3종 타워, 건설 지점 8개, 기존 준비 저장·기록을 유지하면서 조준 → 발사 → 비행 → 충돌 → 피격 → 사망 → 보상의 실제 연결을 완성한다. 한 장면의 이펙트 시연으로 끝내지 않고 준비·전투·강화·승패·다시하기까지 이어서 검수한다.

이 단계에서 러너 조작·낙하·에너지 보급을 디펜스에 섞지 않는다. 디펜스 다음에는 러닝과 밀어내기를 각각의 규칙으로 개선한다. 새로운 게임을 계속 늘리는 대신, 게임마다 같은 품질 관문을 통과한 뒤 라운지에 공개한다. 로컬 저장이나 버튼 연결만 성공한 상태를 게임 완성으로 보고하지 않는다.

게임의 비용·체력·감속·회복은 가상 규칙이다. 훈련량·부상·자세 개선 효과에 대한 실제 처방이나 성장 예측으로 연결하지 않는다.

## 2. 사용자 지정 Threads: 직접 확인한 것

- [사용자 지정 모음 글](https://www.threads.com/@choi.openai/post/Dc6DLf5DwS_)
- [광고를 플레이 가능한 게임으로 재현한 사례 #12](https://www.threads.com/@choi.openai/post/Dc6CNxUD3Nm)
- [모음 글이 지목한 원작자 X 게시물](https://x.com/buildingadlicio/status/2096111709496680842)

직접 페이지 열기는 실패했으나 Jina Reader의 공개 `/media` 경로로 본문과 영상 링크를 읽었다. 사례 #12의 공개 영상도 받아 28초, 720×720, 30fps 파일임을 확인하고 3초 간격의 9개 프레임을 시각 검수했다. 프레임 수·fps는 배포 게임의 실제 성능 수치가 아니다.

영상은 좌측 광고와 우측 재현 결과를 나란히 보여준다. 눈으로 확인한 요소는 등각 시점의 부두, 군집으로 움직이는 물고기, 넓게 휘는 그물, 부두 위 이동 캐릭터, 캐릭터 위로 쌓이는 적재물, 격자로 대기하는 군중, 표시된 상호작용 지점이다. 이 사례는 타워 디펜스가 아니므로 낚시·운반 규칙을 우리 디펜스에 넣는 근거로 사용하지 않는다.

**차용할 제작 방식은 장면·행동·결과를 맞추는 것이다.** 배경색이나 오브젝트 종류만 비슷한 것이 아니라, 카메라와 구역 배치, 대상 수와 크기, 행동 궤적, 행동 후 화면 변화를 같은 장면에서 비교할 수 있다. 우리 게임도 레퍼런스의 어떤 행동을 어떤 화면 피드백과 규칙으로 옮겼는지 대응표를 유지한다.

본문에는 Blender를 사용해 30분 안에 브라우저 게임을 만들었다는 설명이 있다. 이것은 게시자의 주장이다. 전체 제작 과정·프롬프트·소스·총비용·상용 완성도는 확인하지 못했다. 원작자 X 페이지는 403으로 직접 읽지 못했고, 공개 플레이 링크도 확보하지 못했다. 위 영상으로 조작 재현성·긴 플레이의 재미·동접을 검증했다고 하지 않는다.

다른 연결 글에서 확인한 제작 설명도 다음처럼 제한해 사용한다.

| 공개 글 설명 | 이번에 적용할 방법 | 확인하지 못한 것 |
|---|---|---|
| #7: Blender와 Unity로 그래픽·사운드·멀티플레이 슈팅을 함께 제작 | 아트·음향·규칙을 따로 완료 처리하지 않고 한 동작에서 함께 검수 | 해당 게임의 서버 동기화·상용 운영 |
| #10: 리토폴로지는 사람이 했고 UV는 AI로 처리 | 생성 모델도 토폴로지·피벗·UV·애니메이션 적합성을 후처리 | 모든 모델을 자동으로 게임용으로 바꿀 수 있다는 주장 |
| #14: 그리드·여백·타입 규칙을 먼저 정한 UI | 라운지와 게임 조작 패널의 고정된 시각 기준을 먼저 유지 | 원작의 실제 디자인 시스템 파일 |
| #16: 테스트 플레이와 오류 수정을 반복 | 실제 게임 입력으로 실패·성공·재시작을 모두 확인 | 사용량 1%·작업 시간의 독립 검증 |

원본 영상과 접촉시트는 조사 임시 파일로만 보관했다. 상용 원작 화면을 우리 게임 런타임 에셋으로 복사하지 않는다.

**그대로 복사할 수치로 사용하지 않는다.** Outpost의 무작위 출현·타워 수리/파괴·일반 경로 탐색은 현재 고정 경로 디펜스와 다른 규칙이다. 이번에는 공격과 시각 상태의 연결 구조를 차용하며, 기존 여섯 웨이브의 경제를 새로운 게임으로 몰래 바꾸지 않는다.

## 4. 장면 → 행동 → 결과 대응표

| 장면 | 사용자의 판단/행동 | 화면과 규칙에 함께 나타나야 할 결과 | 부족한 구현의 예 |
|---|---|---|---|
| 시작 전 전장 | 입구·길·출구를 보고 지점 선택 | 선택 지점과 사거리, 선택 취소, 실제 가격 | 큰 배경 그림 아래에 메뉴만 배치 |
| 첫 적 접근 | 타워 종류·배치 결정 | 포탑이 적을 조준하고 발사. 투사체가 닿을 때 체력과 피격 표현 변화 | 발사 선을 그리면서 미리 체력 차감 |
| 질주 적 | 빠른 적을 막는 조합 선택 | 빠른 발사와 감속의 차이가 이동·재장전·누락에 반영 | 적 색만 바꾸고 같은 속도·연출 |
| 장갑 적 | 연사에서 포격으로 투자 보완 | 장갑의 낮은 피해와 관통 포격의 차이, 작은 폭발 범위가 보임 | 설명에만 상성 기재 |
| 밀집 웨이브 | 감속 위치와 범위 공격 조합 | 여러 적의 움직임과 폭발 중심이 겹치며 피해 관계를 읽을 수 있음 | 입자/숫자가 적과 길을 모두 가림 |
| 강화 | 화력/사거리와 비용 비교 후 선택 | 새 수치·자금 변화·타워 등급·다음 발사에서 차이를 확인 | 축하 팝업만 띄우고 실제 변화가 불분명 |
| 적 돌파 | 실패 원인 파악 | 출구 접촉·기지 손상·남은 체력·누락 수가 같은 사건을 설명 | 이유 없이 체력 숫자 감소 |
| 마지막 적 | 보상과 다음 웨이브 준비 | 처치 보상 1회, 사망 정리, 정비 버튼. 전투가 뒤에서 계속 진행하지 않음 | 화면 전환 중 적이 계속 공격 |
| 승패 | 결과를 이해하고 다시 시도 | 별·남은 체력·막은 적·놓친 적·다시하기/라운지 복귀 | 의미 없는 점수 증가만 표시 |

## 5. 이번 디펜스 수용 기준

### 전투가 읽히고 조작에 반응한다

1. 기초판은 고정되고 포탑이 실제 목표 방향으로 돌아간다. 발사 원점은 포신 끝과 맞는다.
2. 투사체 비행 중에는 아직 맞지 않은 적의 체력이 줄지 않는다. 충돌 위치에서 피격 반응이 나타난다. 사라진 목표·기지 도착·연속 적중도 중복 보상을 만들지 않는다.
3. 연사·포격·냉각은 실루엣과 색 외에 발사 간격·탄도/효과·피격 결과가 구분된다. 감속 종료와 재적용은 규칙과 시각 표시가 일치한다.
4. 사망 상태는 짧게 남아 결과를 읽을 수 있지만 공격 대상이나 길막 대상이 되지 않는다. 파편은 피격 판정처럼 보이지 않는다.
5. 시각 효과를 줄여도 사거리·피해·감속·체력·승패 정보가 유지된다. 화면 흔들림/섬광은 조작 피드백의 유일한 수단이 아니다.

### 한 판의 판단이 결과로 이어진다

6. 여섯 웨이브를 실제 입력으로 처음부터 끝까지 진행한다. 정찰·질주·장갑·밀집·혼성·대장에 맞춰 투자 판단을 할 수 있어야 한다.
7. 무설치 패배, 연사 위주, 감속+포격 혼합처럼 서로 다른 전략의 결과를 비교한다. 같은 입력·시간 조건으로 기록하고 결과가 유의하게 달라지는 이유를 설명한다. 정해진 정답 배치 하나의 완주만으로 밸런스 합격을 선언하지 않는다.
8. 시작 전 예고, 웨이브 전환, 보상, 결과는 실제 게임 상태와 일치한다. 준비 시간과 전투 시간을 억지로 늘려 플레이 분량을 부풀리지 않는다.
9. 새 판은 새 출발이다. 영구 능력치로 기존 사용자에게 일방적인 우위를 주지 않고, 이번 판의 기록·성과와 저장은 보존한다.

### 휴대폰에서도 플레이를 마칠 수 있다

10. 좁은 화면에서도 길·적·출구가 패널에 가려지지 않는다. 선택 타워의 범위와 구매/강화가 손가락 조작으로 구분된다. 조작 영역은 기존 44px 기준과 접근 가능한 이름을 유지한다.
11. 전투 렌더링을 일부러 낮은 주기로 묶지 않는다. 실제 최대 혼잡 구간에서 프레임 시간과 입력 반응을 측정한다. 데스크톱 자동화 성능을 iPhone 실기 성능으로 보고하지 않는다.
12. 일시정지·화면 이탈·준비 저장·이어하기·저장 없는 나가기·결과 후 재시작을 확인한다. 기존 저장 키와 기존 기록을 지우지 않는다.
13. 파일 누락이나 그래픽 경로 실패 시 빈 화면으로 멈추지 않는다. 저사양/모션 감소에서도 핵심 규칙은 같다.

통합 보고에는 각 조건의 구현 여부, 관찰한 화면, 실패·수정한 항목을 적는다. 검사 개수와 빌드 성공만으로 위 조건 전체를 통과했다고 하지 않는다.

## 6. 이후 게임의 순서와 수용 기준

| 순서 | 게임의 중심 재미 | 필요한 다음 제작 | 완료를 판단할 플레이 |
|---|---|---|---|
| 1. 숲길 방어전 | 배치·상성·투자·누락 관리 | 조준/비행/피격/사망과 전장 가독성, 여섯 웨이브의 흐름 | 서로 다른 전략으로 전체 판을 끝내고 승패 원인을 설명 가능 |
| 2. 러닝 투어 | 속도 조절·장애물 읽기·지속 제스처 | 카메라 추종, 미리 보이는 장애물, 착지/점프/대시 애니메이션과 실제 판정 일치 | 손을 떼지 않은 위아래 제스처 반복, 방치 시 뒤로 밀려 낙하, 구간 전환 후에도 조작 유지 |
| 3. 밀어내기 경기 | 거리·방향·타이밍으로 상대 밀기, 복귀 후 역전 | 공격 준비→유효 판정→반동→낙하→무한 리젠, 양측에 일치하는 판정/종료 | 두 실제 브라우저에서 제한 시간 동안 반복 낙하·복귀, 동시 공격·지연·재접속·동점/종료까지 확인 |
| 4. 다음 독립 게임 | 명확한 장르별 핵심 행동 | 별도의 실제 레퍼런스·라이선스·입력/승패 설계 | 한 판의 완결성과 다른 게임과 구별되는 조작을 먼저 확인한 뒤 라운지에 추가 |

러닝의 카메라 이동은 캐릭터를 화면 중앙에 완전히 고정하는 대신 전방 시야와 약한 지연을 둔다. 장애물은 출현 후 반응할 시간을 제공하고, 예고 이펙트가 본체를 가리지 않는다. 무작위 종류/수 증가만으로 난이도를 올리지 않고 피할 수 있는 간격과 조합을 검증한다. 목표 반응 시간 수치는 게임 속도·실제 입력 지연을 측정한 뒤 정하며 현실 달리기의 안전 수치처럼 표현하지 않는다.

밀어내기는 시간 종료 전 무한 리젠이라는 사용자 결정을 유지한다. 낙하는 한 번의 불이익이고 경기 자체의 즉시 종료가 아니다. 복귀 보호·득점 소유자·자기 낙하·동시 타격 규칙은 양쪽 클라이언트가 같은 서버 결과를 읽어야 한다. 솔로 AI 모드도 같은 공격/리젠 규칙을 사용하되, AI 전용 유리한 판정으로 난이도를 만들지 않는다.

라운지는 게임 이름·무엇을 하는지·혼자/친구 가능 여부·현재 입장 상태를 명확히 보여준다. 실제로 서버가 가능한 게임에만 친구 입장을 표시한다. 아이콘이 늘어났다는 사실을 새로운 게임의 완성으로 세지 않는다.

## 7. Tripo·Blender 작업을 게임 품질로 연결하는 방법

이번 첫 에셋 우선순위는 배경 장식 추가보다 **행동이 가능한 구조**다.

1. 타워: 기초판·회전 포탑·포신을 분리하고 회전 피벗과 포구를 정한다. 수준별 실루엣은 작은 화면에서도 구분한다.
2. 적: 이동·피격·사망 상태를 만들고 동일한 발 위치·중심·크기 기준을 유지한다. 단순히 정지 이미지를 좌우로 옮기는 것으로 끝내지 않는다.
3. 전장: 고정 카메라에서 길의 폭, 타워 높이, 적의 크기, 그림자 방향을 먼저 맞춘다. 장식은 길과 출구 판독을 돕는 위치에 둔다.
4. 효과: 포구 섬광·포탄·충돌·냉각·사망을 작은 재사용 묶음으로 제작한다. 모든 효과를 새 3D 생성물로 만들 필요는 없고, Blender 렌더/프레임 또는 런타임 효과 중 가장 잘 읽히는 경로를 택한다.
5. 검수: 생성 원본→Blender 후처리→게임 크기의 프리뷰→실제 전투 적용→전체 판 순서로 확인한다. 원본이 예쁘거나 GLB 파일이 생겼다는 사실만으로 게임 에셋 완료로 기록하지 않는다.

Tripo 새 생성은 현재 잔액과 비용을 먼저 확인하고 기존 자산으로 해결되지 않는 부족분에 사용한다. Studio와 API 잔액을 혼동하지 않는다. 기존 사용 승인을 매번 재질문하지 않으며, 잔액 소진 자체를 목표로 같은 장식물을 반복 생성하지 않는다.

## 8. 보고 원칙

- 확인한 원문, 영상에서 관찰한 동작, 오픈소스 코드에서 읽은 구조, 직접 플레이한 결과를 서로 구분한다.
- 이번 코드가 반영되어도 모든 게임의 품질 개선이 끝났다고 하지 않는다. 디펜스·러닝·밀어내기의 수용 상태를 각각 적는다.
- 로컬·미리보기·main 반영·공개 배포·실제 계정/친구 왕복을 구분한다.
- 자동 검사는 규칙과 회귀를 확인한다. 인간의 장기 재미와 재방문 효과는 실제 플레이 반응이 모이기 전까지 미검증이다.
- 남은 결함을 '다음에'로 뭉개지 않고 게임·장면·재현 조건으로 남긴다. 이 문서를 작성한 것 자체는 해당 결함 해결이 아니다.
