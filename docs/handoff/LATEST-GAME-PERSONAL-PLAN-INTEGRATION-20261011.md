## CI 병목과 최종 커밋 검증

이전 성공 실행 `37736423120`은 UTC/KST 단위 검사를 직렬로 약 40분, 두 일반 브라우저 경로와 네 화면 조건을 직렬로 약 99분 실행했다. 전체 스키마·해시 검사와 브라우저 범위를 그대로 유지하면서 UTC/KST는 두 독립 작업, 일반 브라우저는 네 고정 화면 조건의 독립 작업으로 나눴다. 각 화면 작업은 기존 빌드·fixture 두 경로를 모두 worker 1로 실행한다. 기존 전용 브라우저 10개 명령과 배포 조건·권한·본문은 보존했다. 실제 단축 시간은 최종 hosted 실행에서 확인해야 한다.

`app-quality`는 두 시간대 모두 성공해야 진행하고, 기존 `app-browser`는 네 일반 화면 작업과 전용 브라우저 작업이 모두 성공해야 통과한다. 실패·취소·건너뜀·빈 결과·누락 결과를 실제 Bash 실행으로 거부하는 검사를 추가했다. 프로젝트 runner는 알려진 화면 조건 하나만 받고 파일·grep·경로 축소 인수를 허용하지 않으며, 전체 runner의 기존 8개 조합도 유지한다.

`11b2ffd1`의 hosted contract 검사는 통과했지만, 로컬에서 최신 화면 fixture의 추가 실패를 재현한 뒤 해당 전체 실행 `38124433639`를 취소했다. 그 실행은 전체 CI 성공 증거가 아니다. 수정과 병렬화를 포함한 최종 PR 커밋에서 전체 gate를 새로 실행하고 그 결과로 병합 여부를 판단한다.

`c39f101a`의 PR 실행 `38125873318`에서도 contract 검사는 통과했지만 UTC/KST는 같은 19개 파일·48개 사례가 실패했다. 양쪽 실패 이름의 차이는 0개였고, unit 실패를 받은 quality 및 browser 집계 guard도 실제로 실패하여 다음 단계가 차단됐다. 이 실행은 전체 통과 증거가 아니다. 이후 fixture와 위 두 런타임 결함을 수정한 커밋에서 전체 검사 범위를 그대로 다시 실행한다.

`902b2493`의 PR 실행 `38128912093`은 두 시간대 모두 `697 normal + 3 heavy = 700` 파일의 분할을 확인했다. 일반 구간은 690개 파일·8,063개 검사 통과, 기존 7개 파일·33개 검사 skip으로 완료됐다. 이전 19개 실패 fixture와 새 overlay 검사는 일반 구간에서 모두 통과했다. 이어 실행한 heavy 3개 파일은 110개 통과·3개 실패·기존 2개 skip이었다. 두 시간대의 실패 이름은 동일했고, 새 skip은 없다. 계약 검사는 성공했으며 unit 실패로 quality 및 browser guard가 실제로 다음 단계 진행을 차단했다. 전체 통과와 병합 증거로 취급하지 않는다. 실행 구간은 UTC 약 20분 16초, KST 약 20분 13초였다.

Windows 집중 검사의 일부 실행은 worker 시작 오류 또는 도구 시작 지연으로 테스트를 실행하지 못했다. 이를 제품 실패나 통과로 세지 않았다. 보존된 산출물을 지우지 않고 추적된 소스만 복사한 별도 검사 사본, 원본과 사본의 SHA256 일치, Node 24.19 및 단일 worker로 집중 검증했다. 브라우저의 설치 Chrome과 CI용 bundled Chromium 결과도 구분했다. 환경 지연의 단일 원인을 확정한 것은 아니며 hosted Linux 전체 gate의 명령·timeout·단언은 변경하지 않았다.

남은 heavy fixture는 실제 PLAIN/COACH 표기, 이전 답의 접근성 이름, 날짜별 reader가 열린 뒤 오전·오후 구획에 접근하는 경로로 맞췄다. RPE fixture의 시계는 Date만 고정해 실제 native Back의 POP을 허용하고, 정리 뒤 pending Back이 없다는 단언도 유지했다. 원래 날짜·만료·계정 전환·rollback·원본 byte 보존 검사는 그대로다. 이 커밋 직전 집중 실행에서 LT와 Oracle 연결 40/40, PlanBeta 33개 통과·기존 2개 skip, RPE 전체 74/74가 UTC에서 통과했다. KST는 LT와 Oracle 연결 40/40 및 PlanBeta 33개 통과·기존 2개 skip을 확인했고 RPE 전체는 같은 소스로 별도 진행한다. KST의 LT 기존 저장 사례가 첫 실행에서 5초 제한을 넘긴 기록과 RPE의 최초 정리 실패 11건도 보존했다. LT 재실행과 RPE의 Date-only 수정 후 UTC 전체는 기존 시간제한에서 통과했다. 새 skip이나 시간제한 증가는 없으며, 최종 KST와 전체 hosted gate 결과는 PR 기록에서 확인한다.

0064 마이그레이션의 운영 배포, 계정 공개·활성화, 개인정보처리방침 반영, dedicated 게임 kill 변수 연결은 이번 코드 통합과 별개다. 운영 DB·실제 A/B 계정·두 기기의 계정 저장 왕복은 확인하지 않았다. 광고 SDK와 현금성 포인트 연결은 없다. 로컬 통과나 임시 DB 통과를 운영 보안·배포 완료로 취급하지 않는다.

추가 읽기 전용 release 검수에서는 저장소의 계정 공개·일지·동기화·공개 프로필 플래그가 켜져 있음을 확인했다. 다만 현재 deploy-pages는 `VITE_ACCOUNT_STORAGE_PRIVACY_RELEASE_APPROVED`와 `VITE_ACCOUNT_STORAGE_PRIVACY_MIGRATION`를 전달하지 않는다. 기존 승인 검사는 계정 공개 시 이 값들을 필수로 요구하므로, 해당 설정으로 main 자동 배포를 실행하면 빌드 전에 거부될 것으로 예상된다. 이는 origin/main에도 있는 기존 배포 경계다. 변수·승인·비밀 값은 변경하지 않았으며 현재 Pages의 계정 공개 상태를 이 코드 검토만으로 단정하지 않는다. 다른 공개 빌드 경로에서 계정을 열 때는 게임 전용 kill 설정도 별도로 검토해야 한다.
