# 인증 통합 후보 후속 감사 · 2026-11-14

이 문서는 기존 인증 후보에서 누락된 연결을 확인하고 수정한 기록이다. 로컬 수정,
검사, 운영 설치, 공개 배포, 실계정 확인을 구분한다. 이번 감사 요청은 이전 자동 승인
검토에서 보류된 운영 작업의 별도 허용으로 해석하지 않는다.

## 발견하고 수정한 다섯 가지 문제

1. **설정의 비밀번호 변경·재인증이 공유 로그인 상태를 따라갈 수 있었다.**
   검증 직후 다른 탭이나 작업에서 계정이 바뀌면 공유 SDK가 다른 계정의 토큰을
   사용할 수 있었다. 검증한 access/refresh token으로 작업 전용 메모리 SDK를 만들고,
   같은 정확한 bearer의 사용자 조회·변경과 재인증 요청만 허용하도록 고쳤다.
   자동 갱신·지속 저장·탭 간 방송을 사용하지 않고 사용 뒤 dispose한다. 전송 직전에도
   공유 계정·세션을 다시 확인한다. 실제 SDK 검사에서 A 작업 대기 중 공유 세션을
   B로 바꿔도 요청은 A에 고정되고 B 세션을 덮지 않음을 확인했다.
2. **로그인 방법 조회·약관 재동의가 선택적 건강정보 보관 동의에 막혔다.**
   공통 fetch가 두 RPC를 건강정보 요청으로 분류해, 입장 전 재동의가 필요한 계정에서
   순환 차단이 생겼다. `get_account_auth_methods`, `reaccept_account_terms`만
   POST JSON·정확한 인수 목록·bearer의 사용자 및 세션과 일치하는 ID로 제한해
   독립 전송한다. 약관 버전은 길이와 문자 형식을 제한하며 추가 건강·일지 필드,
   다른 소유자·세션, URL query 변경과 알 수 없는 Request stream은 차단한다.
   서버의 인증·입장·약관 정책 판정은 그대로 적용한다.
3. **비밀번호 복구 실패 뒤 다시 시도하는 연결이 부족했다.**
   복구 실패 후 같은 화면에서 재시도할 수 있도록 상태와 호출 연결을 보완했다.
   복구 세션의 격리와 일반 계정 권한 차단을 유지한다. 로컬 회귀 검사는 실제 메일이나
   Hosted 공급자의 재시도 성공을 입증하지 않는다.
4. **인증 뒤 목적지 복귀 증명이 일부 경합에서 사라지거나 사용되지 않았다.**
   기존 `returnIntent` 호환, 새로고침 전 완료 처리, 복귀 소비자가 취소된 경우의
   증명 보존을 보완했다. 취소된 소비자가 아직 유효한 TTL 증명을 지우지 않게 하며,
   사용자·정확한 세션·시도·수명 검증과 한 번만 복귀하는 계약을 유지한다.
5. **작은 화면에서 가입 제목과 뒤로 버튼이 위로 잘렸다.**
   DOM 표시 여부만 검사했을 때 통과했지만, 실제 320·375px 화면 캡처에서 드러났다.
   인증 화면 진입·로그인/회원가입 전환은 제목을 포함한 화면 상단에 맞추고,
   첫 방법 선택 단계의 중복 본문 정렬은 없앴다. 공통 스크롤·뒤로가기 복원과
   입력 중 스크롤 보호는 유지한다. 관리 화면의 워치 영역 정렬은 변경하지 않는다.

## 로컬 검사 증거

아래는 각 검사 범위의 결과이며 중복 실행을 합산한 총 검사 수를 만들지 않는다.

| 검사 범위 | 확인 결과 |
|---|---|
| 공통 consent fetch 계약 | 99개 통과 |
| 계정 설정 도메인 | 18개 통과; 기존 17개 보존 및 전송 전 세션 변경 대조군 추가 |
| 작업 전용 설정 클라이언트 실제 SDK | 4개 통과; 토큰 고정, 저장·방송 없음, 만료 시 갱신·logout 전송 없음, 정리 확인 |
| 복구 UI 및 기존 도메인 | 31개 통과 |
| 복구 추가 선택 검사 | 선택한 5개 통과; 선택하지 않은 23개는 이 실행의 통과로 계산하지 않음 |
| 목적지 복귀 최신 검사 | 48개 통과 |
| 로컬 Chromium 화면 검사 | 320·375·1280px에서 홈·회원가입·로그인 9개 상태 통과; 제목·뒤로 버튼의 실제 화면 내 노출, 가로 넘침 없음, 인증 화면에 자료 관리·삭제 없음 |

consent fetch의 새 예외 분기만 비활성화한 결함 주입에서 두 RPC의 실제 SDK 검사가
이름별로 실패했고 주입을 원복했다. 잘못된 소유자·세션·추가 본문과 만료된 토큰은
별도 실패 입력으로 거절을 확인했다.

브라우저는 실제 앱 진입점을 합성 공개 설정으로 실행했고 외부 요청을 차단했다.
실제 계정 생성·인증 요청을 보내지 않았다. 수정 후 320px 가입/로그인 및 375px 가입
캡처를 육안으로 확인했다. 이 결과는 iPhone Safari/PWA 실기기나 운영 인증 증거가 아니다.
최종 빌드 결과와 후보 SHA는 작업 폴더의 `AUTH_IMPLEMENTATION_RESULT_20261114.md` 및
`AUTH_RELEASE_MANIFEST_20261114.json`에 연결한다. 위 집중 검사로 프로젝트의 전체 필수
CI 관문 통과를 대신하지 않는다.

## 운영 읽기 확인과 미적용 범위

개인 데이터 조회와 쓰기 없이 운영 migration 이력만 읽어 확인했다. 관측된 이력은
70개이며 `20261114035856`은 존재한다. 다음 두 migration은 없다.

- `20261114042129_password_account_auth_channel.sql`
- `20261114120000_account_settings_actions.sql`

따라서 로컬 수정이 운영 DB에 반영됐다고 보고할 수 없다. 이 확인은 migration 이력의
존재 여부에 대한 증거이며 Hosted 관리자 설정이나 실제 인증 동작을 입증하지 않는다.
선택 SQL인 `password_auth_comparison_companion.sql`은 별도 comparison 기능 설치·승인
뒤 사용하는 항목으로, 이번 인증 출시의 선행조건이 아니다.

## 남은 출시 작업과 권한 경계

- 관리자 SMTP·발신과 실제 수신, confirmation/recovery 템플릿, canonical redirect,
  이메일 확인·비밀번호 정책의 확인 및 적용 영수증이 필요하다.
- 위 두 migration 적용과 `AUTH_PASSWORD`의 설치 시 닫힘 확인, 운영 준비 뒤 활성화가
  남아 있다. migration의 `ON CONFLICT DO NOTHING`은 기존 true 값을 닫지 않는다.
- 공개 저장소 업로드·병합, canonical 설정과 최종 source SHA를 사용한 DOMAIN 배포,
  전체 필수 CI 또는 규칙에 맞는 기존 결과 재사용 증거, 공개 배포 영수증이 남아 있다.
- 실제 이메일 가입·재발송·복구, Google/PW 로그인과 설정 변경, 다른 브라우저,
  iPhone 홈 화면 PWA의 인증 왕복은 실계정 증거가 필요하다.

이전 자동 승인 검토에서 운영 인증·라운지 함수 변경, 공개 코드 업로드 및 Supabase
관리자 로그인에 대한 정확한 허용 범위가 부족하다고 거절한 상태를 유지한다. 이번
감사 요청은 이 운영 작업의 승인으로 대체하지 않았으며 우회 실행하지 않았다.
필요한 허용과 운영 사실이 확보되기 전에는 운영 반영·공개 완료·실계정 성공으로
표시하지 않는다.
